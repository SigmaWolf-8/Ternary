## 1. CSTL Selection

### 1.1 Lab Requirements

Select a CSTL (Cryptographic and Security Testing Laboratory) accredited by
NVLAP (National Voluntary Laboratory Accreditation Program) for FIPS 140-3
testing scope.

Requirements:
- NVLAP accreditation for FIPS 140-3
- SP 800-90B entropy source testing capability
- Post-quantum algorithm testing experience (preferred)
- Rust/no_std module testing capability (preferred)

### 2.2 ACVTS Submission Process

1. Register at https://acvts.nist.gov
2. Create new module request
3. Upload JSON registration files generated by `acvts.rs`
4. ACVTS server returns test vectors
5. Process vectors through module and return responses
6. ACVTS validates responses and issues certificates

### 2.3 Build Environment Preparation

The CSTL will need to reproduce the module binary. Provide:
- `scripts/cmvp-build.sh` — deterministic build script
- `target/integrity-hash.txt` — expected HMAC-SHA-384 value
- Rust toolchain specification: `rustc 1.75.0`
- Build environment: Ubuntu 24.04 LTS
- Verification command: `openssl dgst -sha384 -hmac "SalviTernaryCryptoModule-v3.0.0-IntegrityKey" -binary libternary.rlib`

## 4. Lab Testing Support

### 4.1 Platform Provisioning

The CSTL tests on two platforms:

**OE-1 (x86_64):**
- Provide or arrange Ubuntu 24.04 LTS x86_64 system
- Install Rust 1.75.0: `rustup install 1.75.0 && rustup default 1.75.0`
- Build: `./scripts/cmvp-build.sh`
- Verify: compare integrity hash to `target/integrity-hash.txt`

**OE-2 (aarch64):**
- Provide or arrange Ubuntu 24.04 LTS aarch64 system (physical or QEMU)
- Install Rust 1.75.0 with aarch64 target
- Build: `./scripts/cmvp-build.sh --target aarch64`
- Verify: compare integrity hash (aarch64 hash will differ from x86_64)

### 4.2 Test Execution Guide

For the CSTL tester, the following commands execute all module tests:

```bash
# POST
cd src/kernel && cargo test --release self_test -- --nocapture

# Conditional tests
cd src/kernel && cargo test --release self_test::tests::conditional -- --nocapture

# Entropy health
cd src/kernel && cargo test --release entropy -- --nocapture

# Module state machine
cd src/kernel && cargo test --release module_state -- --nocapture

# Services and role enforcement
cd src/kernel && cargo test --release services -- --nocapture

# Full crypto suite
cd src/kernel && cargo test --release crypto -- --nocapture
```

### 4.3 Entropy Source Lab Assessment

The CSTL must independently assess the entropy source per SP 800-90B:

1. **Collect raw samples:**
   ```bash
   ./scripts/collect-entropy-samples.sh 1000000
   ```
   Output: `target/entropy-samples-YYYYMMDD.bin`

2. **Lab runs NIST SP 800-90B test suite:**
   ```bash
   # Test as IID source
   ea_iid target/entropy-samples-YYYYMMDD.bin 8

   # Test as non-IID source (if IID hypothesis rejected)
   ea_non_iid target/entropy-samples-YYYYMMDD.bin 8
   ```

3. **Lab documents:**
   - Min-entropy per sample (H_min)
   - IID vs non-IID classification
   - Health test parameter validation (RCT cutoff=21, APT cutoff=325)
   - Conditioning function justification (HMAC-SHA-384 vetted)

## 5. Known Discussion Points

### 5.1 Ternary-Native vs Binary Interop

The module implements ternary-native algorithms (TL-KEM, TL-DSA) that produce
binary-compatible outputs via the CryptoInteropBridge in `compat/`. The CSTL
should test through the interop bridge for CAVP vector compatibility, while
internal operations use balanced ternary GF(3) arithmetic.

### 5.2 Non-Standard Algorithms

The following algorithms are implemented but are NOT submitted for FIPS validation:
- Ternary Sponge Hash (proprietary)
- Ternary Lamport Signatures (being deprecated per 16_MIGRATION_GUIDE.md)
- Phase Encryption (ternary-native, non-standard)

These are blocked by the `agility.rs` policy engine when the module is in
ApprovedMode. They remain available in NonApprovedMode for backward compatibility.

### 5.3 Stateful Signature Index Management

LMS and XMSS are stateful signature schemes. The module enforces:
- Monotonic index advancement (SSP-018, SSP-019)
- `StateExhausted` error when all leaves consumed
- No index reuse (security violation)

The CSTL should verify that signing with a previously-used index is rejected.

## 6. Post-Certification

### 6.1 Certificate Maintenance

After receiving the FIPS 140-3 certificate:
- Module changes require CMVP revalidation or 1SUB/3SUB update
- CAVP certificates must remain current
- Entropy source changes require SP 800-90B re-assessment

### 6.2 Version Control

- `cavp_certs.rs` tracks all CAVP certificate numbers
- `VERSION_MANIFEST.json` tracks module version
- Any crypto code change triggers the `fips-self-tests.yml` CI workflow
