## 2. Cryptographic Module Specification

### 2.1 Module Description

The Salvi Ternary Cryptographic Module is a software cryptographic module
implementing ternary-native equivalents of all 11 CNSA 2.0 algorithms plus
HMAC-DRBG for random number generation. The module operates within a Rust
`no_std` kernel environment targeting post-quantum security at NIST Level 5.
The module provides authenticated encryption, hashing, message authentication,
key encapsulation, digital signatures (including hash-based stateful signatures),
and deterministic random bit generation, all within a single cryptographic
boundary enforced by a finite state machine and role-based access control.

## 4. Software/Firmware Security

### 4.1 Integrity Mechanism

- HMAC-SHA-384 computed over module binary at build time (`scripts/cmvp-build.sh`)
- Integrity key: `"SalviTernaryCryptoModule-v3.0.0-IntegrityKey"` (embedded)
- Verified at power-on as part of POST (POST integrity check in `self_test.rs`)
- `conditional_firmware_load_test()` runs on any module update

### 4.2 Approved Mode Indicator

The module provides a mode indicator queryable at any time via `get_mode_indicator()`:

| State | `is_approved_mode()` | `get_mode_indicator()` |
|---|---|---|
| ApprovedMode | `true` | `Approved` |
| NonApprovedMode | `false` | `NonApproved` |
| Error | `false` | `Error` |
| All others | `false` | `NotReady` |

The Approved mode indicator is set when:
1. All POST pass successfully (SelfTest -> Operational)
2. Policy set to `CnsaOnly` (Operational -> ApprovedMode)
3. Only approved services (26 of 32) are available in this mode

### 4.3 Software Version

- Version string: `"3.0.0"` from `VERSION_MANIFEST.json`
- Queryable via `module_status()` in `module_state.rs`
- Version is part of the integrity-checked binary

## 7. Non-Invasive Security

N/A at Security Level 1.

Non-invasive security testing is not required at Security Level 1 per
FIPS 140-3 Section 7.8. As defense-in-depth, the module implements
the following mitigations:

| Mitigation | Implementation | File |
|---|---|---|

| Formal verification | 13 properties verified (8 exhaustive, 5 dynamic) | formal_verify.rs |

## 8. Sensitive Security Parameter Management

Full SSP inventory: see `ssp-inventory.md` (VE-004). 23 SSPs identified.

### 8.1 SSP Generation

All cryptographic key material is generated via `drbg_generate()` from the
HMAC-DRBG-SHA384 random number generator (`drbg.rs`). The DRBG is seeded
from the SP 800-90B qualified entropy source (`entropy.rs`).

Key generation pipeline:
```
[Entropy Source] → [Health Tests] → [Conditioning] → [DRBG] → [Key Material]
```

### 8.2 SSP Storage

- All SSPs stored in-memory only (stack or heap allocation)
- No persistent key storage within module boundary
- No keys written to disk, database, or non-volatile memory
- Process isolation provided by operating system

### 8.3 SSP Entry/Output

- Keys enter the module via API function parameters
- Private keys and symmetric keys are NEVER exported in plaintext
- Public keys may be exported for distribution
- Shared secrets returned to caller for key derivation

### 8.4 SSP Zeroization

| Method | Description | Verification |
|---|---|---|
| `ct_zeroize()` | Constant-time overwrite with 0x00 (ct_utils.rs) | Formally verified (CT-ZERO) |
| `ct_zeroize_i8()` | Constant-time overwrite for i8 arrays | Formally verified |
| `drbg_uninstantiate()` | Zeroizes DRBG V and Key fields | Tested in self_test.rs |
| Drop trait | Rust destructor calls ct_zeroize automatically | Code review verified |

All zeroization is constant-time to prevent timing-based information leakage.
Compiler optimization cannot remove these writes.

### 9.2 Conditional Self-Tests

| Trigger | Test | Function | Standard |
|---|---|---|---|
| TL-KEM keygen | Encaps/Decaps consistency | `conditional_keygen_test_kem()` | FIPS 140-3 §7.10.3 |
| TL-DSA keygen | Sign/Verify consistency | `conditional_keygen_test_dsa()` | FIPS 140-3 §7.10.3 |
| LMS/XMSS keygen | Sign/Verify consistency | `conditional_keygen_test_signature()` | FIPS 140-3 §7.10.3 |
| DRBG output | Continuous RNG test | `conditional_rng_test()` | SP 800-90A §11.3 |
| Module update | Integrity verification | `conditional_firmware_load_test()` | FIPS 140-3 §7.10.3 |

### 9.3 Error Behavior

On any self-test failure:
1. Module transitions to `Error` state via `module_state.rs`
2. All `CryptoService` calls return `Err(ServiceDenied)`
3. Only `StatusShow` service remains available (returns Error indicator)
4. Recovery requires module reload: Error -> ModuleReload -> Uninitialized -> SelfTest
5. No in-place recovery is possible (FIPS 140-3 §7.2.2)

## 11. Mitigation of Other Attacks

### 11.1 Side-Channel Resistance

| Module | Risk | Mitigation |
|---|---|---|
| AES-256-GCM | Cache-timing | GF(2^8) Fermat inversion S-box (no lookup tables) |
| AES GHASH | Cache-timing | Branchless GF(2^128) multiplication |
| TL-KEM | Chosen-ciphertext | Fujisaki-Okamoto transform with ct_select_vec |
| TL-DSA | Rejection sampling | Inherent to scheme; sampling is public |
| HMAC/Sponge | Timing | No secret-dependent indexing |
| Key comparison | Timing | ct_eq_slices (constant-time, no early termination) |
| Zeroization | Compiler removal | Volatile writes (ct_zeroize) |
