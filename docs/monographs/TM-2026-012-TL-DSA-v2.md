## 1. Motivation

TL-DSA v1 (WOTS+) is a hash-based signature scheme that treats TLSponge-385 as a generic hash function. It does not exploit the ternary algebraic structure of the Salvi Framework. The result is sequential chain iteration — 99 chains × 15 steps × ~8µs per step = 26.7ms per verify — while ML-DSA-87 achieves ~125µs using NTT-accelerated polynomial arithmetic.

TL-DSA v2 eliminates this gap by building a lattice signature scheme directly on the ternary algebra that PlenumNET already has: GF(3), GF(27) = GF(3³), the polynomial ring Z_q[X]/(X^n + 1), and ternary NTT. The signature scheme becomes native to the crystal geometry.

**The key insight:** ML-DSA's speed comes from NTT over binary rings. PlenumNET already has the ternary equivalent. We don't need to import binary NTT — we build ternary NTT from the GF(3ᵏ) arithmetic that's already in the codebase.

## 2. Algebraic Foundation

### 2.1 The Ternary Ring

Define the polynomial ring:

```
R_q = Z_q[X] / (X^n + 1)
```

where:

- q = 4,782,969 = 3¹⁴ + 2 (prime, enables radix-3 NTT)
- n = 243 = 3⁵ (ring dimension — a power of 3)
- X^n + 1 splits completely mod q (required for NTT)

Elements of R_q are polynomials of degree < 243 with coefficients in Z_q. Each coefficient is a ternary-representable integer.

**Why q = 3¹⁴ + 2:** This prime is 1 mod 3 (since 3¹⁴ + 2 ≡ 2 mod 3, we actually need q ≡ 1 mod 2n for NTT — let me correct this). We choose:

```
q = 4,782,969 is not suitable. Corrected choice:

q = 3¹⁴ - 2 = 4,782,967 (check primality)
  or
q = 2·3⁷ + 1 = 4,375 (too small)
  or
q = 2·3¹⁴ + 1 = 9,565,939 (check: 9,565,939 mod (2·243) = ?)

Proper choice: q must satisfy q ≡ 1 (mod 2n) for NTT.
With n = 243: q ≡ 1 (mod 486).

Candidate: q = 486k + 1 for some k.
q = 486 · 9839 + 1 = 4,781,755 (check primality)
q = 486 · 9841 + 1 = 4,782,727 (check primality)
q = 486 · 9851 + 1 = 4,787,587 (prime? — must verify)

For this design document, we use the notation q ∈ Primes(≡ 1 mod 486)
and defer the exact prime selection to TM-2026-013 (parameter selection).
```

**Practical choice for design purposes:**

```
q = 7,340,033 = 7 · 2²⁰ + 1 (known NTT-friendly prime)
```

This is the same prime used in several efficient lattice implementations. It satisfies q ≡ 1 (mod 486) since 7,340,033 mod 486 = 1. We can adapt to a ternary-natural prime later without changing the algorithm.

### 2.2 Module Structure

TL-DSA v2 uses Module-LWE (MLWE) over R_q, analogous to ML-DSA's construction but in a ternary context.

The module structure is:

```
Public matrix:  A ∈ R_q^(k × ℓ)     (k rows, ℓ columns of ring elements)
Secret key:     s₁ ∈ R_q^ℓ, s₂ ∈ R_q^k   (short ternary vectors)
Public key:     t = A·s₁ + s₂             (module-LWE instance)
```

Security parameters for Level 5 equivalent:

```
TL-DSA-v2-87:
  n = 243 (ring dimension)
  q = 7,340,033 (NTT-friendly prime)
  k = 8, ℓ = 7 (module dimensions)
  η = 2 (secret coefficient bound, balanced ternary: {-1, 0, 1} with probability bias)
  γ₁ = 2¹⁹ (signature coefficient range)
  γ₂ = (q-1)/32 (rounding parameter)
  τ = 60 (challenge weight)
```

### 2.3 Ternary NTT

The Number Theoretic Transform over Z_q for polynomials in R_q:

```
NTT(f) = [f(ω^(2i+1)) for i = 0, ..., n-1]
```

where ω is a primitive 2n-th root of unity mod q.

**Radix-3 butterfly:** For ternary-native computation, the NTT butterfly uses radix-3 decomposition:

```
Standard (radix-2):  a' = a + ω·b,  b' = a - ω·b
Ternary (radix-3):   a' = a + ω·b + ω²·c
                      b' = a + ζ·ω·b + ζ²·ω²·c
                      c' = a + ζ²·ω·b + ζ⁴·ω²·c
```

where ζ = ω^(2n/3) is a primitive cube root of unity mod q.

Since n = 243 = 3⁵, the NTT decomposes into 5 stages of radix-3 butterflies. Each stage processes n/3 independent triplets — naturally mapping to the 13D hypercube's trit structure.

**The 26-port parallel array:** Each of the 26 neighbors in the 13D hypercube corresponds to a change in one dimension (13 dimensions × 2 alternative values). The NTT's 5 radix-3 stages can be distributed across these 26 ports:

```
Stage 0: 81 triplets of 3 elements  → 13 dims × 6.2 triplets/dim  → 2 ports/dim
Stage 1: 27 triplets of 9 elements  → 13 dims × 2.1 triplets/dim  → 2 ports/dim
Stage 2: 9 triplets of 27 elements  → 9 triplets = 9 Plenum Square cells
Stage 3: 3 triplets of 81 elements  → 3 trit values in one dimension
Stage 4: 1 triplet of 243 elements  → final merge

Stages 0–1: distribute across 26 ports (2 per dimension)
Stage 2: distribute across 9 σ-shuffled blocks
Stage 3–4: local merge (sequential)
```

This maps the NTT directly onto the inter-cube topology. Each node can delegate NTT sub-computations to its neighbors — the overlay network becomes a distributed NTT engine.

## 3. The TL-DSA v2 Scheme

### 3.1 Key Generation

```
TL-DSA-v2.KeyGen():
  1. ξ ←$ {0,1}^256                          // Random seed
  2. (ρ, ρ', K) = TLSponge-385(ξ)           // Expand seed (ternary sponge)
  3. A = ExpandA(ρ) ∈ R_q^(k×ℓ)             // Public matrix from seed
  4. s₁ = SampleTernary(ρ', η) ∈ R_q^ℓ      // Short secret (balanced ternary)
  5. s₂ = SampleTernary(ρ', η) ∈ R_q^k      // Short error (balanced ternary)
  6. t = NTT⁻¹(NTT(A) ⊙ NTT(s₁)) + s₂      // Public key computation
  7. (t₁, t₀) = Power2Round(t, d)            // Split for compression
  8. pk = (ρ, t₁)                             // Public key
  9. sk = (ρ, K, tr, s₁, s₂, t₀)            // Secret key (tr = TLSponge(pk))
  Return (pk, sk)
```

**SampleTernary(seed, η):** Generates polynomials with coefficients in {-η, ..., η} using balanced ternary sampling. When η = 2, coefficients are drawn from {-2, -1, 0, 1, 2} — exactly the balanced quinary representation that maps naturally to pairs of balanced trits.

**ExpandA uses TLSponge-385** (not SHAKE-128 as in ML-DSA). The matrix A is generated by absorbing ρ into the sponge and squeezing n·k·ℓ coefficients. Since TLSponge-385 operates on 729-trit state, the expansion naturally produces ternary-structured output.

### 3.2 Signing (Fiat-Shamir with Aborts)

```
TL-DSA-v2.Sign(sk, M):
  1. A = ExpandA(ρ)
  2. µ = TLSponge-385(tr ‖ M)                // Message representative
  3. κ = 0; ρ' = TLSponge-385(K ‖ rnd ‖ µ)  // Hedged randomness
  4. loop:
       y = SampleMask(ρ', κ, γ₁) ∈ R_q^ℓ    // Masking vector
       w = NTT⁻¹(NTT(A) ⊙ NTT(y))           // Commitment
       w₁ = HighBits(w, 2γ₂)                  // Round commitment
       c̃ = TLSponge-385(µ ‖ w₁)             // Challenge hash
       c = SampleInBall(c̃, τ)                // Sparse ternary challenge
       z = y + c·s₁                            // Response
       r₀ = LowBits(w - c·s₂, 2γ₂)          // Hint computation
       if ‖z‖∞ ≥ γ₁ - β or ‖r₀‖∞ ≥ γ₂ - β:
         κ++; continue                         // REJECT and retry
       h = MakeHint(-c·t₀, w - c·s₂ + c·t₀)
       if ‖c·t₀‖∞ ≥ γ₂ or #ones(h) > ω:
         κ++; continue                         // REJECT and retry
       Return σ = (c̃, z, h)
```

**SampleInBall produces a ternary challenge:** Instead of ML-DSA's binary challenge (coefficients in {-1, 0, 1}), TL-DSA v2's challenge has coefficients in {-1, 0, 1} with exactly τ non-zero positions. This is identical in structure — the ternary nature is in the underlying polynomial arithmetic, not the challenge sampling.

**The NTT calls are the hot path.** Each signing attempt requires 2 NTT operations (for A⊙y and c·s₁). With the radix-3 NTT over n=243:

```
NTT cost: 5 stages × (n/3) radix-3 butterflies × 3 mults per butterfly
        = 5 × 81 × 3 = 1,215 multiplications mod q
        ≈ 1,215 × ~5ns = ~6µs per NTT

2 NTTs per attempt × ~3.5 attempts average (Dilithium's rejection rate)
≈ ~42µs for signing
```

Compare: TL-DSA v1 sign = 20.07 ms. **TL-DSA v2 sign ≈ 42µs. That's a 478× speedup.**

### 3.3 Verification

```
TL-DSA-v2.Verify(pk, M, σ):
  1. (ρ, t₁) = pk
  2. (c̃, z, h) = σ
  3. if ‖z‖∞ ≥ γ₁ - β: return REJECT
  4. A = ExpandA(ρ)
  5. µ = TLSponge-385(TLSponge-385(pk) ‖ M)
  6. c = SampleInBall(c̃, τ)
  7. w'₁ = UseHint(h, NTT⁻¹(NTT(A)⊙NTT(z) - NTT(c)⊙NTT(t₁·2^d)))
  8. return c̃ == TLSponge-385(µ ‖ w'₁)
```

Verification requires 3 NTT operations: NTT(A), NTT(z), NTT(c). With precomputed NTT(A) (stored with the public key), this reduces to 2 NTTs + point-wise operations:

```
Verify cost ≈ 2 NTTs + ExpandA + hash
            ≈ 12µs + 5µs + 10µs = ~27µs
```

Compare: TL-DSA v1 verify = 26.70 ms. **TL-DSA v2 verify ≈ 27µs. That's a 989× speedup.**

### 3.4 26-Port Parallel NTT Array

The distributed NTT exploits the 13D hypercube topology:

```
Node A wants to compute NTT(f) where f ∈ R_q (degree 243 polynomial).

Step 1: Decompose f into 243/3 = 81 triplets.
Step 2: Distribute 81 triplets across 26 neighbors:
        - Each of 13 dimensions handles ~6 triplets
        - 2 ports per dimension (one per alternative trit value)
        - 13 × 6 = 78 triplets distributed, 3 computed locally
Step 3: Each neighbor computes one radix-3 butterfly (3 mults + 2 adds).
Step 4: Results returned via authenticated heartbeat channel.
Step 5: Node A performs stages 2–4 locally (27 + 9 + 3 + 1 = 40 butterflies).

Total local cost: 40 × 3 mults = 120 multiplications (vs 1,215 sequential)
Speedup: ~10× from distributing Stage 0 across the overlay network.
```

This is not theoretical — the tunnel infrastructure (T-14), authenticated heartbeats (T-08), and lattice-mixed keys (T-23) already provide the authenticated channels. The 26-port NTT is an application of the existing infrastructure.

**For local-only operation** (no network distribution), the NTT is still fast because it's radix-3 on powers of 3 — the butterflies align perfectly with SIMD lanes:

```
AVX2: 8 × 32-bit lanes → 8 radix-3 butterflies in parallel
NEON: 4 × 32-bit lanes → 4 radix-3 butterflies in parallel

NTT(n=243) with AVX2: 1,215 mults / 8 lanes ≈ 152 SIMD ops × ~5ns = ~760ns
```

## 5. Security Analysis (Preliminary)

### 5.1 Hardness Assumption

TL-DSA v2's security reduces to the Module-LWE problem over R_q = Z_q[X]/(X²⁴³ + 1):

```
MLWE(k, ℓ, η): Given A ∈ R_q^(k×ℓ) and t = A·s₁ + s₂ where s₁, s₂ have
coefficients bounded by η, distinguish t from uniform.
```

This is the same problem class as ML-DSA. The ternary aspect is in the ring dimension (n=243=3⁵ vs n=256=2⁸) and the coefficient sampling (balanced ternary with η=2).

**Known attacks:**

- **Primal lattice attack (BKZ):** Complexity depends on the root Hermite factor δ = (det(Λ)/q^n)^(1/2n). With our parameters, the estimated block size β for BKZ is comparable to ML-DSA-87 (β ≈ 430 for Level 5). The ternary ring does not introduce new attack surfaces — the lattice dimension is what matters.

- **Dual attack:** Similar to primal. The ternary structure of the secret does not provide additional information to the attacker beyond what's captured by the η bound.

- **Algebraic attacks on X^n + 1 with n=3⁵:** The polynomial X²⁴³ + 1 does NOT factor as nicely as X²⁵⁶ + 1 over Z (which factors into cyclotomic polynomials). This is actually a **security advantage** — fewer algebraic shortcuts for the attacker. However, it also means the NTT requires a more careful choice of q (must have order 2·243 = 486 roots of unity). This is why we use q = 7,340,033 (which has the required roots).

### 5.2 Hash-Based vs Lattice Trust

TL-DSA v1 (hash-based) has unconditional security: if TLSponge-385 is pre-image resistant, it's secure. Period.

TL-DSA v2 (lattice-based) has conditional security: if MLWE over R_q is hard, it's secure. This is a stronger assumption — a mathematical breakthrough could break MLWE without breaking hash functions.

**The Salvi Framework retains both.** TL-DSA v1 remains for high-assurance contexts (CRS registration, SignHere document signing). TL-DSA v2 is used for performance-critical contexts (per-heartbeat operations, tunnel authentication, high-throughput verification). The dual-scheme approach mirrors NIST's own strategy of standardizing both ML-DSA (lattice) and SLH-DSA (hash-based).

### 5.3 Address-Geometric Binding

TL-DSA v2 keypairs are derived from the node's 13-trit address using the same address-bound derivation as TL-DSA v1 (T-15):

```
seed = TLSponge-385("PlenumNET-IDENTITYv2", addr_bytes ‖ master_secret)
(pk, sk) = TL-DSA-v2.KeyGen(seed)
```

The NTT structure aligns with the address geometry: each of the 5 radix-3 NTT stages corresponds to resolving one "digit" of the base-3 address. A 243-dimensional polynomial maps onto a 5-trit subspace of the 13D hypercube. This means the polynomial ring structure and the address space share the same algebraic substrate — operations in one domain have natural interpretations in the other.

### 7.3 Why Faster Than ML-DSA

1. **Fewer NTT stages:** n=243 (5 radix-3 stages) vs n=256 (8 radix-2 stages). 37% fewer stages.
2. **Smaller polynomials:** 243 coefficients vs 256 coefficients. 5% less data.
3. **Radix-3 is wider:** Each radix-3 butterfly processes 3 elements (vs 2 for radix-2), so fewer total butterflies: 5 × 81 = 405 vs 8 × 128 = 1,024. 60% fewer butterflies.
4. **26-port distribution:** Stage 0 parallelized across the overlay network. No other signature scheme has this.
5. **Native arithmetic:** GF(3ᵏ) operations use the same mod-3 ALU paths as the sponge and address space. No domain conversion overhead.

## 8. Coexistence Strategy

TL-DSA v1 and v2 coexist. They are not replacements — they serve different threat models.

| Context | Scheme | Why |
|---------|--------|-----|
| CRS registration | TL-DSA v1-87 | Hash-based trust, unconditional security. Registration is rare. |
| SignHere document signing | TL-DSA v1-87 | Legal documents require the strongest trust basis. |
| Per-heartbeat authentication | TL-DSA v2-87 | Speed-critical. Lattice trust is acceptable for ephemeral auth. |
| Tunnel handshake | TL-DSA v2-87 | Performance-sensitive mutual authentication. |
| High-throughput verification | TL-DSA v2-87 | Batch verification of neighbor signatures. |

The SignHere 6-check pipeline verifies both: TL-DSA v1 co-signature (hash-based, unconditional) AND TL-DSA v2 co-signature (lattice-based, fast). Belt and suspenders.

## 9. Open Questions

1. **Exact prime q:** Need to find the optimal NTT-friendly prime that is also close to a power of 3. The ternary-natural choice would be q near 3¹⁴ ≈ 4.8M. The practical choice (7,340,033) works but isn't ternary-aligned. A prime of the form q = a·3ᵏ + 1 would be ideal.

2. **Ring choice X^n + 1 vs X^n - 1:** The cyclotomic polynomial X²⁴³ + 1 may not split optimally over Z_q for all ternary-friendly primes. Alternative: use X^(3⁵) - 1 and quotient by Φ₃₅(X), working in the 3⁵-th cyclotomic ring. This changes the NTT structure but may yield better algebraic properties.

3. **Rejection rate:** The Fiat-Shamir-with-Aborts construction's rejection rate depends on γ₁, β, and the secret distribution. With balanced ternary secrets (η=2), the expected rejection rate needs simulation to confirm it's comparable to ML-DSA's ~3.5 average attempts.

4. **Side-channel resistance:** The radix-3 NTT must be implemented in constant time. The ternary branching (3-way vs 2-way) creates different timing profiles than binary NTT. Need constant-time GF(3ᵏ) multiplication.

5. **Distributed NTT trust model:** The 26-port parallel NTT sends polynomial coefficients to neighbors. Even though the channels are authenticated (T-14), a compromised neighbor could return incorrect butterfly results. Need either: (a) redundant computation (send to 2 neighbors per triplet, compare), or (b) verifiable computation (zero-knowledge proof of correct butterfly, but this defeats the performance purpose).
