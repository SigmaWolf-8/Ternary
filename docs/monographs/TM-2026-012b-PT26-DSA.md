## 1. What PT26-DSA Is

PT26-DSA is a digital signature scheme whose hard problem is the geometry of the 13-dimensional ternary hypercube. It is not a lattice scheme. It is not a hash-chain scheme. It is a **topological** signature scheme — the first of its kind.

The signer proves they know a secret path through the 13D hypercube that connects two publicly known vertices while respecting the σ permutation schedule. The verifier checks the path using only the public hypercube structure and the signer's public key. All 26 neighbor ports process in parallel because each port handles one dimension of the traversal simultaneously.

**Why the name:** **P**arallel **T**raversals × **26** ports. The 26 is not a parameter — it's the geometry. A 13D hypercube has exactly 26 edges per vertex (13 dimensions × 2 alternative trit values). This number is fixed by the crystal structure, not chosen by a designer.

**Why this can only exist on PlenumNET:** The signature verification requires an authenticated 13D overlay network with known topology. The verifier must be able to query neighbors, check σ-permuted paths, and validate traversal proofs against the live network geometry. No other system has this infrastructure. The network IS the verification engine.

## 2. The Hard Problem

### 2.1 Ternary Hypercube Walk Problem (THWP)

**Definition:** Given the 13D ternary hypercube G = (V, E) where V = Z₃¹³ (1,594,323 vertices) and each vertex has 26 neighbors, and given:

- A source vertex s ∈ V (the signer's address)
- A destination vertex d ∈ V (derived from the message hash)
- A public walk W_pub = (s, w₁, w₂, ..., w_k, d) of length k

Find a **secret walk** W_sec of length < k that reaches d from s using the σ permutation schedule derived from the signer's secret key.

**Intuition:** The public walk is the "long way around" — it follows the standard greedy path, fixing one mismatched dimension per step. The secret walk uses the σ permutations (σ_A, σ_B, σ_C, σ_D from the Plenum Square) to reorder which dimensions are fixed first, creating shortcuts through the hypercube that are only possible if you know the permutation schedule.

### 2.2 Why This Is Hard

The greedy path from s to d has length equal to the Hamming distance H(s,d), which ranges from 0 to 13. There are H(s,d)! possible orderings of which dimensions to fix. With σ permutations applied at each step, the number of possible walks of length ≤ k is:

```
|Walks(s, d, k)| = Σ_{i=0}^{k} C(13, i) × 2^i × 4^i

where:
  C(13, i) = dimensions to traverse
  2^i = trit value choices per dimension
  4^i = σ permutation choices per step (σ_A, σ_B, σ_C, σ_D)
```

For k = H(s,d) = 13 (maximum distance):

```
|Walks(s, d, 13)| = 13! × 2¹³ × 4¹³ ≈ 6.2 × 10⁹ × 8,192 × 67,108,864
                   ≈ 3.4 × 10²³
```

An exhaustive search over 10²³ walks is infeasible. The σ schedule (derived from the secret key) selects one specific walk from this space.

### 2.3 Security Reduction

The THWP reduces to the **Hidden Permutation Problem** on the symmetric group S₁₃ composed with the σ-action of (S₃)²⁵ × (C₂)² (the automorphism group of the Plenum Square, from TM-2026-008 Program III):

```
Given: Oracle access to f(x) = σ_schedule(secret_key, x) for x ∈ Z₃¹³
Find:  The secret_key ∈ {0,1}^λ that determines the σ schedule

The best generic attack is birthday-bounded:
  O(|Aut(PlenumNET)|^(1/2)) = O(((6^25 × 4)^(1/2)))
                              ≈ O(2^(32.5))  — TOO LOW for Level 5
```

**This is insufficient for standalone security.** The THWP alone doesn't provide Level 5 (256-bit) security. PT26-DSA therefore combines the geometric walk with a sponge-based commitment that binds the walk to a TLSponge-385 hash, raising the security to the sponge's pre-image resistance (385 bits).

The geometry provides the STRUCTURE. The sponge provides the HARDNESS. Neither alone is sufficient.

## 3. The PT26-DSA Scheme

### 3.1 Primitives

| Primitive | Source | Role in PT26-DSA |
|-----------|--------|-----------------|
| TLSponge-385 | `sponge.rs` | Commitment hash, challenge derivation |
| σ_A, σ_B, σ_C, σ_D | `plenum_square.rs` (T-04) | Walk step permutations |
| Hamming distance | `placement.rs` (T-16) | Walk length computation |
| Weight vector W[9] | `plenum_square.rs` | Step cost weighting |
| Magic constant 333 | `plenum_square.rs` | Walk checksum modulus |
| Coprime walk (13,28) | Framework invariant | Schedule period |
| CubeAddr | `cube_addr.rs` | Vertex representation |

### 3.2 Key Generation

```
PT26-DSA.KeyGen(master_secret, address):

  1. addr = address ∈ Z₃¹³                    // Signer's cube address
  
  2. // Derive the secret σ schedule: a sequence of 13 permutation choices
     schedule_seed = TLSponge-385("PT26-SCHEDULE", addr ‖ master_secret)
     
  3. // For each of 13 possible walk steps, select which σ to apply
     for step in 0..13:
       σ_index[step] = schedule_seed[step] mod 4    // {0,1,2,3} → {σ_A,σ_B,σ_C,σ_D}
       dim_order[step] = schedule_seed[13 + step] mod (13 - step)  // Dimension priority
     
  4. // Derive the walk weight key (for weighted commitment)
     weight_key = TLSponge-385("PT26-WEIGHT", addr ‖ master_secret, 27)
     
  5. // Public key: commitment to the schedule WITHOUT revealing it
     pk_commit = TLSponge-385("PT26-PK",
       σ_index[0..13] ‖ dim_order[0..13] ‖ weight_key)
     
  6. pk = (addr, pk_commit)                    // 13 + 48 = 61 bytes
     sk = (addr, σ_index[0..13], dim_order[0..13], weight_key, master_secret)
     
  Return (pk, sk)
```

**Public key size: 61 bytes.** Comparable to TL-DSA v1's 64 bytes. The public key is the node's address plus a 48-byte sponge commitment to the secret schedule.

### 3.3 Signing

```
PT26-DSA.Sign(sk, message):

  1. // Derive message-dependent destination vertex
     msg_hash = TLSponge-385("PT26-MSG", message)
     dest = derive_destination(addr, msg_hash)  // Map hash to Z₃¹³ vertex
     
  2. // Compute Hamming distance (walk length)
     h = hamming_distance(addr, dest)           // 0 ≤ h ≤ 13
     
  3. // Construct the SECRET walk using the σ schedule
     walk = [addr]
     current = addr
     dims_remaining = {d : addr[d] ≠ dest[d]}  // Dimensions that need fixing
     
     for step in 0..h:
       // Apply σ permutation to reorder the block structure
       σ = SIGMAS[σ_index[step]]
       
       // Select which dimension to fix (secret ordering)
       priority = dim_order[step] mod |dims_remaining|
       dim = dims_remaining[priority]
       dims_remaining.remove(dim)
       
       // Step to the neighbor that fixes this dimension
       next = current
       next[dim] = dest[dim]
       
       // Compute weighted step commitment
       triplet_idx = dim / 3                    // Which Plenum Square cell
       step_weight = WEIGHT_VECTOR[σ[triplet_idx]]
       step_commit = TLSponge-385("PT26-STEP",
         current ‖ next ‖ step_weight ‖ weight_key ‖ step)
       
       walk.push((next, step_commit))
       current = next
     
  4. // Walk checksum: weighted sum mod 333 (magic constant)
     walk_checksum = 0
     for (i, (vertex, commit)) in walk[1..].iter().enumerate():
       walk_checksum = (walk_checksum + WEIGHT_VECTOR[σ_index[i] * 2 + (i % 3)]) % 333
     
  5. // Final signature commitment
     sig_commit = TLSponge-385("PT26-SIG",
       addr ‖ dest ‖ walk_checksum ‖ msg_hash ‖ 
       walk.step_commits.concat())
     
  6. // Assemble signature
     σ_sig = {
       dest:           dest,                     // 13 bytes
       walk_length:    h,                        // 1 byte
       walk_checksum:  walk_checksum,            // 2 bytes (mod 333)
       step_commits:   [step_commit; h],         // h × 48 bytes
       sig_commit:     sig_commit,               // 48 bytes
     }
     
  Return σ_sig
```

**Signature size:** 13 + 1 + 2 + (h × 48) + 48 = 64 + 48h bytes. For average h ≈ 8.7 (expected Hamming distance between random Z₃¹³ vertices): **~482 bytes**. For maximum h = 13: **688 bytes**.

This is **dramatically smaller than every PQ signature scheme:**

| TL-DSA v1-87 | 3,168 B |

### 3.4 Verification — The 26-Port Parallel Engine

```
PT26-DSA.Verify(pk, message, σ_sig):

  1. (addr, pk_commit) = pk
     (dest, h, walk_checksum, step_commits, sig_commit) = σ_sig
     
  2. // Verify destination derivation
     msg_hash = TLSponge-385("PT26-MSG", message)
     expected_dest = derive_destination(addr, msg_hash)
     if dest ≠ expected_dest: return REJECT
     
  3. // Verify walk length matches Hamming distance
     expected_h = hamming_distance(addr, dest)
     if h ≠ expected_h: return REJECT
     
  4. // Verify walk checksum is valid mod 333
     if walk_checksum ≥ 333: return REJECT
     
  5. // ═══════════════════════════════════════════════════
     // 26-PORT PARALLEL VERIFICATION
     // ═══════════════════════════════════════════════════
     //
     // The verifier does NOT reconstruct the walk (that requires the secret).
     // Instead, it verifies CONSISTENCY of the step commitments.
     //
     // Each of the 13 dimensions that differ between addr and dest
     // corresponds to exactly one walk step. The verifier dispatches
     // verification of each step's commitment to the neighbor port
     // for that dimension — all 13 (up to h) ports fire simultaneously.
     
     differing_dims = {d : addr[d] ≠ dest[d]}
     assert |differing_dims| == h
     
     // PARALLEL: For each differing dimension, verify the step commitment
     // claims a valid transition in that dimension
     verification_results = parallel_map(differing_dims, |dim| {
       // The step that fixes dimension `dim` must produce a commitment
       // that is consistent with:
       //   - transitioning from value addr[dim] to dest[dim]
       //   - using one of the 4 valid σ permutations
       //   - using a valid weight from the Plenum Square
       
       // Try all 4 σ permutations × valid weight assignments
       for σ_idx in 0..4:
         σ = SIGMAS[σ_idx]
         triplet_idx = dim / 3
         weight = WEIGHT_VECTOR[σ[triplet_idx]]
         
         // Reconstruct what the step commitment SHOULD be
         // for this (dim, σ) combination
         for step_pos in 0..h:
           candidate = TLSponge-385("PT26-STEP",
             interpolate_vertex(addr, dest, dim, step_pos) ‖
             weight ‖ step_pos)
           
           if candidate matches any step_commits[i]:
             return (dim, true, step_pos)
       
       return (dim, false, 0)
     })
     
  6. // All dimensions must be covered by exactly one step commitment
     if any verification_results[dim].valid == false: return REJECT
     if step positions are not a permutation of 0..h: return REJECT
     
  7. // Verify aggregate commitment
     expected_sig_commit = TLSponge-385("PT26-SIG",
       addr ‖ dest ‖ walk_checksum ‖ msg_hash ‖
       step_commits.concat())
     if sig_commit ≠ expected_sig_commit: return REJECT
     
  8. return ACCEPT
```

### 3.5 Parallel Verification Complexity

Each dimension's verification tries 4 σ choices × h step positions = 4h candidates per dimension. With h dimensions verified in parallel:

```
Sequential cost:  h × 4h × TLSponge = h² × 4 × ~10µs
                  For h=13: 169 × 4 × 10µs = 6.76ms

Parallel cost (26 ports): h × 4 × TLSponge / 13 ports
                          = 4 × ~10µs = ~40µs
                          (each port handles ONE dimension)
```

**With TIS-27 fast-path (T-28b) for step commitment verification:**

```
Parallel cost: 4 × ~185ns = ~740ns per dimension
All dimensions: ~740ns (parallel across 13 ports)
Total verify: ~740ns + ~10µs overhead ≈ ~11µs
```

**PT26-DSA verify: ~11µs with 26-port parallel + TIS-27 fast path.**

## 4. The Geometry as Cryptography

### 4.1 Why σ Permutations Are the Secret

The four σ permutations from the Plenum Square are:

```
σ_A = [4, 8, 3, 2, 0, 7, 5, 6, 1]  — Full derangement (0 fixed points)
σ_B = [6, 0, 7, 8, 4, 2, 3, 1, 5]  — Fixes center (1 fixed point)
σ_C = [2, 6, 7, 8, 4, 0, 1, 5, 3]  — Fixes center (1 fixed point)
σ_D = [8, 5, 0, 1, 4, 6, 7, 3, 2]  — Fixes center (1 fixed point)
```

Each σ reorders the 9 blocks of the sponge state. When applied to a walk step, σ determines which Plenum Square cell (and therefore which weight) governs the step's commitment. The signer chooses σ_index[step] at signing time; the verifier must try all 4 options.

The security comes from the COMBINATION of σ choices across all 13 steps. There are 4¹³ = 67,108,864 possible σ schedules. Combined with 13! = 6,227,020,800 dimension orderings, the search space is:

```
4¹³ × 13! ≈ 4.18 × 10¹⁷
```

This alone provides ~58 bits of security — insufficient for Level 5. The TLSponge-385 commitment in each step raises the total security to min(58 + 385, 385) = 385 bits, because an attacker must BOTH guess the σ schedule AND forge the sponge commitment.

### 4.2 The Magic Constant as Checksum

The walk checksum uses the Plenum Square's magic constant 333:

```
walk_checksum = Σ(step_weights) mod 333
```

Every row, column, and diagonal of the Plenum Square sums to 333. This means an attacker who tries to forge a walk by rearranging steps within a row/column/diagonal produces the SAME checksum — the magic property prevents certain classes of permutation attacks from changing the checksum.

### 4.3 The Coprime Walk as Schedule Period

The σ schedule repeats with period lcm(13, 28) = 364 = the ternary circle. For a single signature (walk length ≤ 13), the schedule never repeats. For multiple signatures under the same key, the coprime walk `(step × 13) mod 28` ensures each signature uses a different portion of the schedule cycle.

```
Signature 0:  schedule positions 0–12
Signature 1:  schedule positions 13–25
Signature 2:  schedule positions 26–37 (wraps mod 28)
...
After 28 signatures, the full cycle is exhausted.
```

This gives PT26-DSA a natural per-key signature budget of 28 — after which the key should be rotated. For PlenumNET (where keys rotate every 182 days at arc epoch boundaries, with at most a few registrations per epoch), this budget is more than sufficient.

## 8. Open Questions

1. **Exact security bound.** The 4¹³ × 13! geometric search space (~58 bits) is boosted by TLSponge-385 commitments to 385 bits total. Need a formal proof that these compose correctly — an attacker who partially solves the geometric problem doesn't get a shortcut on the sponge commitment.

2. **Signature budget.** 28 signatures per key (coprime walk period). Sufficient for PlenumNET's use case (few registrations per arc epoch), but limiting for high-volume signing. Solution: re-derive the schedule seed from a counter, extending the budget to 28 × 2⁶⁴ at the cost of one extra sponge call per signature.

3. **Network-dependent verification.** PT26-DSA can only be verified by nodes participating in the overlay. This is a feature (network lock-in) and a limitation (no offline verify). The coexistence strategy (TL-DSA v1 co-signatures for offline) addresses this but adds ~3KB to every dual-signed document.

4. **Timing side channels.** The walk length h leaks the Hamming distance between the signer's address and the message-derived destination. This reveals geometric information about the signer's position. Mitigation: pad all walks to length 13 (maximum) with dummy steps. Cost: signature size increases to 688 bytes (fixed) but h is no longer leaked.

5. **Distributed verification trust.** When a verifier delegates step-commitment checks to neighbor ports, a compromised neighbor could falsely claim "valid" or "invalid." Mitigation: each step commitment includes a MAC under the verifier's own key — the neighbor returns the raw computation, and the verifier checks the MAC locally. This adds one TIS-27 call per step (~185ns × 13 = 2.4µs) but eliminates the trust dependency.
