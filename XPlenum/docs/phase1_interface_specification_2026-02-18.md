## 1. Interface Overview

XPlenum integrates into CVA6's Execute stage as a parallel functional unit. The interface consists of four signal groups: instruction dispatch, result return, CSR access, and exception reporting.

```
                    CVA6 Pipeline
┌──────────────────────────────────────────────────────┐
│                                                      │
│  ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐  │
│  │   ID   │ → │ Issue  │ → │   EX   │ → │ Commit │  │
│  │Decoder │   │Scorebrd│   │        │   │   WB   │  │
│  └───┬────┘   └───┬────┘   │  ┌───┐ │   └───┬────┘  │
│      │            │        │  │ALU│ │       │        │
```

## 2. Signal Definitions

### 2.1 Instruction Dispatch (Issue → XPlenum)

| Signal | Direction | Width | Description | Timing |
|--------|-----------|-------|-------------|--------|
| `xp_valid_i` | In | 1 | XPlenum instruction dispatched from Issue stage | Pulsed for 1 cycle per instruction |
| `xp_instruction_i` | In | 32 | Full 32-bit instruction word | Valid when `xp_valid_i` is high |
| `xp_rs1_data_i` | In | 64 | Source register 1 data (full 64-bit, XPlenum uses [31:0]) | Valid when `xp_valid_i` is high |
| `xp_rs2_data_i` | In | 64 | Source register 2 data (full 64-bit, XPlenum uses [31:0]) | Valid when `xp_valid_i` is high |
| `xp_rd_addr_i` | In | 5 | Destination register address (from instruction[11:7]) | Valid when `xp_valid_i` is high |
| `xp_trans_id_i` | In | 4 | Transaction ID for scoreboard tracking | Valid when `xp_valid_i` is high |

### 2.2 Result Return (XPlenum → Commit)

| Signal | Direction | Width | Description | Timing |
|--------|-----------|-------|-------------|--------|
| `xp_result_o` | Out | 64 | Result data (sign-extended from 32-bit XPlenum output) | Valid when `xp_valid_o` is high |
| `xp_valid_o` | Out | 1 | Result valid — write to register file | Asserted for 1 cycle when result is ready |
| `xp_rd_addr_o` | Out | 5 | Destination register address (passed through) | Valid when `xp_valid_o` is high |
| `xp_trans_id_o` | Out | 4 | Transaction ID (passed through for scoreboard) | Valid when `xp_valid_o` is high |

### 2.3 Pipeline Control

| Signal | Direction | Width | Description | Timing |
|--------|-----------|-------|-------------|--------|
| `xp_ready_o` | Out | 1 | XPlenum ready to accept new instruction | Deasserted during multi-cycle operations |
| `xp_busy_o` | Out | 1 | XPlenum is executing a multi-cycle operation | Asserted until result is produced |
| `flush_i` | In | 1 | Pipeline flush (branch mispredict, exception, trap return) | XPlenum must discard in-flight operation |

### 2.4 Exception Reporting

| Signal | Direction | Width | Description | Timing |
|--------|-----------|-------|-------------|--------|
| `xp_exception_o` | Out | 1 | Exception generated by XPlenum operation | Asserted simultaneously with `xp_valid_o` |
| `xp_exc_cause_o` | Out | 64 | Exception cause code (mcause format) | Valid when `xp_exception_o` is high |
| `xp_exc_tval_o` | Out | 64 | Exception trap value (mtval — offending instruction/address) | Valid when `xp_exception_o` is high |

### 2.5 CSR Access

| Signal | Direction | Width | Description | Timing |
|--------|-----------|-------|-------------|--------|
| `csr_xp_addr_i` | In | 12 | CSR address (0x7C0–0x7CB range) | Valid during CSR read/write cycle |
| `csr_xp_wdata_i` | In | 64 | CSR write data | Valid when `csr_xp_wen_i` is high |
| `csr_xp_wen_i` | In | 1 | CSR write enable | Single-cycle pulse |
| `csr_xp_rdata_o` | Out | 64 | CSR read data | Valid 1 cycle after address presented |
| `csr_xp_valid_o` | Out | 1 | CSR address is in XPlenum range (address decode hit) | Combinational from address input |

## 4. Clock and Reset

| Parameter | Specification |
|-----------|---------------|
| Clock Domain | Single clock domain — same `clk` as CVA6 core |
| Clock Frequency | Target 100 MHz (FPGA), up to 1 GHz (ASIC 22nm) |
| Reset | Active-low asynchronous reset (`rst_n`), synchronised to clock |
| Reset Recovery | All XPlenum state initialised within 1 clock cycle after reset deasserts |

No clock domain crossing is required. XPlenum operates in the same clock domain as the CVA6 pipeline.

## 5. Pipeline Stall Protocol

### Stall Conditions

| Condition | Behaviour |
|-----------|-----------|
| XPlenum busy, new XPlenum instruction in Issue | Issue stage stalls (does not dispatch) |
| XPlenum busy, non-XPlenum instruction in Issue | Issue stage dispatches to other FU (no stall) |
| RAW hazard on XPlenum result | Issue stage stalls until XPlenum result is forwarded |
| Pipeline flush | XPlenum cancels in-flight operation, returns to ready |

### Bubble Insertion

When XPlenum is busy and the Issue stage has a dependent instruction:

1. Issue stage inserts a **pipeline bubble** (NOP) into the Execute stage
2. The dependent instruction remains in the Issue stage
3. When XPlenum produces its result, forwarding delivers it to the waiting instruction
4. Issue stage resumes dispatch on the next cycle

This matches CVA6's existing protocol for FPU multi-cycle operations.

## 6. Exception Handling Protocol

### Exception Priority

XPlenum exceptions are reported at the same priority level as other Execute-stage exceptions. If multiple exceptions occur in the same cycle, CVA6's commit stage resolves priority using its existing arbitration logic.

### Exception Delivery Sequence

1. XPlenum asserts `xp_exception_o` + `xp_exc_cause_o` + `xp_exc_tval_o`
2. Exception propagates through commit stage
3. Controller triggers pipeline flush
4. PC redirects to MTVEC
5. mcause loaded with mapped exception code
6. mtval loaded with offending instruction or address
7. mepc loaded with PC of faulting instruction

### Precise Exceptions

All XPlenum exceptions are **precise**: the instruction that caused the exception is identified in mepc, all instructions before it have committed, and no instructions after it have committed. This is guaranteed by CVA6's in-order commit stage.

## 7. Data Width Adaptation

### Input Narrowing (64 → 32)

```verilog
wire [31:0] xp_rs1_narrow = xp_rs1_data_i[31:0];
wire [31:0] xp_rs2_narrow = xp_rs2_data_i[31:0];
```

### Output Widening (32 → 64)

Sign-extension for consistency with RV64I W-suffix semantics:

```verilog
wire [63:0] xp_result_wide = {{32{xp_result_32[31]}}, xp_result_32};
```

## 8. Register Conventions

| Register | Purpose in XPlenum Context |
|----------|----------------------------|
| rs1 (x1–x31) | Primary operand (data, domain index, capability index, trit value) |
| rs2 (x1–x31) | Secondary operand (mask value, permission bitmap, encoding parameter) |
| rd (x1–x31) | Result destination (masked data, check result, encoded value) |
| x0 | Hardwired zero — writes to x0 are discarded (standard RISC-V behaviour) |
