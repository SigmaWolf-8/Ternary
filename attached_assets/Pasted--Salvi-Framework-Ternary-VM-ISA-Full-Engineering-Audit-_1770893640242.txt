## Part I: Critical Bugs & Contradictions

### BUG-01: Three Incompatible XOR Definitions Across the Codebase

This is the most serious consistency failure in the framework. "Ternary XOR" means three different things depending on which module you're in:

| Location | Definition | Truth Table (-1,-1) | (-1,1) | (1,1) |
|----------|-----------|---------------------|--------|-------|
| **VM opcode `TXor`** (engine.rs:287) | `(a + b) mod 3` balanced | 1 | 0 | -1 |
| **Kernel `Trit::xor()`** (ternary.rs:101) | `min(a, b)` | -1 | -1 | 1 |
| **libternary `ternaryXor()`** (ternary-operations.ts:138) | Identity-if-one-zero, else 0 | 0 | 0 | 0 |

The libternary TypeScript even has a *comment* acknowledging the divergence (line 192–194) — `gf3Xor` is defined as addition, while `ternaryXor` uses a different truth table. But the VM's `TXor` opcode matches neither `ternaryXor` nor `Trit::xor()`.

**Impact:** Any program that uses `TXor` expecting the Kleene/Łukasiewicz min-gate (which is what `Trit::xor()` implements) will get GF(3) addition instead. Any code ported from libternary will get a third behavior.

### BUG-02: `TXor` Is Byte-for-Byte Identical to `TAdd`

Even setting aside the semantic question, lines 245–254 and 287–296 in `engine.rs` are the exact same code. One of these opcodes is a wasted slot.

### BUG-03: `TNeg` Has No Ternary Semantics

`engine.rs:265–270`:
```rust
Opcode::TNeg => {
    let a = self.get_register(inst.src1)?;
    let result = -a;  // ← This is binary i64 negation
```

Compare with `ternary.rs:82–84`:
```rust
pub fn not(&self) -> Self {
    Self { value: -self.value }  // ← Correct for single trit
```

For a single trit in {-1, 0, +1}, binary negation and trit negation happen to coincide. But the VM stores i64 values. If R0 = 42 (a multi-trit balanced ternary number), `TNeg` produces -42, but true ternary negation should flip each trit individually (every -1 ↔ +1, 0 stays). The kernel's `Tryte::not()` does this correctly (line 181–187), but the VM ignores the kernel types entirely.

### BUG-04: `TRot` Silently Discards Multi-Trit Values

`engine.rs:277–283`:
```rust
val = match val {
    -1 => 0, 0 => 1, 1 => -1,
    _ => val,  // ← Values like 42 pass through unchanged
};
```

No error, no warning, no per-trit rotation. The kernel has `Trit::rotate()` and `Trit::rotate_inverse()` that work correctly for single trits, but the VM doesn't decompose words into trits.

### BUG-05: All 6 Ternary Opcodes Operate on Single Trits Only

Every ternary opcode does `a.rem_euclid(3)` as its first step, discarding all but the lowest trit of the register value. The kernel defines `Tryte` (6-trit) and `TernaryWord` (27-trit = 3 trytes) types — none are used by the VM. This means:

- You cannot add two 6-trit trytes in the VM
- You cannot multiply two ternary polynomials using VM opcodes
- The 27-register file (3³) is symbolic — the registers store i64s, not TernaryWords

### BUG-06: `TernaryRegister.ternary_mode` Is Dead Code

`instruction.rs:22`: `pub ternary_mode: bool` — never set, never read by any opcode. The VM cannot distinguish whether a register holds a binary or ternary value.

### BUG-07: `TConvert` Does Offset Arithmetic, Not Representation Conversion

`engine.rs:297–315` — the conversion is `val ± {0,1,2}`, which is the correct transform for a *single trit* between Representations A/B/C. But for multi-trit values (which is what registers actually hold), you need per-trit conversion. The kernel's `convert_representation()` function (ternary.rs:216–230) has the same limitation — it only works for single i8 values.

## Part II: Architectural Gaps

### GAP-01: VM Is Disconnected from Kernel Type System

The kernel has a rich type hierarchy: `Trit` → `Tryte` (6 trits) → `TernaryWord` (27 trits). The `ternary-math` crate has `Gf3`, `BalancedTrit`, polynomial rings, Clifford algebras, torus geometry. **None of this is accessible from the VM.** The VM operates on raw i64 values with inline GF(3) arithmetic that doesn't even match the kernel's own implementations.

### GAP-02: No System Call / Interrupt / Trap Mechanism

The kernel has a full process subsystem (`process/scheduler.rs`, `process/ipc.rs`, `process/context.rs`), a security domain model (`security/domain.rs`, `security/capability.rs`), and memory management (`memory/allocator.rs`, `memory/page.rs`). **None of these are reachable from VM code.** There is no `Syscall` opcode, no interrupt vector table, no privilege level separation. The VM is a sealed calculator with no IO.

### GAP-03: No Heap Allocation Opcodes Despite GC Existing

`vm/gc.rs` implements a full mark-sweep garbage collector with generational support, object types (`Integer`, `TernaryValue`, `Array`, `String`, `Closure`), and the Tribonacci-derived threshold ratio (τ⁻² ≈ 0.2956). But there are no opcodes for `Alloc`, `Free`, `GcHint`, or `GcCollect`. The GC is inert.

### GAP-04: No Timing Opcode Despite Femtosecond Timing Being Core

`src/kernel/src/timing.rs` and `libternary/src/femtosecond-timing.ts` implement the HPTP (High-Precision Timing Protocol) with femtosecond resolution. Phase encryption (`phase.rs`) requires recombination within 50–500 femtosecond windows. There is no `ReadTime`, `TimerStart`, `TimerRead`, or `PhaseSplit` opcode.

### GAP-05: THDL IR Defines Operations the VM Cannot Execute

The THDL hardware description language (`src/thdl/src/ir.rs`) defines these operations as hardware primitives:

| THDL `UnaryOp` | VM Equivalent | Gap |
|----------------|---------------|-----|
| `Not` | `Not` (0x55) | ✓ Present |
| `TritNot` | `TNeg` (0x12) | ⚠️ TNeg is broken (see BUG-03) |
| `TritRotate` | `TRot` (0x13) | ⚠️ TRot is broken (see BUG-04) |
| `Reduce` | — | ✗ **Missing entirely** |

| THDL `BinaryOp` | VM Equivalent | Gap |
|-----------------|---------------|-----|
| `TritAdd` | `TAdd` (0x10) | ✓ Present |
| `TritMul` | `TMul` (0x11) | ✓ Present |
| `TritXor` | `TXor` (0x14) | ⚠️ Wrong semantics (see BUG-01) |
| `Eq`, `Ne`, `Lt`, `Gt` | — | ✗ **No ternary comparison opcodes** |

This means THDL-synthesized hardware and the VM cannot agree on the semantics of a ternary program. You cannot simulate THDL designs in the VM.

### GAP-06: O(n²) Crypto With No VM Acceleration Path

`ternary_lattice.rs:172–202` implements `ring_mul()` as schoolbook O(n²) convolution. The comment at line 28 explicitly acknowledges NTT is not available in GF(3). For n=256 (TL-KEM-512), that's 65,536 multiply-accumulates *per polynomial multiplication*, and each TL-KEM encapsulation requires many such multiplications across a module rank of 2–4.

The VM has no vectorized or polynomial-aware opcodes. Every coefficient operation would require separate `TAdd`/`TMul` instructions — and those only work on single trits, so each coefficient itself requires decomposition.

### GAP-07: No IO / Network Opcodes

PlenumNET is a network protocol. The VM has `Load`/`Store` for memory but no `In`/`Out`, `Send`/`Recv`, or port-mapped IO. There's no way for a VM program to interact with the network stack (`src/kernel/src/network/`), the filesystem (`src/kernel/src/fs/`), or device drivers (`src/kernel/src/drivers/`).

### GAP-08: Instruction Encoding Is Wasteful

Every instruction is 16 bytes: `[op:8bits][dst:8bits][src1:8bits][src2:8bits][imm:64bits][reserved:32bits]`.

- 35 opcodes need 6 bits, not 8. Wasting 2 bits per instruction.
- 27 registers need 5 bits, not 8. Wasting 3 bits × 3 fields = 9 bits.
- Reserved 4 bytes are always zero.
- A compact encoding could fit most instructions in 4 bytes (6 + 5 + 5 + 5 = 21 bits) with variable-length immediates. At 16 bytes per instruction, a 1000-instruction program is 16KB — at 4 bytes it would be 4KB. This matters for instruction cache (configured at 84 instructions = 1,344 bytes, already tight).

### GAP-09: No Assembler, No Compiler Target

Programs must be constructed by manually instantiating `Instruction::new(Opcode::..., dst, src1, src2, imm)` in Rust. There is no text-based assembly language, no macro assembler, and no compiler backend. This makes the VM unusable for anyone who isn't writing Rust test harnesses.

## Part VI: Quick Wins (Ship This Week)

These are small, high-impact fixes that require no architectural decisions:

1. **T-07: Wire `ternary_mode` flag** — 15 lines of code in `engine.rs`. Every `T*` opcode sets `self.registers.registers[inst.dst].ternary_mode = true`. Immediate type safety.

2. **T-02: Delete duplicate `TXor` code** — Even before deciding on XOR semantics, make `TXor` do *something different* from `TAdd`. Minimum viable: implement `min(a,b)` to match `Trit::xor()`.

3. **T-20: Add `TRotInv`** — Copy `TRot` logic, reverse the match arms. 10 lines.

4. **T-18: Add `TCmp`** — Copy `Cmp`, but set result register to {-1, 0, +1} directly instead of just flags. Enables three-way branching without flag inspection.

5. **T-12: Add `ReadTime`** — Stub it with a cycle counter for now. `dst = self.cycles`. Placeholder until HPTP integration.
