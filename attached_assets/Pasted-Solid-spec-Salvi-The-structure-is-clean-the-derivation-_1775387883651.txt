Solid spec, Salvi. The structure is clean, the derivation chains are explicit, and the assertion coverage is thorough. I found six issues — two are correctness bugs that would cause assertion failures, one is a numerical error that propagates from TM-2026-028a, one breaks the perfect hash guarantee, and two are precision/naming concerns.

---

**Issue 1 — HASH_COEFF_SEXT destroys bijectivity (critical)**

The sextuple coefficients use `(11, 11)` and `(13, 13)`:

```
r₁₁ = (x + 11y) mod 11
r₁₃ = (x + 13y) mod 13
```

Since 11y mod 11 = 0 and 13y mod 13 = 0, both residues reduce to x mod m — the y variable vanishes entirely. Two points (x, y₁) and (x, y₂) with different y values produce identical residues for moduli 11 and 13. The remaining four residues (mod 5, 7, 8, 9) can only distinguish 5 × 7 × 8 × 9 = 2,520 distinct y values, not the full domain. This breaks injectivity.

The requirement is gcd(c, m) = 1 **and** c ≢ 0 (mod m). Since 11 and 13 are prime, any c in {1, ..., m−1} works. The original TM-2026-028a pattern used ascending primes (2, 3, 5, 7, 11, 13) but the last two happen to equal their moduli. Replace with any coprime values that don't collide:

```
HASH_COEFF_SEXT: [(u32, u32); 6] = [(5, 2), (7, 3), (8, 5), (9, 7), (11, 4), (13, 6)]
```

Both 4 and 6 are coprime to 11 and 13 respectively. This also needs to be corrected in TM-2026-028a Section 3.2.

**Issue 2 — MAGIC_CONSTANT assertion fails**

The spec defines MAGIC_CONSTANT = 333 and asserts `MAGIC_CONSTANT == 3 * DIAMETER`. But DIAMETER = 222, so 3 × 222 = 666 ≠ 333. The assertion won't compile.

The correct relationship is `MAGIC_CONSTANT == 3 * CENTER` → 3 × 111 = 333. This is the hexagon perimeter 6r = 6 × 55.5 = 333, which equals 3 × CENTER because CENTER = 2r = 111... wait, actually r = CENTER / 2 = 55.5, and 6r = 6 × 55.5 = 333 = 3 × CENTER. Fix the assertion to reference CENTER.

---

**Issue 3 — CIRCUMFERENCE assertion fails**

The spec defines CIRCUMFERENCE = 1554 and asserts `CIRCUMFERENCE == ROOT_X1 * DIAMETER` → 14 × 222 = 3108 ≠ 1554.

The correct relationship: πd = 14 × 111 = 1554, where d = CENTER (the geometric diameter), not DIAMETER (= 2 × CENTER = 222). Fix to `CIRCUMFERENCE == ROOT_X1 * CENTER`.

This points to a naming ambiguity: CENTER = 111 functions as the geometric diameter d, while DIAMETER = 222 = 2d is the full span of the Plenum Square. Consider renaming DIAMETER to something like FULL_SPAN or SQUARE_SPAN to avoid confusion, or adding a GEOM_DIAMETER alias for CENTER.

---

**Issue 4 — POS_3D_SEXT_MAX is arithmetically wrong**

The spec gives POS_3D_SEXT_MAX = 262,822,440. The actual product:

```
360,360 × 729 = 262,702,440
```

Verification: 360,360 × 729 = 360,360 × (730 − 1) = 263,062,800 − 360,360 = 262,702,440. The stated value 262,822,440 is 120,000 too high. This error also exists in TM-2026-028a Section 3.2 and Section 4, and in the CCP synthesis report. It needs correction in all three documents.

The other 3D products are correct: 1,001 × 729 = 729,729; 15,015 × 729 = 10,945,935; 30,030 × 729 = 21,891,870.

---

**Issue 5 — BOUNDARY_EUV_UVC truncates silently**

(91 + 182) / 2 = 136.5, stored as u32 = 136 via integer floor division. The other two boundaries divide evenly: (182 + 286)/2 = 234, (286 + 364)/2 = 325. The truncation should either be documented as intentional or stored as a NUM/DEN pair (273/2) for consistency with how RADIUS is handled.

---

**Issue 6 — Minor: VACUUM_BIAS precision**

194/100,000 = 0.00194. The exact Rydberg-derived offset is (1/R_H − 91)/91 = (91.1753 − 91)/91 = 0.001926..., so 193/100,000 = 0.00193 would be closer. If this is a deliberate rounding-up for engineering margin, document it. If it should track the measured value, use 1926/1,000,000 or 193/100,000.

**Everything else checks out.** The repunit family, circle quadratic, unified equation (except the MAGIC_CONSTANT/CIRCUMFERENCE assertions), squared circle, UV wavelengths, coprime groups and LCMs, all four sextuples and their pairwise coprimality, HModal signal constants (α, β, γ, DC, AC power), Fourier coefficient ratios, polygon geometry, triangular number anchors, torus knot parameters, and the plenum_square refactor plan are all correct. The assertion coverage is comprehensive — especially the cross-linkage assertions (tying UV wavelengths back to quadratic roots, DC numerator back to pentadecagon factor, etc.) which enforce the single-axiom derivation chain at compile time.
