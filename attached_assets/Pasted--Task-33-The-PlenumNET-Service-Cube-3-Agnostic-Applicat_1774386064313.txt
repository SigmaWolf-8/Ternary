## 9. TDNS-L Classification → Slot Projection

### 9.1 The 27→3 Projection

27 TDNS-L dimensions partition into three groups of 9 (27 = 3² + 3² + 3²). Each group determines one port trit via `project_to_gf3(k, 9)` with polarity-adjusted dimensions.

For each port trit: take 9 dimensions, apply polarity (invert if −), count k = polarity-adjusted dimensions with value 3, apply `project_to_gf3(k, 9) = min(floor(k/3), 2) + 1`.

### 9.2 Groups and Polarities

The 27 dimensions partition into three groups of 9. Polarity assignments below use the **code-level semantics** from `derive.rs` (the TDNS v2.3.3 global schema). Where the LAN schema (TM-2026-019.2 §7) uses different dimension names for the same position — specifically D8 (global: Intelligence, LAN: Operational Domain), D19 (global: PolicyPresence, LAN: Mobility), and D20 (global: CostModel, LAN: Power Source) — the polarity is assigned to the global semantic. **Plane group (security domain):** D1, D2(−), D3, D9(−), D10, D17, D19, D25, D26

D19 (PolicyPresence: privacy/terms/GDPR depth) belongs in Plane because compliance posture is a security domain property. More policy presence → deeper trust → management plane (+).

**Role group (functional class):** D5, D6, D7, D8, D12, D18, D22(−), D23, D24(−)

D8 (Intelligence: ML/AI detection) fits Role — what kind of processing does this service perform? More intelligence → more complex role class (+). D18 (DataAppetite: data collection intensity) fits Role — heavier data interaction → secondary/tertiary role (+).

If two services have identical classifications, they receive identical slot assignments. The CRS handles collisions via CRD within the slot.

## 10. Self-Healing Integration

### 10.1 FTS Monitors Slots

The Fault Tolerance Service heartbeats to slots. Health state machine (Up → Suspect → Down → Recovering) operates on 3-trit addresses. The service inside is opaque.

Suspect: forensic capture begins, HD 1 neighbors (6 slots) notified, GLB routes around. Down: forensic committed to vault, Array3 promotes replica or single-node restarts, gateway updates routing.

**Forensic capture scope:** Because the slot is opaque, the cube captures only what it can see from outside the service: slot metadata (classification, registration time, key generation, birth epoch, freshness at failure), system telemetry (CPU, memory, network counters for the slot's port), the slot's Merkle audit trail (every request that passed through the shell), and any cube-mediated persistent state (data the service stored through the cube's storage capability). The service's internal memory is not accessible to the cube — if the service manages its own state outside the cube's storage, that state is lost on failure. This is a feature, not a limitation: the cube's forensic capture is complete for everything the cube provided, and the service is responsible for its own internals.

### 10.2 Quarantine Is Geometric

ZK proof failure or anomaly detection → slot address added to GLB dead set. Traffic rerouted by Hamming distance detour. Works identically for any service.

### 10.3 Heal-Without-Cascade

Isolate by address. Capture by slot state. Replace by re-registration at same classification. Heal by geometric reroute. No other service affected.

## 11. WAN Peer-to-Peer

### 11.1 Relay-Assisted Hole Punching

Both nodes maintain their relay WebSocket. When direct connection is needed:

1. Signal via relay (exchange public endpoints — the relay already knows each node's public IP:port from the WebSocket)
2. Simultaneous NAT traversal — both nodes send UDP packets to each other's public endpoint at the same moment. The relay includes an HPTP timestamp in the signaling message specifying when both sides should send, ensuring synchronization within the HPTP tolerance window. Most NATs (full-cone, restricted-cone, port-restricted-cone) open a pinhole on the first outbound packet
3. TL-DSA mutual auth on direct path (MITM impossible — attacker can't complete the challenge-response without private keys)
4. TLSponge-385 encryption (relay sees nothing after auth completes)
5. Fallback to relay if symmetric NAT on both sides (~10% of consumer NATs) — transparent to the application layer

No STUN (relay knows endpoints). No TURN (relay IS the fallback). Zero external dependencies.

### 11.2 Routing Preference

LAN peer (sub-ms) → WAN direct → Relay (always available). The cube routes to addresses. The transport picks the path. The service is oblivious.

### 11.3 Security

All paths: TL-DSA mutual auth, TLSponge-385, capability tokens, HPTP freshness, Merkle audit, 9-factor shell. WAN P2P is actually stronger — relay can't see the outer envelope.

## 13. TDNS-L → TDNS Promotion: Local to Global

### 13.1 The Two Scopes

TDNS operates at two scopes with the same 54-trit address format:

| Scope | TLD | First 27 trits | Second 27 trits | Example |
|---|---|---|---|---|
| Local (TDNS-L) | `.plm.local` | Ontological classification (27-question scan) | Ternary host identifier (encodes IPv4/IPv6) | `files.salvi-homes.plm.local` |
| Global (TDNS) | `.plm` | Ontological classification (27-question scan) | TL-Sponge-43 identity hash of canonical URL | `files.salvigroup.plm` |

The wire format is identical. The 54 trits are always two halves of 27. The interpretation of the second half depends on the TLD suffix — `.plm.local` means the second half is a ternary host ID (from which IP addresses are derived), `.plm` means the second half is a cryptographic identity anchor. No flag bit, no version field. The TLD IS the mode switch.

### 13.2 What's Preserved, What Changes

When a local service promotes to global:

**Preserved (unchanged):**
- The 27 classification trits (first half) — the service IS the same thing at both scopes
- The TDNS-L slot projection — `project_to_gf3` produces the same 3-trit port address from the same classification
- The 13 capabilities — the cube provides the same stack regardless of scope
- The 9-factor shell — Factor 9 (SignHere) applies identically at both scopes
- The service's TL-DSA identity keypair — same key, same proof of identity
- The CRS registration record — extended with a global address, not replaced

**Recomputed (second 27 trits only):**
- Local: ternary host ID → derived from IPv4/IPv6 via bidirectional bijection (TM-2026-019.2 §6)
- Global: TL-Sponge-43 hash → computed from the canonical global URL

The first half is classification. It doesn't change because the service doesn't change. The second half is binding — local binds to a network position (IP address), global binds to a namespace identity (URL hash). Same service, two bindings, two addresses.

### 13.3 The Promotion Workflow

```
1. Service is registered locally
   Address: [27 classification trits] · [27 ternary host ID trits]
   Resolves: files.salvi-homes.plm.local → 192.168.1.2

2. Operator initiates promotion
   The CRS computes the global second half:
   global_anchor = tl_sponge_43(canonical_url)
   Where canonical_url = "files.salvigroup.plm"

3. Dual registration
   The service now has TWO addresses:
   Local:  [27 classification] · [27 host ID]     → .plm.local (LAN routing)
   Global: [27 classification] · [27 identity hash] → .plm (fabric routing)

4. Both addresses remain live
   LAN clients resolve .plm.local → ternary host ID → IPv4/IPv6 (direct)
   Global clients resolve .plm → identity hash → Inter-Cube fabric routing
   The service processes both — it doesn't know which address the caller used
```

### 13.4 Resolver Behavior

The TDNS-L resolver on the local cube handles both scopes:

**Inbound `.plm.local` query:** Resolve from CRS. Return the ternary host ID, from which IPv4 (A record) and IPv6 (AAAA record) are derived. This is pure local resolution — the query never leaves the site.

**Inbound `.plm` query:** Two cases:
- If the target is a promoted local service: the CRS holds both addresses. Return the global identity hash for fabric routing, OR if the caller is on the same LAN, short-circuit to the local address (why route through the fabric when the service is on the same network?).
- If the target is a remote global service: forward the query to the Inter-Cube fabric via the gateway at (1,1,1). The CON overlay routes to the target site's cube. That site's CRS resolves the global address to a local slot.

**Outbound `.plm` resolution (this site's service accessed from another site):**
The remote site's resolver queries the fabric. The fabric routes to this site's gateway. The gateway routes to the local slot. The 9-factor shell applies at the gateway. The service doesn't know the caller is remote.

### 13.5 The Slot Projection Is Scale-Invariant

The `project_to_gf3` projection uses only the first 27 trits (classification). Since the classification is identical at both scopes, the slot assignment is identical. A file service classified the same way at `.plm.local` and `.plm` gets the same (plane, role, instance) address. Same port. Same position in the cube.

This means: the cube's internal architecture doesn't change when a service promotes. The service keeps its slot. Other services that call it by classification query get the same result. The only thing that changes is the external reachability — the service is now discoverable and routable through the global TDNS fabric, not just the local network.

### 13.6 Multi-Site Resolution Chain

When two sites are connected via Inter-Cube CON tunnels:

```
Site A client → queries "files.salvigroup.plm"
    │
    ▼
Site A TDNS-L resolver → not a local .plm.local → forward to fabric
    │
    ▼
Site A gateway (1,1,1) → routes through CON tunnel to Site B
    │
    ▼
Site B gateway (1,1,1) → 9-factor shell at THIS gateway
    │
    ▼
Site B CRS → resolves global address → routes to local slot
    │
    ▼
Site B file service slot → processes request
```

The 9-factor shell applies at the destination gateway, not the origin. The origin gateway multiplexes and routes. The destination gateway authenticates and authorizes. This prevents a compromised origin from bypassing the destination's security — each site's shell is sovereign.

### 13.7 Geometric Properties Across Scopes

| Property | Local (.plm.local) | Global (.plm) |
|---|---|---|
| Address format | 54 trits (27+27) | 54 trits (27+27) |
| First 27 trits | Classification (identical) | Classification (identical) |
| Second 27 trits | Ternary host ID | TL-Sponge-43 hash |
| Slot projection | project_to_gf3 on first 27 | project_to_gf3 on first 27 (same result) |
| Routing | Hamming distance on LAN cube | Hamming distance on fabric |
| Shell | 9-factor at local gateway | 9-factor at destination gateway |
| Sentinel check | Rep C zero-detection (constant time) | Rep C zero-detection (constant time) |
| Dual checksum | Plenum mod 333 + Repunit mod 364 | Plenum mod 333 + Repunit mod 364 |
| Key rotation arc | 182 (13 × π) | 182 (13 × π) — same epoch |

The mathematical invariants (TM-2026-008 Programs I–III) are preserved because both scopes use 27-trit halves and the same Rep C encoding. The isometry, branch number, and automorphism group are structural properties of the 27-dimensional state — they don't depend on whether the second half is a host ID or an identity hash.

### 13.8 Demotion

A promoted service can be demoted back to local-only by removing its global TDNS entry from the fabric. The local `.plm.local` address remains. The slot doesn't change. The capabilities don't change. The service doesn't know it was demoted. Demotion is a routing change at the fabric level, not an architectural change at the cube level.

### 13.9 Address Lifecycle: The Two Arcs Are the Two Halves

The arc equation (arc² − 832·arc + 118,300 = 0) governs not just key rotation but the lifecycle of the 54-trit address itself. The two halves of the address map to the two roots:

**Second 27 trits at local scope (ternary host ID) → cryptographic arc (182).** The local binding is operational. It rotates when a service heals to another node, when an IP changes, when a slot migrates in Array3. Old binding out, new binding in — symmetric, like the palindrome 20202₃. The CRS installs a redirect from the old local address to the new one. The redirect expires after one arc (182 time-units).

**Second 27 trits at global scope (identity hash) → evidentiary arc (650).** The global binding is persistent. It outlives local rotations. SignHere contracts reference the `.plm` address. Merkle audit entries reference it. Court subpoenas reference it. The global identity must remain resolvable for 650 time-units after last use — directional, like 220002₃.

Three parallel lifecycles, one equation:

```
          0        182        364         650        832
  LOCAL:  |---arc---|---arc---|---arc---|---arc---|
          bind 0    bind 1    bind 2    bind 3
  GLOBAL: |=============== identity ==================|
  KEY:    |---arc---|---arc---|---arc---|---arc---|
          key 0     key 1     key 2     key 3
```

Keys, local bindings, and redirect chains all cycle at 182. The global identity and evidence retention both span 650. Everything closes at 832.

**What falls out:**

**Redirect grace period = ARC_EPOCH (182).** When a local binding changes (service heals, node migrates), the CRS installs an old→new redirect. The redirect lives for exactly one arc. This replaces the configurable grace period in TDNS v2.3.3 §14.2 with a geometry-derived constant.

**Redirect chain depth = 4.** `ceil(650/182) = 4`. A service that heals 4 times accumulates 4 chained redirects. The 5th heal expires the oldest. Same number as the key archive, same derivation — both are ceil(EVIDENCE_ARC / ARC_EPOCH).

**Global identity retention = EVIDENCE_ARC (650).** A promoted `.plm` address stays resolvable for 650 time-units after last active use. Contracts signed against `files.salvigroup.plm` must resolve even if the service demoted and the local binding rotated multiple times. The evidence references the global identity, and the evidentiary arc governs how long that reference must work.

**Re-attestation trigger = 4 local rotations.** After a service's local binding has changed 4 times under one global identity, the global binding is re-attested: co-signed with the current TL-DSA key, re-anchored to the current Hedera HCS topic, 36 verification checkpoints run against the accumulated evidence chain. This keeps the global identity verifiably fresh without changing it.

**Complete address erasure = ADMIN_EPOCH (832).** All local redirects expired AND global identity retention complete AND all referencing contracts past the evidentiary arc. This is the earliest moment at which an address can be fully purged from the system — the same epoch that governs GDPR complete erasure (Section 3.7). The address lifecycle and the data lifecycle close together because they're governed by the same quadratic.
