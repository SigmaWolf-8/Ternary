## 1. Browser Engine Decision: Build from Scratch as Kernel Subsystem

### What We Evaluated

| Engine | Language | License | Status | Verdict |
|--------|----------|---------|--------|---------|
| Servo | Rust | MPL 2.0 | v0.0.5 | ~20+ crates, SpiderMonkey (C++), requires OpenGL/WebRender |
| Ladybird | C++ (adding Rust) | BSD 2-Clause | Pre-alpha | C++/Rust FFI defeats purpose of pure Rust stack |
| Blitz | Rust | Apache 2.0/MIT | Pre-alpha | Still pulls Stylo, Taffy, Parley, Vello, wgpu, winit |
| Ferrum | Rust + Boa | MIT | Pre-alpha | Closest philosophy but insufficient maturity |

### Final Decision: Kernel Subsystem

The browser engine is built as modules within `src/kernel/src/browser/`. Not a fork. Not userspace. The rendering, parsing, JS execution, and network pipelines are kernel subsystems with direct access to the GPU, the ternary cryptographic stack, and the z=0 distributor.

### Why Kernel Space

The anti-capture security model requires that cleartext pixel data never exists in any memory an attacker can reach. In kernel space with GPU rendering, cleartext pixels exist only in GPU VRAM behind an IOMMU — no CPU readback path, no bus-level DMA access. A userspace browser would hold cleartext RGBA in its own process memory, defeating the encryption entirely.

The TIS-27 keyboard encoding and the browser's DOM handler are in the same kernel address space. Encoded keycodes travel by direct function call — no IPC, no shared memory buffer, no boundary to intercept.

### Kernel-Space Stability

**JavaScript execution bounds:** Boa runs in a dedicated kernel task with cooperative termination. The kernel sets a `should_terminate` flag checked by Boa between bytecode instructions. When set, Boa throws a `Termination` exception caught by the tab wrapper. No interrupt-level panic — clean cooperative shutdown.

```rust
impl ScriptExecutor {
    fn execute(&mut self, script: &Source, budget_ms: u64) -> JsResult<JsValue> {
        self.context.set_timeout(budget_ms);  // Cooperative flag
        let result = self.context.eval(script);
        self.context.clear_timeout();
        result
    }
}
```

**Tab isolation:** Each tab runs as a separate kernel task (lightweight thread) with its own stack and heap region. If a task panics — including double panic or OOM — the kernel reclaims the task's resources and continues. Other tabs are unaffected. `catch_unwind` within the task handles recoverable panics; the task boundary handles everything else.

**Parser safety:** HTML and CSS parsers have explicit recursion depth limits. `taffy` uses iterative layout with an explicit work queue, not recursion. Stack overflow prevented by design.

**Font memory:** Fixed per-tab font cache with kernel-wide cap. Web font exceeding the pool falls back to system font. No unbounded allocation.

Seven crates for the CPU-side pipeline (parsing, layout, scripting). GPU rendering replaces `tiny-skia` for pixel output:

| `wgpu` | GPU compute + rendering (Vulkan/Metal/DX12) | MIT/Apache 2.0 |

### Why `wgpu` Replaces `tiny-skia`

`tiny-skia` is CPU-only (~124M pixels/sec at 1080p60). At 4K that quadruples and becomes marginal. `wgpu` is Rust-native, abstracts over Vulkan/Metal/DX12, and enables GPU compute shaders for mesh compositing, Bézier interpolation, and sponge encryption — all in parallel on hardware designed for this workload. The GPU also enables IOMMU-enforced anti-capture (see §7).

`tiny-skia` remains as a **fallback** for systems without GPU support (headless servers, embedded). The rendering pipeline abstracts over both backends.

### Kernel-Space Compatibility

The kernel provides allocator and threading primitives. Parsing/layout crates operate on in-memory data structures — no filesystem or OS APIs required. Font data (system UI, monospace, serif, sans-serif) embedded in the kernel binary. Web fonts fetched via z=0. `wgpu` talks to the GPU via the kernel's own driver — no userspace display server needed.

### Licensing

`html5ever` and `rust-cssparser` are MPL 2.0 (file-level copyleft). Linked without modification — compliance requires `LICENSES/` directory with MPL notices in distributed binaries. All other code is proprietary Capomastro Holdings. Same model Firefox uses. Contingency: `html5gum` (Apache 2.0/MIT) replaces `html5ever` if needed.

## 3. Z-Level Architecture

The z-axis is the dome geometry from TM-2026-017. Above ground (+z) is the upper dome — what the user sees, the presentation layer. Below ground (−z) is the lower dome — what processes, stores, and secures. z=0 is the equatorial plane where the 540 nodes live and the distributor runs.

Things above ground are **presented.** Things below ground are **processed.** Requests fall down. Results bubble up. This is geometry, not an access control policy.

| Z | Role | What Lives Here |
|---|------|-----------------|
| +n | Deep archive | Older snapshots. Z-trit encodes date. |
| +4 | Older snapshot | Incremental backup |
| +3 | Most recent snapshot | Latest monitoring state of all layers |
| +2 | File server | Static files, assets, media, web fonts, documents |
| +1 | UI | Browser, admin console, client pages. Present when needed, absent on headless. |
| **0** | **Distributor** | **Nothing permanent. (7, 11, 13) coprime walk. Routes, never blocks.** |
| −1 | API Gateway | Kong Konnect (33 services, 293 endpoints). Where external requests enter. |
| −2 | Application Services | 8 microservices: SFK, SignHere, payment, timing, tonal-field, blockchain, PQTI, inter-cube |
| −3 | Conventional Apps | Windows via Wine, Linux native, Mac via Darling. Sandboxed containers. |
| −4 | Ternary-native Apps | TernaryVm, Rep C native. Binary malware dies here. |
| −5 | Data Layer | PlenumDB, backend databases, blockchain ledger state, persistent storage |
| −6 | Infrastructure / Crypto | TLSponge-385, TL-DSA, TIS-27, TL-KEM, TDNS, key management. Only layer touching the raw network. |

### z=0 Turntable

z=0 is empty — free to rotate without disrupting any layer. The (7, 11, 13) coprime walk assigns every request to a position on the 540-node ring. Requests fall to the appropriate z-level; results bubble back up. z=0 never blocks.

### Routing is Geometric

The browser at +1 routes through z=0 because z=0 is below it — the ground floor between the presentation layer and everything the browser needs. Requests fall down through z=0 to reach services at −2 or data at −5. This is the architecture of the dome — above ground is what you see, below ground is what processes.

The z-stack routing overhead is negligible. Each hop is a direct function call in kernel space — nanoseconds. A page with 50 resources × 6 hops = 300 kernel function calls = microseconds total. The actual network fetch is milliseconds. The routing is a million times faster than the network round trip.

### z=0 Tilt Mechanism

The z=0 plane tilts, exposing different dome neighborhoods. Natural tilt step: π = 14° custom = 13.85° standard. Four positions:

| Tilt | Angle (std) | cos(α) | Cross-section area |
|------|-------------|--------|--------------------|
| 0 | 0.00° | 1.0000 | 100.0% of equator |
| 1 | 13.85° | 0.9709 | 97.1% |
| 2 | 27.69° | 0.8855 | 88.5% |
| 3 | 41.54° | 0.7485 | 74.9% |

### Request Flow

1. Browser at +1 sends request to z=0
2. Coprime walk assigns position on the 540-node ring
3. Request falls to the appropriate z-level
4. Lower levels call further down as needed (−2 service → −5 data → −6 crypto)
5. Results bubble back up through each layer to z=0
6. z=0 passes result up to +1
7. z=0 has already moved on — never blocks

## 5. GPU Rendering Pipeline

### Architecture

The CPU handles parsing, layout, scripting, and generating render commands. The GPU handles all pixel work: compositing, Bézier interpolation, mesh-to-sRGB conversion, and sponge encryption. This is the natural split — the CPU does the DOM tree, the GPU does the pixels.

```
CPU side:                              GPU side:
┌──────────────┐                      ┌──────────────────────┐
│ parse.rs     │                      │ mesh_composite.wgsl  │
│ layout.rs    │ ── render commands → │ mesh_to_srgb.wgsl    │
│ script.rs    │                      │ sponge_encrypt.wgsl  │
│ render.rs    │                      │ → VRAM (encrypted)   │
└──────────────┘                      └──────────────────────┘
                                              │
                                       scanout decrypt
                                              │
                                           display
```

### GPU Compute Shaders

**mesh_composite.wgsl:** Receives render commands (rectangles, text glyphs, gradients, images). Composites at mesh depth precision. All blending, gradient interpolation, and alpha mixing happens in mesh address space — not 8-bit RGB.

**mesh_to_srgb.wgsl:** Converts final mesh addresses to RGBA pixels for the display. Uses the precomputed LUT (uploaded to GPU at boot) plus Bézier arithmetic for sub-cell interpolation.

**sponge_encrypt.wgsl:** Final pass. XORs every pixel in the framebuffer with the per-frame TLSponge-385 keystream. One GPU instruction per pixel — essentially free when running in parallel across thousands of GPU cores.

### Sponge Handshake

Each frame:
1. Kernel advances the TLSponge-385 sponge state (CPU — fast, sequential)
2. Kernel uploads the per-frame keystream to GPU constant buffer
3. GPU executes: composite → convert → encrypt
4. Encrypted framebuffer sits in VRAM
5. Display controller decrypts per-scanline during output
6. Sponge state advances. Next frame, new key.

### Fallback Path

For headless servers or systems without GPU: `render_cpu.rs` uses `tiny-skia` for CPU rendering. Same pipeline, same mesh compositing, but software-rendered. The sponge encryption is CPU XOR. Performance is lower but functional.

## 6. How Color Works on Windows vs. PlenumOS

### The Windows Pipeline

The Desktop Window Manager (DWM) sits between every application and the display. For decades, the DWM restricted all windowed apps to 8 bits per channel, even on 10-bit panels. Windows 11 Auto Color Management (ACM) composites in FP16 when enabled — but requires specific GPU hardware, display support, and most apps still feed it 8-bit data.

Windows pipeline:
1. App renders → app surface (8-bit typically)
2. DWM composites all windows (FP16 if ACM, else 8-bit)
3. DWM applies ICC profile (trilinear interpolation)
4. Framebuffer → display controller → panel

### The PlenumOS Pipeline

No DWM. GPU renders directly from mesh space to encrypted VRAM.

1. CSS color → `srgb_to_mesh` → mesh address
2. GPU composites, blends, interpolates in mesh space
3. GPU `mesh_to_srgb` shader → `sponge_encrypt` shader → encrypted VRAM
4. Display controller decrypts during scanout → panel

One conversion. No bottleneck. Working precision set by mesh depth.

### Gradient Quality

Dark blue to light blue across 200 pixels:

**Windows 8-bit:** ~12 distinguishable blue levels in dark range. Visible banding.

**Windows ACM FP16:** Better, but interpolating from 8-bit source. Original quantization damage done.

**PlenumOS mesh depth 3:** 540 levels per channel equivalent in GPU working space. Bézier interpolation between mesh nodes. Quantization to display format once at final shader pass. Banding eliminated.

## 7. Anti-Capture Security

### GPU + IOMMU Model

Cleartext pixels exist only in GPU VRAM, behind an IOMMU that blocks all external access. This is a **stronger** guarantee than CPU-only rendering, where encrypted data sits in system RAM accessible to any DMA-capable bus device.

**IOMMU configuration at boot:**

```rust
fn setup_gpu_memory_protection(iommu: &mut Iommu, gpu_vram: PhysicalRange) {
    // CPU can send commands to GPU (write-only)
    iommu.allow(Bus::CPU, gpu_vram, Permission::WriteOnly);
    
    // GPU can access its own VRAM (read/write)
    iommu.allow(Bus::GPU, gpu_vram, Permission::ReadWrite);
    
    // Everything else: blocked
    iommu.deny_all_others(gpu_vram);
}
```

**The pixel lifecycle:**

1. CPU sends render commands to GPU (geometry, mesh addresses — not pixels)
2. GPU executes render shaders, producing cleartext pixels in VRAM
3. GPU sponge_encrypt shader XORs all pixels with per-frame keystream
4. Encrypted pixels sit in VRAM — no CPU readback, no bus DMA access
5. GPU display controller decrypts per-scanline during output to physical cable
6. Monitor shows correct image
7. Sponge state advances. Next frame, new key.

An attacker intercepting GPU commands (step 1) sees draw instructions, not a screenshot. An attacker reading VRAM (if they somehow bypass the IOMMU) sees encrypted data with a key that changes 60 times per second.

### Comparison: CPU-Only vs. GPU Rendering

| | CPU rendering | GPU rendering |
|---|---|---|
| Encrypted framebuffer | System RAM | GPU VRAM |
| DMA attack surface | Any bus device can attempt read | IOMMU blocks all non-GPU access |
| Encryption cost | CPU XOR per pixel (competes with rendering) | GPU shader pass (free — parallel) |
| Rendering performance | ~124M pixels/sec (1080p60 marginal) | Billions of pixels/sec |
| 4K @ 60fps | Infeasible | Trivial |
| Cleartext location | Never in RAM (XOR at write) | Only in VRAM (IOMMU-isolated) |
| Scanout decryption | CPU per-scanline (CPU load) | GPU display controller (dedicated hw) |

### Keyboard Capture Prevention

TIS-27 encoding in the kernel input handler, before any buffer:

```rust
fn handle_key_event(scancode: u8) {
    let encoded = tis27_encode(scancode, self.session_key);
    self.browser.dispatch_key(encoded);  // Direct kernel call
}
```

Decoded to Unicode inside Boa's DOM event handler at the last possible moment.

### Display Driver

The display driver is part of the kernel, under Capomastro's control. For Phase 1, prototyping uses `simplefb` (direct framebuffer control). Phase 2 adds GPU acceleration with the kernel-space Vulkan compute driver. The anti-capture guarantee requires that the kernel controls the entire display pipeline from render to panel — no third-party closed-source GPU drivers.

## 9. How Color Gets to the Screen

A camera sensor counts photons — three numbers per pixel. A designer picks a color — three numbers. CSS `red` = (255, 0, 0) by specification. Display manufacturers build panels to approximate sRGB. Nobody calibrates anything. It works.

PlenumColor changes the math between intent and bytes. The mesh is the **working color space** — high-precision coordinates for compositing, running on the GPU. RGB is the **output format.** All compositing at mesh precision. Quantization to display format once in the final shader pass.

For screen-to-print: both devices convert FROM the same mesh address using the same Bézier interpolation. They match because the math is the same.

## 12. Update Mechanism

Browser binary, default mesh mapping, and GPU shaders are part of the kernel image. Updates delivered as TL-DSA signed binary images via z=−6 infrastructure:

1. Kernel polls for updates via TDNS at configurable intervals
2. Update payload TL-DSA verified against Capomastro release key
3. Browser kernel tasks stopped, GPU pipeline flushed
4. New binary applied, browser tasks restarted, GPU shaders recompiled
5. Rollback: previous kernel image retained, automatic revert if new image fails health check within 30 seconds

Full kernel updates require reboot. Browser subsystem updates (parsing, layout, rendering, shaders) can be hot-swapped by restarting browser tasks while the kernel continues running.
