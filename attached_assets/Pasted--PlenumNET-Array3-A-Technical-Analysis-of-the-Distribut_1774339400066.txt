# PlenumNET Array3: A Technical Analysis of the Distributed Compute Stack

## Abstract

PlenumNET Array3 is a deployment tool that creates a local three‑node cluster of the PlenumNET distributed compute network. Each **PlenumNET node** (implemented by an Inter‑Cube daemon) features post‑quantum cryptography (TL‑KEM, TL‑Sponge‑385, PT26‑DSA), ternary addressing (13‑trit base‑3 addresses), and outbound WebSocket connections to a public relay for NAT traversal. This paper verifies the claims made about the system against its actual implementation, reveals that the codebase is significantly larger and more comprehensive than initially described (≈577 000 lines vs. 330 000), and analyzes the complexity of rebuilding such a stack from scratch. It also explores the security benefits and practical use cases of the firewall‑friendly, post‑quantum peer‑to‑peer architecture.

---

## 1. Introduction

The tool `Deploy PlenumNET Array3` (v0.4.0) automates the creation of a three‑node cluster on a local machine. Its description highlights several advanced features:

- Three **PlenumNET nodes** (each backed by an Inter‑Cube daemon), each with a PT26‑DSA identity and a 13‑trit ternary address.
- Post‑quantum encrypted relay tunnels (TL‑KEM + TL‑Sponge‑385).
- A coordinator (Node 1) that allocates addresses and registers workers (Nodes 2 and 3).
- Outbound WebSocket connections to `plenumnet.replit.app` for NAT traversal.
- **YODA** – an orchestration layer that routes queries (from end users, AI agents, or automated systems) to local compute engines.

This document provides a detailed technical review of these claims based on an examination of the actual source code, corrects earlier assumptions about the codebase size, and assesses the engineering effort required to rebuild the entire system from scratch.

**Section Summary:** The introduction describes the scope of PlenumNET Array3 and outlines the paper’s goals—to verify implementation, quantify codebase size, and analyze rebuild complexity.

## 2. Architecture and Implementation Verification

### 2.1 Post‑Quantum Cryptography

All claimed cryptographic components are present and fully implemented:

- **TL‑KEM** – Implemented in `ternary-math/src/tl_kem.rs` and `src/kernel/src/crypto/tl_kem.rs`. Three security tiers (512/768/1024) use Module‑LWE over a ternary ring with the Fujisaki‑Okamoto transform.
- **TL‑Sponge‑385** – Located in `src/kernel/src/crypto/sponge.rs` and `keyed_sponge.rs`. Features a 729‑trit state, 243‑trit rate, and a multi‑layer round function (Chi, Theta, Pi).
- **PT26‑DSA** – A 994‑line implementation in `ternary-math/src/pt26_dsa.rs` based on 13‑dimensional hypercube walks and GF(3) arithmetic.
- **TL‑DSA** – Fiat‑Shamir with aborts, three security tiers (`src/kernel/src/crypto/tl_dsa.rs`).

Additional cryptographic infrastructure includes wire‑level ECC (`wire_ecc.rs`), a lattice mixer (`lattice_mixer.rs`), and formal security proofs (e.g., `TL-KEM-IND-CCA2-proof.tex`).

**Section Summary:** All post‑quantum cryptographic components claimed are present, including TL‑KEM, TL‑Sponge‑385, PT26‑DSA, and TL‑DSA, along with supporting infrastructure and formal proofs.

---

### 2.2 Ternary Addressing

Ternary addressing is implemented as described:

- 13‑trit addresses in `services/inter-cube/src/cube_addr.rs` using Representation C.
- Three representation variants (A, B, C) are defined in `src/kernel/src/ternary.rs`.

**Section Summary:** Ternary addressing (13‑trit) with three representation variants is correctly implemented.

---

### 2.3 Node Implementation and Cluster Coordination

Each node is implemented by an Inter‑Cube daemon (`services/inter-cube/src/main.rs`), which supports both coordinator (CRS) and worker (Cube) modes. The registration protocol, CON overlay, FTS fault tolerance, and GLB geometric load balancer are all present.

**Section Summary:** The daemon supports both coordinator and worker roles; full cluster infrastructure (registration, overlay, fault tolerance, load balancing) is present.

---

### 2.4 WebSocket Relay and NAT Traversal

The relay logic resides in `services/inter-cube/src/ws_relay.rs` (314 lines). It uses `tokio-tungstenite`, a `RelayEnvelope` protocol, and TL‑DSA‑87 challenge‑response authentication. Nodes indeed connect outbound to `plenumnet.replit.app`.

**Section Summary:** WebSocket relay with authentication and NAT traversal is implemented as described.

---

### 2.5 YODA – Query Routing

In PlenumNET Array3, **YODA** is the orchestration layer responsible for routing queries to the appropriate compute engine. Queries are handled via `inference_request` and `inference_response` messages in `main.rs`. YODA forwards each query to a local LLM engine at `127.0.0.1:{LLM_PORT}` and returns the result through the encrypted relay tunnel.

A **query** in this context is any unit of work that requires computation by a model or algorithm. Queries can originate from multiple sources:

- **End‑user queries** – Direct inputs from a human interacting with a chat interface, API, or application. Examples: “Summarize this document,” “Generate an image,” or “Translate a sentence.”
- **AI agent queries** – Requests generated autonomously by another AI system, such as a reasoning agent, a multi‑agent orchestrator, or a higher‑level model that calls the inference engine as a subroutine.
- **Batch processing jobs** – Scheduled or triggered queries for bulk data processing, e.g., nightly inference on a dataset.
- **System health checks** – Internal queries used to verify model availability or performance.
- **Experimental workloads** – Queries generated by researchers for testing new models or load conditions.

Thus, YODA acts as a generic dispatcher: it accepts any query (user‑initiated, agent‑initiated, or automated) and routes it securely through the PlenumNET overlay to the worker node that runs the corresponding compute engine.

**Section Summary:** YODA routes queries—from end users, AI agents, batch jobs, or system tasks—to local compute engines via the encrypted relay.

## 3. Codebase Size and Scope

The original description estimated the codebase at ≈330 000 lines. A comprehensive count of the source tree (Rust, TypeScript, JavaScript, Verilog, Python, excluding `node_modules` and attached assets) yields **≈577 000 lines**. This discrepancy highlights that the system is not a modest research project but a production‑grade platform with extensive infrastructure.

**Section Summary:** The actual codebase is ≈577 000 lines—substantially larger than initially estimated—indicating a mature, production‑grade system.

## 4. Complexity of Rebuilding from Scratch

Rebuilding the entire PlenumNET stack would require expertise across multiple, highly specialized domains:

- **Cryptography** – Implementation of post‑quantum primitives, side‑channel resistance, formal verification, and hardware‑aware design.
- **Distributed systems** – Coordinator/worker protocols, CON overlay, FTS, GLB, and TDNS.
- **Networking** – WebSocket relay, NAT traversal, wire‑level ECC, lattice mixer.
- **Systems engineering** – Daemon development, performance optimization, hardware RTL (Verilog).
- **Application layer** – YODA orchestration, compute engine integration.
- **Blockchain engineering** – Integration with Hedera, Algorand, XRPL.
- **Frontend and DevOps** – React dashboard, Kong gateway, build automation, testing.

The codebase includes formal proofs and compliance artifacts, indicating that the system has been designed with rigorous security and certification in mind.

**Section Summary:** Rebuilding the stack requires deep expertise across cryptography, distributed systems, networking, hardware, blockchain, and DevOps.

## 5. Team and Timeline Estimates

Given the actual scope, rebuilding the stack from scratch would require a multi‑disciplinary team. A realistic composition includes:

- 2–3 senior cryptographers / security engineers  
- 2–3 senior distributed systems engineers  
- 2 senior networking engineers  
- 2 senior systems / embedded engineers (including hardware RTL)

Smaller teams would extend the timeline to 2–3 years and likely require simplification of some components (e.g., hardware RTL, formal proofs, blockchain witnessing).

**Section Summary:** A team of 14–18 senior specialists would likely need 12–18 months to rebuild the full stack; smaller teams would face longer timelines and would need to simplify certain components.

## 6. Use Cases and Security Benefits

The architecture (outbound‑only nodes, encrypted relay tunnels, post‑quantum cryptography) is well‑suited for:

- **Private AI inference / federated learning** – Run models on sensitive data without exposing internal networks.
- **Critical infrastructure & IoT** – Secure telemetry and command delivery without inbound ports.
- **Censorship‑resistant networks** – Nodes only need outbound connectivity, making them harder to block.
- **Multi‑cloud / hybrid cloud fabrics** – Lightweight overlay spanning diverse environments.
- **Research** – Testbed for novel consensus, post‑quantum protocols, and alternative addressing schemes.

### Security Highlights

- No inbound ports → reduced attack surface.
- Built‑in NAT traversal → nodes can run anywhere.
- End‑to‑end encryption → relay sees only ciphertext.
- Post‑quantum readiness → protects against future quantum decryption.
- Formal proofs and compliance targets (CNSA 2.0, FIPS 140‑3) indicate a high level of assurance.

### Trade‑offs

- Increased operational complexity (ternary addressing, TDNS, identity management).
- Potential latency and CPU overhead from relay routing and encryption.
- Relay dependency (redundancy required).
- Some features may rely on optional hardware acceleration (Verilog RTL).

**Section Summary:** The architecture enables secure, firewall‑friendly distributed computing across multiple domains, with strong cryptographic protections, but introduces operational complexity and relay dependencies.

---

## 7. Conclusion

Deploy PlenumNET Array3 accurately implements the features described in its documentation. However, the system is far more extensive than the original description suggests: it includes a full production‑grade stack with blockchain witnessing, ternary DNS, hardware RTL, formal proofs, and a comprehensive dashboard. The codebase totals ≈577 000 lines, reflecting a multi‑year engineering effort.

Rebuilding such a system from scratch would demand a large, highly specialized team (14–18 engineers) and a timeline of 12–18 months. While the Array3 deployment tool makes it easy to experiment locally, the underlying technology is a sophisticated, security‑focused platform intended for serious distributed computing applications.

**Section Summary:** The documented features are accurately implemented, but the actual system is far larger and more complex. Rebuilding it is a major undertaking, though the Array3 tool provides accessible local experimentation.
