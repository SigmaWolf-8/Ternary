#1 - Self-Hosted Model Install & PlenumNET Tunnel Button
What & Why
Add a single "Install & Connect" button to each Engine slot when self-hosted mode is active. Clicking downloads a platform-specific script that in one run:

Installs PlenumNET (via the existing install.sh from the Ternary repo — clones, builds inter-cube-daemon)
Starts inter-cube-daemon in cube mode → daemon calls out to YODA's CRS, tunnel is live immediately
Installs Ollama and pulls the selected model (slow step — happens while tunnel is already up)
Starts Ollama serving locally (localhost:11434, never exposed publicly)
YODA on Replit runs the CRS side (inter-cube-daemon in crs mode). The user's laptop initiates outbound — no port-forwarding needed. T-14 mutual auth handshake (TLSponge-385 HMAC / TL-KEM) happens automatically. Heartbeats every 30s keep the tunnel alive. YODA's GLB then routes inference requests to the laptop through the established tunnel.

Cloud providers (Anthropic, OpenAI, xAI, Google, DeepSeek API) never show the button — those need only an API key.

Architecture
User's server (fully private — zero ports opened)     YODA on Replit
──────────────────────────────────────────            ─────────────────────────────────
inter-cube-daemon (cube mode)
  ├─ initiates outbound connection ─────────────────► CRS accepts registration
  ├─ T-14 mutual auth handshake                        assigns 13D address
  └─ heartbeat every 30s (keeps tunnel alive) ───────► CRS keeps record live
         │
         │◄── inference request arrives via tunnel ◄── GLB forwards here
         │
         └─► localhost:11434  (Ollama, same machine, never exposed)
CUBE_ENDPOINT=<ip>:51820 = logical routing label for hypercube topology.
Port 51820 is NOT publicly exposed. No firewall rules. No port forwarding.
Done looks like
On YODA Replit: inter-cube-daemon starts in CRS mode alongside yoda-api on boot.
CRS listens on an internal port (via CUBE_API_PORT env var, default 8081 to avoid conflicts with yoda-api's 8080)
scripts/replit-run.sh starts both the API and the CRS daemon
An "Install & Connect" button appears below <ModelCard> only when mode === 'self_hosted' and the model name is in OLLAMA_TAG or MANUAL_INSTALL_URL
Clicking opens a modal with two OS tabs — macOS/Linux (bash) and Windows (PowerShell) — auto-selected via navigator.userAgent
Each tab shows the complete script in a monospace block:
macOS/Linux bash script:
Install PlenumNET first: curl -fsSL https://plenumnet.replit.app/install/install.sh | bash (clones Ternary repo, builds inter-cube-daemon)
Start tunnel immediately: CUBE_MODE=cube CUBE_CRS_URL=<YODA_DEPLOYED_URL> CUBE_ENDPOINT=$(hostname -I | awk '{print $1}'):51820 CUBE_ROLE=inference ~/PlenumNET/target/release/inter-cube-daemon & — daemon reaches out to YODA's CRS (outbound only), T-14 handshake, tunnel is live. Script must include a comment: "# No ports need to be opened — the daemon calls out to YODA, your router allows this naturally. Port 51820 is a logical routing label only."
Install Ollama if missing (curl -fsSL https://ollama.com/install.sh | sh)
ollama pull <tag> for the selected model (slow — may take minutes)
Ensure ollama serve is running in background
Echo: "Tunnel is live and model is ready. Return to YODA — your laptop is registered."
Windows PowerShell script: same 6 steps adapted for PowerShell (Invoke-WebRequest for Ollama, winget/scoop for Rust if missing, same inter-cube-daemon invocation)
The YODA_DEPLOYED_URL is embedded at script-generation time using window.location.origin (the real Replit .app domain)
"Copy" button: copies script to clipboard with brief "Copied!" confirm
"Download" button: saves as yoda-connect-<modelslug>.sh or .ps1
For GLM-5 and Kimi-K2.5 (not on Ollama): modal shows a notice explaining why and links directly to the provider's installation page instead of generating a script
Modal closes on Escape, backdrop click, or Close button
