## EXECUTIVE SUMMARY

We have completed our initial assessment of both the public repository (1,027 commits; TypeScript 49%, Rust 27%, Makefile 21%) and the live SaaS deployment. The engagement team consisted of counsel specializing in software licensing, SaaS agreements, and Canadian IP law, supported by a senior software engineer and IT systems architect who conducted the technical audit.

**The headline:** The legal document suite currently deployed is substantially more comprehensive than what we encounter at most early-stage technology companies. Fourteen legal instruments are committed to the repository root, a CI pipeline enforces copyright headers on pull requests, secret scanning is configured, CODEOWNERS is in place, and the proprietary license is well-drafted with Alberta-specific jurisdiction, ABCA entity description, and comprehensive IP reservation clauses. The prior work product is professional.

> **[3PR — CONTRAST]** The third-party Review characterizes the project as having a "catastrophic legal and compliance foundation" and as "actively on fire." As documented in Appendix A, this characterization is not supported by the evidence. The Review misidentifies three of its five "existential threats" — fabricating a nonexistent dependency (`xmss` crate 0.6.1), misreading timezone offsets as "future-dated commits," and claiming the absence of a NOTICE file that contains 23 third-party attributions. Our assessment is that the foundation is sound with targeted gaps requiring remediation, not reconstruction.

However, we have identified **17 discrete findings** across three severity tiers that require remediation. Six are critical — meaning they create actual legal exposure if left unaddressed. The rest are high-priority hardening items and housekeeping that, if left undone, weaken the enforceability of the documents already in place.

We have organized this memo as follows: (I) What's working, (II) Findings by severity, (III) Recommended remediation plan, and (IV) Strategic observations.

**FINDING C-1: Live SaaS Deployment Has No Enforceable Terms**

| | |
|---|---|
| **Location** | `client/src/pages/landing.tsx`, lines 1130–1131 |
| **Issue** | The footer of the live deployment at https://PlenumNET.replit.app contains "Privacy" and "Terms" links that both point to `href="#"` — dead anchors. | **Priority** | **P0 — Immediate** |

Our verification confirms these strings are present.
>
> **Our assessment:** The marketing language concern is **legitimate and should be incorporated into the C-1 remediation**. When the SaaS footer links are wired to actual legal pages, the marketing copy should be revised in the same deployment cycle. The words "compliant," "built in," and "regulatory certification" should be changed to "targeting," "designed for," or "architecture supports" — with a clear disclaimer that FINRA/MiFID compliance requires a complete operational framework beyond timing precision alone.

Fraudulent inducement requires (1) a false statement of material fact, (2) knowledge of falsity, (3) intent to induce reliance, and (4) actual reliance causing damages. A marketing page for a platform not yet in regulated production deployment, with no customers who have relied on the language, does not meet this threshold. The appropriate remediation is a content edit, not a crisis response. See Appendix A, Claim 1 for full analysis.

**FINDING C-2: 99 of 167 Source Files Lack Copyright Headers**

| | |
|---|---|
| **Location** | Across `src/kernel/`, `src/tsl/`, `src/thdl/`, `server/`, `client/src/`, `shared/` |
| **Issue** | The CI pipeline (`license-check.yml`) exists and checks for "Capomastro Holdings" in source files, but it has not been retroactively applied. 59% of source files (99 out of 167) have no copyright header. Missing files include critical cryptographic modules (`crypto/sponge.rs`, `crypto/hash.rs`, `crypto/hmac.rs`, `crypto/kdf.rs`), the entire TSL parser (`parser.rs`, `ast.rs`, `lexer.rs`), timing hardware (`thdl/timing.rs`), and every file in `server/` and `client/src/`. |

In Canada, the absence of marking doesn't eliminate rights but weakens practical enforcement posture. More critically, the 5 cryptographic source files without headers (`sponge.rs`, `hash.rs`, `hmac.rs`, `kdf.rs`) represent core Crown Jewel IP operating without any visible ownership assertion. |
| **Remediation** | Run a batch script applying the Rust/TypeScript/Python headers from `FILE-HEADER-TEMPLATE.md` to all 99 files. Then enable the CI pipeline to *block* merges (not just warn) on files without headers. |
| **Effort** | 2–3 hours (scripted application + manual review of edge cases) |

The README reports "484+ commits" and "Roadmap: 80/80 milestones complete." The actual commit count is 1,027. The `PLATFORM_GUIDE.md` in `ternary-math/` references "121 commits." Stale statistics in investor-facing documentation undermine credibility during due diligence. Update to reflect current state.

**FINDING H-2: Cargo.toml License String Inconsistency**

`ternary-math/Cargo.toml` uses `license = "Proprietary"` while `plenumnet-tsl` and `plenumnet-thdl` use `"LicenseRef-Proprietary"`. Neither is a valid SPDX identifier, but `LicenseRef-Proprietary` is the correct SPDX convention for non-standard licenses. All three should use `LicenseRef-Proprietary` for consistency. Additionally, `ternary-math/Cargo.toml` has no `repository` field — add `repository = "https://github.com/SigmaWolf-8/Ternary"`.

---

**FINDING H-3: libternary/LICENSE Entity Description**

The subsidiary license at `libternary/LICENSE` states "incorporated under the laws of Canada" without specifying Alberta. Same issue as NOTICE file. Align with the root LICENSE.

---

**FINDING H-4: No NOTICE-FILE.md for Structured Attribution**

The `NOTICE` file serves its purpose but is a flat text file. For FIPS/CMVP compliance submission and enterprise sales, a structured `NOTICE-FILE.md` cross-referencing each dependency with its license type, version, and SBOM classification would strengthen the compliance posture. This is a "nice to have" that becomes a "must have" during enterprise procurement.

> **[3PR — RELATED]** The Review's Phase I, Action 3 proposes "Generate THIRD-PARTY-NOTICES.md — Automated report, PR" to "Stop infringing copyrights." The recommendation to enhance attribution documentation is reasonable, but the framing ("stop infringing copyrights") is incorrect — the existing NOTICE file already satisfies MIT and Apache-2.0 attribution requirements. An enhanced, structured version is a best-practice improvement, not a compliance gap closure.

---

**FINDING H-5: attached_assets/ Empty Directory Committed**

An empty `attached_assets/` directory remains in the repository root. While not a legal risk, it creates clutter and questions during due diligence ("what was attached here?"). Remove it.

---

**FINDING H-6: No `.env.example` or Environment Variable Documentation**

The live deployment requires environment variables (database credentials, API keys, blockchain endpoints) that are not documented anywhere in the repository. While the `.gitleaks.toml` scanning is properly configured, the absence of a `.env.example` means that anyone cloning the repository cannot understand what configuration is needed. For a proprietary project this is less critical than for open source, but it matters for onboarding enterprise evaluators and for demonstrating operational maturity during due diligence.

### TIER 3 — MEDIUM (Best Practice)

---

**FINDING M-1: SECURITY.md Lacks PGP Key**

The security policy states "PGP key: [to be published]." Security researchers expect an encryption option for vulnerability reports. Publish a PGP public key or set up a security reporting platform (e.g., GitHub Security Advisories, which is already available on the repository).

---

**FINDING M-2: No SBOM (Software Bill of Materials)**

Enterprise and government procurement increasingly require SBOM in CycloneDX or SPDX format. The NOTICE file provides manual attribution, but an automated SBOM generation step in CI would future-proof the compliance posture, particularly for the FIPS validation path.

---

**FINDING M-3: CLA Execution Mechanism Missing**

The CLA document exists and CONTRIBUTING.md references it, but there is no actual execution mechanism. Options include CLA Assistant (GitHub App), a DocuSign flow, or a simple "sign and email" process. Without a mechanism, the CLA is aspirational rather than operational.

---

**FINDING M-4: GitHub Repository Description**

The repository "About" description reads "Salvi Framework - Bijective Ternary Logic Library" — this undersells the project. Recommend updating to include "Post-Quantum • Ternary Computing • Precision Timing • CNSA 2.0" for better discoverability and positioning.

---

**FINDING M-5: No GitHub Release Tags**

Zero releases are published. For patent priority dates and version-specific licensing, tagged releases with changelogs provide an unambiguous public record of what was available when. Consider creating v1.0.0 corresponding to the current state.

## IV. STRATEGIC OBSERVATIONS

**4.1 — The document suite is unusually comprehensive for this stage.**

Most pre-revenue technology companies have a LICENSE file and nothing else. This repository has 14 coordinated legal instruments, Alberta-specific jurisdiction, ABCA entity identification, EIPA export classification, PIPEDA/PIPA dual privacy compliance, and a CI pipeline that checks copyright headers. The foundation is solid. The findings above are refinements, not reconstructions.

> **[3PR — CONTRAST]** The Review states: "bolted-on compliance after the fact... worse than none — it creates the appearance of diligence while concealing fundamental breaks." We disagree with this characterization. The legal documents are internally consistent, reference correct statutory authorities, and align with the repository structure. The fact that they were committed recently does not make them "bolted on" — it makes them new. The architecture of the legal suite (proprietary root license, separate NOTICE for third-party attributions, CLA for contributions, export control classification, IP notice with patent marking) follows the same structural pattern used by MongoDB, Redis Labs, Elastic, and other dual-license/proprietary projects. The execution needs refinement (as itemized in our findings); the architecture does not need "rebuilding."

**4.2 — The mathematical innovations require urgent patent triage.**

The Ternary Circle axiom system, the Tribonacci Golden Angle, and the Z₂₈ walk engine producing quasicrystalline point sets are, in our assessment, genuinely novel. We found no prior art for a complete angular geometry derived from base-3 repunits, nor for the application of the Tribonacci constant to aperiodic packing in a non-standard angular system. The Cl(3,0) Clifford algebra over GF(3) for classical gate composition also appears to be a first.

However, these innovations are sitting in a public repository. The Canadian one-year grace period (Patent Act, s. 28.2(1)(a)) and the U.S. one-year grace period (35 U.S.C. §102(b)(1)(A)) are running. If any of these were committed more than 6 months ago, the filing window is half-closed. We strongly recommend that IP counsel receive the patent claims list within 30 days for priority assessment.

> **[3PR — OMISSION]** The third-party Review does not mention patent grace periods, does not identify any of the seven novel mathematical innovations, and does not address the time-sensitivity of patent filing. This is the most consequential strategic gap in the Review.

**4.3 — The SaaS legal gap is the single highest-risk item.**

A live, publicly accessible web application with authentication flows, API endpoints, and data collection — operating without any accessible Terms of Service or Privacy Policy — is the definition of unforced legal exposure. This is a P0 because it is the only finding that could result in regulatory action (PIPEDA compliance) independent of any adversarial party. Fix this first.

**4.4 — The proprietary license is well-constructed but consider a dual-license strategy.**

The current all-rights-reserved license is appropriate for the current stage. However, as the project moves toward enterprise partnerships and community adoption, a dual-licensing model (proprietary + commercial open-source for selected non-Crown-Jewel components) may accelerate adoption without compromising the core IP. The `TRADEMARK-NOTICE.md` already contemplates this in its Open Source section. We can develop a tiered licensing strategy when the time comes — the internal Component Licensing Matrix (which we understand has been removed from the public repository) would inform that work.

> **[3PR — PARTIAL AGREEMENT]** The Review's Phase II, Action 4 proposes: "Adopt dual-distribution model: Core: Proprietary, binary / Client libs: MIT/Apache 2." We agree this is a sound long-term strategic direction. However, it requires careful tiering of which components are open-sourced — exactly the analysis that the (now-removed) internal Component Licensing Matrix was designed to support. This is a 6-month roadmap item, not a 30-day emergency.

**4.5 — The contact placeholder issue is more serious than it appears.**

Seventeen placeholder fields across ten documents is not just an inconvenience — it renders several legal instruments partially inoperative. A CLA that cannot be returned to anyone cannot be executed. A Privacy Policy that identifies a Privacy Officer who cannot be reached does not satisfy PIPEDA Principle 1. A Security Policy that directs vulnerability reports to nowhere invites public disclosure instead. One email alias setup resolves all seventeen instances.

## PURPOSE

The client has provided a third-party legal assessment ("the Review") for our evaluation. The Review identifies what it characterizes as three "existential threats" and proposes a two-phase remediation plan. We have verified every factual claim in the Review against the actual repository state. Our findings are below.

**Summary:** The Review contains **one legitimate finding** that warrants immediate attention (FINRA/MiFID marketing language), **one partially valid architectural observation** (WASM crypto consolidation for FIPS boundary), and **three claims that are factually incorrect or significantly overstated** (copyright infringement, timestamp fraud, XMSS crate vulnerability). ### CLAIM 1: "Fraudulent Inducement Exposure"

**The Review states:** *Website says "FINRA 613 & MiFID II compliant built in." Repository has "No audit trails, no NIST sync, no compliance endpoints." First regulated customer will "sue you for fraud — not breach, fraud. Personal liability for officers."*

**Our verification:**

The landing page (`client/src/pages/landing.tsx`) does contain the following language:

- Line 225: *"High-Precision Timing Protocol with optical clock sync and regulatory certification for FINRA 613 & MiFID II."*
- Line 408: *"FINRA 613 & MiFID II regulatory compliance built in"*
- Line 670: *"FINRA 613 & MiFID II built-in"*
- Line 896: *"FINRA 613 & MiFID II compliant timing"*

However, the Review's factual predicate is partially incorrect. The claim that the repository has "no audit trails, no NIST sync, no compliance endpoints" does not fully hold:

- **NIST references** appear in **30+ files** across `src/kernel/src/crypto/` (ACVTS, CAVP, KAT vectors, DRBG, FIPS module state) and in timing services.
- **Audit trail** references exist in `src/timing-api/unified-metadata-schema.ts` and `server/salvi-core/unified-metadata-schema.ts` (line 93: "Populated post-execution for audit trail").
- **Compliance endpoints** exist: `server/routes.ts` line 2538 references `["plenumnet", "certification", "audit", "finra-cat", "mifid-ii", "compliance"]` tags.

The system has audit and compliance infrastructure in development. It is not a void. That said, the marketing language overstates the current state of that infrastructure.

**Our assessment: The language concern is LEGITIMATE. The legal characterization is OVERSTATED.**

The words "regulatory certification," "compliant," and "built in" on the live SaaS landing page do create a risk of misrepresentation if a prospective customer relies on them. This is a real issue that should be addressed.

However, calling this "fraudulent inducement" with "personal liability for officers" is a significant overstatement. Fraudulent inducement requires (1) a false statement of material fact, (2) knowledge of its falsity (scienter), (3) intent to induce reliance, and (4) actual reliance causing damages. A marketing page for a platform that is not yet in regulated production deployment — with no customers who have actually relied on the language to make purchasing decisions — does not meet this threshold. The appropriate characterization is **marketing language that should be revised to accurately reflect the platform's current state**, not a fraud crisis.

We note that the README.md is more careful. It includes a section titled **"Applied Physics vs. Theoretical Validation"** that explicitly distinguishes between verified implementation claims and theoretical claims. This suggests the client already understands the distinction and has been precise in some contexts while less precise in marketing copy.

**Recommended action:** Revise the landing page language. Change "compliant" and "built in" to "targeting" or "designed for." Change "regulatory certification" to "regulatory-grade precision." This is a content edit, not a legal crisis. We have incorporated this into Finding C-1's remediation scope.

| Verdict | **Legitimate concern — OVERSTATED characterization** |
|---------|------|
| Action | Revise marketing language (folded into P0 remediation) |

### CLAIM 3: "Timestamp Integrity = Legal Fiction"

**The Review states:** *Commit history shows "future-dated commits (Feb 12, 2026)." Today is Feb 11. Your HPTP femtosecond timing service is built by machines that cannot keep correct time. "No FINRA examiner, no FIPS auditor, no court will ever trust your audit logs."*

**Our verification:**

The most recent commits show timestamps of `2026-02-11 22:20:20 -0700`. The `-0700` offset is **Mountain Standard Time (MST)**, which is the timezone for **Alberta, Canada** — the Company's jurisdiction. February 11 at 22:20 MST is February 12 at 05:20 UTC.

The reviewer appears to have observed UTC-rendered timestamps (which would display as February 12) and concluded the commits were "future-dated" relative to their own local time. This is a timezone normalization artifact, not a clock integrity issue.

**Our assessment: This claim is FACTUALLY INCORRECT and demonstrates a fundamental misunderstanding.**

Git commits carry timezone-aware timestamps. The `git log` output confirms the commits were made at valid local times in the MST timezone. There is no anomaly.

We note, for completeness, that Git commit timestamps are trivially forgeable and would never be relied upon as evidence of timing integrity in a FINRA or FIPS context. The HPTP timing protocol is a server-side cryptographic timestamping system — its integrity is entirely independent of the local clock on the developer's workstation. Any auditor who confused Git commit timestamps with a production timing protocol would be disqualified from the engagement.

We recommend **against** implementing the Review's proposed "TIMESTAMP-ANOMALY.md" document. Publishing a mea culpa for a timezone rendering artifact would create the appearance of a problem where none exists.

| Verdict | **FACTUALLY INCORRECT** (timezone artifact) |
|---------|------|
| Action | None — do NOT publish TIMESTAMP-ANOMALY.md |

### CLAIM 4: "XMSS Crate 0.6.1 → Known Side-Channel Vulnerability"

**The Review states:** *Update `xmss` crate from 0.6.1 → 0.8.2. Current version has "known side-channel vulnerability." CNSA 2.0 claim is "false" until fixed.*

**Our verification:**

We searched every `Cargo.toml` and `Cargo.lock` file in the repository. **There is no external `xmss` crate dependency.** The XMSS implementation is **entirely custom Rust code** written in `src/kernel/src/crypto/signature.rs`. The functions `xmss_keygen()`, `xmss_sign()`, `xmss_verify()`, `xmss_build_tree()`, and `xmss_auth_path()` are all implemented from first principles within the kernel module. The only external crate dependencies in the entire project are internal path references (`plenumnet-kernel = { path = "../kernel" }`).

Additionally, the Review states its architect can "Review Cargo.toml together and spot xmss 0.6.1 as a legal vulnerability." We reviewed all three Cargo.toml files. None contain an xmss dependency. The `[dependencies]` section of `ternary-math/Cargo.toml` is empty. The TSL and THDL crates depend only on `plenumnet-kernel` via local path.

**Our assessment: This claim appears to be FABRICATED.**

The specific version number "0.6.1," the upgrade path "→ 0.8.2," and the assertion of a "known side-channel vulnerability" do not correspond to any dependency in this repository. We cannot determine whether the reviewer hallucinated this dependency, confused it with another project, or fabricated it to justify the engagement urgency.

The Review also references `libternary/crypto.ts` — a file that does not exist. The actual file is `libternary/src/phase-encryption.ts`. Similarly, the Review references `src/kernel/src/time.rs` — also nonexistent. These reference errors further suggest the Review was not conducted against the actual repository.

| Verdict | **FABRICATED** — no such dependency exists |
|---------|------|
| Action | None |

### CLAIM 6: Phase II Architectural Recommendations

**WASM Crypto Consolidation (Phase II, Action 1):**

The Review recommends deprecating all crypto in `libternary/` and consolidating to a WASM-compiled Rust core for FIPS 140-3 validation. This is a reasonable long-term architectural observation. The current dual-language crypto (Rust kernel + TypeScript `libternary/src/phase-encryption.ts`) does complicate the FIPS cryptographic boundary definition. However, the FIPS boundary can be drawn to exclude the TypeScript layer if needed. This is a 6-month roadmap item, not a 30-day emergency.

**Compliance Gateway Service (Phase II, Action 2):**

Valid recommendation. FINRA 613 requires NIST-traceable timestamps and audit trails. The current HPTP provides precision timing but the audit infrastructure around it is in early development. We concur this should be on the product roadmap.

**XMSS Crate Update (Phase II, Action 3):**

Fabricated. See Claim 4 above. There is no external XMSS crate.

**Dual-Distribution Model (Phase II, Action 4):**

Reasonable strategic direction that aligns with our own observation (Section IV.4 of the main memo). Requires careful component tiering.

**CCATS Filing with BIS (Phase II, Action 5):**

This recommendation confuses Canadian and U.S. regulatory frameworks. Capomastro Holdings Ltd. is a Canadian corporation. The primary export control regime is Canada's EIPA/ECL, not the U.S. EAR. A CCATS (Commodity Classification Automated Tracking System) filing is a U.S.-specific procedure. The Export Control Notice already correctly classifies the software under both Canadian ECL Group 5 Category 2 and U.S. ECCN 5D002. The immediate priority is a Canadian export permit analysis under EIPA, not a U.S. CCATS filing.
