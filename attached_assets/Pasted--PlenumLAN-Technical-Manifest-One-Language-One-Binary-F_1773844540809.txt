That experience is the same whether the server is running on Replit, on a laptop, on a dedicated office machine, or on a USB-bootable appliance. The web console is the permanent interface. The server underneath it is what moves.

**PlenumLAN is written entirely in Rust.** One language. One compiled program. No bridges between languages. No code written twice. No migration from one technology to another. The same program that runs on Replit is the same program that runs on a customer's office machine. Nothing changes but the address in the browser.

On Replit, the server is in a data center — it cannot see your office printer. On your laptop or office server, it can. The code is identical. The server just needs to be in the same room as the things it manages.

## 5. The 54-Trit Dual-Interpretation Address

### 5.1 Format

Every TDNS address — global or local — is a 54-trit Rep C structure. Rep C encodes each trit as {1, 2, 3}. Zero is structurally impossible. A zero in any position is mathematical proof of forgery, detectable in constant time with no branching on secrets.

The 54 trits are always two halves of 27:

| Half | Position | Global (.plm) | Local (.plm.local) |
|---|---|---|---|
| First 27 trits | Classification | Ontological scan: 27 questions answered from live HTTP fetch | Ontological scan: 27 questions answered from entity registration profile |
| Second 27 trits | Binding | TL-Sponge-43 identity hash of canonical URL (collision resistance for internet namespace) | Ternary host identifier (native network address; IPv4/IPv6 derived deterministically) |

The wire format is identical at both tiers. The interpretation of the second half is determined by scope: the resolver knows whether it is handling a `.plm` or `.plm.local` query, and applies the corresponding interpretation. No flag bit, no version field, no mode switch. The TLD suffix IS the mode switch.

**Reference implementation** — one function handles both local and global modes, with constant-time zero-sentinel forgery detection:

```rust
// plenumlan/src/address/rep_c.rs
pub fn parse_54_trit(address: &[u8; 54]) -> Result<(Classification, Binding), ForgeryError> {
    if address.iter().any(|&t| t == 0) {
        return Err(ForgeryError::ZeroSentinel); // constant-time, no secret branches
    }
    let class = Classification::from_trits(&address[0..27]);
    let binding = if is_local_scope() {
        Binding::HostId(TernaryHostId::from_trits(&address[27..54])) // derives IPv4/IPv6
    } else {
        Binding::Identity(TlSponge43::hash_url(&address[27..54])) // global identity
    };
    Ok((class, binding))
}
```

The dual-interpretation design preserves every proven result that depends on the 54-trit structure:

### 5.3 Why Not Encode IP Addresses Directly?

The second 27 trits are NOT an encoded IPv4 or IPv6 address. They are the ternary-native host identifier — the real address — from which legacy IP addresses are derived as protocol translations. This distinction matters:

- **Protocol independence.** If the second half were an encoded IPv4 address, it would be useless on an IPv6-only network. If it were an encoded IPv6 address, it would waste trit space on binary structure. The ternary host identifier is native to the cube and derives both protocols simultaneously.
- **Address space.** 3²⁷ = 7,625,597,484,987 unique host identifiers per site cube. That's ~7.6 trillion addresses from the ternary space, vastly exceeding any LAN requirement.
- **Sentinel preservation.** An encoded IPv4 address would contain zeros (e.g. 192.168.0.1 → the .0. octet). In Rep C, zero is forgery. The ternary host identifier is computed in Rep C from the start — zeros are never introduced.

## 6. Bidirectional Address Binding: IP ↔ Ternary Host Identifier

The second 27 trits of a TDNS-L address are the ternary host identifier. The mapping between this identifier and standard IPv4/IPv6 addresses is **bijective** — it works in both directions. This is critical because PlenumLAN must handle two completely different situations:

**Situation 1 — Existing network (day one).** The office already has devices with IP addresses. The printer is already at 192.168.1.50. John's laptop is already at 192.168.1.101. PlenumLAN does not reassign IP addresses to a running network. Instead, it scans each device's existing IP and **computes the ternary host identifier FROM the IP**. The device keeps its address. The 54-trit ternary address wraps around the existing IP, not the other way around.

**Situation 2 — New device (PlenumLAN is primary).** A new device joins the network after PlenumLAN is the infrastructure authority. PlenumLAN assigns a ternary host identifier from the cube vertex space and **derives the IP FROM the host identifier**. The device gets both a ternary address and an IP in one registration.

**Situation 3 — Legacy device (doesn't speak PlenumLAN).** A printer or VoIP phone sends a raw DHCP DISCOVER. The legacy DHCP responder assigns an IP from the available pool. The CRS then **computes the matching ternary host identifier FROM the assigned IP**, completing the registration. From the device's perspective, it got a normal DHCP lease. From the cube's perspective, a vertex was occupied.

All three situations use the same bijective conversion functions. The direction depends on which value is known first.

### 6.1 The Bijective Conversion

Every conversion passes through a single intermediate value: the **host integer**. This is a plain integer in the range [0, 3²⁷ – 1] = [0, 7,625,597,484,986].

```
  27-trit Rep C host identifier
           ↕  (positional base-3 with Rep C offset)
       host integer (u64)
           ↕  (modular arithmetic for IPv4, direct embed for IPv6)
    IPv4 address + IPv6 address
```

**Both directions are pure functions. No lookup table. No state. No database query.**

**Direction A: Ternary → Integer → IP** (new device registration)

```
host_int = Σ(i=0..26) (trit[i] – 1) × 3ⁱ
```

Since each trit is {1, 2, 3}, the subtraction `trit[i] – 1` maps to {0, 1, 2} for the positional calculation.

**Direction B: IP → Integer → Ternary** (existing device scan / DHCP import)

```
host_int = ipv4_host - range_start    (IPv4 path — approximate; see collision note)
host_int = interface_id & 0x7FF_FFFF_FFFF   (IPv6 path — exact, no loss)

trit[i] = ((host_int / 3ⁱ) mod 3) + 1   (for i = 0..26)
```

The IPv6 path is **lossless** — the 43-bit host integer is embedded directly in the interface ID, so extraction is exact. The IPv4 path loses information during modular reduction (254 possible values mapped from 7.6 trillion), so the CRS records the full host integer at registration time to ensure the round-trip is exact.

### 6.2 Site Network Configuration

Each site stores a single network configuration record in the Local CRS:

| Field | Example | Purpose |
|---|---|---|
| site_ipv4_prefix | 192.168.1.0/24 | IPv4 subnet for this site |
| site_ipv4_host_range | 1–254 | Usable host range (excludes network + broadcast) |
| site_ipv6_prefix | fd00:abcd:1234::/48 | ULA prefix for this site |
| site_ipv6_subnet_bits | 16 | Bits available for subnet segmentation |
| shell_to_vlan | {Inner: VLAN 10, Void: VLAN 20, Outer: VLAN 30} | Maps cube shell security domains to VLANs |

This configuration is set once at site initialization (the First-Run Wizard auto-detects it from the local network). It never changes during normal operation.

### 6.3 Direction A: Ternary Host ID → IP Address (New Device Registration)

When PlenumLAN assigns a ternary host identifier to a new device, it derives both IPv4 and IPv6:

**IPv4:**

```
ipv4_host = (host_int mod host_range_size) + range_start
ipv4_addr = site_prefix | ipv4_host
```

Example for a /24 subnet (254 usable hosts):

```
host_int  = 4,831,207,913,542  (from 27-trit conversion)
ipv4_host = 4,831,207,913,542 mod 254 + 1 = 159
ipv4_addr = 192.168.1.159
```

**IPv6:**

```
interface_id (64 bits):
  Bits 63–43:  21-bit structural prefix = 0x15A (Rep C sentinel pattern)
  Bits 42–0:   43-bit host_int direct embed

ipv6_addr = fd00:abcd:1234:[subnet]:[interface_id]
```

Key properties:

- **No IPv6 collision.** 3²⁷ ≈ 2⁴³ fits entirely within the 64-bit interface identifier with 21 bits to spare. Every 27-trit host ID maps to a unique IPv6 interface ID.
- **Sentinel prefix.** The 21 high bits carry a fixed Rep C sentinel pattern (0x15A). Any IPv6 address without this prefix was not issued by TDNS-L — detectable as unauthorized at the network layer.
- **Subnet segmentation.** The site's /48 ULA prefix provides 16 bits for subnet IDs (65,536 subnets). Shell security domains (Inner/Void/Outer on axis 12) map to subnet IDs, providing geometric VLAN segmentation.
- **Reversible.** Given any PlenumLAN-issued IPv6 address, the ternary host identifier can be extracted by stripping the sentinel prefix and converting the 43-bit integer back to 27 Rep C trits. No lookup required.

**Reference implementation** — Direction A (ternary → IP):

```rust
// plenumlan/src/address/derivation.rs
pub fn ternary_to_ip(host_id: &TernaryHostId, cfg: &SiteConfig) -> (Ipv4Addr, Ipv6Addr) {
    let host_int = host_id.to_u64(); // 27-trit → integer

    // IPv4 (modular reduction — may collide, CRS override table handles it)
    let ipv4_host = ((host_int % cfg.ipv4_range_size) as u32) + cfg.range_start;
    let ipv4 = cfg.ipv4_prefix | Ipv4Addr::from(ipv4_host);

    // IPv6 (collision-free: sentinel prefix + 43-bit host_int)
    let interface_id = (0x15A_u64 << 43) | (host_int & 0x7FF_FFFF_FFFF);
    let ipv6 = Ipv6Addr::from_parts(cfg.ipv6_prefix, cfg.subnet, 0, interface_id);

    (ipv4, ipv6)
}
```

### 6.4 Direction B: IP Address → Ternary Host ID (Existing Device Scan / DHCP Import)

When PlenumLAN scans an existing network or a legacy device obtains an IP via DHCP, the ternary host identifier is computed FROM the known IP address.

**From IPv6 (lossless — preferred path):**

If the device has a PlenumLAN-issued IPv6 address (sentinel prefix present), extraction is exact:

```
host_int = interface_id & 0x7FF_FFFF_FFFF   (strip sentinel, keep 43-bit host_int)
trit[i] = ((host_int / 3ⁱ) mod 3) + 1       (for i = 0..26)
```

This is a pure mathematical inversion. No state. No lookup. The round-trip is perfect.

**From IPv4 (lossy — requires CRS record):**

IPv4 modular reduction is many-to-one (7.6 trillion host integers map to 254 IPv4 addresses in a /24). The inverse is ambiguous — given 192.168.1.159, you cannot reconstruct which of the ~30 billion possible host integers produced it.

The solution: **when scanning an existing device with only an IPv4 address, the CRS assigns a NEW ternary host identifier that, when converted forward via Direction A, produces the device's existing IPv4 address.** The CRS searches the host integer space for the lowest value that maps to the target IPv4 host number:

```
target_ipv4_host = device_ip - range_start   (e.g. 192.168.1.50 - 1 = 49)
host_int = target_ipv4_host                   (simplest: use the host number directly)
```

Since the host number (0–253 for a /24) is already a valid host integer within [0, 3²⁷–1], the simplest approach is to use the IPv4 host number directly as the host integer, then convert to 27 trits. This guarantees the forward derivation reproduces the original IPv4 address exactly. The ternary host identifier is small (low vertex in the cube) but mathematically valid.

For devices that also have an IPv6 address with the PlenumLAN sentinel, the IPv6 path takes precedence — it preserves the full 43-bit host integer without ambiguity.

**Reference implementation** — Direction B (IP → ternary):

```rust
// plenumlan/src/address/derivation.rs

/// Lossless: extract host_int from PlenumLAN-issued IPv6 address
pub fn ipv6_to_ternary(ipv6: &Ipv6Addr, cfg: &SiteConfig) -> Option<TernaryHostId> {
    let iface_id = ipv6.interface_id();
    let sentinel = (iface_id >> 43) & 0x1FFFFF;
    if sentinel != 0x15A { return None; } // not a PlenumLAN address
    let host_int = iface_id & 0x7FF_FFFF_FFFF;
    Some(TernaryHostId::from_u64(host_int))
}

/// Lossy (IPv4): assign the lowest host_int that maps to this IPv4 address
pub fn ipv4_to_ternary(ipv4: &Ipv4Addr, cfg: &SiteConfig) -> TernaryHostId {
    let ipv4_host = ipv4.host_part() - cfg.range_start; // e.g. 192.168.1.50 → 49

    // Use host number directly so forward mod reproduces exact same IPv4
    // (round-trip guaranteed: 49 → mod 254 → 49 → .50 again)
    TernaryHostId::from_u64(ipv4_host as u64)
}

/// Bidirectional: prefer IPv6 extraction, fall back to IPv4 assignment
pub fn ip_to_ternary(
    ipv4: Option<&Ipv4Addr>,
    ipv6: Option<&Ipv6Addr>,
    cfg: &SiteConfig,
) -> TernaryHostId {
    // IPv6 is lossless — always prefer it
    if let Some(v6) = ipv6 {
        if let Some(id) = ipv6_to_ternary(v6, cfg) {
            return id;
        }
    }
    // Fall back to IPv4 assignment
    ipv4_to_ternary(ipv4.expect("device must have at least one IP"), cfg)
}
```

### 6.5 The Three Registration Flows

Here is exactly what happens in each situation, step by step. A developer implementing this section must handle all three flows.

**Flow 1: Scan of existing device (day one import)**

```
1. Network scan discovers device at 192.168.1.50 (IPv4) and/or fd00:...:15a:...:0031 (IPv6)
2. Admin classifies device → first 27 trits computed from ontological scan (Section 7)
3. ip_to_ternary() computes second 27 trits FROM the device's existing IP
   → IPv6 path if sentinel present (lossless extraction)
   → IPv4 path otherwise (host number 49 → host_int 49 → 27 trits)
4. CRS records: 54-trit address, original IPv4, original IPv6, host_int
5. DEVICE KEEPS ITS EXISTING IP. Nothing changes on the wire.
6. The 54-trit address now wraps the device's real network position.
```

**Flow 2: New device registration (PlenumLAN is primary)**

```
1. New device has no IP yet
2. Admin classifies device → first 27 trits from scan
3. CRS bitmap allocator assigns next available vertex → second 27 trits = host_int
4. ternary_to_ip() derives IPv4 and IPv6 FROM the host_int
5. CRS records: 54-trit address, derived IPv4, derived IPv6, host_int
6. Device receives its addresses (via PlenumLAN agent, or manual config, or DHCP response)
7. RESOLVER serves A/AAAA records derived from the CRS record
```

**Flow 3: Legacy DHCP device (no PlenumLAN awareness)**

```
1. Device sends DHCP DISCOVER
2. Legacy DHCP responder assigns next available IPv4 from the CRS pool (e.g. 192.168.1.55)
3. CRS computes ternary host ID from the assigned IP: ipv4_to_ternary(192.168.1.55)
4. Admin is prompted to classify the device (or auto-classification runs from MAC OUI/mDNS)
   → first 27 trits from scan
5. CRS records: 54-trit address, assigned IPv4, derived IPv6, host_int
6. Device thinks it got a normal DHCP lease. Cube registered a new vertex.
```

**The invariant across all three flows:** after registration, every CRS record contains the full 54-trit address, the IPv4 address, the IPv6 address, and the host integer. The forward function (ternary → IP) and the reverse function (IP → ternary) both work. The record is the single source of truth. The resolver serves A/AAAA records from it. The ternary address indexes it. The IP addresses are consistent with the ternary host identifier.

### 6.6 IPv4 Collision Handling

For Direction A (ternary → IPv4), 3²⁷ >> 254, so multiple host integers will map to the same IPv4 host address via modular reduction. The Local CRS maintains a collision set per IPv4 address. On first registration, the mapping is recorded. On collision, the CRS increments to the next available host address and records the override. This is the only state the CRS must maintain for IPv4 — a sparse override table, not a full binding table. In practice, a 10-person office will never see a collision.

For Direction B (IPv4 → ternary), collisions don't arise — the CRS assigns the lowest host integer that maps to the target IPv4, which is unique by construction (the host number itself).

**Reference implementation** — collision override table (stays empty in most deployments):

```rust
// plenumlan/src/crs/collision.rs
use std::collections::HashMap;

pub struct Ipv4CollisionTable {
    overrides: HashMap<u32, u32>, // original_host → actual_host
}

impl Ipv4CollisionTable {
    /// Direction A only: check if this IPv4 host is already taken
    pub fn resolve(&self, host_int: u64, range_size: u32, range_start: u32) -> u32 {
        let candidate = ((host_int % range_size as u64) as u32) + range_start;
        self.overrides.get(&candidate).copied().unwrap_or(candidate)
    }

    pub fn record_collision(&mut self, original: u32, next_available: u32) {
        self.overrides.insert(original, next_available);

        // Alert if collisions pile up — suggests subnet is too small
        if self.overrides.len() > 10 {
            log::warn!(
                "High IPv4 collision count: {} overrides. Consider expanding subnet.",
                self.overrides.len()
            );
        }
    }
}
```

### 6.7 Dual-Stack Resolution

When the TDNS-L resolver receives a query for a `.plm.local` name, it returns:

| Query Type | Response | Source |
|---|---|---|
| A (IPv4) | 192.168.1.50 | From CRS record (original IP preserved, or derived via Direction A) |
| AAAA (IPv6) | fd00:abcd:1234:10:15a:0000:0000:0031 | From CRS record (extracted via Direction B, or derived via Direction A) |
| TDNS-L native (PlenumNET client) | Full 54-trit Rep C address + classification metadata | Direct from CRS record |

All three responses describe the same entity. Legacy devices get IP addresses. PlenumNET-aware devices get the full ternary address. The resolver serves all from a single CRS record.

### 6.8 What This Eliminates

| Eliminated Component | Reason |
|---|---|
| DHCP server (for PlenumLAN-aware devices) | IP addresses are derived from the ternary host ID at registration time (Direction A). No lease negotiation. |
| IP binding table | The CRS record IS the binding. host_int ↔ IP is a bijective function. The CRS record stores both. |
| DNS dynamic updates (DDNS) | Registration in the CRS is the authoritative record. The resolver serves A/AAAA records from it directly. |
| IP address management (IPAM) software | The CRS is the IPAM. The address space is the cube. Utilization is vertex occupancy. |

**What is NOT eliminated (day one):**

| Preserved Component | Reason |
|---|---|
| Legacy DHCP responder | Devices that don't speak PlenumLAN (printers, VoIP phones, badge readers) still send DHCP DISCOVER. The responder assigns an IP and the CRS computes the matching ternary host ID (Flow 3). This shim exists until all devices are PlenumLAN-aware. |
| Existing IPv4 addresses | On an existing network, every device keeps its current IP. The ternary host ID is computed FROM the IP (Direction B), not the other way around. Zero disruption on day one. |
| DHCPv6 / SLAAC (transitional) | Until PlenumLAN manages IPv6 natively for all devices, existing IPv6 mechanisms coexist. The CRS records both PlenumLAN-derived and externally-assigned IPv6 addresses. |

## 7. The LAN Ontological Scan: 27-Dimensional Network Discovery, Asset Management, and Security Posture Assessment

The 27-dimension scan classifies every LAN-connected entity using signals that are native to local networks. No HTTP fetch of a public URL. No web-centric heuristics. Every derivation relies on LAN-native signals only:

- MAC OUI + DHCP class/option fingerprint (options 60, 55, 12, 77, 81, etc.)
- mDNS announcements + TXT records
- SNMP sysDescr / sysObjectID / LLDP chassis and port capabilities
- Port scan + observed protocol behavior + STP/BPDU inspection
- OS/firmware/version self-report at CRS registration
- TL-DSA key presence + heartbeat + shell location (Inner/Void/Outer)
- Historical association patterns, power state changes, traffic analysis
- Quantitative thresholds: `gf3(k, n) = min(floor(3k/n), 2) + 1`

The result is a mutually exclusive and collectively exhaustive classification for all LAN-connected devices — endpoints, servers, infrastructure, OT equipment, IoT sensors, and everything in between.

## 8. Cube Geometry as LAN Infrastructure

The 13-dimensional ternary cube provides five subsystems. On a LAN, each subsystem maps directly to a Windows Server function without requiring a new service.

### 8.1 Topology → Network Routing

Vertices ARE network nodes. Hamming distance IS hop count. Geodesic routing follows cube adjacency. On a LAN:

- **Service discovery:** Querying "all entities where D5=3" (device class) returns all printers, sensors, and IoT devices. The classification IS the discovery mechanism. No mDNS broadcast storms. No manual printer deployment via GPO.
- **Department segmentation:** Entities in the same cube region (matching address prefix) are topologically adjacent. The Engineering department's devices cluster in one region; Finance in another. Emergent from consistent scanning, not manual VLAN assignment.
- **Nearest-service routing:** When a workstation prints, the resolver finds the printer with the smallest Hamming distance from the workstation's cube position. No print server queue management. Geometric proximity is the routing decision.

### 8.2 Shell Security Domains → Network Segmentation

Axis 12 (depth) partitions the cube into three shells: Inner, Void, Outer. On a LAN:

| Shell | Axis 12 Value | LAN Security Zone | IPv6 Subnet | Equivalent |
|---|---|---|---|---|
| Inner | 1 | Management plane: PDS server, Local CRS, audit fabric, root CA | fd00:...:10::/64 | Management VLAN |
| Void | 2 | Service plane: file servers, application servers, internal APIs | fd00:...:20::/64 | Server VLAN |
| Outer | 3 | Client plane: workstations, printers, IoT, guest devices | fd00:...:30::/64 | Client VLAN |

Cross-shell transitions require explicit authorization — a capability token with shell-transition permission. This is the 802.1X / NPS function: a workstation (Outer) accessing a file server (Void) must present a valid capability token that authorizes the cross-shell access. The geometric structure enforces the policy.

**Reference implementation** — security zone determination is a single trit lookup:

```rust
// plenumlan/src/cube/shell.rs
pub fn shell_from_address(addr: &[u8; 54]) -> Shell {
    match addr[11] { // axis 12 (zero-indexed = position 11)
        1 => Shell::Inner,   // management VLAN — PDS, CRS, audit, root CA
        2 => Shell::Void,    // services VLAN — file servers, APIs
        3 => Shell::Outer,   // client VLAN — workstations, printers, IoT
        _ => unreachable!()  // Rep C invariant: only {1, 2, 3} possible
    }
}
```

Every packet, every file access, every remote login checks this one trit. That single-digit lookup replaces VLAN configuration, firewall rules, and Group Policy security filtering.

**Reference implementation** — cross-shell authorization enforcement (called in PFS, PTS, RADIUS shim):

```rust
// plenumlan/src/network/vlan.rs
pub fn authorize_cross_shell(from: Shell, to: Shell, cap: &CapabilityToken) -> bool {
    if from == to { return true; } // same shell = always permitted
    cap.has_permission(Permission::ShellTransition) // crossing requires explicit token
}
```

### 8.3 Sponge Cryptography → Authentication & Encryption

The inner ring (axes 1–6) defines the 3⁶ = 729-trit sponge state. This provides:

- **TL-DSA keypairs:** Every registered entity receives a TL-DSA keypair at scan/registration. The private key is held by the entity; the public key is stored in the CRS. This IS the identity system.
- **TIS-27 integrity:** Every CRS record, every file on PFS, every audit log entry is TIS-27 hashed. Integrity verification is structural, not optional.
- **Phase encryption:** Data at rest on PFS is phase-encrypted. Data in transit between PlenumNET-aware devices uses phase-encrypted tunnels.
- **Capability tokens:** HMAC-chained, HPTP-timestamped, TL-DSA-signed. Unforgeable, attenuable, delegable. Replace AD group membership, DACLs, and GPOs in a single mechanism.

### 8.4 HPTP Timing → Lease Management & Token Expiration

Z₂₈ encodes 28 angular positions in the ternary circle. On a LAN:

- **Token expiration:** Capability tokens carry HPTP femtosecond-precision expiration. No NTP dependency. No Kerberos 5-minute clock skew tolerance.
- **Registration TTL:** CRS registrations carry HPTP timestamps. An entity that fails to heartbeat within its TTL window is transitioned through FTS health states: Up → Suspect → Down → Recovering.
- **Key rotation:** Arc = 182 = π(π−1) defines the semicircular key epoch. TL-DSA key rotation follows the geometric schedule.
- **Audit timestamps:** Every event in the Merkle-chained audit fabric carries an HPTP timestamp. Tamper-evident and femtosecond-precise.

### 8.5 Capabilities → Authorization (ACLs + GPO + Groups Unified)

Capability tokens replace three separate Windows Server systems in a single primitive:

| Windows Server Concept | Capability Token Equivalent | Mechanism |
|---|---|---|
| DACL (file/object permission) | Resource-scoped capability token | Token encodes (subject, resource, action, expiration). Verified by any service holding the root public key. |
| Group membership | Delegation chain | Group capability is HMAC-attenuated and delegated to members. Adding user to group = delegating the group's capability to that user's TL-DSA identity. |
| Group Policy Object (GPO) | Issuance rule on cube region | Rule: "all objects with address prefix P receive capability set C." Evaluated at registration. The token set IS the applied policy. |
| VLAN assignment (802.1X) | Shell-transition capability | Cross-shell access requires a token with shell-transition permission. The shell IS the VLAN. |
| Kerberos ticket | Session capability token | HPTP-timestamped, TL-DSA-signed. Non-replayable. No KDC single point of compromise. |

The issuance rules are CRS metadata on cube regions. When an entity registers and its 27 ontological trits place it in a particular cube region, the Local CRS evaluates all matching issuance rules and attaches the resulting capability tokens to the entity's CRS record. The evaluated token set *is* the GPO. No separate policy engine. No separate policy evaluation. No XML documents linked to OU paths.

## 9. Protocol Bridges

The cube provides the infrastructure. What it does not provide is protocol translation for legacy devices and legacy protocols. A Cisco switch speaks RADIUS, not TL-DSA. A Windows laptop speaks SMB, not Rep C. A printer speaks CUPS/IPP, not capability tokens.

Protocol bridges are thin translation layers. They receive legacy protocol requests, translate them into cube operations (CRS lookups, capability verifications, TL-DSA challenges), and return legacy protocol responses. The bridge is not the service — the cube is the service. The bridge is the interpreter.

### 9.1 PFS: File Protocol Bridge

PFS (Plenum File Service) is the largest protocol bridge and the only genuine **net-new build** required. It translates SMB 3.1.1 and NFS v4.2 file operations into capability-mediated access against cube-addressed storage.

**Inbound path (client → PFS → cube):**

- SMB client sends authentication request (NTLMSSP or Kerberos).
- PFS translates to TL-DSA challenge-response against the client's CRS-registered identity.
- On success, PFS requests a file-access capability token from the CRS for the target share.
- Subsequent file operations (read/write/delete) are authorized against the capability token.
- Every file is TIS-27 integrity-hashed on write. Reads include verification.
- Data at rest is phase-encrypted. Decryption requires the capability token + owner's TL-DSA key.

**Outbound path (cube → PFS → client):**

- PFS presents file contents via SMB/NFS protocol to the legacy client.
- File share namespace is the TDNS-L address: `\\files.salvi-homes.plm.local\projects`.
- Cube topology IS the namespace. No DFS configuration. No drive mappings. No GPO mount scripts.

**Subsystems absorbed by PFS (not separate services):**

- **Backup:** TIS-27 Merkle tree snapshots are a PFS operation. A snapshot is a Merkle root + phase-encrypted archive. No separate backup service.
- **Update distribution (WSUS replacement):** A PFS share containing TL-DSA-signed manifests. Clients verify signatures, download deltas. Two endpoints, not a service.
- **Print driver distribution:** Drivers served from a PFS share, TL-DSA-signed. Unsigned drivers rejected. PrintNightmare structurally eliminated.

### 9.2 Auth Protocol Shims

Three thin shims translate legacy authentication protocols into TL-DSA challenge-response:

**9.2.1 RADIUS Shim (for 802.1X switches)**

- Receives RADIUS Access-Request from switch.
- Translates to TL-DSA challenge via EAP-TLS.
- Queries CRS for client's capability tokens → maps to RADIUS attributes (VLAN = shell, ACL = capability scope).
- Returns RADIUS Access-Accept/Reject.
- Accounting records logged to Merkle audit fabric.

Implementation: 3 endpoints. `/api/radius/auth`, `/api/radius/acct`, `/api/radius/status`.

**9.2.2 LDAP Compatibility Shim (for legacy directory queries)**

- Accepts LDAP bind and search operations from legacy applications expecting AD.
- Translates LDAP search filters to CRS cube queries (e.g., `(objectClass=user)` → query entities where D5=2, D7=1).
- Returns LDAP-formatted results from CRS records.
- Read-only: LDAP writes are translated to PDS API calls requiring TL-DSA-signed capability tokens.

Implementation: 4 endpoints. `/api/ldap/bind`, `/api/ldap/search`, `/api/ldap/compare`, `/api/ldap/unbind`.

**9.2.3 Legacy DHCP Responder (for non-PlenumNET devices)**

- Receives DHCP DISCOVER from devices that don't speak PlenumNET (printers, IoT, guest devices).
- Assigns a scan template based on MAC OUI or mDNS announcement.
- Registers the device in the CRS with a templated ontological scan.
- Derives IPv4 from the ternary host identifier.
- Returns standard DHCP OFFER/ACK with the derived IP, TDNS-L resolver as DNS, and standard gateway.

From the device's perspective, it received a normal DHCP lease. From the cube's perspective, a new vertex was occupied and a 54-trit address was assigned. Implementation: 2 endpoints. `/crs/dhcp-discover`, `/crs/dhcp-request`.

### 9.3 Print Bridge

CUPS is the cross-platform print system used by Linux and macOS. The PlenumNET print bridge wraps CUPS with cube-native discovery and authorization:

- **Discovery:** Printers are CRS-registered entities with D5=3 (device class). Querying the resolver for device-class entities in the same cube region returns the topologically nearest printer.
- **Authorization:** Print jobs require a capability token with print-resource scope. Department restrictions are cube-region issuance rules.
- **Drivers:** Served from PFS, TL-DSA-signed (see Section 6.1).

Implementation: CUPS configuration + 2 CRS registration endpoints for printer-class entities. No net-new code beyond PFS.

## 10. Directory Operations on the Cube

PDS (Plenum Directory Service) is not a separate data store. It is an API layer over the CRS that provides directory-style operations: user enrollment, authentication orchestration, capability lifecycle management, and administrative tooling. The CRS IS the directory. PDS is the management interface.

### 10.1 Entity Registration Workflow

When a new entity joins the LAN:

- **Step 1 — Scan:** The entity is scanned using its class template (Section 4). The 27 ontological trits are derived.
- **Step 2 — Host ID Assignment:** The CRS assigns a 27-trit host identifier from the cube vertex space. The CRS bitmap allocator (flatIndex/fromFlatIndex bijection) selects the next available vertex.
- **Step 3 — TL-DSA Key Generation:** A TL-DSA-87 keypair is generated. Private key stored on the entity; public key registered in the CRS record.
- **Step 4 — Capability Evaluation:** The CRS evaluates all issuance rules matching the entity's cube region prefix. Matching capabilities are attached to the CRS record.
- **Step 5 — IP Derivation:** IPv4 and IPv6 addresses are derived from the host identifier per Section 3. Recorded in the CRS record for resolver serving.
- **Step 6 — Heartbeat Starts:** The entity begins HPTP-timestamped heartbeats to the Local CRS. FTS monitors health: Up → Suspect → Down → Recovering.

The entity now has: a 54-trit Rep C address, a TL-DSA identity, capability tokens, IPv4 and IPv6 addresses, a `.plm.local` DNS name, and a heartbeat. It is fully operational on the LAN. Total registration time: one CRS write + one IP derivation + one capability evaluation. No domain join. No computer account. No GPO processing delay.

### 10.2 Authentication Flow

| Step | Kerberos (AD) | PDS (PlenumNET) |
|---|---|---|
| 1. Identity proof | AS-REQ: password hash sent to KDC | Client signs HPTP-timestamped challenge with TL-DSA private key |
| 2. Session token | AS-REP: TGT issued (symmetric key) | PDS issues HPTP-bound session capability token (HMAC-chained) |
| 3. Service access | TGS-REQ: service ticket requested | Client presents session token; CRS evaluates and issues service-scoped capability with HMAC attenuation |
| 4. Verification | AP-REQ: service decrypts ticket | Service verifies TL-DSA signature on capability. No decryption step — verification is public-key. |
| 5. Mutual auth | Optional: AP-REP | Default: service signs response. Mutual auth is the default, not optional. |
| 6. Expiration | Ticket lifetime (~10 hrs, NTP-dependent) | HPTP femtosecond-precision expiration. Zero clock skew tolerance. |

**Critical advantage:** Kerberos requires all machines synchronized within 5 minutes (MaxClockSkew). A desynchronized clock causes authentication failures. HPTP eliminates clock skew as an attack vector and an operational failure mode simultaneously.

### 10.3 AD Concept Mapping

| AD Concept | PDS / Cube Equivalent | Mechanism |
|---|---|---|
| Forest | PlenumNET fabric (all sites) | Inter-Cube topology. Activates when second site onboards. |
| Domain | Site cube (.plm.local scope) | Single 13D hypercube. |
| Organizational Unit | Cube region (address prefix) | First N dimensions of classification address. |
| User account | CRS record with TL-DSA keypair | Scan template: Workstation or explicit user enrollment. |
| Computer account | CRS record with TL-DSA keypair | Same as user — no distinction needed. Entity is entity. |
| Security group | Capability delegation chain | HMAC-chained tokens propagated to members. |
| Group Policy link | Issuance rule on cube region | CRS metadata: prefix P → capability set C. |
| Trust relationship | Inter-Cube mutual TL-DSA auth | CON tunnel handshake between site cubes. |
| Replication | CRS Merkle-tree sync | TIS-27 Merkle root comparison. |
| DNS SRV records | TDNS-L classification query | Query by dimension values returns matching entities. |
| LDAP search | CRS cube query via LDAP shim | Dimension-based filtering translated from LDAP syntax. |

## 11. Security: Structural Elimination of AD Attack Classes

The PlenumNET LAN is not a security improvement over Windows Server. It is a structural category change. Every known AD attack class is eliminated by the architecture, not mitigated by a security product:

| Attack | Windows Vulnerability | PlenumNET: How It's Prevented |
|---|---|---|
| Pass-the-Hash | NTLM hashes replayable | No password hashes exist. TL-DSA is asymmetric and challenge-response. Nothing to steal, nothing to replay. |
| Kerberoasting | Service tickets crackable offline | No Kerberos. Capability tokens are HMAC-chained with HPTP expiration. No offline crack path exists. |
| Golden Ticket | KRBTGT key forges all tickets | No single key controls all auth. Each capability chain is independently verifiable from the root public key. |
| DCSync | Replication leaks password hashes | CRS Merkle sync compares state hashes. No credential material in the sync stream. Nothing to intercept. |
| GPO abuse | Unsigned XML silently modified | Issuance rules are TL-DSA-signed. Modification without signing key = cryptographic verification failure. |
| PrintNightmare | Unsigned drivers run as SYSTEM | PFS serves TL-DSA-signed drivers only. Unsigned binary = rejected at the cryptographic layer. |
| NTLM relay | Auth relayed to other services | TL-DSA mutual auth is bound to specific service identity. Relay = signature mismatch. Cryptographically prevented and Merkle-audited. |
| Certificate theft | Stolen CA issues arbitrary certs | Root TL-DSA key in HSM. Issuance logged to Merkle fabric. Theft = detectable. Forged cert = invalid chain. |
| Shadow credentials | User attrs modified for persistence | CRS writes require TL-DSA-signed capability. Every modification Merkle-chained. Tamper = detectable. |
| Clock skew attack | Kerberos 5-min tolerance exploited | HPTP femtosecond precision. Zero tolerance window. Clock is a cryptographic service, not NTP. |
| Unconstrained delegation | Delegated tickets forwarded anywhere | Capability attenuation: each delegation hop narrows scope. Widening is cryptographically impossible. |
| AS-REP roasting | Accounts without pre-auth cracked | No pre-auth concept. TL-DSA challenge-response requires private key possession. No crackable material exposed. |

The paradigm shift: AD is *trust-then-verify* — trust that the Domain Admin is legitimate, detect abuse after the fact, hope the audit logs haven't been cleared. PlenumNET is *prove-then-act* — every action requires cryptographic proof of authorization that is independently verifiable and immutably logged. Every proof is Merkle-chained. Every timestamp is HPTP-precise. Every identity is TL-DSA-bound. The security model is the geometry.

## 12. Promotion Path: Local → Global

Any TDNS-L entity can acquire a TDNS Global address without architectural change. The process is second-half recomputation, not migration:

| Step | Action | Address Change |
|---|---|---|
| 1. Local registration | Entity registered at signhere.salvi-homes.plm.local | [27 ontological] · [27 ternary host ID] |
| 2. Promotion request | Operator registers the same entity with global TDNS fabric | First 27 trits: unchanged (same ontological classification) |
| 3. Second-half recomputation | TL-Sponge-43 computes identity hash of global canonical URL (sign.salvigroup.plm) | Second 27 trits: host ID replaced by identity hash |
| 4. Dual resolution | Both addresses resolve to the same entity | .plm.local: LAN routing via host ID. .plm: fabric routing via identity hash. |

The `.plm.local` address remains live for LAN access. The `.plm` address enters the Inter-Cube fabric for internet access. The entity's TL-DSA identity, capability tokens, and CRS registration are unchanged. Only the second 27 trits differ between the two addresses, and they serve different purposes at different scopes.

When a second site comes online, the CON service activates, tunnels connect the two cubes (26 tunnels per cube, TL-DSA mutual auth, phase-encrypted), and the GLB starts routing cross-cube queries. Each site's LAN entities remain on their `.plm.local` addresses within their local cube. Cross-site services use `.plm` addresses routed via the Inter-Cube fabric. Zero reconfiguration at either site.

The React web console is the only part written in TypeScript. It runs in the admin's browser, not on the server. It sends standard web requests and displays what the server returns. ### 13.1 Why One Language Matters

The existing PlenumNET web application (plenumnet.replit.app, 278 features) is written in TypeScript with the cryptographic functions duplicated from Rust. Two programs computing the same thing. When one gets a bug fix, the other needs the same fix.

PlenumLAN does not inherit this. It is a new application. It is written in Rust from line one. Every function exists once. Every bug is fixed once. Every test is run once. There is no bridge between languages, no translation layer, no duplication, no migration from one technology to another.

### 13.2 What This Eliminates

| Eliminated | What It Was | What Replaced It |
|---|---|---|
| TypeScript server code | Duplicate of Rust logic | Not needed. Rust called directly. |
| Language bridge | Translation layer between TypeScript and Rust | Not needed. Same language. Same program. |
| Duplicate bug fixes | Fix in TypeScript, then fix again in Rust | Fix once. In Rust. |
| Duplicate test suites | Two test frameworks testing the same logic | One test framework. Rust. |
| Technology migration | Rewrite from TypeScript to Rust (6–8 weeks) | No rewrite. Was Rust from the start. |

## 16. Secure Remote Administration

The web console runs on the office network. How does an administrator manage the network from home or while traveling?

### 16.1 The Encrypted Tunnel

PlenumLAN includes a built-in secure tunnel that connects the admin's browser to the office console from anywhere in the world. The tunnel uses post-quantum encryption — security that protects against both current and future quantum computers.

**How it works:**

1. **One-time setup (in the office).** The admin connects a laptop or phone to the office network and enrolls it as an authorized remote device. The device generates a cryptographic identity key. This takes about 30 seconds.

2. **Remote connection (from anywhere).** The admin opens a browser and goes to `remote.your-site.plm`. The server challenges the device to prove its identity. The device responds via WebAuthn — the browser prompts for biometric confirmation (face or fingerprint on a phone, fingerprint or PIN on a laptop) and completes the cryptographic challenge. If verified, an encrypted tunnel opens and the console loads — identical to being in the office.

3. **Session ends automatically.** The tunnel has a precise expiration time. When it expires, the connection closes. There is no "remember me." Every remote session requires fresh authentication.

### 16.2 Why This Is Not a VPN

A traditional VPN gives you full access to the entire office network. If someone compromises your VPN connection, they can reach every device in the office. PlenumLAN's tunnel only connects to the management console — not to the office network. An attacker who somehow compromises the tunnel can see the console but cannot reach your file server, your printers, or your other computers through it. The tunnel terminates at the console. Period.

If the admin needs to reach a specific service remotely (for example, a remote desktop connection to a particular computer), that requires a separate authorization token scoped to that specific service. Each remote service has its own tunnel. Each tunnel is individually authorized and individually logged.

### 16.3 Managing from a Phone

The web console is designed to work on phone screens. Initial mobile authentication uses WebAuthn/FIDO2 — the web standard for passwordless login that works in all modern browsers. The admin registers a security key or biometric credential during enrollment. On subsequent logins, the browser prompts for biometric confirmation (face or fingerprint) and the WebAuthn protocol handles the cryptographic challenge-response. No password to type. No separate app to install.

**Future capability (native agent):** Direct access to the device's secure hardware enclave (iOS Secure Enclave, Android StrongBox) for storing the TL-DSA private key requires a native application, which browsers cannot access today. A lightweight PlenumLAN agent app would provide this deeper hardware integration. For Release 1.0 through 2.0, WebAuthn provides strong passwordless authentication that works in standard browsers on any phone.

**Device revocation.** If an enrolled remote device is lost or compromised, the admin revokes its authorization through the console. The Directory Service publishes a revocation record to the Local Registry, which propagates on the next Merkle sync. The revoked device's WebAuthn credential is invalidated server-side — even if the attacker possesses the device, the tunnel endpoint rejects the authentication challenge. Revocation takes effect immediately; no certificate revocation list propagation delay. The audit log records the revocation event with a precision timestamp.

## 17. The Four-Stage Platform Trajectory

The same compiled program runs at every stage. The only thing that changes is what's underneath it — and at every stage, the admin opens a browser and sees the same web console.

```
Stage 1: Replit               The program runs on Replit's servers.
                               Full console. Download button for local install.

Stage 2: Office Computer       The same program runs on a computer in the office.
                               Full console + full network management.
                               Linux is underneath (providing hardware drivers).

Stage 3: PlenumNET OS          The same program boots directly from a USB stick.
                               No Linux underneath. No operating system to maintain.
                               Plug in, power on, manage network.

Stage 4: Custom Hardware        The same program runs on a purpose-built chip
                               that executes ternary math in hardware.
                               Maximum speed. Minimum attack surface.
```

### 17.1 Stage 1: Replit

The program runs on Replit's servers. The admin goes to PlenumLAN.replit.app and uses the full web console. All computational features work: scanning, registration, address derivation, cube visualization, policy management, audit logging. Network features that require physical presence (file sharing, printer management, network address allocation, switch communication) work in the code but have no local network to connect to — because the server is in Replit's data center, not in the office.

The Replit deployment also hosts the Download section for local installation.

### 17.2 Stage 2: Office Computer (Linux Underneath)

The same program runs on any computer in the office — a dedicated server, a spare laptop, a Raspberry Pi. It's packaged as a standard Linux or Windows application. Linux provides the hardware drivers (network card, hard drive, USB). Everything above the hardware drivers is PlenumLAN's Rust code.

This is the production deployment for real offices. Full network management. Full web console. Secure remote access.

### 17.3 Stage 3: PlenumNET Operating System (No Linux)

The Linux layer is removed. PlenumLAN boots directly from a USB stick or network boot, using a minimal Rust-based bootloader that provides just enough hardware support (network card driver, hard drive driver, USB) to run the PlenumLAN program. There is no Linux. No operating system to maintain. No patches to apply. No terminal. No command line. No way to log into the machine except through the web console.

You plug a USB stick into any standard computer, turn it on, and 30 seconds later the admin opens a browser and the network is managed. That's the appliance vision.

**Driver strategy.** Writing bare-metal network card and storage drivers from scratch is non-trivial — interrupt handling, DMA safety, PCI enumeration, and power management edge cases take time. The pragmatic path: leverage existing `no_std` Rust crates for initial driver support (`smoltcp` for a `no_std` userspace TCP/IP stack paired with a custom kernel socket layer, `virtio-drivers` for virtual machine environments), then develop custom physical PCI/PCIe drivers (Intel e1000e, Realtek r8169) for common commodity hardware as a follow-on effort. Storage drivers start in polling mode with basic read/write; interrupt-driven asynchronous I/O follows in later sprints. This approach delivers a bootable appliance for virtual machines first, then extends to bare-metal hardware incrementally.

**Emergency console.** If the network dies and the web console is unreachable, an administrator can plug in a USB keyboard and see a read-only text display: system uptime, FTS health states, last audit chain hash, and scrollable log output. No shell. No login. No command execution. Read-only status and reboot — nothing else.

**Async I/O primitives.** On Stage 2 (Linux), the Axum web server uses Tokio, which relies on Linux's `epoll` for asynchronous I/O. Stage 3 removes Linux — so PlenumNET OS must provide its own async I/O primitives. The kernel implements an epoll-equivalent notification system: a lightweight event loop supporting edge-triggered and level-triggered file descriptor monitoring, timer events (for HPTP token expiration), and inter-process notifications (for CRS registration events). This is designed early (during Stage 3 kernel development) rather than retrofitted, because Axum/Tokio's runtime depends on it for every HTTP connection, every WebSocket stream, and every PTS tunnel session. The notification API is specified before driver development begins so that NIC drivers, storage drivers, and the Guacamole display streamer can all use the same async primitives.

```rust
// plenumlan/src/display/emergency.rs
pub fn emergency_console() {
    if !network_up() {
        let mut con = TextConsole::new(); // VGA framebuffer or serial
        con.print("PlenumNET OS — Emergency Mode\n");
        con.print("Network: DOWN. Web console unreachable.\n");
        con.print_status(); // uptime, FTS health, last Merkle audit hash
        // Read-only keys: arrows to scroll logs, Ctrl+R to reboot
        loop { handle_key_blocking(&mut con); }
    }
}
```

### 17.4 Stage 4: Custom Hardware (XPlenum)

The ternary math operations that the program currently computes in software are executed by custom hardware instructions on a purpose-built RISC-V processor chip. The admin still opens a browser and sees the same console. Everything is faster because the math runs in silicon instead of software.

The hardware design exists: 2,407 lines of verified chip description code, 22 of 22 tests passing, synthesized to a 19,173-gate circuit. Timeline depends on hardware fabrication partnerships. The architecture is ready; the silicon is patient.

**PlenumDB specification.** PlenumDB is the native storage backend for the device registry. It stores every registered entity record, every cryptographic public key, every capability token chain, every permission issuance rule, and every entry in the tamper-proof audit log. In Stage 1 (Replit) and early Stage 2, data is stored in an embedded key-value store (sled or redb — proven Rust-native storage engines). PlenumDB replaces this with a purpose-built key-value store optimized for three specific access patterns: ternary-addressed entity lookup (27-trit key → record), Merkle-tree audit chain traversal (sequential reads along the hash chain), and the bitmap allocator's vertex occupancy map (1,594,323-bit bitmap with fast scan for next available vertex). In Stage 3 (PlenumNET OS), PlenumDB operates directly on raw block devices without a filesystem intermediary. Crash safety is provided by a write-ahead log (WAL): every write is journaled before it modifies the primary data structure, ensuring that a power failure or crash at any point leaves the database in a consistent, recoverable state. WAL correctness is verified by a crash-injection test harness: automated tests simulate power failure at every I/O boundary (before journal write, after journal write but before data write, during data write, after data write but before journal clear), then verify that the database recovers to a consistent state on restart. This harness runs in CI alongside the integration tests.

**Elapsed: 30–38 weeks cumulative.**

**Driver development strategy.** Network card and storage drivers begin with virtual machine targets (`virtio-net`, `virtio-blk`) using existing `no_std` Rust crate abstractions, then progress to physical PCI/PCIe devices (Intel e1000e, Realtek r8169, NVMe). Storage drivers start in polling mode with basic read/write operations; interrupt-driven asynchronous I/O follows in subsequent sprints. This delivers a bootable appliance for VM environments (Proxmox, VMware, Hyper-V) first, extending to commodity bare-metal hardware incrementally.

**Unsafe code discipline.** Stage 3 drivers and boot code will contain `unsafe` blocks for MMIO register access, page table manipulation, DMA buffer setup, and interrupt handling. Every `unsafe` block must document its safety invariants in a `// SAFETY:` comment. In addition to unit tests, debug-mode builds include runtime assertions in critical paths: page table walks verify alignment and present bits, DMA buffers verify physical address alignment, and interrupt entry/exit routines verify stack pointer bounds. These assertions are compiled out of release builds but catch subtle errors (missing memory barriers, incorrect page flags, unaligned MMIO) during development. For the most safety-critical code (context switch, interrupt dispatch), the existing Kani/MIRI formal verification pipeline is extended with targeted proof harnesses.

**Stage 4: XPlenum Hardware** is the long-term target. The chip design is verified (2,407 lines of hardware description, 22 of 22 tests passing, synthesized to 19,173 logic gates). Timeline depends on hardware fabrication partnerships.

## 22. Windows Application Compatibility: ReactOS on PlenumNET OS

PlenumLAN replaces Windows Server. But some offices will always have Windows-only software — QuickBooks Desktop, AutoCAD, industry-specific tools, legacy line-of-business applications that have no web version and no Linux port. Replacing the server infrastructure doesn't eliminate the need to run these applications. The question is how to run them without reintroducing Windows.

### 22.1 The Problem with "Just Run a Windows VM"

The obvious answer — run Windows virtual machines — reintroduces everything PlenumLAN eliminates: a Windows license, a Windows attack surface, Windows patching, and a dependency on Microsoft for the core of the office workflow. Running Windows VMs on a PlenumLAN server is the same as running Windows Server with extra steps.

### 22.2 The Answer: ReactOS

ReactOS is an open-source operating system designed from the ground up to be binary-compatible with Windows. It provides the same APIs that Windows provides — kernel32, user32, gdi32, ntdll — all rewritten as free, open-source code. Windows executables run on ReactOS the same way they run on Windows. It is not a translation layer. It is not emulation. It is the actual API implementation, built clean-room with zero Microsoft code and zero Microsoft licensing.

ReactOS has been in active development since 1996. It runs Microsoft Office, QuickBooks, AutoCAD LT, and thousands of business applications today. It is GPL licensed — free to use, modify, and distribute.

### 22.3 Architecture: ReactOS as a Managed Subsystem

On PlenumNET OS (Stage 3 — the bootable appliance), ReactOS runs as a managed guest subsystem inside the PlenumNET environment. The Rust bootloader owns the hardware. PlenumLAN owns the network and security. ReactOS owns the Windows API surface. Each does one job.

```
PlenumNET OS (Rust bootloader — owns the hardware)
    │
    ├── PlenumLAN binary
    │   ├── Cube management (CRS, PDS, TDNS-L, audit)
    │   ├── Web console (Axum serving React)
    │   ├── Network services (PFS, RADIUS, DHCP, DNS)
    │   └── Application Manager (registers and controls ReactOS guest)
    │
    └── ReactOS subsystem (managed guest — runs Windows applications)
            │
            ├── QuickBooks.exe
            ├── AutoCAD.exe
            ├── CustomIndustryApp.exe
            └── (any standard Windows application)
```

No Linux anywhere. No Windows anywhere. No Microsoft licensing. The office runs on a ternary cube with a Windows-compatible application layer built from open-source code.

**Virtualization approach.** ReactOS runs as a hardware-virtualized guest using the host processor's virtualization extensions. On x86_64 this is VT-x/EPT — mature, well-supported, and the primary target for initial ReactOS integration. On ARM64 it requires EL2 (Hypervisor Exception Level) support, available on most server-class ARM processors. On RISC-V it requires the H (Hypervisor) extension, which is not yet ubiquitous in commodity hardware. Therefore: ReactOS compatibility ships on x86_64 first. ARM64 support follows when the target hardware is confirmed. RISC-V support tracks hypervisor extension availability. The architecture choices in PlenumNET OS (address space layout, interrupt routing, memory management) are designed from Stage 3 onward to reserve the structures needed for guest isolation, so no redesign is required when additional architectures gain hypervisor support.

### 22.4 How It Works for the Admin

1. **Install an application.** The admin opens the PlenumLAN console, navigates to the Applications surface, and uploads a Windows installer file (.exe or .msi). PlenumLAN passes the installer to the ReactOS subsystem. ReactOS installs it the same way Windows would — writing files, registering DLLs, creating shortcuts.

2. **Assign access.** The admin creates a capability token scoping which users can launch which application. "Maria can access QuickBooks. John can access AutoCAD. Nobody else." Same capability model as every other PlenumLAN permission — scoped, expiring, attenuable, Merkle-audited.

3. **User launches the application.** The user opens the PlenumLAN console in their browser (from any device, anywhere), goes to the Applications screen, and clicks "QuickBooks." The application launches on the ReactOS subsystem on the office server. The display streams to the user's browser as an interactive desktop session.

4. **Files save to PFS.** The application saves files to what it thinks is a network drive. That drive is a PFS share — capability-gated, integrity-verified, phase-encrypted, Merkle-snapshotted. The user's documents are protected by the full PlenumLAN security model.

5. **Session ends.** The user closes the browser tab. The application session terminates. The audit log records: who connected, which application, when, from what device, how long.

### 22.5 How It Works for the User

The user doesn't know or care about ReactOS. They open a browser, log in with their face or fingerprint (WebAuthn), see the list of applications they're authorized to use, click one, and a familiar Windows application appears in their browser. They work normally. They save files. They print. They close the tab and walk away.

No Windows on their laptop. No application installed on their device. No VPN. No RDP client. No special software. Just a browser.

### 22.6 What ReactOS Can and Cannot Do Today

ReactOS is production-capable for many business applications but not yet for everything. This is the honest assessment:

| Works today on ReactOS | May have issues | Unlikely to work (yet) |
|---|---|---|
| Microsoft Office (2003–2010) | Office 2016/2019 (partial) | Office 365 desktop (heavy COM) |
| QuickBooks Desktop (older versions) | QuickBooks 2020+ (testing needed) | Applications with kernel drivers |
| AutoCAD LT | Full AutoCAD (GPU-dependent) | Applications with hardware dongles |
| Most .NET Framework apps | .NET Core/5+ apps (improving) | Kernel-mode anti-cheat or DRM |
| Standard Win32 business tools | Electron apps (varies) | Games requiring DirectX 12+ |
| Installers (MSI, NSIS, Inno) | Complex installers (WiX) | UEFI-dependent applications |

By the time PlenumLAN reaches the appliance stage (12–18 months out), ReactOS will be further along. The project is actively maintained with regular releases. Compatibility improves with every version.

For applications that genuinely cannot run on ReactOS, the fallback is a Windows VM accessed through the same browser-based remote desktop (Section 23). But this is positioned as the last resort — not the default.

### 22.7 The Complete Elimination Story

PlenumLAN replaces Windows Server (the infrastructure). ReactOS replaces Windows Desktop (the application platform). Combined:

- Zero Microsoft licenses — server or desktop
- Zero Microsoft dependencies — no Active Directory, no Windows Update, no patch Tuesday
- Zero Windows attack surface — no NTLM, no RDP exposed, no SMB vulnerabilities in Windows code
- All applications managed through the cube — capability-gated, audit-logged, post-quantum secured

- Everything boots from a USB stick — the ternary cube, the network stack, and the Windows application layer, all from one device

## 23. Browser-Based Remote Desktop: Post-Quantum Secure Application Streaming

When a user launches a Windows application through the PlenumLAN console, the application's display must travel from the office server to the user's browser. This is the remote desktop component. It is built into PlenumLAN — not a separate product, not a third-party service, not an exposed RDP port.

### 23.1 How It Works

The display streaming uses the Guacamole protocol — a proven open-source technology (Apache project, in production for over a decade) that translates desktop display protocols into an HTML5 Canvas stream that renders in any standard browser.

```
User's browser (anywhere in the world)
    │
    │  PTS tunnel
    │  Phase-encrypted (post-quantum)
    │  WebAuthn authenticated
    │  Capability token authorized
    │
    ▼
PlenumLAN Console
    │  "Applications" surface — click to launch
    │
    ▼
Guacamole rendering engine (inside PlenumLAN spoke agent or binary)
    │
    │  Translates display output → HTML5 Canvas
    │  Translates keyboard/mouse input → application input
    │  Translates clipboard → bidirectional copy/paste
    │  Translates file transfer → PFS share access
    │
    ▼
ReactOS subsystem (or Windows VM as last-resort fallback)
    │
    └── Application.exe running, display rendered, input processed
```

### 23.2 Every Layer Is Post-Quantum Secured

This is not standard RDP. Every layer of the connection is protected by PlenumLAN's post-quantum cryptographic stack:

| Layer | What Protects It | How |
|---|---|---|
| Authentication | WebAuthn + TL-DSA | User proves identity with biometric (face/fingerprint). Device's cryptographic key is verified against PDS. No password. No NTLM hash. Nothing to steal. |
| Authorization | Capability token | The user must hold a valid `application:{app-id}` token to launch the session. Token is scoped, expiring, and attenuable. Even if someone intercepts the session, they can't launch a different application or access a different VM. |
| Transport | PTS tunnel (phase encryption) | The entire display stream — every pixel, every keystroke, every clipboard copy — travels through the PTS tunnel. Phase encryption provides post-quantum confidentiality. A quantum computer intercepting the traffic cannot decrypt it. |
| Session binding | HPTP timestamp | Each session has a precision-timestamped start and expiration. The session token cannot be replayed — it is cryptographically bound to the specific time window and specific device. |
| Audit | Merkle chain | Session start, session end, user identity, source device, target application, duration — all logged to the tamper-proof audit fabric with precision timestamps. Every session is provable and every absence of a session is provable. |
| File access | PFS capability | Files saved during the session go through PFS — capability-gated, integrity-hashed, phase-encrypted at rest. The application cannot write to arbitrary disk locations — only to PFS shares the user's token authorizes. |

### 23.3 What This Replaces

| What offices do today | What PlenumLAN does instead |
|---|---|
| Expose RDP port 3389 to the internet | Never exposed. PTS tunnel only. Port 3389 does not exist on the network perimeter. |
| Require a VPN to reach the RDP server | No VPN. Browser only. PTS tunnel handles encryption and authentication. |
| Windows username + password for RDP | No password. WebAuthn biometric + capability token. |
| RDP client installed on every remote device | No client software. Any device with a browser. |
| Full desktop access to the entire server | Scoped: each user gets access to specific applications only. Not the full desktop. |
| No meaningful audit trail (Event Viewer is clearable) | Merkle-chained, tamper-proof, precision-timestamped session log. |
| Pre-quantum encryption (TLS 1.2/1.3) | Post-quantum (PTS phase encryption + TL-DSA authentication). |
| Anyone with the password can log in from anywhere | Capability token is scoped to specific user, specific application, specific time window, specific enrolled device. |

### 23.4 Single-Application Mode

For most office use cases, the user doesn't need a full Windows desktop. They need one application — QuickBooks, AutoCAD, the custom industry tool. PlenumLAN supports single-application mode: when the user clicks "QuickBooks" in the console, only the QuickBooks window appears in the browser, not the full Windows desktop. This is similar to Microsoft's RemoteApp feature, but implemented through the Guacamole rendering layer.

The user sees QuickBooks in a browser tab, not a remote desktop with a Start menu and icons. This is cleaner, faster (less data to stream), and more secure (the user cannot browse the server's filesystem or launch unauthorized programs).

### 23.5 Multi-Site Application Hosting

In a multi-site deployment (hub and spoke model), each office's spoke agent can host its own ReactOS subsystem and applications. The admin manages all applications across all sites from a single console. A user in Office A can launch an application hosted on Office B's server — the PTS tunnel connects through the Inter-Cube fabric, the Guacamole stream delivers the display, and the experience is seamless.

The admin sees: all applications, all sites, all active sessions, all audit records — in one console.

- **Appliance roadmap.** Eventually boots from a USB stick. No operating system to maintain. Plug in. Power on. Manage network. Run applications.
- **Custom hardware roadmap.** Purpose-built chip executing ternary math natively. Maximum speed. Minimum attack surface.

## Appendix B: Deployment Example


A 10-person construction office. Mixed Windows/Linux workstations. One file server. Two printers. Internet-facing SalviSign.

Note: In this deployment, PlenumLAN is installed on an existing office network. All devices already have IPv4 addresses. The ternary host identifiers are computed FROM the existing IPs (Direction B — Section 6.4). No IP addresses change on day one.

| Entity | Tier | TDNS-L Address | IPv4 (preserved) | IPv6 (assigned) |
|---|---|---|---|---|
| PlenumNET Server | Local | pds.salvi-homes.plm.local | 192.168.1.1 | fd00:abcd:1234:10:15a:... |
| File Server | Local | files.salvi-homes.plm.local | 192.168.1.2 | fd00:abcd:1234:20:15a:... |
| Color Printer | Local | printer-color.shomes.plm.local | 192.168.1.50 | fd00:abcd:1234:30:15a:... |
| B&W Printer | Local | printer-bw.shomes.plm.local | 192.168.1.51 | fd00:abcd:1234:30:15a:... |
| John's Workstation | Local | john-pc.shomes.plm.local | 192.168.1.101 | fd00:abcd:1234:30:15a:... |
| Maria's Laptop | Local | maria-lt.shomes.plm.local | 192.168.1.102 | fd00:abcd:1234:30:15a:... |
| HR API | Local | hr-api.shomes.plm.local | 192.168.1.10 | fd00:abcd:1234:20:15a:... |
| SalviSign (internal) | Local | signhere.shomes.plm.local | 192.168.1.11 | fd00:abcd:1234:20:15a:... |
| SalviSign (public) | Global | sign.salvigroup.plm | N/A (fabric-routed) | N/A (fabric-routed) |
| PlenumNET Portal | Global | portal.capomastro.plm | N/A (fabric-routed) | N/A (fabric-routed) |

Note the IPv6 subnet segmentation: the PlenumNET server is on `:10:` (Inner shell — management plane), file server and APIs are on `:20:` (Void shell — service plane), workstations and printers are on `:30:` (Outer shell — client plane). This segmentation is *derived from each entity's cube position*, not manually configured per device. The scan determines the shell; the shell determines the subnet; the subnet determines the VLAN. Geometry is the policy.

**Hardware requirement:** Any Linux box (x86-64 or ARM64), 4 cores, 16 GB RAM, 256 GB SSD. The entire PDS + CRS + resolver + PFS + audit stack runs as Rust services on a single machine. No AD domain controller. No Windows Server license. No CALs. No NTP server. No DHCP server. No separate DNS server. No PKI server. One cube.
