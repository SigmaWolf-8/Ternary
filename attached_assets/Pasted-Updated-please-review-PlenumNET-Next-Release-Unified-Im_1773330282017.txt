Executive Summary

This specification consolidates three workstreams into a single release plan:





Security Hardening — Cryptographic binding of the operational layer (signed CRS, authenticated heartbeats, address-bound keys, mutual tunnel authentication)



Bootstrap Optimization — Geometric placement strategy for sparse cube connectivity



Plenum Square Integration — Crystal-lattice ECC, two-scale sponge dynamics, reciprocal-lattice key mixing, arc-synchronized key rotation

All items use existing primitives (TL-DSA, TIS-27, TLSponge-385). No new cryptographic dependencies. The four Inter-Cube services (CRS, CON, GLB, FTS) retain their current interfaces with additive fields.

After implementation, the security claim becomes: every CRS record, heartbeat, identity key, and tunnel session is cryptographically bound to the geometric position, the registered identity, and the post-quantum primitives. No operation proceeds without proof of geometric occupancy. The Plenum Square provides structural ECC, crystal-dynamics diffusion, and calendar-synchronized key rotation — all derived from the half-turn arc = 182 = π(π − 1) = 14 × 13 = 20202₃.

Technical Detail — §1. Signed CRS Registrations

Threat Model

The current CRS register endpoint accepts an address, endpoint URL, and public key with no proof that the registrant controls the corresponding private key. An attacker who can reach CRS — or a compromised CRS node — can claim any unclaimed address and redirect tunnels destined for the legitimate occupant. This is the single largest gap because CRS is the trust root for neighbor resolution.

Design

Every registration payload includes a TL-DSA signature computed by the registering node. CRS stores the signature alongside the record. Querying nodes verify the signature before establishing tunnels.

Registration Payload:

struct CrsRegistration {
    address:        CubeAddr,         // 13-trit geometric position
    endpoint:       String,           // reachable host:port
    public_key:     TlDsaPublicKey,   // TL-DSA-87 verification key
    kem_public_key: TlKemPublicKey,   // TL-KEM-1024 encapsulation key
    timestamp:      u128,             // femtosecond since Salvi Epoch
    signature:      TlDsaSignature,   // sig over canonical payload
}


Signature Construction: Canonical concatenation: address.to_wire() ‖ endpoint.as_bytes() ‖ public_key.as_bytes() ‖ kem_public_key.as_bytes() ‖ timestamp.to_le_bytes(). Domain: "PlenumNET-CRS-REG-v1". TL-DSA-87.

CRS Record (updated):

struct CrsRecord {
    address:         CubeAddr,
    endpoint:        String,
    public_key:      TlDsaPublicKey,
    kem_public_key:  TlKemPublicKey,
    registered_at:   u128,
    last_heartbeat:  u128,
    reg_signature:   TlDsaSignature,
}


Verification, Replay Protection, Sybil Cost

On registration: verify signature, reject on failure. On query: response includes reg_signature — querying node verifies before tunnel. Compromised CRS cannot forge (no signing key). Timestamp freshness: 30s window. Re-registration requires newer timestamp. Per-identity Sybil cost: 1 keypair + 26 tunnels + 26 heartbeats/interval. Structural resistance from geometry.

Technical Detail — §4. Mutual Tunnel Authentication

Three-message handshake: CHALLENGE (0x40, encrypted nonce) → RESPONSE (0x41, nonce+1 + own nonce) → CONFIRM (0x42, their nonce+1). Both sides prove same topology key. State: Connecting → Authenticating → Up. 5s timeout, backoff. Rekey: Up → Rekeying → Authenticating → Up with new epoch.

Type Code Payload CHALLENGE 0x40 addr(7) + enc_nonce(32) + iv(12) + tag(16) + epoch(8) + ts(16) RESPONSE 0x41 addr(7) + enc_nonces(64) + iv(12) + tag(16) + epoch(8) + ts(16) CONFIRM 0x42 enc_nonce(32) + iv(12) + tag(16) + ts(16)

Technical Detail — §5. Address-Bound TL-DSA Keys

Sponge parameters: TLSponge-385 = 729-trit state, 9 rounds, stride 13, rate 243, capacity 486 (≈ 385-bit security). The "385" in the name refers to the security level from the capacity, not the state width.

fn derive_address_bound_keypair(
    address:       &CubeAddr,
    master_secret: &[u8; 48],

    tl_dsa_keygen_from_seed(&seed)

Technical Detail — §8. Plenum Square Integrations

§8.1 Dual Checksum (T-05): mod-364 + mod-333. CRT → modulus 121,212. 12 trits. 0.0008% false-pass.

§8.2 Wire ECC (T-10): 8-line mod-9 parity. Unique syndrome per triplet. Correct in place.

§8.3 Sponge Shuffles (T-11): σ_A first (double derangement), then σ_B, σ_C, σ_D — one per round, applied before stride-13 each round. For TIS-27 (4 rounds): σ_A, σ_B, σ_C, σ_D — one per round, perfect fit. For TLSponge-385 (9 rounds): σ_A, σ_B, σ_C, σ_D, σ_A, σ_B, σ_C, σ_D, σ_A — cycling. Note: the "27" in TIS-27 refers to the trit count (rate 27, capacity 27, state 54), not the round count.

§8.4 Arc Rotation (T-12): 182 days. Epochs: 0, 182, 364. Triggers rekey + re-auth.

§8.5 Lattice Mixer (T-15): Weight × triplets mod 333. Magic constant prevents bias.

§8.6 SignHere Syndrome (T-16): Hash → 9 triplets → 8-line parity. Non-zero → reject before TL-DSA.

§8.7 Three-Scale Kernel (T-19): 729 = Δ₂ = 1+4(182). Inner σ_A–σ_D + outer Plenum Square.

§8.8 Agent Scheduling (T-20): Coprime walk + Plenum grouping + σ_A derangement. 28 = 2π.

They address concerns raised in external reviews regarding master secret protection, denial of service, protocol versioning, performance, and deployment strategy.

Master Secret Protection

The master_secret (48 bytes) is the root of trust for heartbeat HMAC keys (T-02), address-bound key derivation (T-08), and tunnel key material. Its compromise would allow impersonation of any node.





Generation: Use a cryptographically secure random number generator with at least 384 bits of entropy. Document the generation process in operational runbooks.



Storage: Encrypt on disk with a key derived from a node-specific secret (TPM-backed where available, passphrase-derived otherwise). Never store in plaintext. Never transmit over the network.



Rotation: Master secret rotation requires re-registration (new keypair derived from new secret + same address). Schedule rotation at arc boundaries (182-day epochs) to align with key rotation.

CRS Rate Limiting and DoS Protection

Even with signed registrations (T-01), an attacker can flood CRS with valid signatures (each requiring a new keypair but no ongoing tunnel cost if the attacker doesn't maintain tunnels).





Per-source IP rate limiting: Cap registration attempts per IP per time window (e.g., 10 registrations per minute per IP).



Proof-of-work for registration: Require a lightweight hash puzzle (e.g., find nonce where TIS-27(address ‖ nonce) has K leading zero trits) to raise the cost of mass registration. K is tunable: low during bootstrap, higher under load.



FTS integration: Nodes that register but never respond to heartbeats accumulate "ghost" scores. CRS can deprioritize or purge registrations with zero tunnel activity after a grace period.

Protocol Version Negotiation

This release introduces wire-format changes: dual checksum (T-05, +12 trits), ECC syndrome (T-10, +8 trits), new message types (T-07, 0x40–0x42), and authenticated heartbeats (T-02, +sequence + auth). These break compatibility with older nodes if deployed without versioning.





Version field: Add a protocol_version: u8 to the wire message header. Current = v1, this release = v2.



Negotiation: During tunnel establishment, nodes exchange supported versions. Both sides use the highest common version. If no overlap, tunnel fails with IncompatibleVersion.



Dual-acceptance period: For T-05 (dual checksum) and T-10 (wire ECC), accept both old and new formats during Phase 1 rollout. Require new format after Phase 2 ships.



Monitoring: Log version mismatches. Track the percentage of v1 vs v2 nodes to know when the dual-acceptance period can end.

Performance Caching

Several operations in the spec involve repeated computation of the same result. Caching eliminates redundant work without changing security properties.





CRS verification cache: After verifying a neighbor's reg_signature, cache the result with a TTL (e.g., 5 minutes). Re-verify only on cache expiry or CRS record change. Reduces TL-DSA verify calls during steady-state operation.



Address-bound keypair cache: The derived keypair for a given (address, master_secret) is deterministic and immutable. Cache in memory. Invalidate only on master secret rotation (every 182 days).



Heartbeat HMAC key cache: Derived once at registration, stored in CrsRecord. Never recomputed unless master_secret changes.



Bootstrap placement cache: For allocateOptimal(), cache the neighbor-occupancy map between registrations. Invalidate incrementally (only the 26 neighbors of the newly registered node change occupancy status).

Deployment Strategy





Canary rollout: Deploy Phase 1 (PR 1) to 10% of nodes first. Monitor CRS auth success rate, heartbeat verification rate, and tunnel establishment latency for 48 hours before full rollout.



Feature flags: Gate Plenum Square items (T-05 dual checksum, T-10 wire ECC, T-11 sponge shuffles) behind runtime flags. Enable per-node for testing, then globally.



Telemetry: Add metrics for: registrations signed vs unsigned, heartbeat auth pass/fail, tunnel auth pass/fail, v2.5 fallback attempts (should drop to zero after T-04). Expose via existing Kong Konnect metrics endpoints.



Rollback plan: If Phase 1 causes issues, revert to unsigned CRS with a single config flag (CRS_REQUIRE_SIGNATURE=false). Tunnels built during the signed period remain valid — they were authenticated at establishment time.

v2.5 Teardown Grace Period

T-04 removes the v2.5 key derivation fallback. Existing v2.5 tunnels must be handled:





On upgrade: Nodes tear down any v2.5 tunnels and re-establish using v3 (TL-KEM + TLSponge-385).



Grace period: For 7 days after PR 1 ships, log v2.5 attempts as warnings instead of hard rejections. After 7 days, hard-reject. This gives all nodes time to upgrade.



Test coverage: The 6 existing tests using #[allow(deprecated)] calls to v2.5 must be updated to expect None (no key derived) instead of a valid key.

External Cryptographic Audit

The system relies on custom primitives (TL-DSA-87, TIS-27, TLSponge-385). Internal monographs (TM-2026-008, TM-2026-011) provide security analysis, but third-party review is required before production deployment at scale.





Scope: Engage an external cryptographic auditor to review: (a) the TLSponge-385 permutation and its wide-trail bounds, (b) the T-AE-MAC dual-phase authenticated encryption construction, (c) the TL-DSA and TL-KEM parameter sets, and (d) the topology-derived key derivation protocol.



Timeline: After CIPO provisional patents are filed (P-01 through P-05) and before ePrint submission. The audit results inform both the patent claims and the academic publication.
