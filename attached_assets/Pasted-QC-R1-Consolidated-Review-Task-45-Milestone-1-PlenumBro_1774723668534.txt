Agent 1: Security Engineer
Finding 1
Finding ID: R1-A1-1
Section: Done looks like / Tasks §1
Severity: CRITICAL
Finding: The SpongeRekeyState in sponge_rekey.rs stores per-frame cryptographic keystream material in a Vec<u8>. When the vector is dropped or reallocated, the old buffer is freed but never zeroed. The BumpAllocator doesn't deallocate at all (leaked), and even a proper allocator would return the memory to the free list with keystream bytes intact. A subsequent allocation by any tab could read stale keystream material from the heap. This is a classic key-material-in-freed-memory vulnerability.
Recommendation: Implement Drop for SpongeRekeyState that zeroes the state vector before drop. Use core::ptr::write_volatile or a zeroize crate equivalent to prevent compiler elision. The plenum-std allocator should also support a SecureAllocator trait that zeroes on dealloc for all crypto-sensitive types.
Verification: After dropping a SpongeRekeyState, read the memory region that contained the state vector and confirm all bytes are zero.
Finding 2
Finding ID: R1-A1-2
Section: Done looks like / Tasks §2
Severity: CRITICAL
Finding: Boa v0.21's GC uses std::thread::LocalKey for per-thread root sets. The spec maps this to kernel task-local storage (TLS) via per-ProcessDescriptor storage slots. However, the spec does not define isolation guarantees for task-local storage. In a same-address-space model (no separate page tables), if one tab's kernel task can enumerate another task's TLS block (e.g., via PID iteration on the ProcessTable), it can read GC root pointers — which point into the other tab's heap. Combined with the lack of ASLR in the kernel's flat memory model, this is a cross-tab information leak.
Recommendation: Task-local storage must be access-controlled: only the owning task (matching current PID from scheduler) can access its TLS block. The ProcessTable API must not expose other tasks' TLS. Add a test that attempts cross-task TLS access and confirms it returns an error.
Verification: Write a kernel test where Task A stores a value in TLS, then Task B attempts to read Task A's TLS slot — must fail with PermissionDenied.
Finding 3
Finding ID: R1-A1-3
Section: Done looks like / Tasks §1
Severity: IMPORTANT
Finding: The plenum-std std::sync::Mutex<T> wraps the kernel's ticket spinlock (sync/spinlock.rs). Ticket spinlocks guarantee fairness but not priority inheritance. If a low-priority background tab holds a shared mutex (e.g., the global font cache lock) and a high-priority foreground tab blocks on it, the high-priority tab spins until the low-priority tab is scheduled — classic priority inversion. With 20+ tabs and a single-core QEMU setup, this could starve the foreground tab.
Recommendation: Document this as a known Phase 1 limitation. For Phase 2, implement priority inheritance or switch shared resources (font cache) to lock-free data structures. In the meantime, ensure the font cache lock is held for minimal duration (lookup only, not rasterization).
Verification: Stress test with 20 tabs contending on the font cache; measure foreground tab frame latency.
Finding 4
Finding ID: R1-A1-4
Section: Done looks like
Severity: IMPORTANT
Finding: Tab isolation uses "same-address-space isolation with hardware-assisted bounds checking" via guard pages (4KB). A guard page catches stack overflow and heap overrun at page-fault granularity, but a wild pointer that skips over the guard page (e.g., a buffer indexed at base + 8192) lands in the adjacent tab's memory without triggering a fault. The spec acknowledges this model but does not quantify the risk or define mitigations.
Recommendation: Document the guard-page bypass risk as a known limitation. Consider multi-page guard zones (e.g., 64KB) to reduce skip probability. For Phase 2, evaluate separate page table entries per tab (heavyweight but provably isolated).
Verification: Write a test that attempts to access guard_page_high + GUARD_PAGE_SIZE + 1 from a tab and confirm the behavior (should fault if guard zone is extended, silently succeeds with current 4KB guard).
Finding 5
Finding ID: R1-A1-5
Section: Done looks like
Severity: IMPORTANT
Finding: The cooperative watchdog for Boa relies on should_terminate being checked "between bytecode instructions." This works for JS bytecode but not for native host functions registered in the Boa context (DOM operations, layout recalculation, font rasterization). A host function that enters an unexpectedly long computation (e.g., rasterizing a complex SVG via resvg) will not check should_terminate until it returns to the bytecode interpreter. The spec does not define a secondary watchdog mechanism (e.g., timer interrupt) for host function hangs.
Recommendation: Add a hardware timer interrupt watchdog (separate from the cooperative one) that fires after MAX_BUDGET_MS and forcibly terminates the tab's kernel task. This is the last-resort mechanism. Document the two-tier watchdog: cooperative (soft, checks between instructions) and preemptive (hard, timer interrupt kills the task).
Verification: Register a Boa host function that sleeps for 60 seconds. Verify the tab is terminated within MAX_BUDGET_MS + tolerance.
Finding 6
Finding ID: R1-A1-6
Section: Out of scope
Severity: MINOR
Finding: The spec notes "embedded content only (plenum://home, plenum://settings, plenum://about)" and defers external HTTP fetch to Phase 1.5. However, there is no threat model boundary documented for plenum:// content. Since the content is embedded in the kernel binary, it is trusted by construction — but the spec does not state this explicitly. If a future phase adds dynamic content loading, the trust model changes fundamentally.
Recommendation: Add a single sentence to the spec: "All plenum:// content is embedded in the kernel binary at compile time and is trusted by construction. Dynamic content loading in future phases requires a separate threat model review."
Verification: Confirm no code path in the browser fetches content from outside the kernel binary.
Summary Verdict: FAIL
Two CRITICAL findings (R1-A1-1: keystream material in freed memory; R1-A1-2: cross-tab TLS information leak). Both are exploitable in the current same-address-space isolation model. The keystream leak is straightforward to fix (zeroing on drop). The TLS isolation requires access-control enforcement on the ProcessTable API. Neither is architecturally difficult but both must be resolved before implementation proceeds.

Agent 3: PlenumNET Integration Specialist
Finding 1
Finding ID: R1-A3-1
Section: Tasks §1 / Relevant files
Severity: CRITICAL
Finding: The spec lists src/kernel/src/memory/heap.rs as a relevant file and says "upgrade to linked-list or buddy allocator" as part of Task §1 (sysroot validation). However, the allocator upgrade is buried inside the sysroot work — it should be a prerequisite, not a sub-step. The current allocator (BumpAllocator in main.rs:19-44) has unsafe fn dealloc(&self, _ptr: *mut u8, _layout: Layout) {} — it literally does nothing on dealloc. Every Vec::drop(), String::drop(), Box::drop() is a no-op memory leak. html5ever's tree builder creates and destroys thousands of temporary nodes during parsing. Boa's GC cycle frees objects. Taffy's layout pass allocates work queues. All of these will silently leak until the 1MB heap is exhausted, at which point the allocator returns null and the kernel panics. This is not a "fix during sysroot work" issue — it blocks all eight crates from functioning at all.
Recommendation: Make the allocator upgrade Task §0 — a prerequisite that must be completed and verified before any sysroot or crate integration work begins. The new allocator must pass: (1) alloc/dealloc cycle test (allocate 10,000 objects, free all, allocate again — must not OOM), (2) fragmentation test (random-sized alloc/free for 1M cycles), (3) thread-safety test (concurrent alloc/free from multiple kernel tasks).
Verification: cargo test for the allocator module passes all three tests. The heap size is configurable and defaults to at least 64MB for browser workloads.
Finding 2
Finding ID: R1-A3-2
Section: Done looks like
Severity: IMPORTANT
Finding: sponge_rekey.rs implements the TLSponge-385 per-frame rekey as 729 bytes XOR'd in binary. The TLSponge-385 specification defines a 729-trit state with GF(3) operations (ternary addition, chi permutation, iota constants). The current implementation stores bytes (Vec<u8>) and performs binary XOR — this is not TLSponge-385, it is a binary stream cipher that uses 729 as a magic number. INVARIANT 8 states: "No raw binary integers may enter sponge absorb. All inputs must be properly encoded (Rep A/B/C trit encoding)." The sponge state itself must be in trit representation. Crypto Status: INCORRECT.
Recommendation: The sponge rekey must use the actual TLSponge-385 implementation from ternary-math/src/sponge385.rs (or the kernel's crypto/sponge.rs). The state must be 729 trits in Rep A encoding. The keystream must be generated by squeezing the sponge and converting trits to bytes for the XOR pass. Do not reimplement the sponge — call the existing one.
Verification: Verify the rekey state matches a known TLSponge-385 test vector after N rounds. Verify the keystream bytes match the same test vector's squeeze output converted to bytes.
Finding 3
Finding ID: R1-A3-3
Section: Done looks like
Severity: IMPORTANT
Finding: The spec describes "CPU sponge encryption — per-frame TLSponge-385 rekey, in-place XOR on simplefb framebuffer." This is confidentiality-only encryption with no integrity protection. It is not T-AE-MAC (which provides IND-CPA + INT-CTXT). A framebuffer attacker (DMA, physical memory access, or a breached tab that writes to the framebuffer region) can flip arbitrary pixels without detection. The spec does not mention authentication tags, MACs, or integrity checks for the encrypted framebuffer. Crypto Status: INCORRECT — the spec claims TLSponge-385 encryption but implements unauthenticated XOR.
Recommendation: Either: (a) upgrade to T-AE-MAC for authenticated encryption of the framebuffer (adds ~2KB per frame for the authentication tag, negligible at 1080p), or (b) document this as a known Phase 1 limitation with an explicit threat model statement: "Phase 1 framebuffer encryption provides confidentiality only. Integrity protection via T-AE-MAC is deferred to Phase 2. The threat model assumes the framebuffer memory region is not writable by untrusted code in Phase 1."
Verification: If (a): verify authentication tag is generated and checked per frame. If (b): verify the threat model statement is in the spec.
