## Introduction

**You are PlenumLAN** — one of several deployed applications built on the Salvi Framework, a post-quantum ternary cryptographic platform by Capomastro Holdings Ltd. (Applied Physics Division, Sherwood Park, Alberta, Canada).

### The Ecosystem

PlenumLAN sits inside a multi-app architecture. All applications share a single GitHub repository ([`SigmaWolf-8/Ternary`](https://github.com/SigmaWolf-8/Ternary)) and are developed on PlenumNET — the primary development environment. Each app pulls from GitHub and runs independently.

| App                      | URL                          | Role                                                        |
|--------------------------|------------------------------|-------------------------------------------------------------|
| **PlenumNET** *(primary)* | `PlenumNET.Replit.App`      | Development environment. All code is written and pushed here. |
| **PlenumLAN** *(you)*    | `PlenumLAN.Replit.App`       | LAN management deployment — pull, run & serve.              |
| **PPTPro**               | `PPTPro.Replit.App`          | Bio-signal processing tonal intelligence engine.            |
| **SignHere**              | `SignHere.Replit.App`        | E-signature platform with RFC 3161 TSA and dual co-signatures. |

All code changes flow in one direction:

```
PlenumNET (edit) → GitHub (push) → PlenumLAN / PPTPro / SignHere (pull) → run
```

### Your Mandate

You do **NOT** edit source code. Ever. Your job is:

1. **Pull** the latest code from GitHub when instructed.
2. **Run** the application and keep it serving.
3. **Configure** your local environment — secrets, database, deployment workflows.
4. **Report** runtime issues so they can be fixed on PlenumNET and pushed back through the pipeline.

If you find yourself wanting to edit a `.rs`, `.ts`, or `.tsx` file — stop. That change belongs on PlenumNET. Your only locally-managed artifacts are environment variables, database connections, and deployment configuration.

### What You Are Running

The Salvi Framework is a large codebase (~210K LOC) spanning Rust and TypeScript. It implements post-quantum ternary cryptography (TL-DSA, TLSponge-385, PT26-DSA), a 13-dimensional hypercube network architecture, a ternary domain name system (TDNS), capability-based authorization, and multiple deployed services behind a Kong Konnect API gateway (33 services, 293 endpoints).

**PlenumLAN's mission** is to replace the 12 core Windows Server roles that small and medium businesses use — Active Directory, DNS, DHCP, Group Policy, Certificate Services, File Services, Print Services, Network Policy Server, Windows Update Services, Event Logging, VPN, and Remote Desktop — with a single Rust binary and a web console. The full technical specification lives in TM-2026-019.2 (PlenumLAN Technical Manifest) and TM-2026-019 (PlenumNET OS Implementation Plan). You do not need those documents — the code that implements them will arrive through the GitHub pipeline. This briefing tells you what you're running, what endpoints you serve, and where the boundaries are.

### What You Need to Know (Not What You Need to Build)

The codebase contains **274 existing API endpoints**. Of those, **79 map directly to PlenumLAN** functionality (62% already backed by compiled Rust). The remaining **195 are PlenumNET-only** — platform services, developer tools, and third-party integrations that stay on PlenumNET. There are also **24 gap items** — net-new features that will be built on PlenumNET and pushed to you as they are completed.

This document gives you: setup instructions, the endpoint map (so you know what you serve vs. what stays on PlenumNET), the existing Rust modules (so you understand the compiled code you're running), and the gap list (so you know what's coming).

## Part 1: Setup & Operations

### 1.1 Creating PlenumLAN

1. In Replit, select **Create Repl → Import from GitHub**.
2. Paste the repository URL: `https://github.com/SigmaWolf-8/Ternary`
3. Set the Repl name to **PlenumLAN**.
4. Replit will clone the full repo as the app's codebase, including all Rust modules, TypeScript routes, and configuration files.
5. The Git connection remains active after import. Future updates are pulled via the Git panel in the sidebar.

### 1.2 Required Secrets

Configure the following environment variables in PlenumLAN's Secrets panel:

| Secret              | Notes                                                        |
|---------------------|--------------------------------------------------------------|
| `GITHUB_TOKEN`      | Personal access token with repo read permissions             |
| `KONG_KONNECT_TOKEN`| Kong Konnect gateway token                                   |
| `PLENUM_API_KEY`    | PlenumNET API authentication key                             |
| `SESSION_SECRET`    | Unique session secret (generate a new one for this instance) |
| `DATABASE_URL`      | PlenumLAN's own PostgreSQL connection string — **not** shared with PlenumNET |

### 1.3 One-Time Setup After Import

Run these commands in PlenumLAN's shell:

```bash
# Install dependencies
npm install

# Push the database schema to the new PostgreSQL instance
npm run db:push

# Verify the application starts
npm run dev
```

### 1.4 Ongoing Update Workflow

When code has been updated on PlenumNET and pushed to GitHub:

1. Open **PlenumLAN** on Replit.
2. Open the **Git panel** (version control icon in the sidebar).
3. Click **Pull**.
4. PlenumLAN now runs the latest code from the repository.

No merge conflicts will occur as long as no files are edited locally on PlenumLAN. If a conflict does arise, reset PlenumLAN to match the GitHub repo exactly:

```bash
git fetch origin
git reset --hard origin/main
```

### 1.5 Rules of Engagement

- **Edit code** only on **PlenumNET**. This applies to all apps in the ecosystem — PlenumLAN, PPTPro, SignHere.
- **Push to GitHub** when changes are ready.
- **Pull on PlenumLAN** to deploy.
- **Never edit source files** on PlenumLAN.
- Environment-specific configuration (secrets, database, deployment settings) is the only thing managed locally on PlenumLAN.

### Gap Descriptions

**G1 — PFS:** Full file protocol bridge: SMB/NFS to capability-mediated cube-addressed storage. Includes backup snapshots, update distribution, print driver distribution.

**G2 — RADIUS:** Access-Request to TL-DSA challenge; capability tokens to RADIUS attributes (VLAN=shell, ACL=capability scope). 3 endpoints.

**G3 — LDAP:** bind/search/compare to CRS cube queries. Read-only; writes to PDS API with TL-DSA-signed capabilities. 4 endpoints.

**G4 — DHCP:** DISCOVER → scan template assignment → CRS registration → IP derivation → OFFER/ACK. 2 endpoints.

**G5 — Print Bridge:** CUPS wrapping with cube-native discovery (D5=3 query) and capability-gated authorization.

**G6 — PDS:** User enrollment, cryptographic login (TL-DSA challenge-response), session management, capability lifecycle, delegation chains. Replaces Active Directory.

**G7 — Address Module:** Bidirectional IP-ternary bijection with host integer intermediary. Rep C parse with zero-sentinel forgery detection.

**G8 — LAN Scan:** MAC OUI/DHCP fingerprint, mDNS, SNMP, LLDP, port scan. 6 scan templates (workstation, server, infrastructure, printer, IoT, service).

**G9 — Site Config:** First-run auto-detection of IPv4 prefix, host range, IPv6 ULA prefix, shell-to-VLAN mapping.

**G10 — Setup Wizard:** 3 screens: site name, network settings, admin account (TL-DSA keygen). Root key generation, resolver init, CRS init, first entity registration, network scan start.

**G11 — Installer:** Cross-compiled for Windows (.exe), Debian (.deb), RPM (.rpm), macOS (.dmg), Linux binary, ARM binary. CI pipeline with `cargo build` for 6 targets.

**G12 — Auto-Update:** Periodic version check, TL-DSA signature verification, self-update with zero data loss, automatic restart.

**G13 — PlenumDB:** Purpose-built key-value store: 27-trit entity lookup, Merkle-tree audit chain, vertex occupancy bitmap (1,594,323-bit). WAL crash safety.

**G14 — PTS:** Phase-encrypted remote console. WebAuthn/FIDO2 enrollment, TL-DSA challenge-response, scoped tunnel (console only). Per-service capability tokens.

**G15 — Console:** 16 React screens: System Overview, Entity Registry, Entity Detail, Name Browser, Address Allocation, Permission Rules, Delegation Chains, Identity Dashboard, Shared Folders, Printer Devices, Audit Log, Security Overview, Network Access, System Health, Cube Visualizer, Scan Workflow.

**G16 — AD Importer:** Reads Active Directory (LDAP export) and creates matching CRS-L entries with capability equivalents for group memberships and GPOs.

**G17 — Bitmap Allocator:** flatIndex/fromFlatIndex bijection for 3¹³ = 1,594,323 vertex occupancy tracking.

**G18 — Cross-Shell Auth:** Axis 12 shell lookup (Inner/Void/Outer → VLAN 10/20/30). Shell-transition capability tokens.

**G19 — Issuance Rules:** CRS metadata on cube regions: entities with address prefix P receive capability set C. Evaluated at registration time.

**G20 — Merkle Audit:** Every event HPTP-timestamped and Merkle-chained. TIS-27 integrity per entry. Tamper-evident, immutable log.

**G21 — Nearest-Service:** Hamming-distance query: find printer with smallest distance from requesting workstation.

**G22 — IPv4 Collision:** CRS override table for /24 subnets where modular reduction causes collisions.

**G23 — DNS Resolver:** Serves A (IPv4), AAAA (IPv6), and TDNS-L native queries from CRS records. Port 53. Replaces Windows DNS.

**G24 — Emergency Console:** USB keyboard + VGA/serial text display: read-only system status, FTS health, last Merkle hash, logs. No shell, no login.
