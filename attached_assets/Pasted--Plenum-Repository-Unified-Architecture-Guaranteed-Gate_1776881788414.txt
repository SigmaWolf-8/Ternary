## 6. Wavefront Witnesses

Witnesses do not form a central Merkle chain. They propagate as a **wavefront** over the Z₂₇ × Z₂₈ lattice.

### 6.1 Emission and Propagation

- Each write event occurs at a unique spacetime coordinate: `(HPTP_femtosecond, TDNS_position)`.
- The gatekeeper emits a witness at that coordinate.
- The witness propagates outward along deterministic paths (the same Hamiltonian cycles that define the coprime walk) to neighboring cells.
- Each cell maintains the latest witness it has received for each source ring.

### 6.2 Audit by Conservation

The witness field satisfies a continuity equation:

\[
\frac{\partial \rho}{\partial t} + \nabla \cdot \mathbf{J} = 0
\]

where:
- \(\rho\) is witness density (number of witnesses per cell),
- \(\mathbf{J}\) is witness current (propagation along lattice edges).

Audit is local: a cell verifies that the witnesses it has received from a given source are consistent with the wavefront arrival times predicted by its neighbors. Divergence indicates tampering or propagation failure.

**Verification:** "Did this witness arrive on the expected wavefront from its source?" — computable from neighbor states, globally consistent by the lattice topology.

### 6.3 Storage

Witnesses are stored in `.witness/` sharded by the source's TDNS position and HPTP timestamp. No global chain head.

## 9. Native Trit Query Engine (`plenum-quaerito`)

The repository includes a query engine that evaluates **Trit Query Algebra (TQA)** expressions directly on the lattice.

### 9.1 Trit Query Algebra — Five Primitives

| Operator | Description |
|:---|:---|
| `ANCHOR(handle)` | Start walk at the document with given MDNS. |
| `WALK(steps, rule)` | Move along the lattice according to coprime walk or reading order. |
| `RING(k)` | Expand to all documents within `k` rings of current position. |
| `HAMMING(tolerance)` | Filter by Hamming distance from anchor's Ω28 vector. |
| `FK(mode)` | Follow FK references of specified mode. |

Queries are composed left‑to‑right. Example:

```
ANCHOR(@my_doc) → WALK(reading) → RING(2) → HAMMING(3)
```

"Starting at my document, walk in reading order, expand to 2 rings, keep only documents within Hamming distance 3 of my classification."

### 9.2 Execution and Caching

- The engine resolves queries by walking the filesystem and extended attributes.
- Materialized views are stored in `.cache/` keyed by `(anchor_mdns, rule_hash)`.
- Caches are invalidated **ring‑locally**: when a document changes, only caches whose anchor lies within the affected ring are invalidated.
- The engine runs as a daemon (`plenum-quaerito`) serving a lightweight wire protocol carrying TQA ASTs as TritInt.

### 9.3 QARBAS — Continuous Incremental Maintenance

Frequent queries are maintained incrementally by the gatekeeper. When a document is added/modified, the gatekeeper updates the `.cache/` entries for all queries that depend on its ring. Staleness is bounded by wavefront propagation delay, not structurally impossible—but practically fresh.

## 10. Encryption and Key Exchange

### 10.1 Framework‑Native Cryptographic Primitives

| Primitive | Purpose | Parameters |
|:---|:---|:---|
| **TIS‑27** | Hash function | 54‑trit output, 4 rounds, stride 13 |
| **TLSponge‑385** | AEAD, KDF | 729‑trit state, 9 rounds |
| **TL‑DSA** | Signatures | 87‑trit signatures, NIST Level‑5 equivalent |
| **TL‑KEM** | Key encapsulation (post‑quantum) | Lattice‑based, ternary‑native |

### 10.2 Encryption at Rest

Every file is individually encrypted:

1. Plaintext is stored in **TritInt packed format** (5 trits per byte)—this is the compression.
2. A file encryption key (FEK) is derived: `FEK = TLSponge‑385::derive(MDNS, salt)`. Salt is a random 27‑trit nonce stored in `user.mdts.salt`.
3. Packed plaintext is encrypted with **TLSponge‑385 AEAD**. Ciphertext is written to disk.
4. FEK is wrapped with the repository master key (held by Ninja Exec) and stored in `user.mdts.fek`.

**Encryption Gate:** Gatekeeper verifies presence of wrapped FEK, unwraps via Ninja Exec, and verifies AEAD tag. Failure → quarantine.

### 10.3 Encryption in Transit

All inter‑component communication uses **PlenumLAN secure channels**:

- Mutual authentication via **TDNS‑bound certificates** (see §10.4).
- Key exchange via **TL‑KEM**.
- AEAD encryption of all messages using ephemeral keys derived from the KEM shared secret.

### 10.4 TDNS‑Bound Certificates (No CA)

Certificates are **not** X.509. A certificate is:

- The 27‑trit TDNS address of the peer.
- A TL‑DSA public key.
- A signature over (TDNS, public_key) by a TLSponge‑385 key derived from the peer's **Inter‑Cube topology position**.

Trust is established by verifying that the signing key matches the topological position claimed by the TDNS address. No root CA. No expiry. Trust derives from geometry.

## 13. Quarantine and Wavefront Re‑Evaluation

Files that fail **deferrable** invariants (due to ArcCompTriadis unavailability) or that are placed in quarantine for other reasons are **re‑evaluated on each wavefront pass**.

- No TTL. The wavefront itself is the scheduler.
- When the wavefront crosses the cell containing a quarantined file, the gatekeeper re‑runs validation.
- If validation passes, the file is released to its intended path.
- If a file remains in quarantine for N consecutive wavefront passes (configurable), it is dissolved (deleted).

## 14. Co‑Location by Wavefront on Disk

Files are stored in **extents** ordered by their wavefront arrival time at each ring.

- Adjacent writes in wave‑time land in adjacent extents.
- Walk queries become sequential reads instead of random seeks.
- The lattice geometry drives storage layout; storage layout serves the lattice.

Implementation: each ring maintains a write‑ahead log of extents. The gatekeeper appends new files to the current extent; when full, a new extent is created.

## 15. Operational Flow — A File's Journey

1. **Creation:** Application writes document to the path derived from its Ω28 vector.
2. **Gatekeeper intercepts:** Filesystem event triggers `plenum-gatekeeper`.
3. **Fast‑path checks:** Zero‑exclusion, signature presence, legal header schema, FP₂₈ match.
4. **ArcCompTriadis calls:** For heavy invariants, call the appropriate daemon. If unavailable, mark deferred.
5. **FK point‑to‑point validation:** Verify `fk_identity` and `fk_fp28` targets exist.
6. **Encryption & packing:** Apply TritInt packing and TLSponge‑385 AEAD (if not already done).
7. **Witness emission:** Emit receipt witness at `(HPTP_now, TDNS_position)`. Propagate wavefront.
8. **Quarantine:** On block or defer, move to `.quarantine/`, emit violation/deferred witness.
9. **Cache update:** Gatekeeper invalidates affected ring caches.
