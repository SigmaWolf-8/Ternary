The fundamental problem TM-2026-013 identified honestly: the key is derived from public inputs. Anyone who knows both addresses can compute the tunnel key. That's not key agreement — it's a deterministic PSK from public data.
The fix uses primitives you already have. Here's the upgrade path:
The geometry determines WHO connects to whom. TL-KEM determines the actual key material. These are separate concerns and should be separated in the construction.
Right now: TIS-27(context ‖ addr_a ‖ addr_b) → 256-bit key. All public inputs. No secret.
Proposed upgrade — three layers:
Layer 1: Neighbor determination (geometry, unchanged). The 13D hypercube still determines which nodes are adjacent. Hamming distance still equals hop count. The routing is still geometric. This is the novel part and it stays.
Layer 2: TL-KEM key exchange during CRS registration. When a node registers with CRS, it generates a TL-KEM public key and publishes it. When two adjacent nodes establish a tunnel, each fetches the other's TL-KEM public key from CRS and performs encapsulation. The shared secret from TL-KEM is now a computationally secret value — you can't derive it from addresses alone. This gives you real IND-CCA2 key secrecy inherited from TL-KEM.
Layer 3: Topology-bound KDF composition. The tunnel key becomes:
TLSponge-385(context ‖ addr_a ‖ addr_b ‖ TL-KEM_shared_secret ‖ epoch)
The topology binding (addresses) is still there — you can't use a key derived for edge (A, B) on edge (A, C). But the secrecy comes from the TL-KEM shared secret, not from the addresses. The epoch counter enables key rotation without re-exchanging TL-KEM (hash ratchet), and periodic TL-KEM refresh gives forward secrecy.
