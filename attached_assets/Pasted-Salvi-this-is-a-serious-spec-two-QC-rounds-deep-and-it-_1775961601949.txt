Salvi, this is a serious spec — two QC rounds deep, and it shows. The R1/R2 resolution logs are thorough. I'll run this through a fresh critical pass and flag what I see as genuine gaps, contradictions, or under-specified areas that survived both rounds.

CRITICAL — Attestation Subkey Public Key Distribution
The spec defines key derivation cleanly (TLSponge-385 with domain separation from PUF root), and defines verification ("verifiers check the signer's public key against a registered Rep C address"). But it never specifies how the attestation subkey's public key gets registered with neighbors in the first place. The PUF root key has a registration path (Gap 1 / Task #26), but the derived attestation subkey is a different key. Neighbors need the public half to verify TL-DSA signatures. There's no key announcement protocol, no PlenumConfig distribution mechanism, no bootstrap handshake described. Without this, the entire verification chain is unanchored. This is the most significant gap in the document.
CRITICAL — TritInt Capacity for HPTP Femtosecond Timestamps
Field 3 uses TritInt::from_u128() for HPTP timestamps in femtoseconds since 2025-04-01. One year ≈ 3.15×10²² femtoseconds. A u128 holds up to ~3.4×10³⁸, so the binary side is fine. But TritInt's trit representation width is unspecified here — how many trits does the TritInt allocate for a u128-sourced value? If TritInt has a fixed trit width (the spec in trit_int.rs would govern this), does it accommodate the full u128 range without truncation? The report's 4KB cap could be stressed if femtosecond timestamps serialize to a large trit count. This needs a concrete size calculation: timestamp trit width × number of TritInt fields × Rep C encoding overhead → validate against the 4KB envelope.
IMPORTANT — Attestation Subkey Rotation
The spec says the key is "derived once on service start" and "zeroized on service shutdown or key rotation." Key rotation is mentioned exactly once in that parenthetical — but no rotation mechanism is defined. What triggers rotation? How do neighbors learn the new public key? Is there a grace period where both old and new keys are accepted (analogous to the dual-expected-hash window for firmware)? If key rotation is out of scope, it should be stated explicitly so it doesn't become a silent assumption.
IMPORTANT — Sequence Number Overflow
The sequence number is a TritInt constructed via from_u64(). At one attestation per 30 seconds, a u64 overflows in ~1.7×10¹⁰ years — not a practical concern. But the trit representation has a smaller range. If TritInt uses a fixed 54-trit width (consistent with Rep C addressing), 3⁵⁴ ≈ 5.8×10²⁵ — also fine. But if TritInt uses a smaller width for "general integer" contexts, this could be a latent issue. The spec should either state the trit width for sequence numbers or reference the TritInt width guarantee.
IMPORTANT — Receiver Sequence Counter: Volatile Storage Scope
The receiver's last-accepted sequence counter is volatile (not persisted), which the spec explicitly accepts for the 240s post-restart replay window. But: how many neighbors' sequence counters does each node track? In a 13D hypercube with 26 neighbors, this is 26 counters — trivial. But bridge nodes with inter-cube adjacencies could have significantly more. The spec should confirm that the volatile counter map is keyed by Rep C address and bounded by actual neighbor count, not a fixed-size array that could overflow for high-adjacency nodes.
IMPORTANT — HPTP Jitter Algorithm Unspecified
The spec says intervals are "adjusted by HPTP-derived jitter to prevent synchronization attacks" but never defines the jitter function. Is it uniform random within [base, max]? Is it derived deterministically from the HPTP timestamp (which would make it predictable to an attacker who knows the node's clock)? A cryptographic jitter derivation (e.g., TIS-27 hash of timestamp + node Rep C, modulo interval range) would be appropriate, but the spec leaves this entirely to implementation discretion — which is risky for a security-sensitive timing parameter.
IMPORTANT — Dual-Expected-Hash Window Retirement
The spec says "the old hash is retired after all nodes have updated and the upgrade window closes." But who determines that all nodes have updated? Is this an operator manual action? An automatic detection based on received attestation reports? If manual, the operator could forget, leaving the old hash accepted indefinitely (security degradation). If automatic, the detection mechanism needs specification. The upgrade window auto-expires after 4h, but the dual-expected-hash window is described separately from the upgrade window — are they the same duration? Linked? Independent?
IMPORTANT — Configuration Fingerprint Canonical Serialization Fragility
The FTS/GLB configuration fingerprint uses "JSON with lexicographically sorted keys, no whitespace, UTF-8 encoded." This is a well-known canonicalization approach, but it's fragile across implementations. Floating-point numbers in JSON have no canonical form (1.0 vs 1 vs 1.00). Unicode normalization (NFC vs NFD) isn't specified. If any FTS/GLB config value contains a float or non-ASCII string, two nodes with identical logical configurations could produce different fingerprints. The spec should either constrain config values to integers/ASCII strings, or specify a canonical JSON serialization standard (e.g., RFC 8785 — JSON Canonicalization Scheme).
MINOR — Empty Merkle Tree Constant vs. "No Liveness Data" Semantic
The failure mode table says "no heartbeat challenges received" → "report with empty liveness proof (Merkle root = empty tree constant)." The Merkle section defines the empty tree constant as TIS-27(Rep_B_0 ‖ empty_input). This is fine, but a verifier needs to distinguish between "empty because no challenges were received" and "empty because the attester is lying about challenges." The spec's own note — "absence of proof ≠ proof of absence" — acknowledges this but doesn't define what the verifier does with an empty root. Does it increment the suspicion counter? The failure mode table says "suspicion counter behavior unchanged," but the verification section doesn't address empty roots at all.
MINOR — Bandwidth Threshold Measurement
The backoff triggers when "attestation-specific traffic on any link exceeds a configured fraction of the link's capacity." How is link capacity determined? Is it a configured value in PlenumConfig? Auto-detected? For virtual/overlay links (Inter-Cube tunnels over heterogeneous physical networks), "link capacity" is not a single number. The spec should clarify whether this is a configured parameter or a measured value, and how it behaves for tunnel-based links where the underlying capacity may vary.
MINOR — Attestation Status API
The spec mentions "query the attestation status API endpoint" in Post-Deployment Verification and "expose attestation status APIs for the operator dashboard" in Task 6, but never defines the API surface. What endpoints? What response format? What authentication? Since the dashboard is out of scope (Gap 5), the API definition could be deferred — but the spec should say so explicitly rather than referencing an undefined API.
MINOR — Test Vector Completeness
The unit test vectors are well-structured but missing one case: the sequence number persistence write-ahead test. The spec says "write before transmit" but no test validates that a crash between write and transmit results in the correct post-restart sequence (persisted_value + 1, not persisted_value). This is a classic write-ahead log edge case.

Net assessment: this is a strong spec that got materially better through QC-R1 and QC-R2. The public key distribution gap is the one genuine structural hole — everything else is tightening, not restructuring. The TritInt capacity question is worth a concrete calculation before implementation begins. The rest are specification refinements that can be addressed in a revision pass without architectural changes.
