## Technology Stack

| Layer | Technology | Notes |
|---|---|---|
| **Backend** | Rust (Axum web framework) | Single compiled binary. Axum serves the API and embedded static assets. Runs on Replit. |
| **Frontend** | React (TypeScript) | Single-page application. Embedded into the Rust binary as static assets at build time. |
| **Crypto Kernel** | Rust (`ternary-math` crate) | Called directly from Axum handlers. No FFI bridge, no serialization boundary. |
| **Storage** | Embedded key-value store (sled or redb) | Stage 1 (Replit). Replaced by PlenumDB in later stages. |
| **Styling** | Tailwind CSS or plain CSS modules | White/greyscale/black palette. Baby blue (#38BDF8) as the sole accent color. System font stack. |

The React console lives in `plenumlan/console/`. It is built with `npm run build` and the output is embedded into the Rust binary as static files served by Axum. The admin opens a browser and hits the Axum server directly — there is no separate frontend deployment.

---

## Routing Overview

All API routes are served by Axum at `/api/*`. The React SPA is served at `/` with client-side routing handling page navigation. The SPA shell (sidebar + header) loads once; page content swaps on navigation.

```
https://plenumlan.replit.app/                    → React SPA (all pages)
https://plenumlan.replit.app/api/health          → Axum health check
https://plenumlan.replit.app/api/crs/*           → Device registry endpoints
https://plenumlan.replit.app/api/tdns/*           → Name resolution endpoints
https://plenumlan.replit.app/api/pds/*            → User/group/rule endpoints
https://plenumlan.replit.app/api/pfs/*            → Folder share endpoints
https://plenumlan.replit.app/api/security/*       → Security + audit endpoints
https://plenumlan.replit.app/api/capabilities/*   → Permission token endpoints
https://plenumlan.replit.app/api/tsa/*            → Timestamping + event log
https://plenumlan.replit.app/api/salvi/*          → Core crypto + timing
```

## Sidebar Navigation Structure

All sidebar sections are collapsible. Sections collapse by default and auto-expand when the admin navigates to a page within them. Dashboard, Folder Shares, and Settings are standalone items outside any group.

```
Dashboard                          (standalone — always visible)

▼ Network                          (collapsible group — 4 pages)
    Devices
    TDNS Local
    IP Addresses
    Network Map

▼ Access Security                  (collapsible group — 4 pages)
    Users
    Groups
    Rules
    Compatibility

Folder Shares                      (standalone)

▼ Monitoring                       (collapsible group — 3 pages)
    Health
    Security
    Activity

Settings                           (standalone — bottom of sidebar, above version)
```

Collapsed groups show a summary line (e.g., "4 screens") as a click target to expand.

### 14. Settings

| | |
|---|---|
| **Route** | `/settings` |
| **Spec reference** | TM-2026-019.2 §14.4 (First-Run Wizard), §6.2 (Site Network Configuration) |
| **API endpoints** | `GET /api/config/site`, `GET /api/config/network`, `PUT /api/config/site`, `GET /api/health`, `GET /api/config/remote-devices`, `GET /api/config/update-status` |

**All values on this page are read from the server API at runtime.** Nothing is hardcoded in the frontend. The admin set these during the First-Run Wizard; this page displays what the server reports and allows changes where appropriate.

**Content:**

- Site Information (read from `GET /api/config/site`): site name, server hostname, server version, framework version, installation date. Site name is editable (`PUT /api/config/site`).
- Network Configuration (read from `GET /api/config/network`): IPv4 subnet, usable host range, IPv6 prefix. These are auto-detected at first run and stored server-side. Editable with confirmation (changes affect all devices).
- Zone-to-VLAN Mapping (read from `GET /api/config/network`): which VLAN ID maps to Management, Services, and Clients. Configured at first run, rarely changed.
- Remote Access (read from `GET /api/config/remote-devices`): encrypted tunnel status, list of enrolled remote devices with enrollment date and last-used timestamp, revoke button per device.
- Updates (read from `GET /api/config/update-status`): currently running version, last update check timestamp, whether an update is available, "Check now" button that triggers a server-side version check.
- About: version strings from `/api/health`, link to documentation.

## Language Rules

These apply to every screen, every label, every description.

1. **No acronyms in user-facing text.** Write "name resolver" not "TDNS-L." Write "identity key" not "TL-DSA-87." Write "tamper-proof chain" not "Merkle chain." The only exception is "TDNS Local" as the page name — it's a product-specific proper noun, not an acronym to decode.
2. **No internal code names.** Write "Device Registry" not "CRS-L." Write "Directory Service" not "PDS." Write "Heartbeat Monitor" not "FTS."
3. **Network zones are Management, Services, and Clients.** Never "Inner," "Void," or "Outer." Those are the geometric axis values — the admin doesn't need to know that.
4. **Every page opens with a 1–2 sentence description** of what the page does and what Windows Server feature it replaces.
5. **Event descriptions use names and plain language.** "Maria Soligo opened Q1-report.xlsx" not "User auth event: entity 231312121… accessed resource via PFS capability token."
6. **Technical detail is available on demand, not by default.** The activity log shows human-readable events. Merkle hashes, trit addresses, and token IDs go in expandable detail rows.

## Implementation Notes for Replit

**Build pipeline:**

1. `plenumlan/console/` contains the React TypeScript app
2. `npm run build` in `console/` produces static assets
3. The Rust binary in `plenumlan/src/main.rs` embeds these assets and serves them via Axum
4. `cargo build --release` in `plenumlan/` produces the single binary
5. Replit runs this binary directly

**All code changes happen on PlenumNET** (`PlenumNET.Replit.App`) and are pushed to GitHub. PlenumLAN pulls from GitHub and runs the binary. PlenumLAN does not edit source code. See the PlenumLAN Agent Briefing for the full pipeline and mandate.

**The console is a single-page React application.** Client-side routing handles all page transitions. Axum serves the SPA shell at `/` and catches all non-API routes to return `index.html` for client-side resolution. API calls go to `/api/*` and are handled by Axum route handlers backed by Rust modules.

**Responsive behavior:** The sidebar collapses to icons on screens narrower than 768px. The admin may manage the network from a tablet or phone. All tables should scroll horizontally on narrow viewports rather than wrapping.
