## BLOCKING — TritInt Is Phase 0a, Not "Out of Scope"

The session summary says: **"NO u32 for repunit arithmetic — TritInt is unbounded."**

The architecture defines Phase 0a as `trit_int.rs` — the first thing built before anything else exists.

Every revision of Task #101 has deferred this into "Out of scope" with the justification "u32 covers R₁–R₆." This contradicts the session's explicit kill decision and the architecture's build order. The task keeps shipping a u32/u64 type system that was killed months ago.

TritInt is not optional. It is Phase 0a — the foundation everything else stands on. coprime.rs should not accept u64. Grid coordinates should not be u32. Constants should flow through TritInt. The casting gymnastics between u32 constants and u64 function signatures exist only because the proper type doesn't.

**Required fix:** Remove trit_int.rs from "Out of scope." Add it as Item 0a — Phase 0a, user builds, first file delivered. All downstream modules (coprime.rs, sparse.rs, grid.rs, cell.rs, preset.rs) use TritInt where they currently use u32/u64 for ternary arithmetic. u8 remains for raw trit values {0,1,2}. WASM boundary converts TritInt↔JsValue via serde.
