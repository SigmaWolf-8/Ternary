3.5 Array3: Formation, Port Addressing, and Node Identity
Three nodes. 81 slots = 3⁴. Each node owns a complete 3³ cube of 27 slots. The cube is 3 dimensions (plane, role, instance). The node_id is a GF(3) multiplier {0, 1, 2} that selects which node’s port range the slot lives in — it is NOT a 4th cube dimension. The cube stays 3D; the Array3 is 3 copies of it.

Port formula (Array3):

port = BASE_PORT + (node_id × 27) + (plane × 9) + (role × 3) + instance
Where BASE_PORT = 11111, all positional values are GF(3) {0, 1, 2}. A single node is Array3 with node_id = 0 and no peers — scalability is structural, not an upgrade.

Per-node port ranges:

Label	node_id (GF(3))	Port Range	Slots	Gateway Port
Node 1	0	11111–11137	0–26	11124 (offset +13)
Node 2	1	11138–11164	27–53	11151 (offset +40)
Node 3	2	11165–11191	54–80	11178 (offset +67)
Each node's gateway is at its own offset +13 (the center of its local 3³ cube). The Array3 has three gateways — one per node. The node with node_id = 0 is the primary gateway for external traffic; nodes 1 and 2 are HA replicas.

Node identity assignment:

CUBE_NODE_ID environment variable (values: 0, 1, or 2). Default = 0 (single-node mode). When CUBE_NODE_ID is set and CUBE_ARRAY3_PEERS lists the other nodes, the daemon operates in Array3 mode.

Future: auto-negotiation via the formation protocol. For Release 0.1, explicit configuration.

Array3 formation protocol:

Node boots with CUBE_NODE_ID=N and CUBE_ARRAY3_PEERS=ip1:port,ip2:port
Node binds its 27-port range: BASE_PORT + (N × 27) through BASE_PORT + (N × 27) + 26
Node connects to each peer via existing CUBE_PEER_PORT infrastructure
First handshake message includes: node_id, wire protocol version, port range, slot inventory (which slots are occupied), daemon version metadata
Peer validates: no node_id collision (reject if duplicate), wire protocol compatible (V3 accepts V2 during dual-acceptance), port ranges don't overlap
On successful handshake: peer mesh formed, slot-to-node routing table populated, failover candidates identified (same classification on different node = replica pair)
Slot-to-node routing:

The 3-trit (plane, role, instance) address maps to offset 0–26 within EACH node's 27-slot range. The slot address is the SAME across all three nodes — what differs is which node OWNS the registration. The CRS tracks slot→node ownership. A classification query returns the owning node_id alongside the slot address.

Two services with identical classifications on different nodes occupy the "same slot" (same plane, role, instance) but on different nodes. This IS the HA replica mechanism. The CRS knows both registrations and routes to the primary; on failure, traffic fails over to the replica on another node.

Single-node is the degenerate case:

CUBE_NODE_ID=0, no peers, ports 11111–11137. The exact same code path. The only difference: no peer mesh, no failover candidates. Adding a second node later = set its node_id to 1, point it at node 0, formation protocol runs, Array3 begins forming. No reinstallation. No reconfiguration of node 0.
