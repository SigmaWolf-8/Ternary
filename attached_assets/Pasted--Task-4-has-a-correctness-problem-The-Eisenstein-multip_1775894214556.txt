**Task 4 has a correctness problem.** The Eisenstein multiplication formula requires subtraction: `a₁a₂ − c₁c₂` and `a₁c₂ + a₂c₁ − c₁c₂`. TritInt is unsigned — `sub` panics when the result would be negative. For Eisenstein multiplication of arbitrary values, `a₁a₂ < c₁c₂` is entirely possible. Example: `(0 + 1·ω) × (0 + 1·ω) = −1 − ω` — the integer part is −1, which TritInt cannot hold.

This isn't an edge case. ω² = −1 − ω is the DEFINING RELATION of the algebra. The very first test you'd write (ω × ω = −1 − ω) panics on unsigned subtraction.

Three ways to handle this:

**Option A: Track sign separately inside mul_eisenstein.** Compute both `a₁a₂` and `c₁c₂`, compare, subtract the smaller from the larger, and return a `(TritInt, bool)` for each component where the bool is the sign. This means `mul_eisenstein` returns a signed result type, not a Trit.

**Option B: Defer mul_eisenstein to Phase 3 (Rep A).** Rep A is balanced ternary {−1, 0, +1} — it handles negative values natively. Implement mul_eisenstein once signed arithmetic exists. Phase 2 ships mul_golden and mul_scalar only.

**Option C: Use modular arithmetic.** If all Eisenstein operations happen mod some modulus (e.g., mod 3 for GF(3) closure), then subtraction wraps and never underflows. This matches how gf3_algebra.rs already works — `gf3_add` and `gf3_mul` operate mod 3. But then mul_eisenstein operates on individual trits (mod 3), not on multi-digit TritInts.

**My recommendation: Option B.** mul_eisenstein depends on signed arithmetic. Shipping it with unsigned TritInt will produce panic-prone code or a parallel sign-tracking system that duplicates what Rep A provides. The task should move mul_eisenstein and norm_eisenstein to Phase 3, and the "Out of scope" note about signed arithmetic should acknowledge this dependency explicitly.
