On proving the Ternary Hypercube Walk security:PT26-DSA's PQ claim actually rests on two things, and you've already proven one of them.What's already proven: The sponge. Every PT26-DSA operation ends with sponge.derive_key(PT26-BIND, ...). The binding hash is TLSponge-385 with 385-bit post-quantum security margin. A quantum computer running Grover's algorithm gets a square-root speedup on pre-image search — that takes 385 bits down to ~192 bits of quantum security, which is above the 128-bit threshold that NIST requires. The PQ claim for the hash layer is solid by the same argument that makes SPHINCS+ (hash-based NIST standard) post-quantum.What's not yet externally proven: The walk structure. The question is whether the 13D hypercube walk leaks information that lets an attacker forge signatures WITHOUT breaking the sponge. Specifically — can someone find two different walk schedules that produce the same binding output, or recover a walk schedule from the public commitment, using some shortcut that exploits the hypercube geometry?What you CAN test right now — and should:
Collision search on walk tokens. Generate 2²⁰ random walk schedules, compute their binding outputs, check for collisions. If the walk structure is sound, you should find zero. If it's broken, you'll find collisions faster than the birthday bound predicts.

Differential analysis on the walk. Take two walk schedules that differ in one step. Measure how many output bits change. Should be ~50% (avalanche). If changing one step only changes a few bits, the walk has weak diffusion.

Schedule recovery attack. Given a public commitment (the output), try to find ANY valid walk schedule that produces it. Brute-force search should be the only path. If you can narrow the search space using the geometric structure, that's a weakness.

Port distinguishability. Given a signature and the 26 possible destination ports, check whether the signature leaks which port was used. It shouldn't — the binding should look random regardless of destination.
These aren't theoretical exercises. They're concrete tests you can run on your hardware right now. I can write them as additions to the benchmark suite — they'd be security tests, not performance tests. Each one either passes (no weakness found) or fails (vulnerability discovered). A battery of passing security tests doesn't constitute a formal proof, but it's what every practical cryptosystem does before the formal proofs arrive.The path to full credibility is: run these tests internally, then publish the results alongside a formal security reduction (monograph TM-2026-XXX), then invite external review. That's exactly what NIST candidates did — Dilithium published their security proofs, then the community spent 6 years trying to break them.
