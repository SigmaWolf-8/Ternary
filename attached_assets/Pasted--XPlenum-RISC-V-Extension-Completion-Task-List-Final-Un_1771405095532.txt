## Executive Summary

This document enumerates all development tasks required to bring the XPlenum RISC-V custom extension from its current state — a complete, formally verified, standalone IP block — to a fully integrated and operational system. Every task listed below can be completed in simulated environments using standard development tools and AI-assisted engineering workflows.

Three items are explicitly excluded from this scope because they require physical-world interaction: FPGA board validation (loading the design onto physical silicon), physical True Random Number Generator characterisation (measuring actual hardware entropy), and FIPS 140-3 laboratory certification (formal evaluation by an accredited testing facility). These three activities become relevant only after every task in this document is complete.

The document is structured in two tiers:

**Tier 1 — Core Completion (Phases 1–7)**: The 42 tasks required to bring XPlenum from standalone IP block to a simulation-proven, kernel-integrated, fuzz-tested, documentation-ready system. Estimated effort: 60–78 person-days with AI-assisted workflows. Add 20–30% buffer for solo or small-team execution with learning curve on the selected core.

**Tier 2 — Beyond Defense-Grade (Phase 8)**: Five optional enhancement tracks that elevate XPlenum from defense-grade (FIPS 140-3 Level 3–4, EAL5–6 equivalent) into ultra-high-assurance / national security-grade territory (EAL7-level formal proofs, higher-order side-channel resistance, quantum-resistant cryptographic primitives, independent red-team validation, and Protection Profile targeting for national security systems). Estimated additional effort: 65–130 person-days plus external costs.

**Tier 1 Phases**:

**Phase 1** — RISC-V Core Selection and Preparation: Choose and prepare the target processor core for integration.

**Phase 2** — Hardware Integration: Wire XPlenum into the selected core's pipeline at the Register-Transfer Level.

**Phase 3** — Integrated Simulation and Verification: Validate the combined system through testbenches, formal proofs, power simulation, and benchmarks.

**Phase 4** — Deterministic Random Bit Generator Implementation: Replace the Linear Feedback Shift Register with a NIST-compliant algorithm.

**Phase 5** — Rust Kernel Integration: Build software interfaces so the Salvi Framework kernel can issue XPlenum instructions.

**Phase 6** — Emulation and System Validation: Boot and test the full system in a RISC-V emulator, including security fuzzing.

**Phase 7** — Documentation and Compliance Preparation: Produce the technical documentation and compliance paperwork.

**Tier 2 Phase**:

**Phase 8** — Beyond Defense-Grade Enhancements: Full-system formal verification, higher-order masking, quantum-resistant primitives, adversarial red-team validation, and national security Protection Profile targeting.

### Phase 1: RISC-V Core Selection & Preparation

**Goal**: Select and prepare a compatible open-source RISC-V core.
**Risk**: Pipeline mismatch could require XPlenum interface redesign. Mitigate by prioritising cores with extensible decode stages and standardised extension interfaces (CV-X-IF in CVA6 or RoCC in Rocket).
**Effort Estimate**: 5–7 person-days.
**Parallelism**: Phase 4 can begin after Task 1.1 completes.

**Core Selection Guidance (2026 Context)**: CVA6 (from OpenHW Group) is strongly recommended for this integration. It provides native CV-X-IF (CORE-V eXtension Interface) — a standardised coprocessor/extension interface designed specifically for adding custom instructions without deeply modifying the decode stage. Its 6-stage in-order pipeline is clean and well-documented, with active community maintenance and 2025–2026 releases targeting TRL 4–5. Rocket Chip remains an excellent alternative if generator-based configurability or the RoCC (Rocket Custom Coprocessor) interface is preferred for a tightly-coupled coprocessor approach. BOOM (out-of-order) is overkill for initial integration and harder to modify for custom decode. PicoRV32 is too minimal for 64-bit operation with complex extensions like capabilities and trit DSP.

### Phase 4: DRBG Implementation (LFSR Replacement)

**Goal**: Replace the pseudo-random LFSR with a NIST SP 800-90A compliant Deterministic Random Bit Generator, suitable for eventual FIPS 140-3 certification.
**Risk**: DRBG implementation errors could compromise all masking security. Mitigate with statistical validation, Known Answer Tests, and pre-verified AES core if available.
**Effort Estimate**: 9–11 person-days.
**Parallelism**: Can begin after Task 1.1. Independent of Phases 2–3 until integration merge at Gate 1.
**Algorithm Selection**: CTR_DRBG with AES-256 recommended for hardware efficiency and wide NIST acceptance. Hash_DRBG (SHA-512 based) is a viable fallback if AES IP licensing or availability is a concern in open-source flows — it avoids AES dependency at the cost of larger area and lower throughput.

## Phase 8: Beyond Defense-Grade

**Goal**: Elevate XPlenum from defense-grade assurance (FIPS 140-3 Level 3–4, EAL5–6 equivalent) into ultra-high-assurance territory suitable for national security systems, classified edge compute, secure bootstrap, or MILS (Multiple Independent Levels of Security) architectures.
**Prerequisite**: Gate 3 (all Tier 1 tasks complete).
**Risk**: Scope creep, high external costs, and limited availability of formal verification expertise. Mitigate by treating each track as independently scoped and budgeted — pursue only those tracks justified by the target deployment environment's threat model.
**Total Effort Estimate**: 65–130 person-days plus external costs ($50K–$200K+ for independent red-team and certification lab fees).

### Track 8B: Higher-Order Masking (2nd/3rd Order Side-Channel Resistance)

**Beyond Defense-Grade Value**: First-order masking is the enterprise and defense baseline. Second and third-order masking protects against sophisticated adversaries who combine multiple leakage traces (higher statistical moments), glitch attacks, or electromagnetic probing — the threat model for nation-state physical access scenarios. **Approach**: Upgrade to 3–4 shares using Domain-Oriented Masking (DOM) or ISW gadgets for non-linear operations. Hardware support requires new custom instructions for secure multi-share AND/XOR/multiplication operations.

## Key Observations

**Tier 1 Critical Path**: Phases 1 through 3 and Phase 5 form the critical path. The three phase gate checkpoints (Integration Stable, Kernel Ready, Tier 1 Complete) prevent cascading rework from premature phase transitions. Phase 4 (DRBG) operates as an independent parallel track beginning after core selection. Phase 7 (Documentation) develops incrementally throughout.

**Tier 2 Sequencing**: Within Phase 8, formal verification (Track 8A) must come first as it establishes the assurance foundation that all subsequent tracks build upon. Higher-order masking (8B) and quantum-resistant primitives (8C) can run in parallel after 8A completes. Red-team validation (8D) follows all technical tracks, and Protection Profile targeting (8E) is the final step. Tracks 8D and 8E involve external parties and physical-world activities that partially overlap with Tier 1's excluded items — they are best sequenced after FPGA bring-up.

**Effort Distribution (Tier 1)**: Approximately 55% hardware engineering and verification in Verilog simulation, 24% software development in Rust, and 21% documentation, tooling, and integration testing. All 42 Tier 1 tasks can be executed on standard development machines using open-source tools.

**Core Selection**: CVA6 is strongly recommended for its native CV-X-IF extension interface, which significantly reduces integration effort in Phase 2. The CV-X-IF request/response protocol was designed specifically for the type of custom instruction integration XPlenum requires.

**Emulation Strategy**: The Spike-first, QEMU-second approach (Tasks 6.1a and 6.1b) provides faster iteration on instruction semantics before committing to the more complex full-system emulator integration. Cross-verification (Task 6.7) between RTL simulation and emulator catches semantic divergence early.

**Beyond Defense-Grade Positioning**: Completing Tier 2 positions XPlenum as one of the most assured open RISC-V security extensions in existence — potentially suitable for classified edge compute, secure bootstrap in national systems, or foundational security components in MILS architectures. The combined formal verification, higher-order masking, quantum resistance, and independent red-team validation exceeds the assurance level of most commercially available security processors.

### A.2 — CV-X-IF Extension Interface Adapter (Verilog, Task 2.1 CVA6 Variant)

```verilog
// CVA6 CV-X-IF adapter for XPlenum
// Maps CV-X-IF request/response to xplenum_top.v interface
module xplenum_cvxif_adapter (
    input         clk,
    input         rst_n,
    // CV-X-IF compressed interface
    input         x_issue_valid,
    output        x_issue_ready,
    input  [31:0] x_issue_req_instr,
    input  [63:0] x_issue_req_rs1,
    input  [63:0] x_issue_req_rs2,
    output        x_result_valid,
    output [63:0] x_result_data,
    output [4:0]  x_result_rd,
    output        x_result_we
);
    // Decode: accept only XPlenum opcodes
    wire [6:0] opcode = x_issue_req_instr[6:0];
    wire accept = (opcode == 7'b0001011) || (opcode == 7'b0101011);
    assign x_issue_ready = accept;

    // Instantiate XPlenum core
    xplenum_top xp (
        .clk(clk), .rst_n(rst_n),
        .instruction(x_issue_req_instr),
        .rs1_data(x_issue_req_rs1),
        .rs2_data(x_issue_req_rs2),
        .rd_data(x_result_data),
        .rd_wen(x_result_we)
    );

    assign x_result_valid = accept & x_result_we;
    assign x_result_rd    = x_issue_req_instr[11:7];
endmodule
```

### A.4 — Simplified CTR_DRBG (Verilog, Task 4.2)

```verilog
// Conceptual CTR_DRBG module — replace LFSR in xplenum_mask_unit.v
// IMPORTANT: Production version must implement full Instantiate/Update/Generate
// per NIST SP 800-90A §10.2.1, including derivation function and reseed resistance.
module drbg_ctr_aes (
    input         clk,
    input         rst_n,
    input         reseed,
    input         generate,
    input  [255:0] seed,
    output [31:0]  rand_out,
    output         valid
);
    reg [127:0] V;          // Counter block
    reg [255:0] Key;        // AES key
    wire [127:0] aes_out;

    aes_256_encrypt aes_inst (
        .clk(clk), .key(Key), .plaintext(V), .ciphertext(aes_out)
    );

    assign rand_out = aes_out[31:0];

    always @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            V   <= 128'b0;
            Key <= 256'b0;
        end else if (reseed) begin
            Key <= seed;
            V   <= 128'b0;
        end else if (generate) begin
            V <= V + 1;
        end
    end
endmodule
```

```rust
    core::arch::asm!(
        ".insn r 0b0001011, 0, 0, {rd}, {rs1}, {rs2}",
        rd  = out(reg) result,
        rs1 = in(reg) data,
        rs2 = in(reg) mask,
    );
    result
}

/// Safe wrapper with type enforcement
pub fn apply_mask(data: SensitiveValue, mask: MaskValue) -> MaskedValue {
    // SAFETY: Instruction encoding verified against xplenum_pkg.vh.
    // Hardware guarantees constant-time execution.
    let raw = unsafe { xmask_apply(data.as_u64(), mask.as_u64()) };
    MaskedValue::from_raw(raw)
}
```

```c
// In target/riscv/insn_trans/trans_xplenum.c.inc (QEMU patch)
// Emulate XMASK.APPLY: rd = rs1 ^ (rs2 & lfsr_state)
// Simplified — full emulation requires per-unit dispatch
static bool trans_xmask_apply(DisasContext *ctx, arg_r *a)
{
    TCGv dest = dest_gpr(ctx, a->rd);
    TCGv src1 = get_gpr(ctx, a->rs1, EXT_NONE);
    TCGv src2 = get_gpr(ctx, a->rs2, EXT_NONE);

    // Emulate masking operation (simplified XOR model)
    tcg_gen_xor_tl(dest, src1, src2);

    gen_set_gpr(ctx, a->rd, dest);
    return true;
}
```
