# TSA CALENDAR CONTEXT EXTENSION
# Per-Policy + Request-Level Multi-Calendar Enrichment for RFC 3161 Tokens

**Date:** February 24, 2026
**Repository:** SigmaWolf-8/Ternary
**Modifies:** `server/services/tsa-service.ts`
**Creates:** `server/services/tsa-calendar-enrichment.ts`
**Depends on:** Calendar service at `/api/salvi/timing/epoch/calendars` (already built)
**Standard:** Custom non-critical TSTInfo extension — fully RFC 3161 compliant

---

## WHAT THIS DOES

Enriches RFC 3161 Time-Stamp Tokens with multi-calendar date representations.
Calendar data is embedded as a **non-critical X.509v3 extension** in TSTInfo —
standard verifiers (OpenSSL, Adobe, jarsigner) skip it without error;
PlenumNET-aware tools extract it.

Calendar enrichment comes from **two sources, merged at token time:**

1. **Policy-tier defaults** — automatic, per-tier configuration. COMPLY gets
   7 financial-jurisdiction calendars. FORENSICS gets all 24. Others get none.

2. **Request-level supplement** — optional `calendars` parameter on any
   timestamp request, including DEFAULT. A construction firm in Bangkok adds
   `calendars: ['buddhist']` to their DEFAULT-tier requests and gets Buddhist
   Era on every daily timestamp without upgrading their tier or taking on
   FORENSICS-level payload.

Request-level calendars are **additive** — they merge with (never replace)
policy defaults. Duplicates are deduplicated. Invalid system names are
silently skipped with a warning log.

The JSON API also returns calendar context as a top-level field for consumers
that don't parse ASN.1.

---

## WHY THIS MATTERS

| Jurisdiction | Legal Calendar | Use Case |
|-------------|---------------|----------|
| Saudi Arabia, UAE, Bahrain, Qatar, Kuwait | Hijri (Islamic) | Shariah-compliant finance — contracts dated in Hijri |
| Thailand | Buddhist Era (BE 2569 = 2026 CE) | Thai legal filings, court documents |
| Japan | Imperial Era (Reiwa 8 = 2026 CE) | Japanese corporate filings, financial reports |
| Israel | Hebrew | Israeli financial records, government documents |
| Iran | Solar Hijri (Jalali) | Iranian legal and financial records |
| India | Saka Era | Indian government gazette, legal notices |
| China, Taiwan, Korea | Chinese lunisolar | Cultural/regulatory contexts in East Asia |
| Ethiopia | Ge'ez | Ethiopian legal system (13 months, ~7 year offset) |

**The problem with tier-only configuration:** A small Thai firm using DEFAULT
tier for daily timestamping shouldn't need FORENSICS (24 calendars, ~3KB
overhead per token) just to get Buddhist Era dates. A Dubai-based fund on
COMPLY already gets Hijri from policy defaults, but an Israeli fintech on
DEFAULT shouldn't need COMPLY just for Hebrew dates.

**The solution:** Any tier can request any calendar system. Policy defaults
handle the common cases automatically. The `calendars` parameter handles
everything else — one field, zero tier changes, minimal payload.

## CALENDAR RESOLUTION MODEL

```
┌─────────────────────────────────────────────────────────────┐
│                   Calendar Resolution                        │
│                                                              │
│   Policy Config          Request Param        Final Set      │
│   (automatic)       +    (optional)      →    (deduplicated) │
│                                                              │
│   DEFAULT:  []      +    ['buddhist']    →    ['buddhist']   │
│   COMPLY:   [7]     +    ['ethiopian']   →    [8 calendars]  │
│   COMPLY:   [7]     +    ['hijri']       →    [7 — deduped]  │
│   FORENSICS:['*']   +    ['buddhist']    →    [all 24]       │
│   SENTINEL: []      +    []              →    [] — no ext    │
│   DEFAULT:  []      +    []              →    [] — no ext    │
│   DEFAULT:  []      +    ['*']           →    [all 24]       │
└─────────────────────────────────────────────────────────────┘
```

**Rules:**
1. Policy config provides the floor (automatic, no request needed)
2. Request `calendars` parameter is additive (merged, deduplicated)
3. Either source can use `['*']` wildcard for all 24 systems
4. Empty merged set = no calendar extension = clean token
5. Invalid calendar names are silently dropped with a warning log

## PER-POLICY CALENDAR DEFAULTS

| Tier | Default Calendars | Rationale |
|------|------------------|-----------|
| **DEFAULT** | `[]` — none | Operational timestamping. UTC only. Zero overhead unless requested. |
| **COMPLY** | `['hijri', 'hebrew', 'japanese', 'buddhist', 'chinese', 'indian-saka', 'solar-hijri']` | Financial compliance across major non-Gregorian jurisdictions |
| **FORENSICS** | `['*']` — all 24 | Maximum provenance. Court evidence may surface in any jurisdiction. |
| **SENTINEL** | `[]` — none | Military/government timeline reconstruction. UTC is the only reference. |
| **SECURE** | `[]` — none | Zero-trust access control. Calendar context irrelevant unless requested. |

Any tier's defaults can be supplemented per-request via the `calendars` parameter.

## CUSTOM EXTENSION OID

```
PlenumNET base:     1.3.6.1.4.1.0.100
TSA extensions:     1.3.6.1.4.1.0.100.2
Calendar context:   1.3.6.1.4.1.0.100.2.1

id-plenumnet-tsa-calendarContext OBJECT IDENTIFIER ::= { 1 3 6 1 4 1 0 100 2 1 }
```

Extension properties:
- **Critical:** `FALSE` — standard verifiers MUST skip unknown non-critical extensions
- **Value:** DER-encoded UTF8String containing JSON payload

## FILE 1: `server/services/tsa-calendar-enrichment.ts` (NEW)

```typescript
/**
 * TSA CALENDAR CONTEXT ENRICHMENT
 *
 * Repository: SigmaWolf-8/Ternary
 * Location:   server/services/tsa-calendar-enrichment.ts
 *
 * Resolves which calendar systems to embed in a TSA token by merging
 * policy-tier defaults with optional request-level supplements.
 * Calls the PlenumNET calendar service and returns a CalendarContext
 * for embedding as a non-critical TSTInfo extension.
 *
 * Best-effort: failure never blocks token issuance.
 */

import { TSA_POLICY_METADATA } from './tsa-service';

// ── Extension OID ─────────────────────────────────────────────────────────
export const CALENDAR_EXTENSION_OID = '1.3.6.1.4.1.0.100.2.1';

// ── Calendar system identifiers ───────────────────────────────────────────
// Keys MUST match the keys returned by /api/salvi/timing/epoch/calendars.
// Used for validation of request-level calendar parameters.
export const CALENDAR_SYSTEMS = {
  GREGORIAN:     'gregorian',
  HIJRI:         'hijri',           // Islamic (lunar)
  SOLAR_HIJRI:   'solar-hijri',     // Iranian (Jalali)
  HEBREW:        'hebrew',
  JAPANESE:      'japanese',        // Imperial era (Reiwa)
  BUDDHIST:      'buddhist',        // Thai Buddhist Era
  CHINESE:       'chinese',         // Chinese lunisolar
  INDIAN_SAKA:   'indian-saka',     // Indian national calendar
  ETHIOPIAN:     'ethiopian',       // Ge'ez calendar
  COPTIC:        'coptic',
  MAYAN:         'mayan',           // Long Count
  VEDIC:         'vedic',
  THIRTEEN_MOON: '13-moon',         // Dreamspell / 13-Moon
  PERSIAN:       'persian',         // alias for solar-hijri in some contexts
  TIBETAN:       'tibetan',
  BENGALI:       'bengali',
  THAI_SOLAR:    'thai-solar',      // Thai solar (distinct from Buddhist Era)
  MINGUO:        'minguo',          // Republic of China / Taiwan
  JUCHE:         'juche',           // North Korean
  BALINESE:      'balinese',        // Pawukon
  BYZANTINE:     'byzantine',       // Anno Mundi variant
  HOLOCENE:      'holocene',        // Human Era (HE)
  IGBO:          'igbo',            // Igbo calendar
  AKAN:          'akan',            // Akan calendar
} as const;

// Set of all known system names for validation
export const KNOWN_CALENDAR_SYSTEMS = new Set(Object.values(CALENDAR_SYSTEMS));

// ── Per-policy calendar defaults ──────────────────────────────────────────
// These are AUTOMATIC — no request parameter needed.
// Empty array = no default enrichment for this tier.
// ['*'] = all available systems.
// Request-level calendars are ADDITIVE to these defaults.
export const POLICY_CALENDAR_CONFIG: Record<string, string[]> = {
  'DEFAULT':    [],
  'COMPLY':     [
    CALENDAR_SYSTEMS.HIJRI,
    CALENDAR_SYSTEMS.HEBREW,
    CALENDAR_SYSTEMS.JAPANESE,
    CALENDAR_SYSTEMS.BUDDHIST,
    CALENDAR_SYSTEMS.CHINESE,
    CALENDAR_SYSTEMS.INDIAN_SAKA,
    CALENDAR_SYSTEMS.SOLAR_HIJRI,
  ],
  'FORENSICS':  ['*'],  // All — maximum provenance
  'SENTINEL':   [],
  'SECURE':     [],
};

// ── Types ─────────────────────────────────────────────────────────────────

export interface CalendarDate {
  system: string;        // e.g. 'hijri', 'hebrew', 'japanese'
  display: string;       // Human-readable: "7 Sha'ban 1447 AH"
  year: number | string;
  month: number | string;
  day: number | string;
  era?: string;          // e.g. 'Reiwa', 'BE', 'AH', 'AM'
}

export interface CalendarContext {
  /** UTC ISO timestamp that was converted */
  utcTimestamp: string;
  /** Julian Day Number — universal bridge between all calendar systems */
  julianDayNumber: number;
  /** Salvi Epoch offset (days since April 1, 2025 UTC) */
  salviEpochDay: number;
  /** Calendar representations included in this token */
  calendars: CalendarDate[];
  /** Policy tier that provided the default calendar set */
  policyTier: string;
  /** Which calendars came from policy defaults vs request supplement */
  source: {
    policy: string[];     // e.g. ['hijri', 'hebrew', ...] — from tier config
    requested: string[];  // e.g. ['ethiopian'] — from request param
  };
  /** Extension OID for ASN.1 embedding */
  extensionOid: string;
}

// ── Calendar service client interface ─────────────────────────────────────

export interface CalendarServiceClient {
  /**
   * Call /api/salvi/timing/epoch/calendars to convert a date.
   * Returns all 24 calendar representations keyed by system name.
   */
  convertDate(utcTimestamp: string): Promise<{
    julianDayNumber: number;
    salviEpochDay: number;
    calendars: Record<string, CalendarDate>;
  }>;
}

// ── Calendar system resolution ────────────────────────────────────────────

/**
 * Resolve the final set of calendar systems to embed in a token.
 *
 * Merges policy-tier defaults with request-level supplements.
 * Deduplicates. Validates against known systems. Returns empty
 * array if no calendars should be embedded.
 *
 * @param policyTier       Tier name (DEFAULT, COMPLY, etc.)
 * @param requestCalendars Optional array from request `calendars` param
 * @returns Deduplicated array of validated calendar system names
 */
export function resolveCalendarSystems(
  policyTier: string,
  requestCalendars?: string[],
): string[] {
  const policyDefaults = POLICY_CALENDAR_CONFIG[policyTier] || [];
  const requested = requestCalendars || [];

  // Wildcard from either source → all systems
  if (policyDefaults[0] === '*' || requested.includes('*')) {
    return ['*'];
  }

  // Merge and deduplicate
  const merged = new Set<string>([...policyDefaults, ...requested]);

  // Validate — drop unknown systems with a warning
  const validated: string[] = [];
  for (const sys of merged) {
    if (KNOWN_CALENDAR_SYSTEMS.has(sys)) {
      validated.push(sys);
    } else {
      console.warn('Unknown calendar system requested (skipped)', {
        system: sys,
        policyTier,
        hint: `Valid systems: ${[...KNOWN_CALENDAR_SYSTEMS].join(', ')}`,
      });
    }
  }

  return validated;
}

/**
 * Determine which calendars came from policy vs request for audit trail.
 */
export function classifyCalendarSources(
  policyTier: string,
  requestCalendars?: string[],
): { policy: string[]; requested: string[] } {
  const policyDefaults = POLICY_CALENDAR_CONFIG[policyTier] || [];
  const requested = requestCalendars || [];

  if (policyDefaults[0] === '*') {
    return { policy: ['*'], requested: [] };
  }
  if (requested.includes('*')) {
    return { policy: policyDefaults, requested: ['*'] };
  }

  const policySet = new Set(policyDefaults);
  const supplemented = requested.filter(
    sys => !policySet.has(sys) && KNOWN_CALENDAR_SYSTEMS.has(sys),
  );

  return {
    policy: policyDefaults,
    requested: supplemented,
  };
}

// ── Main enrichment function ──────────────────────────────────────────────

/**
 * Enrich a TSA token with multi-calendar context.
 *
 * Resolution order:
 *   1. Policy tier defaults (automatic)
 *   2. Request-level supplements (additive)
 *   3. Merge, deduplicate, validate
 *   4. Call calendar service for resolved systems
 *   5. Return CalendarContext or null (if no calendars resolved)
 *
 * @param utcTimestamp     The genTime from HPTP (ISO 8601 UTC)
 * @param policyTier       Tier name (DEFAULT, COMPLY, FORENSICS, etc.)
 * @param calendarClient   Client for the calendar service
 * @param requestCalendars Optional array from request `calendars` param
 * @returns CalendarContext if any calendars resolved, null otherwise
 */
export async function enrichWithCalendars(
  utcTimestamp: string,
  policyTier: string,
  calendarClient: CalendarServiceClient,
  requestCalendars?: string[],
): Promise<CalendarContext | null> {
  // 1. Resolve which systems to include
  const systems = resolveCalendarSystems(policyTier, requestCalendars);
  if (systems.length === 0) {
    return null;  // No calendars requested or configured — clean token
  }

  try {
    // 2. Call the calendar service (one call returns all 24 systems)
    const result = await calendarClient.convertDate(utcTimestamp);

    // 3. Filter to resolved systems
    let calendars: CalendarDate[];
    if (systems[0] === '*') {
      calendars = Object.values(result.calendars);
    } else {
      calendars = systems
        .filter(sys => result.calendars[sys])
        .map(sys => result.calendars[sys]);
    }

    if (calendars.length === 0) {
      console.warn('Calendar service returned no matching systems', {
        requested: systems,
        available: Object.keys(result.calendars),
      });
      return null;
    }

    // 4. Classify sources for audit trail
    const source = classifyCalendarSources(policyTier, requestCalendars);

    // 5. Build context
    return {
      utcTimestamp,
      julianDayNumber: result.julianDayNumber,
      salviEpochDay: result.salviEpochDay,
      calendars,
      policyTier,
      source,
      extensionOid: CALENDAR_EXTENSION_OID,
    };

  } catch (error) {
    // Calendar enrichment failure is non-fatal — same as TL-DSA pattern
    console.warn('Calendar enrichment failed (non-fatal)', {
      policyTier,
      utcTimestamp,
      requestedSystems: systems,
      error: (error as Error).message,
    });
    return null;
  }
}

/**
 * Serialize CalendarContext to JSON for embedding in TSTInfo extension.
 * DER-encoded as UTF8String OCTET STRING in the extension value.
 */
export function serializeForExtension(context: CalendarContext): string {
  return JSON.stringify({
    v: 1,                               // Schema version
    oid: context.extensionOid,
    utc: context.utcTimestamp,
    jdn: context.julianDayNumber,
    sed: context.salviEpochDay,
    tier: context.policyTier,
    src: context.source,                // { policy: [...], requested: [...] }
    cal: context.calendars.map(c => ({
      sys: c.system,
      d: c.display,
      y: c.year,
      m: c.month,
      day: c.day,
      ...(c.era ? { era: c.era } : {}),
    })),
  });
}
```

## NON-NEGOTIABLE RULES

1. **Calendar enrichment NEVER blocks token issuance.** Best-effort, same as TL-DSA. Log failure; issue token without extension.

2. **Extension is NON-CRITICAL.** `critical: FALSE` in ASN.1. Any verifier that doesn't understand it MUST skip it per X.509v3 rules.

3. **Request-level calendars are ADDITIVE.** They merge with policy defaults, never replace them. COMPLY always includes its 7 financial calendars even if the request asks for only 1.

4. **No calendars resolved = no extension.** DEFAULT with no `calendars` param produces a clean token. Zero overhead.

5. **Calendar data is derived, not authoritative.** UTC genTime from HPTP is the legal timestamp. Calendar representations are informational enrichment.

6. **Schema versioned.** JSON payload includes `"v": 1`. Bump on format changes.

7. **Julian Day Number is the bridge.** Included in every CalendarContext for independent verification of calendar conversions.

8. **Source attribution.** Every CalendarContext records which calendars came from policy defaults vs request supplement. Full audit trail.

9. **Invalid system names are silently dropped.** Warning logged, token not blocked. Typos don't crash timestamps.
