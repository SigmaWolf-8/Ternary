### 2.1 TL-DSA Formal Security Proof

Produce a formal security reduction proving TL-DSA is secure under the Module-LWE hardness assumption. This is a mathematical document, not code.

| Aspect | Detail |
|---|---|
| Effort | 2–3 days |
| Output | LaTeX paper: definitions, security model (EUF-CMA), reduction from TL-DSA forgery to Module-LWE solver, concrete security bounds |
| Inputs | `tl_dsa.rs` (523 lines), `ternary_lattice.rs` (1,216 lines) — extract parameters, ring structure, noise distribution |
| Impact | "Lattice-based (assumed secure)" → "Provably secure under Module-LWE with concrete bounds" |
| Target | Submittable to IACR ePrint |

## Tier 3 — BRIDGE

**Goal:** Connect the Rust kernel to the TypeScript platform via WASM compilation. This is the single most impactful tier — it replaces every interim bridge (ed448 for TL-DSA, simulated ternary processing in SFK pipeline) with the real Rust implementations.

### 3.1 WASM Build Pipeline

Configure `wasm-pack` to compile the Rust kernel's crypto and ternary modules to WebAssembly. `Cargo.toml` already has `crate-type = ["cdylib"]`. This task produces the build infrastructure, not the bindings.

| Aspect | Detail |
|---|---|
| Effort | 1–2 days |
| Output | `wasm-pack` config, `wasm-bindgen` annotations on public API surface, build script, CI integration |
| Target Functions | `tl_dsa::{keygen, sign, verify}`, `tl_kem::{keygen, encapsulate, decapsulate}`, `ternary::{add, mul, rot}`, `sponge::hash`, `gateway::convert` |
| Blocks | None — start immediately |

### 3.2 TL-DSA WASM Bridge

Replace the ed448 interim bridge (`tl-dsa-bridge.ts`) with TypeScript bindings that call the compiled Rust TL-DSA via WASM. This is the change that makes the entire TypeScript layer genuinely post-quantum.

| Aspect | Detail |
|---|---|
| Effort | 1–2 days |
| Files | New: `tl-dsa-wasm.ts`. Modified: `key-management.ts` (swap provider) |
| Verification | Capability token signed with WASM TL-DSA → delegated → verified → signature valid against real lattice public key |
| Blocks | 3.1 (WASM build must work) |

### 3.3 TL-KEM WASM Bridge

Same pattern for key encapsulation. Replace any interim key exchange with the real Rust TL-KEM via WASM.

| Aspect | Detail |
|---|---|
| Effort | 1 day |
| Output | `tl-kem-wasm.ts` with encapsulate/decapsulate calling Rust WASM |
| Blocks | 3.1 |

### 3.4 SFK Pipeline Real Ternary Processing

Replace the SHA-256 placeholder in `sfk-operations-service.ts` `performTernaryProcessing()` with actual ternary computation via the WASM-compiled kernel. Operations will execute real GF(3) arithmetic instead of hashing their parameters.

| Aspect | Detail |
|---|---|
| Effort | 1–2 days |
| Files | `sfk-operations-service.ts` (replace `performTernaryProcessing`) |
| Result | SFK operations produce deterministic ternary computation results, not parameter hashes |
| Blocks | 3.1 (WASM ternary module must be compiled) |

**Tier 3 Total Estimated Effort: 4–7 days**

## Tier 4 — DEMONSTRATE

**Goal:** Produce demonstration artifacts that prove hardware-level claims. AI generates the code, scripts, and configurations; human runs them on physical hardware where required.

### 4.1 QEMU Bare-Metal Boot Package

Write the linker scripts, QEMU launch configuration, and minimal boot shim that demonstrates the SFK kernel booting on QEMU for x86_64, aarch64, and riscv64. `boot.rs` exists for all three architectures.

| Aspect | Detail |
|---|---|
| Effort | 2–3 days |
| Output | `boot/` directory: linker scripts per arch, QEMU launch scripts, Makefile, expected boot log |
| Verification | `make boot-qemu-x86_64` produces kernel boot log showing memory init, TVM ready, security mode active |
| Impact | "Code exists" → "Bootable on QEMU" (physical hardware is a human follow-up) |

### 4.2 FPGA Synthesis Scripts

Generate Xilinx Vivado TCL scripts, constraint files (.xdc), and testbenches for the 4 RTL modules produced by `fpga_hdl.rs`. AI produces the synthesis-ready package; human runs Vivado.

| Aspect | Detail |
|---|---|
| Effort | 2–3 days |
| Output | `fpga/` directory: Vivado project TCL, timing constraints, pin constraints (KCU116 target), SystemVerilog testbenches, simulation scripts |
| Targets | GF(3) ALU, sponge permutation, AES S-box, polynomial MAC |
| Impact | "RTL generated" → "Synthesis-ready package" (bitstream is a human follow-up) |

### 4.3 Xplenum RISC-V ISA Test Suite

Write test vectors and a Spike/QEMU custom extension plugin skeleton for the 21 Xplenum instructions. AI produces the test infrastructure; simulation can run in software.

| Aspect | Detail |
|---|---|
| Effort | 2–3 days |
| Output | `xplenum/tests/` directory: instruction encoding tests, CSR access tests, expected behavior vectors, Spike extension scaffold |
| Coverage | All 21 instructions, all 12 CSRs, edge cases (boundary checks, domain transitions, mask operations) |
| Impact | "ISA defined" → "ISA tested with deterministic vectors" |

### 4.4 Network Testbed Software Stack

Write the node software, configuration, and orchestration scripts for a 3–5 node T3P/TDNS/TTP testbed. AI produces the complete software stack; human deploys on Raspberry Pis or Docker containers.

| Aspect | Detail |
|---|---|
| Effort | 3–4 days |
| Output | `testbed/` directory: node binary (compiles T3P+TDNS+TTP into standalone), config templates, Docker Compose for local testing, topology visualization, latency measurement scripts |
| Verification | `docker compose up` launches 3 nodes, routes a message through torus topology, measures RTT |
| Impact | "Routing algorithm" → "Demonstrated protocol (containerized)" |

### 4.5 Quantum Error Correction Test Suite

Write comprehensive tests for the [[3,1,2]]₃ stabilizer code opcodes (0xA0–0xAF) in ISA v2. These are some of the most novel opcodes and have minimal test coverage.

| Aspect | Detail |
|---|---|
| Effort | 1–2 days |
| Output | Rust test module: QCorrect, QSyndrome, QNormalize operations with known error patterns, syndrome tables, correction verification |
| Impact | Novel opcodes verified with deterministic test vectors |

### 4.6 Side-Channel Resistance Validation

Write timing analysis tests that verify constant-time behavior of critical crypto paths using `ct_utils.rs` and `side_channel.rs`. Produces statistical evidence of constant-time execution.

| Aspect | Detail |
|---|---|
| Effort | 1–2 days |
| Output | Timing test harness: runs TL-DSA sign/verify with different inputs, measures variance, produces t-test results |
| Tools | `dudect`-style statistical analysis in Rust |
| Impact | "Side-channel resistance utilities exist" → "Constant-time verified by statistical test" |

### 4.7 API Conformance Test Suite

Write a comprehensive API test suite that exercises all 100+ endpoints across all 23+ Kong services. Produces a machine-readable conformance report.

| Aspect | Detail |
|---|---|
| Effort | 2–3 days |
| Output | Test runner (TypeScript): endpoint inventory from Kong catalog, request/response validation, error handling verification, auth flow testing, rate limit verification |
| Result | JSON conformance report: endpoint, method, status, latency, response schema valid |
| Impact | Proves every registered endpoint works, not just the demo path |

**Tier 4 Total Estimated Effort: 14–20 days**
