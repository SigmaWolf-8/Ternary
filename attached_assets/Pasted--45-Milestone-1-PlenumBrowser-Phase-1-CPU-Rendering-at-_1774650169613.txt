#45 - Milestone 1 — PlenumBrowser Phase 1: CPU Rendering at Full HD
What & Why
The kernel boots, runs a 320x200 smoke test, and halts. The full browser subsystem scaffolding exists — parse, layout, script, tabs, input, net, mesh, color, distributor, layers — but everything is stubs and type definitions. Nothing renders real content, processes real input, or drives the 1920x1080 framebuffer that BootParams already declares.

This milestone delivers Phase 1 of the approved PlenumBrowser architecture (ref: "PlenumBrowser & PlenumColor Architecture Summary — March 2026"). The browser is a kernel subsystem — not userspace, not a fork. After boot, the user sees PlenumBrowser rendering styled HTML/CSS content at 1920x1080 through the full pipeline: parse → layout → script → render (CPU/tiny-skia) → mesh color pipeline → sponge encrypt → simplefb. No window manager, no DWM, no compositor layer — single pipeline from DOM to framebuffer.

Phase 1 uses the CPU fallback path (tiny-skia + CPU sponge XOR). Phase 2 (GPU via wgpu, IOMMU-isolated VRAM, mesh compute shaders, scanout decryption) is future work and out of scope. The render backend is behind a trait so Phase 2 swaps in without touching browser or distributor modules.

This aligns with the architecture document's Phase 1 milestones 1.1 through 1.6:

1.1: HTML/CSS rendering via tiny-skia to simplefb
1.2: Boa integration with cooperative watchdog
1.3: Tab isolation via kernel tasks
1.4: Mesh color pipeline (CPU) — sRGB↔mesh conversion, Bézier interpolation, depth 3 gradients without banding
1.5: z=0 distributor coprime walk routing through full z-stack
1.6: CPU sponge encryption — in-place XOR on simplefb framebuffer
Critical Architecture Decision: Custom std Shim (Redox OS Approach)
The kernel is #![no_std] + alloc. Three of the seven browser crates (html5ever, rust-cssparser, boa_engine) require std. Rather than forking each crate or building no_std replacements — which creates permanent maintenance burden and risks conformance drift — this milestone uses the Redox OS approach: build a custom Rust target with a std shim backed by existing kernel primitives.

The kernel already has everything std actually provides:

std API	Kernel Primitive	Location
std::alloc	BumpAllocator + #[global_allocator]	main.rs:19-44
std::collections::HashMap	hashbrown (what std uses internally anyway)	re-export
std::sync::Mutex	Security-aware Mutex<T> + ticket Spinlock	sync/mutex.rs, sync/spinlock.rs
std::sync::RwLock	Kernel Semaphore-backed read/write lock	sync/semaphore.rs
std::thread::spawn	ProcessTable::create_process + priority scheduler	process/table.rs, process/scheduler.rs
std::time::Instant	FemtosecondTimestamp + HptpProvider	timing.rs, drivers/femtoclock.rs
std::io::Read/Write	Thin trait wrappers over kernel buffers	new shim code
std::fmt	Already in core — zero work	built-in
std::net	Stub returning Err(Unsupported) — browser uses z=0, not sockets	stub
std::fs	Stub returning Err(Unsupported) — fonts embedded, no filesystem	stub
The shim is three custom Rust targets (x86_64-plenum-none, aarch64-plenum-none, riscv64gc-plenum-none) plus a plenum-std crate that re-exports core, alloc, and thin wrappers around kernel primitives under the std:: namespace. Every upstream crate (all eight) compiles unmodified. No forks. No no_std alternatives. No deferred functionality. And every future crate just works.

This is real work — the biggest single task in Phase 1. But it solves the problem permanently.

Tasks
Build the PlenumNET std shim and custom Rust targets — This is the critical path, the biggest single task in Phase 1, and must be done first. The shim permanently solves crate compatibility for the entire project. This is not "write some wrapper code" — it is replicating the public API surface of the Rust standard library (every module, every type, every trait that the seven crates import via use std::*) backed by kernel primitives. Estimate 3-5 weeks. Reference: Redox OS solved this identically with relibc + redoxer toolchain.

(a) Nightly Rust + -Z build-std sysroot: Requires nightly Rust with -Z build-std enabled. Create JSON target specs for x86_64-plenum-none, aarch64-plenum-none, riscv64gc-plenum-none based on the corresponding *-unknown-none targets. The build system compiles core, alloc, and the custom plenum-std (as the std crate) into a sysroot that rustc uses for all downstream compilation. The plenum-std crate must present exactly the same module tree and public API surface that std does — use std::collections::HashMap, use std::sync::Mutex, use std::thread, etc. must all resolve. Crates don't know they're running on PlenumNET — they call std and get kernel primitives underneath.

(b) plenum-std crate — full std API surface mapping:

std::alloc → existing #[global_allocator] BumpAllocator (must be upgraded — see (c))
std::collections::HashMap/HashSet/BTreeMap/BTreeSet → hashbrown for hash maps (what std uses internally), core BTree re-exports
std::sync::Mutex<T> → kernel Mutex<T> from sync/mutex.rs (wraps the ticket spinlock)
std::sync::RwLock<T> → kernel semaphore-backed implementation from sync/semaphore.rs
std::sync::Arc/Weak → re-export from alloc::sync (already available)
std::thread::spawn → ProcessTable::create_process + kernel task with priority scheduler
std::thread::JoinHandle<T> → kernel task completion signaling with return value
std::thread::LocalKey / #[thread_local] → kernel task-local storage (TLS). This is critical for Boa. Boa's GC uses std::thread::LocalKey for per-thread GC root sets. The kernel task model must provide per-task storage slots that LocalKey::with() can access. Implementation: each ProcessDescriptor gets a TLS block (a BTreeMap<TypeId, Box<dyn Any>> or a fixed-slot array) that the std::thread::LocalKey shim indexes into using the current task's PID from the scheduler. Without this, Boa's GC will not function — it stores root pointers in thread-locals and expects them to be task-isolated.
std::time::Instant → FemtosecondTimestamp from timing.rs (backed by HptpProvider / femtoclock driver). Must implement Instant::now(), Instant::elapsed(), Instant::duration_since().
std::time::Duration → re-export from core (already available)
std::time::SystemTime → map to FemtosecondTimestamp with a fixed epoch offset
std::io::{Read, Write, Error, ErrorKind, Result, Cursor, BufReader, BufWriter} → thin trait wrappers over kernel buffers. ErrorKind must cover at minimum: NotFound, PermissionDenied, Unsupported, Other, WouldBlock, InvalidInput, UnexpectedEof. html5ever uses std::io::Read to consume input; the shim must make this work over in-memory byte slices.
std::fmt → re-export from core (zero work)
std::string::String, std::vec::Vec, std::boxed::Box → re-export from alloc
std::net → stub module where TcpStream::connect(), TcpListener::bind(), etc. all return Err(io::Error::new(ErrorKind::Unsupported, "use z=0 distributor")). Browser networking goes through z=0, not sockets.
std::fs → stub module where File::open(), read_to_string(), etc. all return Err(io::Error::new(ErrorKind::Unsupported, "fonts embedded, no filesystem")). Font files are embedded in the kernel binary.
std::env → stub returning empty/defaults
std::process → stub (no child processes in kernel)
std::panic → wire to kernel panic handler with catch_unwind support for tab isolation
(c) Allocator upgrade: The current BumpAllocator (1MB heap, no dealloc) cannot support real crate workloads. Upgrade to a proper kernel allocator (e.g., linked-list or buddy allocator) that supports deallocation and can grow the heap well beyond 1MB. This is load-bearing — Boa's GC, html5ever's tree builder, and Taffy's layout tree all allocate and free continuously. The allocator must handle the browser's memory profile: ~8MB framebuffer + ~5.25MB mesh LUT + font caches (256MB global + 16MB×active tabs) + per-tab DOM/layout/JS heaps.

(d) Build system integration: Configure .cargo/config.toml with the custom target, -Z build-std=core,alloc,std, and sysroot paths. Pin to a specific nightly toolchain version in rust-toolchain.toml. Ensure cargo build --target x86_64-plenum-none compiles the kernel + all eight crates in a single pass. CI must use the same pinned nightly.

(e) Validation: Compile all eight crates against the shim — if any use std::* path fails to resolve, the shim's module tree is incomplete and must be extended. Run existing kernel boot test in QEMU to verify the shim doesn't break boot. Specifically test: Boa's GC roots survive across yield points (proves TLS shim works), HashMap::insert/get round-trips (proves hashbrown wiring), Instant::elapsed() returns non-zero (proves timer shim), thread::spawn + JoinHandle::join completes (proves task shim).

(f) Early integration test: After shim completion, compile html5ever alone and parse a simple HTML string (<html><body><h1>test</h1></body></html>) inside the kernel as a standalone validation test before wiring the full browser pipeline. This proves the shim's std::io::Read, std::collections::HashMap, and allocator all work correctly under html5ever's actual usage patterns. Run this test in QEMU as part of the boot sequence.

Derive default mesh↔sRGB mapping and implement PlenumColor mesh pipeline (CPU path) — This is a math + implementation task, not just wiring. The existing mesh.rs and color.rs modules contain stubs with placeholder logic that must be replaced with the real derivation.

Mathematical foundation — every constant from arc² − 832·arc + 118,300 = 0:

Arc equation roots: red arc = 182°, green arc = 650° (in ternary 364° circle)
Product: 182 × 650 = 118,300 (= ARC_PRODUCT)
Sum: 182 + 650 = 832 (= arc equation coefficient)
Coprime step: 1001 = 7 × 11 × 13; gcd(1001, 540) = 1 — guarantees full coverage of all 540 nodes in a single walk at any depth
Overlap slots: 1001 − 540 = 461 (prime) — used for sponge rekey scheduling
Recursive self-similar polygon mesh:

540 nodes per level (482 interior + 58 rim), from 11 polygons (3-gon through 13-gon) inscribed in the 364° unit circle
Self-similar: each node at depth d contains a full 540-node mesh at depth d+1
Tunable depth — Phase 1 implements depth 3, architecture supports arbitrary depth
Precision model (depth → effective bits/channel with Bézier):

Depth 1: 540 addresses → 3.03 bits/ch discrete, ~5.3 effective
Depth 2: 291,600 addresses → 6.05 bits/ch discrete, ~8.3 effective
Depth 3: 157,464,000 addresses → 9.08 bits/ch discrete, 11.3 effective (between 10-bit HDR and 12-bit cinema) — Phase 1 target
Depth 4: 85,030,560,000 addresses → 12.10 bits/ch discrete, 15.1 effective (matches 14-bit RAW camera) — future
Bézier interpolation: 4.8× improvement per level (proven), 531× at depth 4
Implementation requirements:

Derive the default sRGB↔mesh lookup table from the arc equation, the two Bézier arcs (red 182°, green 650° control points already in color.rs), and the 540-node recursive polygon mesh geometry
Implement srgb_to_mesh() to convert CSS RGB values to recursive mesh addresses at depth 3 — must use per-channel conversion through the mesh topology, not the current placeholder weighted-sum approach
Implement mesh_to_srgb() to convert mesh addresses back to RGBA for display output — must reconstruct per-channel, not the current grayscale-only stub
Implement Bézier interpolation between mesh nodes for sub-cell precision (4.8× per level)
Parallel coprime walk: gcd(1001, 540) = 1 ensures 540 steps cover all nodes — use this for LUT construction and gradient sampling
Precompute the depth-3 LUT at boot (~5.25MB) and store in kernel memory — this is the default compiled mapping, GPU-ready format for Phase 2
All compositing happens at mesh depth 3 precision — no 8-bit DWM bottleneck anywhere in the pipeline
Optional 1,080-patch calibration for print matching (vs ICC's 4,913 patches) is out of scope — default compiled mapping only
Validation: gradients must render without banding — this is the primary visual criterion. sRGB round-trip error must be ≤1 LSB per channel at depth 3.
Standalone test harness: Write a standalone test binary (separate from the browser pipeline) that computes the depth-3 LUT, renders a set of reference gradients (black→white, red→blue, dark navy #141E30→light cyan), and compares output against golden reference images (pixel-exact comparison with ≤1 LSB tolerance). This validates the math independently before integration. Run as a CI step.
Wire CPU sponge encryption on framebuffer — Per-frame TLSponge-385 rekey using sponge_rekey.rs. XOR every pixel with per-frame keystream after render. Rekey in the 461 overlap slots (1001 − 540 = 461, prime) of the coprime walk. Key advances every frame. This is the CPU XOR path — Phase 2 moves this to GPU shader. SIMD-accelerated XOR (AVX2 on x86_64, NEON on aarch64) for the encryption pass — 8MB × 30fps = 240 MB/s of XOR at the 30 FPS target, which is feasible with SIMD but marginal without it on slower CPUs. If full-frame XOR exceeds the frame budget, encrypt only dirty regions (tiles that changed since last frame) — this aligns with the dirty-rectangle tracking in the render pipeline.

Wire tab isolation via kernel tasks — Each tab runs as a separate kernel task with own stack/heap. Each tab's heap is a separate allocator region with guard pages. Page faults in a tab's region trigger task termination, not kernel panic. This is same-address-space isolation with hardware-assisted bounds checking, not separate address spaces. catch_unwind for recoverable panics. Double-panic or OOM: kernel reclaims task resources, other tabs unaffected. 30-second health check with automatic rollback on subsystem failure.

Wire keyboard input through TIS-27 to browser DOM — Serial receive (COM1/PL011/SBI) at interrupt level, TIS-27 encode before any buffer, direct kernel call to BrowserInputHandler, decode to Unicode inside Boa's DOM event handler at the last possible moment. No IPC, no shared memory buffer.

Wire z=0 distributor end-to-end — Verify the existing coprime walk (7,11,13) on 540-node ring routes browser requests through the full z-stack. Browser at z=+1 dispatches only through z=0, requests fall to z=-1 through z=-6 as needed, results bubble back. Import enforcement: the browser module imports only from crate::distributor::RequestInterface (the well-defined request/response trait). Zero imports from crate::layers::*, crate::crypto::*, crate::network::*, or any other subsystem below z=0. The distributor itself imports from layers — the browser does not. Enforced structurally via module visibility.

Update QEMU CI smoke test — Boot → full resolution init → browser subsystem OK → home page renders → tab open/close/crash recovery → cooperative watchdog terminates runaway JS → clean exit. Three verification mechanisms, all must pass:

(a) Encryption verification (raw memory ≠ expected pixels): Read raw framebuffer bytes from QEMU guest physical memory (via QEMU monitor xp command or -dump-vmstate). Compare pixel values at known coordinates (e.g., (100,100), (960,540), (1800,1000)) against the expected unencrypted RGBA values from the home page. The raw bytes must NOT match the expected pixels — this proves sponge encryption is active on the framebuffer. If raw bytes equal expected pixels, encryption is broken or bypassed.
(b) Decryption verification (display output = expected pixels): The kernel's display pipeline decrypts before scanout. Use QEMU's VNC or screenshot capture (screendump monitor command) to capture the displayed output. Pixel-sample at the same coordinates — these must match the expected RGBA values. This proves the decrypt path works correctly.
(c) Framebuffer checksum: CRC32 of the full raw framebuffer after render. This checksum covers the encrypted bytes and must match a known-good baseline (computed once and committed). If it drifts, either the render output changed or the sponge key schedule changed — both require investigation.
Additional checks: tab open/close/crash recovery, cooperative watchdog terminating runaway JS (verify via serial output that watchdog fired and tab was reclaimed).
