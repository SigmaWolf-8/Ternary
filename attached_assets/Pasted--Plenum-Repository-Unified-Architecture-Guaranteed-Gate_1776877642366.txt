## 3. Document Identity — The Three Hashes

Every document carries three orthogonal identifiers, computed at write time and stored as extended attributes.

| Hash | Attribute Name | Content | Purpose |
|:---|:---|:---|:---|
| **MDNS** | `user.mdts.mdns` | TIS‑27 hash of full document content (54 trits) | Cryptographic identity — "What exact document is this?" |
| **Classification** | `user.mdts.omega28` | 28‑trit classification vector (Rep C, 28 trits) | Structural identity — "What kind of document is this?" |
| **FP₂₈** | `user.mdts.fp28` | TIS‑27 hash of title + header outline (54 trits) | Outline fingerprint — "What does its structure look like?" |

These three hashes answer three independent questions and form the foundation for all indexing and foreign keys.

### 3.1 The 28‑Trit Classification Vector

The classification vector is derived by the Forma Codex Document Classification Engine. It consists of 27 classification trits (Who/What/Where/When/Why/How/Peace) plus the FP₂₈ fingerprint trit. Values are Rep C {1,2,3}; zero is structurally excluded (corruption detection).

The vector determines the document's **ring position** in the Z₂₇ lattice via the Chinese Remainder Theorem on the coprime triple (7,11,13), yielding a unique residue modulo 1001.

## 4. Primary and Foreign Keys

### 4.1 Primary Key — MDNS Hash

The **MDNS hash** is the primary key. It is content‑addressed: identical content yields identical MDNS. The file is stored under its classification path with the MDNS as filename.

### 4.2 Foreign Keys — Four Modes

Documents reference other documents via four FK modes, stored as extended attributes or in YAML frontmatter.

| Mode | Attribute | Value | Semantics |
|:---|:---|:---|:---|
| **FK‑by‑Identity** | `user.mdts.fk.identity.<n>` | Target MDNS hash | References exact document; broken if target deleted or content changed. |
| **FK‑by‑Classification** | `user.mdts.fk.classification.<n>` | 28‑trit vector + Hamming tolerance | References documents of a structural kind. |
| **FK‑by‑Fingerprint** | `user.mdts.fk.fp28.<n>` | Target FP₂₈ hash | References documents with a specific header outline, survives content changes. |
| **FK‑by‑AngularBacking** | `user.mdts.fk.tier.<n>` | Tier level (1‑4) + angle tolerance | References documents with sufficient geometric backing tier. |

The gatekeeper validates FKs on write and maintains an in‑memory index for fast resolution.

## 5. Guaranteed Gates — Invariant Enforcement

Every directory in the repository is a **gate**. A `.plenum-gate.toml` file (inherited from parents) defines invariants that files must satisfy when written into that directory.

### 5.1 Gate Definition

```toml
[gate]
name = "density-gate"
enforce = true

[[invariants]]
name = "density_non_negative"
check = "density >= 0"
on_violation = "block"

[[invariants]]
name = "horn_profile"
check = "rho(x) == 1/x"
on_violation = "warn"

[[attestation]]
require_signature = true
min_key_tier = 2
```

### 5.2 Invariant Examples

| Gate | Invariant | Check |
|:---|:---|:---|
| `density/` | Density non‑negative | `ρ ≥ 0` |
| `density/mass/` | Horn profile | `ρ(x) = 1/x` for defined x |
| `electromagnetic_field/` | Maxwell compliance | `∇·E = ρ/ε` (within tolerance) |
| `harmonic_modes/` | Prime chord closure | `mode ∈ {7,11,13}` or combination |
| `any` | Theorem‑45 | No coprime solution with exponents ≥3 |
| `any` | Liouville conservation | Phase‑space density conserved |

Complex checks call Array 3 daemons.

### 5.3 Gatekeeper Daemon

`plenum-gatekeeper` watches the filesystem (inotify/FSEvents/USN journal). On file write:

1. Parse content and metadata.
2. Evaluate all invariants for the directory and its ancestors.
3. **Block violation:** Move file to `.quarantine/`, write violation witness.
4. **Warn violation:** Accept file, write warning witness.
5. **Pass:** Write receipt witness, update chain head, set extended attributes.

## 6. Witnessing and Timestamping

Every file operation that passes a gate produces a **witness**—a signed, HPTP‑timestamped record in a Merkle chain.

### 6.1 Witness Chain Structure

```
.witness/
├── chain_head          # Latest chain hash (TIS‑27)
├── receipts/
│   └── YYYY-MM-DDThh-mm-ss-fffffffff_<hash>.receipt
└── violations/
    └── YYYY-MM-DDThh-mm-ss-fffffffff_<hash>.violation
```

### 6.2 Receipt Contents

- HPTP timestamp (femtosecond precision)
- File MDNS hash
- Gate path and invariants checked
- Signatures (author, gatekeeper)
- Parent chain hash → new chain hash

### 6.3 Violation Records

Include all of the above plus the failed invariant and the offending value.

## 9. Native SQL Engine (`plenum-sqld`)

The repository includes a SQL engine that presents the filesystem and extended attributes as virtual tables. It answers the 14 canonical queries (and more) with lattice‑aware operators.

### 9.1 Virtual Table `documents`

| Column | Type | Source |
|:---|:---|:---|

|:---|:---|

### 9.3 QARBAS — Continuous Incremental Maintenance

The 14 canonical queries are **QARBAS** (Queries Answered Recursively Before Asked, Statefully). The gatekeeper maintains materialized views in `.cache/`. The SQL engine serves queries directly from these caches. Updates are incremental; staleness is structurally impossible.

## 10. Encryption and Compression

### 10.1 Framework‑Native Cryptographic Primitives

| Primitive | Purpose | Parameters |
|:---|:---|:---|
| **TIS‑27** | Hash function | 54‑trit output, 4 rounds, stride 13 |
| **TL‑Sponge‑385** | AEAD, KDF | 729‑trit state, 9 rounds |
| **TL‑DSA‑87** | Signatures | 87‑trit signatures, NIST Level‑5 equivalent |
| **Rep C Run‑Length** | Compression | Variable‑length encoding of ternary data |

### 10.2 Encryption at Rest

Every file is individually encrypted:

1. Plaintext is compressed with **Rep C Run‑Length**.
2. A file encryption key (FEK) is derived: `FEK = TL‑Sponge‑385::derive(MDNS, salt)`. Salt is a random 27‑trit nonce stored in `user.mdts.salt`.
3. Compressed plaintext is encrypted with **TL‑Sponge‑385 AEAD**. Ciphertext is written to disk.
4. FEK is wrapped with the repository master key (held by Ninja Exec) and stored in `user.mdts.fek`.

**Encryption Gate:** Gatekeeper verifies presence of wrapped FEK, unwraps via Ninja Exec, and verifies AEAD tag. Failure → quarantine.

### 10.3 Encryption in Transit

All inter‑component communication uses **PlenumLAN secure channels**:

- Mutual TLS with TL‑DSA‑87 certificates.
- Perfect forward secrecy via ephemeral TL‑Sponge‑385 keys.
- AEAD encryption of all messages.

**mTLS Gate:** Daemons only connect to peers presenting valid certificates signed by the Plenum Root CA.

### 10.4 Compression

- **At rest:** Rep C Run‑Length before encryption (~40% reduction for Markdown/ternary data).
- **In transit:** Same compression before AEAD encryption.

**Compression Bomb Gate:** Decompressor rejects files expanding >100× compressed size.

## 11. Ninja Exec — Local Signing Agent

**Ninja Exec** is the sole holder of private key material. It runs as a daemon with keys protected by `mlock`.

**Responsibilities:**

- Manage repository master key (FEK wrapping/unwrapping).
- Manage TL‑DSA‑87 key pairs for service identities.
- Sign witness receipts, legal headers, and API responses.
- Verify signatures on incoming documents.
- Provide Unix socket API (`/run/plenum/ninja.sock`).

**API:**

| Command | Input | Output |
|:---|:---|:---|
| `SIGN <key_id> <data>` | Key ID, data | `SIGNATURE <sig>` |
| `VERIFY <pubkey> <data> <sig>` | Public key, data, signature | `VALID` or `INVALID` |
| `WRAP_KEY <key_id> <plaintext>` | Key ID, plaintext key | `WRAPPED <ciphertext>` |
| `UNWRAP_KEY <wrapped>` | Wrapped key | `UNWRAPPED <plaintext>` |

**Key Access Gate:** Clients must present a capability token (signed assertion of permissions) issued by the Plenum Directory Service. Tokens are short‑lived.

**CLI:** `ninja-cli` provides administrative commands for key generation, rotation, and manual signing.

## 13. Operational Flow — A File's Journey

1. **Creation:** Application writes document to appropriate family directory (e.g., `harmonic_modes/atomic_orbitals/<mdns>.md`).
2. **Gatekeeper intercepts:** Filesystem event triggers `plenum-gatekeeper`.
3. **Legal header check:** Verifies YAML frontmatter and signature.
4. **Invariant evaluation:** Calls Array 3 daemons for complex checks.
5. **FK validation:** Verifies all foreign key targets.
6. **Encryption & compression:** If not already done, applies Rep C Run‑Length and TL‑Sponge‑385 AEAD.
7. **Witness generation:** On pass, writes receipt, updates chain head, sets extended attributes.
8. **Quarantine:** On block violation, moves file to `.quarantine/` and writes violation witness.
9. **Cache update:** Gatekeeper updates in‑memory index and QARBAS materialized views.
