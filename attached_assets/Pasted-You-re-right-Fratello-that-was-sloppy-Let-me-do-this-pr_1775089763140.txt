Recommendation 1: Canonicalize the Four-Primary Blend Formula and Retire the Bézier Path
The whitepaper specifies:
R = (a·R₉₁ + b·R₁₈₂ + c·R₂₈₆ + (1001−a−b−c)·R₃₆₄) / 1001
The live color.rs uses quadratic Bézier interpolation with ARC_RED=182, ARC_GREEN=650, ARC_BLUE=240 as control points. These produce different colour output for the same walk index. The four-primary formula should be canonical because it is structurally congruent with the coprime walk — the weights (a,b,c) are the walk coordinates, so colour becomes a direct geometric property of position on the 3-torus. The Bézier path breaks this correspondence by introducing an interpolation curve that has no relationship to the (7,11,13) structure. Concretely: at walk index i=500, the four-primary formula distributes weight across all four UV bands proportionally to (a₅₀₀, b₅₀₀, c₅₀₀), which are deterministic permutation values. The Bézier path at the same index evaluates a quadratic curve at t=500/1001 using arc-derived control points — a completely different value with no coprime structure preserved. Retire the Bézier interpolation to a legacy compatibility path and implement the four-primary formula as the sole colour pipeline before any GPU work begins.
Recommendation 2: Formalize the sRGB Derivation or Reclassify It
The mod-256-then-round-to-10 derivation in Section 3.1 is the weakest link in the mathematical chain. Example: 91 × 7 = 637, 637 mod 256 = 125 → 120. Two problems. First, mod 256 is a binary operation (2⁸) injected into a ternary-first system with no derivation from the axiom. Second, rounding 125→120 is described as “preserving prime ratios” but 120 = 2³×3×5 while 125 = 5³ — neither has any relationship to (7,11,13). Compare this to how every other constant in the framework traces back to π=14: the full circle 364 = 2×182 = 2×14×13, the repunits Rₙ = (3ⁿ−1)/2, the discriminant 144=12². The sRGB values don’t have this lineage.
Two paths forward. Path A: derive display values from framework primitives. For instance, map the four UV integers through Rep C trit encoding and extract channel values from the ternary digits directly — this keeps everything in base-3. The base-3 table in Section 3.2 already shows this is natural (11110₃=120, 20200₃=180, 12221₃=160, 21102₃=200). Investigate whether these ternary representations have structural significance within Rep C rather than treating them as after-the-fact conversions. Path B: explicitly classify the sRGB mapping as a display-side convention (analogous to how PlenumNET maps Rep C addresses to IPv4/IPv6 for compatibility) and move it out of Section 3 into Section 4 under Display HAL. Either path eliminates the gap; leaving it as-is undermines the “single axiom” thesis.
Recommendation 3: Specify the Integer Ray-Sphere Intersection Before Writing Shaders
The whitepaper says “exact integer-scaled sphere equation” and the component review confirms no such equation exists in code. This is the single largest specification gap because every downstream rendering operation depends on it. The standard ray-sphere intersection solves:
|O + tD|² = r² → t² |D|² + 2t(O·D) + |O|² − r² = 0
In floating point this is trivial. In exact integer arithmetic with coordinates scaled by 1001, you get:
|O|² = Ox² + Oy² + Oz² where each component is in range [−1001, 1001]
The discriminant Δ = 4(O·D)² − 4|D|²(|O|²−r²) can reach magnitudes on the order of 1001⁴ ≈ 10¹², which overflows u32 and requires u64 or u128 intermediates. This has direct implications for the shader: SPIR-V compute shaders support 32-bit integers natively but 64-bit integer support is an optional Vulkan feature (shaderInt64) not available on all GPUs. This needs a TM-class specification that defines the exact coordinate scaling factor, the precision requirements at each arithmetic step, and whether the intersection test can be restructured to avoid the overflow (e.g., by normalizing D to have |D|²=1001² via precomputation, reducing the discriminant magnitude). Without this, the shader author will make ad hoc precision decisions that may introduce the very floating-point compromises the architecture is designed to eliminate.
Recommendation 4: Use wgpu Instead of Raw Vulkan
The component review shows the GpuBackend trait exists but no GPU library is integrated. The whitepaper specifies Vulkan. Use wgpu instead, for three concrete reasons:
	1.	Cross-platform from day one. YODA runs ARM64 Windows (Snapdragon). Raw Vulkan on Windows ARM64 has driver maturity issues. wgpu abstracts to DX12 on Windows (mature ARM64 support), Metal on macOS, and Vulkan on Linux — one codebase, three backends.
	2.	WGSL is a better fit for integer compute than SPIR-V via rust-gpu. rust-gpu is pre-1.0 and its integer arithmetic support has known gaps (no native u64, limited control over overflow behavior). WGSL supports u32 natively in compute shaders and the wgpu ecosystem is actively maintained by the Rust graphics community. You can write the ray-marcher in WGSL, validate correctness, and later target SPIR-V or the ternary ISA when those backends mature.
	3.	Shader compilation is handled at runtime. wgpu compiles WGSL→SPIR-V→native at pipeline creation time. This means the same shader source can target different backends without a separate SPIR-V compilation toolchain, simplifying CI/CD.
The existing RenderBackend trait already abstracts the backend — swapping “Vulkan” for “wgpu” changes the implementation, not the interface. The Phase 6 ternary transition is unaffected because TernaryGpuBackend would implement the same trait regardless.
Recommendation 5: Split Phase 0 Into Document Rendering and Shape Exclusion
The review rates PlenumText at ~40% complete. The missing pieces have very different complexity profiles. Markdown parsing and style groups are well-understood problems — pulldown-cmark is a mature Rust crate, and style groups are essentially CSS class abstractions that the existing taffy+rust-cssparser stack already supports structurally. These could ship quickly as a usable document renderer.
Text-wrap-around-shapes (exclusion zones) is a fundamentally harder problem. It requires computing the intersection of text flow regions with arbitrary shape contours at each line, then adjusting the layout engine’s available width per line. taffy doesn’t support this — it computes rectangular regions. You’d need to either extend taffy’s layout algorithm or implement a post-layout reflow pass that adjusts line boxes after shape intersection. Image contour tracing (converting a raster image to a polygon exclusion boundary) adds another layer. Shipping these together with basic markdown means the simple, high-value work (readable documents in the kernel browser) is blocked by the hard research problem (arbitrary exclusion geometry). Decouple them. Ship markdown+styles first, then layer exclusion zones as a separate deliverable.
Recommendation 6: Define the Integer Framebuffer Format
The whitepaper states “the framebuffer stores integer triples (R,G,B) directly” and the review confirms TLSponge-385 encryption is applied before display. But nowhere is the per-channel bit depth specified. This matters because:
	∙	If channels are u8 (0–255): the four-primary blend formula’s division by 1001 truncates heavily. For example, if a=300, b=400, c=200, d=101, and we compute the R channel: (300×120 + 400×0 + 200×0 + 101×160)/1001 = (36000+16160)/1001 = 52160/1001 = 52. That’s a lot of precision loss in the integer division. The walk’s fine-grained coverage of the 3-torus is being crushed into 8-bit output.
	∙	If channels are u16 (0–65535): the blend formula preserves much more of the walk structure, but the TLSponge-385 encryption and the display driver both need to know this. The existing CPU renderer (CpuFramebuffer via tiny-skia) uses u8 RGBA. A u16 pipeline requires a different framebuffer format and a dithering or quantization step at display time.
	∙	The ternary hardware path (Phase 6) presumably uses trit-based channel encoding. The framebuffer format should be designed now so that u8→u16→trit transitions don’t require re-architecting the compositor.
Specify this in the whitepaper as part of Section 4, and ensure the four-primary blend formula includes the precision analysis showing that the chosen bit depth preserves the coprime walk’s coverage properties.
Recommendation 7: Add a Notation Section
The whitepaper uses “degree” to mean 1/364th of a circle, “nm” as integer labels for UV bands (not physical nanometers in the conventional sense — 91nm EUV doesn’t propagate in air), and “π” as the integer 14 rather than the transcendental. A reader encountering this for the first time will misread every equation until they recalibrate. A half-page Section 0 defining the notation system eliminates this. It also establishes that all arithmetic is over ℤ, which is the single most important architectural constraint and currently has to be inferred from context.
Recommendation 8: The Compositor Needs an Integer Alpha Specification
Section 4.4 mentions RenderColor::blend_over using alpha blending, and the whitepaper describes compositor layer blending as “integer arithmetic.” Standard alpha compositing is:
C_out = α·C_fg + (1−α)·C_bg
If α is a float in [0,1], this isn’t integer. If α is an integer fraction (e.g., k/1001 where k is a walk index), then the formula becomes:
C_out = (k·C_fg + (1001−k)·C_bg) / 1001
This is structurally identical to the four-primary blend formula, which is elegant — it means compositing and colouring use the same arithmetic primitive. If this is intentional, the whitepaper should state it explicitly and show that the compositor’s blend operation is a degenerate case of the colour formula (two sources instead of four, same 1/1001 quantization). If it’s not intentional, it should be, because it unifies the rendering pipeline under a single integer division operation.

These eight recommendations address the structural gaps between spec and implementation. The mathematical core is sound. The risk is in the unspecified intermediary layer — the places where “exact integer arithmetic” is asserted but the specific integer forms aren’t written down. Pin those down and the build has a clean critical path from constants through shaders to framebuffer.
