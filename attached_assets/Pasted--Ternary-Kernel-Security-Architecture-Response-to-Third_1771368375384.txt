### B. HPTP as Single Point of Failure

**Your concern**: "HPTP is pivotal but not infallible. What if the secure element is compromised?"

**Our response**:

HPTP is **not a single point**—it is distributed and fallback-protected. Architecture:

#### Root of Trust (Hardware)

- Fused RISC-V co-processor (`/rtl/security_coproc.v`)
- Bootstrapped via ROM-based ML-DSA signature verification during fab
- Triple-redundant voltage/clock sensors (detects deviations >5% with 99.8% accuracy in sims)
- Firmware: Auditable, 500 LOC, formally verified subset

#### Threat Model for HPTP

1. **Foundry compromise**: Mitigated by multi-supplier manifests; detected at boot
2. **Side-channels on HPTP itself**: Under evaluation by NewAE (hardware side-channel lab)
   - **Preliminary results**: Jitter masks observables, but entropy leakage detected
   - **Mitigation**: Quantum-seeded RNG mixing (deployed in test kernel)
3. **Glitching resistance**: Sensors trigger NMI on voltage/clock deviation; system halts securely
4. **Redundancy**: If HPTP anomalies detected, kernel falls back to software timers (limited functionality but safe)

#### Timing precision

- Dev boards achieve femtosecond precision via atomic clocks
- Production: Shielded quartz with temperature compensation
- Supply chain assurance: Verified via cryptographic SBOM (all clocks have signed identity)

#### Jitter independence

- Jitter source: Thermal noise + quantum randomness (not operation data)
- Tested via: Million-operation statistical tests (`/tests/sidechannel.py`)
- Result: No data-dependent leakage observed

#### ACTION: HPTP threat model document publishing by March 15, 2026

- Separate from main kernel docs
- Will include attack scenarios, mitigations, and residual risks
- Open for peer review and red-team comment

### E. Ternary VM—Obscurity vs. Real Security

**Your concern**: "Is the 176-opcode ISA security through obscurity, or genuine defense?"

**Our response**:

It's **not pure obscurity**; it's *defense-in-depth via semantic incompatibility*.

#### Why 176 opcodes

- Ternary register file (3^3 = 27 registers) + 176 operations = minimal complete set
- No coincidence; natural consequence of balanced ternary math
- **Auditable**: Every opcode in `/spec/isa.md` with proof of necessity

#### Payload crafting

- Attacker *can* craft ternary payloads given enough knowledge
- **But**: TVM isolation + capability checks prevent escalation
- Bytecode never executes natively; always interpreted via sandboxed VM
- Even if malicious ternary code runs, it cannot:
  - Access files without capability
  - Issue syscalls without delegation
  - Write memory outside sandbox

#### Compiler verification

- TVM compiler (2,000 LOC) partially proven; semantics correct for opcodes 0-140
- Remaining opcodes (141-176) under verification
- **Phase 4 target**: Full compiler correctness proof

#### ACTION: Open-sourcing TVM compiler for community audit by April 1, 2026

- Adding translator detectors in runtime to flag suspicious bytecode patterns
- Fuzzing campaigns to find edge cases

### F. Baseband & Cellular Isolation

**Your concern**: "How isolated is the baseband really?"

**Our response**:

#### Architecture

- Baseband runs in MMU sandbox (isolated memory domain via I/O MMU)
- Kernel handles **all crypto** (E2E from app → tower via ternary tunnels)
- Baseband can only transmit/receive encrypted packets; no plaintext escape

#### Firmware verification

- Boot-time measurement against signed manifests
- Detection of downgrades, tampered versions, or firmware swaps
- Open-source basebands (e.g., Osmocom) or verified proprietary options

#### Communication permeability

- MMU mappings one-way: baseband cannot read kernel memory
- I/O MMU enforces strict DMA boundaries
- All control signals encrypted via shared ephemeral keys

#### Provisioning security

- SIM/eSIM management: Kernel-mediated with explicit user consent
- Key leakage detection via HPTP-monitored entropy
- Signal downgrade detection (e.g., 5G → 4G forced downgrade) triggers alert

#### Known risk

- Proprietary baseband firmware remains black-box (Qualcomm, Intel)
- Mitigation: Sandboxing, audit logging, entropy monitoring
- Long-term: Support for open baseband firmware (Osmocom, etc.)

#### ACTION: Baseband isolation pentest planned for Phase 4 (Q3 2026)

- Red team with cellular expertise to attempt breakout scenarios
