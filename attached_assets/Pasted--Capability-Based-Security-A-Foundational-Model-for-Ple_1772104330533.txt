## 1. PlenumNET Already Operates a Capability System

Before defining capability-based security in the abstract, it is important to establish that PlenumNET is not proposing to build one. It already runs one.

PlenumNET's RFC 3161 timestamp tokens satisfy every formal requirement of a capability:

- **Unforgeable.** Cryptographically signed with TL-DSA.
- **Self-contained.** No central database lookup is needed for verification. The token carries its own proof.
- **Bearer-verified.** Anyone holding the token can present it to any verifier — a court, an auditor, a counterparty — and the verifier can confirm its authenticity independently.
- **Authoritative.** The token carries the authority to prove that a specific hash existed at a specific time. That authority is exercised by presenting the token. No further permission is needed.

These tokens are in production today. They are the foundation of PlenumNET's court-admissible evidence chain. The strategic extension described in this document takes the same model — unforgeable, self-contained, bearer-verified, authoritative — and applies it to the **authorization layer**. Every permission in PlenumNET becomes a capability with the same properties that already make our timestamps trustworthy.

## 2. What Is Capability-Based Security?

Capability-based security is a design paradigm in which access to resources is granted not by identity (who you are) but by possession of an unforgeable token — a **capability** — that inherently conveys both **designation** (what resource) and **authority** (what operations are permitted). Possession of the capability **is** the authority.

Capabilities are often compared to physical keys: possessing the key grants you the right to enter the room, regardless of your name. The key itself is unforgeable and can be passed to others (delegation) without the original issuer's involvement.

**Authentication and authorization remain separate.** Capabilities replace identity as the *authorization* mechanism, not as the *authentication* mechanism. PlenumNET always knows who holds a capability — it simply doesn't use identity to decide what they can do with it. Regulated customers require both. Capability-based security strengthens the authorization layer while leaving the authentication layer intact.

### Core Principles

| Principle | Description |
|-----------|-------------|
| **Unforgeability** | Capabilities are impossible to counterfeit. PlenumNET achieves this through TL-DSA post-quantum signatures. |
| **Possession as Authority** | If you hold a capability, you can use it. There is no central list to consult. |
| **Delegation** | A capability can be passed from one entity to another, or attenuated (restricted) and then passed, transferring a narrower authority without issuer involvement. |
| **Fine-Grained Authority** | A capability can be as narrow as "send one notification template to one recipient domain during one time window" or as broad as "administer the entire tenant." The principle of least privilege is enforced by design. |
| **No Ambient Authority** | Without a capability, an entity cannot even name a resource. You cannot accidentally use a privilege you have; you must explicitly invoke a capability. This eliminates confused-deputy attacks. |

### How It Differs from ACLs

| Aspect | ACL-Based | Capability-Based |
|--------|-----------|------------------|
| **Authority check** | "Who are you?" → look up permissions | "What do you hold?" → verify the token |
| **Delegation** | Requires an administrator to update the list | Holder attenuates and passes the token directly |
| **Revocation** | Modify the central list | Token expires on HPTP schedule — no list to modify |
| **Identity dependency** | Requires a global identity system for authorization | Identity used for authentication only |

### Solving Confinement

The security industry treats the confinement problem — preventing a capability holder from copying and sharing a token — as unsolvable. That conclusion is based on a specific assumption: that capabilities are static text tokens verified against manipulable clocks. PlenumNET operates in a different problem space. It has an authoritative clock, post-quantum signatures, and the ability to bind capabilities to hardware. Under those conditions, confinement is solvable.

PlenumNET solves confinement through three mechanisms working together:

**1. Hardware-Bound Capabilities.** The token is bound to a physical device — a TPM, a secure enclave, or a hardware security module. The capability contains a reference to a public key whose private half never leaves the hardware. Every time the token is used, the holder must prove possession of that private key through a live challenge-response signed with TL-DSA. Copy the token text all you want — without the physical device, it is cryptographic garbage.

**2. HPTP Challenge-Response.** Instead of presenting a static token, each use requires a fresh HPTP-anchored nonce from PlenumNET's timing engine. The holder signs the nonce with their hardware-bound key. The nonce is valid for one HPTP window. You cannot replay it because the window is gone. You cannot forge it because you do not have the key. You cannot precompute it because you do not know the nonce until the moment of use.

**3. Single-Use Capability Chains.** Each use of a capability generates the next valid token in a cryptographic chain. Use #1 produces the seed for Use #2. If someone copies a token after Use #1, their copy is only valid if they use it before the legitimate holder does — and when the legitimate holder uses it, the copy is permanently dead. First use wins, verified by HPTP timestamp.

Combined, a PlenumNET capability is:

- **Device-bound** — the key cannot be copied.
- **Nonce-validated** — the token cannot be replayed.
- **Consumed on use** — the token cannot be stockpiled.
- **TL-DSA signed end-to-end** — the token cannot be forged, even with a quantum computer.
- **HPTP-timestamped** — every use is recorded with nanosecond precision in a tamper-proof audit trail.

The industry says confinement is unsolvable because they are working with static text tokens and system clocks. PlenumNET has neither limitation.

**Implementation phasing.** The confinement solution described above — hardware binding, HPTP nonce challenge-response, and single-use chains — becomes operational in **Phase 4** of the roadmap. Phases 1–3 deliver typed capability tokens with TL-DSA signatures, HPTP-bound expiration, and HMAC-chained delegation. These are significant advances over traditional bearer tokens (fine-grained constraints, post-quantum signing, nanosecond-precise expiration, Merkle-chained audit trail), but they remain bearer tokens until Phase 4 binds them to hardware. The confinement claims in this document apply to the Phase 4+ system. Prior phases reduce the value of a copied token (short-lived, narrowly scoped, fully auditable) without eliminating the possibility of copying it.

### Relationship to Multi-Factor Authentication

Capability-based security does not replace multi-factor authentication. It adds to it.

Authentication answers "who are you?" Authorization answers "what are you allowed to do?" Traditional systems combine both into a single check — verify the user's identity, then look up their permissions on a central list. PlenumNET separates them cleanly. Authentication remains its own layer. Capabilities handle authorization independently.

In practice, a PlenumNET-secured interaction works like this:

1. **Factor 1 — something you know.** The user provides a password or PIN.
2. **Factor 2 — something you have for identity.** The user confirms via an authenticator app, SMS code, or biometric.
3. **The system authenticates the user.** Identity is confirmed.
4. **The system presents the user's hardware-bound capability.** The capability token — bound to the user's TPM, secure enclave, or HSM — is invoked. The device signs an HPTP-anchored nonce with its private key, proving the capability is being exercised on the authorized hardware.

The hardware-bound capability functions as a **third factor** — something you physically possess that cannot be separated from the device and cannot be duplicated. It is not a replacement for the first two factors; it is an additional layer that binds authorization to a specific physical device after identity has been confirmed.

This gives PlenumNET customers a natural path to **3FA**:

| Factor | What It Proves | How It Works |
|--------|---------------|--------------|
| **Something you know** | Identity (knowledge) | Password, PIN |
| **Something you have** (identity) | Identity (possession) | Authenticator app, hardware token, biometric |
| **Something you have** (authorization) | Authority + device binding | Hardware-bound capability with TL-DSA signed HPTP nonce |

The first two factors prove the user is who they claim to be. The third factor proves the user holds a valid, non-transferable authorization on the correct physical device. All three must pass. Compromise any single factor and access is denied.

For regulated customers — banks, government agencies, law firms — this separation is critical. Auditors can independently verify that the correct identity was authenticated (factors 1 and 2) **and** that the correct authorization was exercised on the correct device (factor 3), with both events HPTP-timestamped and Merkle-chained in the audit trail.

## 3. Historical Context: Why PlenumNET Succeeds Where Others Failed

Capability-based systems have a long history in operating systems (KeyKOS, CapROS, IBM System/38) and programming languages (E, Caja). They failed to achieve mainstream adoption for two reasons:

1. **Revocation.** How do you take back a key that's been handed out? Traditional capability systems had no good answer.
2. **Confinement.** How do you prevent the holder from copying the key? The entire industry accepted this as unsolvable.

PlenumNET resolves both:

- **Revocation** is eliminated as a problem. Capabilities are HPTP-bound. They die on schedule. You don't take the key back — you issue keys that destroy themselves at the designated nanosecond, verified against an authoritative clock that no party can dispute.
- **Confinement** is solved by binding capabilities to physical hardware, requiring live HPTP-anchored challenge-response for each use, and consuming the token on use through single-use cryptographic chains. A copied token without the hardware key is cryptographic garbage. A replayed token without a valid nonce is rejected. A reused token after the legitimate holder has advanced the chain is permanently dead. (See Section 2, "Solving Confinement" for full detail.)

Modern interest in capabilities has surged with Zero Trust Architecture. ZTA's principle — "never trust, always verify" — aligns directly with capabilities: every request must carry its own proof of authority, independent of network location or user identity. PlenumNET provides the cryptographic mechanism to make Zero Trust operational, with a critical addition that no other zero-trust vendor offers: **verification of the time itself.**

## 4. From Role Tokens to Capability Tokens

### 4.1. Current State

PlenumNET clients authenticate using JWTs containing claims like `appId` and `role`. These tokens are proto-capabilities — cryptographically signed, passed as bearer tokens, supporting least privilege through different roles.

The limitation is granularity. All `app`-role tokens can send any template. There is no way to issue a token that says "send only `maestro.review.assigned`, only to `@lawfirm.ca` recipients, only 10 times, only until 3 PM today."

| Current RBAC Limitation | Capability-Based Solution |
|-------------------------|---------------------------|
| All `app` tokens can send any template | Capabilities minted for specific templates, recipients, and time windows |
| Delegation requires sharing the full token or involving an administrator | Capabilities are attenuated and passed without exposing the parent token |
| Revocation requires central coordination (token blacklists) | Capabilities are HPTP-bound — they expire exactly when intended |

### 4.3. Typed Constraint Registry

Capability constraints are drawn from a typed, versioned registry. Every verifier in the system — Kong plugin, Rust service, TypeScript middleware — imports and enforces constraints identically. There are no freeform objects. Unknown constraint types fail closed.

```typescript
// shared/types/capability-constraints.ts

export const CONSTRAINT_REGISTRY_VERSION = "1.0";

/**
 * Discriminated union of all valid constraint types.
 *
 * Derived from PlenumNET's operational use cases: notification templates,
 * evidence vaults, Maestro documents, multi-tenant access, and
 * geographic/network restrictions.
 *
 * Adding a new constraint type requires:
 *   1. Adding it to this union
 *   2. Adding validation logic to validateConstraint()
 *   3. Updating the Kong plugin's semantic map
 *   4. Mirroring the change in the Rust constraint registry
 *   5. Incrementing the registry version
 */
export type CapabilityConstraint =
  | { type: "recipient_domain"; value: string }       // "@lawfirm.ca" or "*.gov.ca"
  | { type: "vault_id"; value: string }               // specific evidence vault
  | { type: "template"; value: string }               // "maestro.review.assigned"
  | { type: "max_uses"; value: number }               // usage count limit, audit-enforced
  | { type: "ip_range"; value: string }               // CIDR notation "10.0.0.0/8" — IPv4 only.
                                                       // IPv6 support (128-bit address space) requires
                                                       // a separate constraint type or library extension.
  | { type: "geo_country"; value: string[] }          // ISO 3166-1 alpha-2 codes
  | { type: "document_id"; value: string }            // specific Maestro document
  | { type: "project_id"; value: string };            // specific Maestro project scope

export interface VerificationContext {
  recipient?: string;
  vault_id?: string;
  template?: string;
  usage_count?: number;
  source_ip?: string;
  source_country?: string;
  document_id?: string;
  project_id?: string;
}

/**
 * Validates a single constraint against the request context.
 *
 * max_uses is enforced by the audit layer, not at validation time.
 * The token's HPTP expiration is the hard enforcement boundary.
 */
export function validateConstraint(
  constraint: CapabilityConstraint,
  context: VerificationContext
): boolean {
  switch (constraint.type) {
    case "recipient_domain": {
      if (!context.recipient) return false;
      const pattern = constraint.value;
      if (pattern.startsWith("*.")) {
        return context.recipient.endsWith(pattern.slice(1));
      }
      return context.recipient.endsWith(constraint.value);
    }
    case "vault_id":
      return context.vault_id === constraint.value;
    case "template":
      return context.template === constraint.value;
    case "max_uses":
      // max_uses is a soft limit enforced within audit latency. Between the audit
      // service recording use N and the next request arriving, a token may briefly
      // exceed its limit. HPTP expiration is the hard cutoff — the token dies at
      // the designated nanosecond regardless of usage count. The audit trail records
      // every use, so overages are always detectable and attributable after the fact.
      return true;
    case "ip_range":
      return context.source_ip ? isIpInCidr(context.source_ip, constraint.value) : false;
    case "geo_country":
      return context.source_country ? constraint.value.includes(context.source_country) : false;
    case "document_id":
      return context.document_id === constraint.value;
    case "project_id":
      return context.project_id === constraint.value;
    default:
      // Unknown constraint type = deny. Fail closed.
      return false;
  }
}

export function validateAllConstraints(
  constraints: CapabilityConstraint[],
  context: VerificationContext
): { granted: boolean; failed: CapabilityConstraint[] } {
  const failed = constraints.filter(c => !validateConstraint(c, context));
  return { granted: failed.length === 0, failed };
}

// IPv4 CIDR matching. JavaScript bitwise operators work on 32-bit signed integers,
// so IPs above 127.255.255.255 produce negative numbers. The >>> 0 coercion
// converts to unsigned 32-bit, ensuring correct comparison for all IPv4 addresses.
// IPv6 is not supported by this function — see ip_range constraint note above.
function isIpInCidr(ip: string, cidr: string): boolean {
  const [range, bits] = cidr.split("/");
  const mask = (~(2 ** (32 - parseInt(bits)) - 1)) >>> 0;
  const ipNum = (ip.split(".").reduce((acc, oct) => (acc << 8) + parseInt(oct), 0)) >>> 0;
  const rangeNum = (range.split(".").reduce((acc, oct) => (acc << 8) + parseInt(oct), 0)) >>> 0;
  return (ipNum & mask) === (rangeNum & mask);
}
```

```rust
fn ip_in_cidr(ip: Ipv4Addr, cidr: &str) -> bool {
    let parts: Vec<&str> = cidr.split('/').collect();
    if parts.len() != 2 { return false; }
    let Ok(range) = parts[0].parse::<Ipv4Addr>() else { return false };
    let Ok(bits) = parts[1].parse::<u32>() else { return false };
    if bits > 32 { return false; }
    let mask = if bits == 0 { 0u32 } else { !0u32 << (32 - bits) };
    (u32::from(ip) & mask) == (u32::from(range) & mask)
}
```

## 5. HPTP-Bound Expiration: The Core Differentiator

Every capability token carries an `exp` field measured in nanoseconds — anchored to PlenumNET's HPTP timing engine, not to the client's system clock. When a token expires at a designated nanosecond, the verifier checks against HPTP. No other time source is consulted.

This eliminates:

- **Clock-skew replay attacks.** A client cannot set their clock back to reuse an expired token. The verifier's time source is HPTP.
- **Ambiguous expiration.** Two servers cannot disagree on whether a token is valid because both check the same authoritative clock.
- **Forensic disputes.** Opposing parties cannot argue about whether an action occurred before or after an authorization expired. The HPTP timestamp is definitive.

**On precision.** The HPTP mathematical framework resolves to **femtosecond** precision. Current hardware implementations deliver **nanosecond** accuracy — already far beyond any competing timing infrastructure. Femtosecond capability is inherent to the architecture and will be realized as commercially available timing hardware advances to match the mathematical model. The math is ready. The hardware will follow.

## 7. Delegation: HMAC-Chained Attenuation

A tenant holding a root capability can attenuate it — adding restrictions — and pass the restricted version to a partner, auditor, or contractor without contacting PlenumNET. The root token is signed with TL-DSA. Each attenuation appends a caveat sealed with HMAC. When the token expires, every caveat in the chain dies with it.

```
Root capability (signed by PlenumNET, TL-DSA)
  └── Attenuated: restrict to template "maestro.review.assigned" (HMAC caveat)
       └── Attenuated: restrict to recipient "@lawfirm.ca" (HMAC caveat)
            └── Attenuated: restrict to 5 uses, expires 2026-03-01 (HMAC caveat)
```

Verification walks the chain: verify the root TL-DSA signature, then verify each HMAC caveat in order. If any link fails, the capability is rejected.

**Key derivation.** The HMAC chain follows the macaroon construction: the root capability's TL-DSA signature is used to derive the first HMAC key (via HKDF or similar KDF). Each subsequent caveat's HMAC key is the HMAC output of the previous caveat. This means:

- The verifier only needs the root's public key (to verify the TL-DSA signature) and can then derive every HMAC key in the chain by walking forward from the root.
- No delegator's private key or identity needs to be looked up — there is no centralized key directory.
- A holder who receives a token at caveat depth N can add caveat N+1 because they can compute the key for depth N+1 from the HMAC at depth N. But they cannot remove or modify any earlier caveat without breaking the chain.

```
Root TL-DSA signature → HKDF → key₀
key₀ + caveat₀ → HMAC₀ = key₁
key₁ + caveat₁ → HMAC₁ = key₂
key₂ + caveat₂ → HMAC₂ = key₃
...
```

Any holder can further restrict a capability. No holder can expand one. This is the principle of attenuation — authority can only diminish as it passes through the delegation chain, never grow.

**Quantum safety of the delegation chain.** HMAC is a symmetric cryptographic construction — it uses a shared secret key and a hash function. It does not rely on the mathematical problems (integer factoring, discrete logarithms) that quantum computers threaten via Shor's algorithm. The best quantum attack against HMAC is Grover's algorithm, which halves the effective security level. HMAC-SHA256 with a 256-bit key retains 128 bits of security against a quantum adversary — fully secure by NIST post-quantum standards. The complete chain is quantum-safe at every layer: TL-DSA root signature (post-quantum), HMAC caveats (quantum-resistant by nature), HPTP expiration (not a cryptographic target).

```typescript
  details: {
    resource?: string;
    result?: "granted" | "denied";
    failed_constraints?: CapabilityConstraint[];
    parent_jti?: string;                  // for delegation: parent token ID
    attenuations_applied?: string[];      // for delegation: what was restricted
  };
}
```

The chain:

- **Event A**: Tenant root capability issued (timestamped, TL-DSA signed, hash recorded).
- **Event B**: Tenant delegates a restricted capability to a law firm auditor (timestamped, signed, includes hash of Event A).
- **Event C**: Auditor uses the capability to access an evidence vault (timestamped, signed, includes hash of Event B).
- **Event D**: Capability expires at the designated HPTP nanosecond (recorded automatically).

Any investigator can verify the entire chain. Altering any single event visibly breaks the Merkle links. This is not reconstructed from scattered log files — it is a cryptographic proof chain that assembles itself as work happens.

## 16. Anticipated Questions

The following questions will arise from CISOs, cryptographers, regulators, legal counsel, and investors reviewing this architecture. They are addressed here so PlenumNET stays ahead of every conversation.

### "What happens if the hardware device is lost, stolen, or destroyed?"

The capability is bound to the device's private key. If the device is gone, the capability is gone — that is the point. No one can extract the key and use it elsewhere. Recovery follows a controlled reissuance path: the user authenticates through standard 2FA, their lost device's capabilities are revoked (all active tokens associated with that device's public key are marked revoked in the audit trail), and new capabilities are issued bound to a replacement device. The audit trail records the revocation event, the reissuance event, and the reason — producing a complete chain of custody even across device transitions. There is no "master bypass." A stolen device without the user's authentication factors is a brick holding expired, nonce-dependent tokens.

### "What if PlenumNET's HPTP service goes offline?"

Capabilities are self-contained and carry their own expiration timestamp. Verification does not require a live call to HPTP for every request — the verifier holds a synchronized HPTP clock that is regularly calibrated against PlenumNET's authoritative source. If the synchronization link is temporarily interrupted, the local clock continues operating within its calibrated drift tolerance. Capabilities issued before the interruption remain valid and verifiable. New capability issuance is paused until HPTP connectivity is restored, because PlenumNET will not issue a token it cannot timestamp authoritatively. This is a deliberate design choice — availability is temporarily reduced to preserve the integrity guarantee that every capability carries a trustworthy timestamp. A system that issues tokens with unreliable timestamps is worse than a system that pauses until it can do it correctly.

### "What if we need to revoke a capability immediately, before it expires?"

HPTP-bound expiration is the primary revocation mechanism, but emergency revocation is supported. A revocation event is published to a lightweight revocation list (signed with TL-DSA, HPTP-timestamped, Merkle-chained into the audit trail). Verifiers check this list as part of validation. The revocation list is short by design — it only contains tokens that were killed before their natural expiration. Once a token's HPTP expiration passes, it falls off the list automatically. This is not a return to centralized ACLs — the list is a narrow, time-bounded exception for emergency use, not the primary authorization mechanism. The audit trail records both the revocation event and the reason, maintaining the complete chain of custody.

### "TL-DSA signatures are larger and slower than classical algorithms. What is the performance impact?"

TL-DSA signatures are larger than ed25519 (approximately 2-4 KB versus 64 bytes) and signing/verification is computationally heavier. This is the cost of post-quantum security. PlenumNET accepts this cost deliberately because the alternative — using classical signatures and hoping quantum computers arrive later than expected — is an unacceptable risk for a Trust Infrastructure. The performance impact is managed through efficient implementation in Rust (libternary), hardware acceleration where available, and the fact that capability validation is not the bottleneck in any real-world workflow — network latency, database access, and business logic dominate request processing time. The PQTI service is already optimized for TL-DSA throughput. Capability signing uses the same path.

### "The immutable audit trail records everything. How does that comply with GDPR's right to erasure?"

The audit trail records capability events — token issuance, validation, delegation, expiration. It records *authorization decisions*, not personal data. The `sub` field in a capability token can reference a pseudonymous identifier rather than a natural person's name. The mapping between the pseudonymous identifier and the person's identity is stored separately, in a system that supports deletion. If a data subject exercises their right to erasure, the identity mapping is deleted. The audit trail retains a record that "subject X was issued capability Y at time Z" — but "subject X" is now a meaningless identifier that cannot be linked back to a person. The cryptographic integrity of the audit chain is preserved while the personal data linkage is severed. This approach aligns with GDPR's recognition that data rendered truly anonymous is no longer personal data. Legal counsel should validate this approach for each jurisdiction, but the architecture supports it by design.

### "What if PlenumNET's root TL-DSA key is compromised?"

Root key compromise is the most serious threat to any signing infrastructure. PlenumNET manages this through key hierarchy and rotation. The master root key is held in an HSM (hardware security module) and is used only to sign intermediate keys. Intermediate keys sign capability tokens. If an intermediate key is compromised, it is revoked (published to the revocation list, HPTP-timestamped, Merkle-chained), and a new intermediate key is issued from the root. All capabilities signed by the compromised intermediate are invalidated. The blast radius is limited to the tokens signed by that specific intermediate key during the window between compromise and detection. The audit trail records the entire incident — which key was compromised, when the revocation occurred, which tokens were affected. If the master root key itself is compromised — an event that requires physical breach of the HSM — the entire key hierarchy is rotated. This is a catastrophic scenario for any PKI, not unique to PlenumNET, and the standard mitigations (HSM physical security, multi-party key ceremonies, geographic distribution) apply.

### "Can existing systems integrate with this, or does everything need to be replaced?"

PlenumNET's capability tokens are JWTs. Any system that validates JWTs can validate a PlenumNET capability token — it just needs to understand the `cap[]` claim structure and import the constraint validation logic from the typed registry. The legacy `role` field is preserved in the token for backward compatibility. Systems that do not yet understand capabilities fall back to role-based validation. This means adoption is incremental — existing services continue working while new services adopt capability-based authorization. There is no flag day. There is no system-wide cutover. The constraint registry (TypeScript and Rust implementations) is a library that can be imported into any service without architectural changes.

### "Single-use capability chains — what happens if two requests arrive simultaneously?"

The single-use chain advances deterministically. Each use produces the seed for the next valid token. If two requests attempt to use the same chain position, the HPTP timestamp determines which arrived first. The first use advances the chain; the second use holds a token at a chain position that has already been consumed and is rejected. This is not a race condition — it is a deterministic ordering guaranteed by HPTP. The rejected request receives a clear error indicating the chain has advanced, and the client re-requests a fresh token at the current chain position. In high-throughput scenarios, the chain can be pre-advanced in batches — issuing a window of valid chain positions rather than a single position — trading strict single-use enforcement for throughput while maintaining the property that each position can only be consumed once.

### "Does this work across international jurisdictions?"

The capability model is jurisdiction-agnostic. The tokens are cryptographic objects — they carry their own proof and do not depend on any jurisdiction's legal framework to function. However, the *admissibility* of the audit trail as evidence varies by jurisdiction. PlenumNET's RFC 3161 timestamp tokens conform to an international standard (RFC 3161, IETF) and are recognized in jurisdictions that accept digital evidence standards including eIDAS (EU), ESIGN/UETA (US), and PIPEDA (Canada). The capability certificates described in Section 12 extend this same standard into the authorization layer. Legal counsel should validate admissibility requirements for each specific jurisdiction and use case, but the architecture is built on internationally recognized standards rather than proprietary formats.

### "What prevents a malicious tenant from issuing capabilities that exceed their own authority?"

Attenuation is enforced cryptographically. A tenant's root capability defines the maximum scope of their authority. Every delegation via HMAC caveat can only *add* restrictions — restrict to a narrower template set, a shorter time window, fewer uses, a specific vault. The HMAC chain is verified against the root capability's constraints. If a caveat attempts to *expand* authority beyond what the root grants (for example, accessing a vault not in the root's constraint set), the verification fails because the constraint falls outside the root's scope. You cannot give someone a key to a room you don't have access to yourself. This is enforced by the cryptographic structure of the chain, not by policy.
