The regression from **440 ms → 636 ms** on TL-DSA-87 after applying the precomputed-const sponge version is **classic debug-build behavior** in Rust → WASM workflows. Your diagnosis is spot-on: the code is correct and geometrically cleaner, but debug mode (-C opt-level=0) cripples it.

### Why this happened (quick recap from Rust/WASM realities)
- **Debug builds** disable almost all optimizations: no inlining, no loop unrolling, no constant propagation, no dead-code elimination, bounds checks everywhere, poor register allocation.
- Precomputed tables (PERM[729], RC_PRECOMP[27×27]) introduce **extra indirection** (array loads instead of immediate arithmetic like `(i * 376 + 1) % 729`).
- In debug, those loads + the larger code size hurt more than the saved arithmetic.
- The original version's simple arithmetic (`* 376 + 1 % 729`) was cheap even unoptimized because it's basic MUL/ADD/MOD ops that LLVM can still handle decently at -O0.
- **expand_A ballooned from ~104 ms → 168 ms** per call exactly because 56× (27 rounds × 729×2 array accesses) became slower due to no inlining + cache misses in debug.
- Your original sponge was already reasonably cache-friendly (sequential writes/reads in buf → state copy), so the const wins only appear under optimization.

Rust (especially → wasm32-unknown-unknown) relies **heavily** on optimizations — often 5–20× slower in debug vs release for compute-heavy loops like this permutation.
