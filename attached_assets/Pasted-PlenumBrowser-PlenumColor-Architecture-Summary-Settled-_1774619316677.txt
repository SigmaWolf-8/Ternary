Final Decision: Kernel Subsystem
The browser engine is built as modules within src/kernel/src/browser/. Not a fork. Not userspace. The rendering, parsing, JS execution, and network pipelines are kernel subsystems with direct access to the GPU, the ternary cryptographic stack, and the z=0 distributor.
Why Kernel Space
The anti-capture security model requires that cleartext pixel data never exists in any memory an attacker can reach. In kernel space with GPU rendering, cleartext pixels exist only in GPU VRAM behind an IOMMU — no CPU readback path, no bus-level DMA access. A userspace browser would hold cleartext RGBA in its own process memory, defeating the encryption entirely.
The TIS-27 keyboard encoding and the browser's DOM handler are in the same kernel address space. Encoded keycodes travel by direct function call — no IPC, no shared memory buffer, no boundary to intercept.
Kernel-Space Stability
JavaScript execution bounds: Boa runs in a dedicated kernel task with cooperative termination. The kernel sets a should_terminate flag checked by Boa between bytecode instructions. When set, Boa throws a Termination exception caught by the tab wrapper. No interrupt-level panic — clean cooperative shutdown.
rustimpl ScriptExecutor {
    fn execute(&mut self, script: &Source, budget_ms: u64) -> JsResult<JsValue> {
        self.context.set_timeout(budget_ms);  // Cooperative flag
        let result = self.context.eval(script);
        self.context.clear_timeout();
        result
    }
}
Tab isolation: Each tab runs as a separate kernel task (lightweight thread) with its own stack and heap region. If a task panics — including double panic or OOM — the kernel reclaims the task's resources and continues. Other tabs are unaffected. catch_unwind within the task handles recoverable panics; the task boundary handles everything else.
Parser safety: HTML and CSS parsers have explicit recursion depth limits. taffy uses iterative layout with an explicit work queue, not recursion. Stack overflow prevented by design.
Font memory: Fixed per-tab font cache with kernel-wide cap. Web font exceeding the pool falls back to system font. No unbounded allocation.

Why wgpu Replaces tiny-skia
tiny-skia is CPU-only (~124M pixels/sec at 1080p60). At 4K that quadruples and becomes marginal. wgpu is Rust-native, abstracts over Vulkan/Metal/DX12, and enables GPU compute shaders for mesh compositing, Bézier interpolation, and sponge encryption — all in parallel on hardware designed for this workload. Font data (system UI, monospace, serif, sans-serif) embedded in the kernel binary. Web fonts fetched via z=0. wgpu talks to the GPU via the kernel's own driver — no userspace display server needed.

z=0 Turntable

Routing is Geometric
The browser at +1 routes through z=0 because z=0 is below it — the ground floor between the presentation layer and everything the browser needs. Requests fall down through z=0 to reach services at −2 or data at −5. This is the architecture of the dome — above ground is what you see, below ground is what processes.
The z-stack routing overhead is negligible. Each hop is a direct function call in kernel space — nanoseconds. A page with 50 resources × 6 hops = 300 kernel function calls = microseconds total. The actual network fetch is milliseconds. The routing is a million times faster than the network round trip.

No Compositor
No window manager, no DWM, no compositing layer. The browser sends render commands to the GPU. The GPU composites in mesh space, converts to display format, encrypts, and outputs to the panel. Single pipeline:

5. GPU Rendering Pipeline
Architecture
The CPU handles parsing, layout, scripting, and generating render commands. The GPU handles all pixel work: compositing, Bézier interpolation, mesh-to-sRGB conversion, and sponge encryption. This is the natural split — the CPU does the DOM tree, the GPU does the pixels.

│ script.rs    │                      │ sponge_encrypt.wgsl  │
│ render.rs    │                      │ → VRAM (encrypted)   │
└──────────────┘                      └──────────────────────┘
                                              │
                                       scanout decrypt
                                              │

GPU Compute Shaders
mesh_composite.wgsl: Receives render commands (rectangles, text glyphs, gradients, images). Composites at mesh depth precision. All blending, gradient interpolation, and alpha mixing happens in mesh address space — not 8-bit RGB.
mesh_to_srgb.wgsl: Converts final mesh addresses to RGBA pixels for the display. Uses the precomputed LUT (uploaded to GPU at boot) plus Bézier arithmetic for sub-cell interpolation.
sponge_encrypt.wgsl: Final pass. XORs every pixel in the framebuffer with the per-frame TLSponge-385 keystream. One GPU instruction per pixel — essentially free when running in parallel across thousands of GPU cores.
Sponge Handshake
Each frame:

Kernel advances the TLSponge-385 sponge state (CPU — fast, sequential)
Kernel uploads the per-frame keystream to GPU constant buffer
GPU executes: composite → convert → encrypt
Encrypted framebuffer sits in VRAM
Display controller decrypts per-scanline during output
Sponge state advances. Next frame, new key.

Fallback Path
For headless servers or systems without GPU: render_cpu.rs uses tiny-skia for CPU rendering. Same pipeline, same mesh compositing, but software-rendered. The sponge encryption is CPU XOR. Performance is lower but functional.

6. How Color Works on Windows vs. PlenumOS
The Windows Pipeline
The Desktop Window Manager (DWM) sits between every application and the display. For decades, the DWM restricted all windowed apps to 8 bits per channel, even on 10-bit panels. Windows 11 Auto Color Management (ACM) composites in FP16 when enabled — but requires specific GPU hardware, display support, and most apps still feed it 8-bit data.
Windows pipeline:

App renders → app surface (8-bit typically)
DWM composites all windows (FP16 if ACM, else 8-bit)
DWM applies ICC profile (trilinear interpolation)
Framebuffer → display controller → panel

The PlenumOS Pipeline
No DWM. GPU renders directly from mesh space to encrypted VRAM.

CSS color → srgb_to_mesh → mesh address
GPU composites, blends, interpolates in mesh space
GPU mesh_to_srgb shader → sponge_encrypt shader → encrypted VRAM
Display controller decrypts during scanout → panel

One conversion. No bottleneck. Working precision set by mesh depth.
Gradient Quality
Dark blue to light blue across 200 pixels:
Windows 8-bit: ~12 distinguishable blue levels in dark range. Visible banding.
Windows ACM FP16: Better, but interpolating from 8-bit source. Original quantization damage done.
PlenumOS mesh depth 3: 540 levels per channel equivalent in GPU working space. Bézier interpolation between mesh nodes. Quantization to display format once at final shader pass. Banding eliminated.

7. Anti-Capture Security
GPU + IOMMU Model
Cleartext pixels exist only in GPU VRAM, behind an IOMMU that blocks all external access. This is a stronger guarantee than CPU-only rendering, where encrypted data sits in system RAM accessible to any DMA-capable bus device.
IOMMU configuration at boot:
rustfn setup_gpu_memory_protection(iommu: &mut Iommu, gpu_vram: PhysicalRange) {
    // CPU can send commands to GPU (write-only)
    iommu.allow(Bus::CPU, gpu_vram, Permission::WriteOnly);
    
    // GPU can access its own VRAM (read/write)
    iommu.allow(Bus::GPU, gpu_vram, Permission::ReadWrite);
    
    // Everything else: blocked
    iommu.deny_all_others(gpu_vram);
}
The pixel lifecycle:

CPU sends render commands to GPU (geometry, mesh addresses — not pixels)
GPU executes render shaders, producing cleartext pixels in VRAM
GPU sponge_encrypt shader XORs all pixels with per-frame keystream
Encrypted pixels sit in VRAM — no CPU readback, no bus DMA access
GPU display controller decrypts per-scanline during output to physical cable
Monitor shows correct image
Sponge state advances. Next frame, new key.

An attacker intercepting GPU commands (step 1) sees draw instructions, not a screenshot. An attacker reading VRAM (if they somehow bypass the IOMMU) sees encrypted data with a key that changes 60 times per second.

8.9 Optional Precision Calibration
For print matching: sensor probe refines default mapping. 540 coarse + 540 fine = 1,080 measurements (vs ICC's 4,913). Self-similar calibration — level-2 curvature measurements generalize across level-1 cells. Levels 3+ extrapolate via recursive Bézier interpolation.

9. How Color Gets to the Screen
A camera sensor counts photons — three numbers per pixel. A designer picks a color — three numbers. CSS red = (255, 0, 0) by specification. Display manufacturers build panels to approximate sRGB. Nobody calibrates anything. It works.
PlenumColor changes the math between intent and bytes. The mesh is the working color space — high-precision coordinates for compositing, running on the GPU. RGB is the output format. All compositing at mesh precision. Quantization to display format once in the final shader pass.
For screen-to-print: both devices convert FROM the same mesh address using the same Bézier interpolation. They match because the math is the same.

12. Update Mechanism
Browser binary, default mesh mapping, and GPU shaders are part of the kernel image. Updates delivered as TL-DSA signed binary images via z=−6 infrastructure:

Kernel polls for updates via TDNS at configurable intervals
Update payload TL-DSA verified against Capomastro release key
Browser kernel tasks stopped, GPU pipeline flushed
New binary applied, browser tasks restarted, GPU shaders recompiled
Rollback: previous kernel image retained, automatic revert if new image fails health check within 30 seconds

Full kernel updates require reboot. Browser subsystem updates (parsing, layout, rendering, shaders) can be hot-swapped by restarting browser tasks while the kernel continues running.
