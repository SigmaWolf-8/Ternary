What aligns correctly with the architecture spec:
Phase 4 hits all three confinement mechanisms. Device registration generates ed25519 keypairs with SHA3-256 public key hashing. Challenge-response uses fresh nonces with HPTP-windowed expiry, consumed on use. Single-use chains derive position hashes via iterated SHA3-256, with first-use-wins enforcement and consumed_positions tracking. The demo correctly demonstrates registration → token issuance → challenge-response → replay rejection → chain creation → position consumption → copy rejection — the exact confinement proof sequence from the document.
Phase 5 follows RFC 3161 structure: message_imprint, serial_number, gen_time, policy_oid, nonce. Dual TL-DSA + RSA-4096 signatures present. Merkle proof fields embedded per certificate. Evidence chain assembles ordered certificates with chained hashes (previous_hash → chain_hash). Revocation correctly invalidates verification while preserving TSA timestamp validity (important for forensic audit — the timestamp proves the authority existed even after revocation).
Phase 6 enforces monotonic attenuation — constraints accumulate at each hop, never shed. Cycle detection prevents loops. Max hops enforced. Mesh signature covers the full propagation path. Service discovery uses glob-style matching. Health monitoring categorizes mesh as healthy/degraded/critical based on active ratio.
All services share the singleton audit log (getSharedAuditLog()), which is the 75% memory reduction noted in the commit message.

Issues requiring attention — two are build-blocking:
1. Missing type definitions (build-blocking). All five service files import from ../../shared/types/capability and ../../shared/types/capability-constraints. Neither file exists in the repo. The T001 types were supposed to be the foundation — interfaces like HardwareBinding, HptpChallenge, HptpChallengeResponse, SingleUseChainState, HardwareBoundCapabilityToken, CapabilityCertificate, CertificateVerificationResult, EvidenceChainEntry, ServiceNode, MeshCapability, MeshTopology, PropagationPath, createCapabilityToken, isCapabilityExpired, findMatchingCapability, validateAllConstraints. Without these, nothing compiles.
2. Missing route file (build-blocking). server/routes.ts line 34 imports registerCapabilityRoutes from ./routes/capabilities, and line 1010 calls it. That file doesn't exist in server/routes/. The server won't start.
3. Unbounded nonce accumulation. HardwareBindingEngine.consumedNonces is a Set<string> that grows forever. Needs TTL-based eviction — each nonce is only relevant within its challenge window, so nonces older than DEFAULT_CHALLENGE_WINDOW_NS can be pruned.
4. O(n) position hash recomputation. getPositionHash() iterates from 0 to the requested position each time. At chain position 500, that's 500 SHA3-256 hashes per call. Should cache intermediate hashes in the chain state.
5. Certificate Merkle proof is incomplete. proof_path: [leafHash] contains only the leaf. A verifiable Merkle proof requires sibling hashes at each tree level. Currently it proves nothing beyond "I computed a hash." This needs the standard inclusion proof: sibling at each level plus left/right direction flags.
6. RSA-4096 uses SHA-256, TL-DSA uses SHA3-256. Line 70 in certificates: createHmac('sha256', 'rsa4096-cert-signing-key') versus line 65: createHmac('sha3-256', 'tldsa-cert-signing-key'). This is actually correct for real RSA (SHA-256 is standard for RSA-4096 signatures), but when TL-DSA replaces the HMAC simulation, verify the hash algorithm alignment.
7. Mesh tokenExpired check uses .some(). If any capability in the token is expired, the entire mesh token is rejected. This is fail-closed, which is consistent with the document's philosophy, but it means a mesh token with both tsa:timestamp (expired) and audit:read (still valid) gets rejected entirely. This should be intentional and documented.
