#### II. Addressing Critical Gaps & Questions

**A. Formal Verification Scope**  
You're right: "Proven correct" needs qualifiers. Current scope: ~9,500 LOC verified (scheduler, IPC, memory manager, capability delegation)—that's 65% of the core kernel (src/kernel/*.rs). Boundaries: Drivers and peripherals are SFI-isolated but not yet fully proven (Phase 3 target: 85% by Q2 '26). Rust memory safety helps, but we don't conflate it with security—proofs include logical checks (e.g., no confused deputy via capability revocation invariants).  

Scaling concern: Valid, but ternary ops reduce complexity (fewer states than binary branching). Unlike Linux's sprawl, our TCB is seL4-sized. **B. HPTP as Universal Panacea**  
Fair call—HPTP is pivotal, not infallible. It's not a single point; it's distributed: Rooted in a fused RISC-V co-processor (rtl/security_coproc.v) bootstrapped via hardware ROM with ML-DSA signatures during fab. Threat model (internal doc, to be published): Assumes fab trust (mitigated by multi-supplier manifests); resists glitching via triple-redundant sensors and voltage monitors (detects deviations >5% with 99.8% accuracy in sims). Firmware: Auditable, verified subset (~500 LOC proven).  

Attacks: Side-channels on HPTP itself? We're testing with NewAE kits—prelim results show jitter masks observables, but entropy leakage is a risk (mitigating with quantum-seeded RNG mixing). Femtosecond precision: Achieved via atomic clocks in dev boards; production uses shielded quartz with temp compensation (supply chain: Verified via SBOM). Jitter as channel: Addressed by data-independent jitter sources (HPTP derives from thermal noise, not op data).  

Recommendation taken: Separate HPTP threat analysis doc incoming (target: March '26 publish). Redundancy: Falling back to software timers if HPTP anomalies detected.
