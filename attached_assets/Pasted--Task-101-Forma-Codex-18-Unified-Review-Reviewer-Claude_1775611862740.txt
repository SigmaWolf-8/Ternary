## CONFLICT 7 — GUARD_MARKER definition contradicts session

Task #101 Item 2 defines `pub const GUARD_MARKER: u64 = 0x0D0D_0D0D_0D0D_0D0Du64` (REPUNIT_3 repeated 8×).

Session kills this: "NO separate GUARD_MARKER constant — guard uses Rep C algebraic validation via gf3_algebra."

These cannot both be true. A GUARD_MARKER is a fixed bit pattern written to z=0 and checked for corruption. Algebraic validation via gf3_algebra checks whether values are in {1,2,3}. These are different mechanisms:
- GUARD_MARKER: "did the sentinel change?" (Layer 2 in spec §26)
- Rep C validation: "is this address valid?" (Layer 1 in spec §26)

The spec §26 describes THREE detection layers. Layer 1 is address validation (Rep C). Layer 2 is sentinel verification (known non-zero marker pattern). Layer 3 is native ternary. The session's kill of GUARD_MARKER contradicts the spec's Layer 2.

**Required fix:** Reconcile. If Layer 2 sentinel verification survives (spec §26 says it does), then a marker value must exist somewhere — either as a constant or computed from gf3_algebra. Define where the marker lives and what its value is. If Layer 2 is killed, update spec §26 to remove it.

## ISSUE 9 — coprime_combinations needs a complexity bound

`coprime_combinations(moduli: &[u64]) -> Vec<Vec<u64>>` in coprime.rs (Item 1) enumerates all pairwise-coprime subsets. This is exponential in |moduli|. Task #101 acknowledges this: "Exponential in |moduli|. For auto-selection, |moduli| ≤ ~15."

But coprime.rs is a shared module, not just for auto-selection. The Forma Codex custom grid dialog uses `coprime_options()` (not `coprime_combinations`), so the exponential function may never be called from FC. However, the function exists in the public API with no enforced bound.

**Required fix:** Add to the coprime.rs spec:
- Hard limit: `coprime_combinations` returns `Err` if `moduli.len() > 15`
- Or: the function takes a `max_results: usize` parameter and stops enumeration early
- Document that this function is primarily for the future BQ auto-selection and is not called by Forma Codex

## ISSUE 10 — Phase 5 JSX is underspecified

Task #101 gives Rust modules function-level API detail (signatures, imports, invariants, formulas). The seven JSX files get paragraph-level descriptions. This is insufficient for a rendering engine.

**canvas.ts** needs: draw function signatures for each of the 14 Z-layers, draw order (z=0 bottom → z=13 top → selection → walk path → cursor → scrollbar), viewport culling algorithm (which cells to draw given scroll position and viewport dimensions), sub-pixel alignment strategy, DPR scaling, cell border rendering (shared edges drawn once, not twice), morph effect compositor pattern (offscreen canvas capture → blend → composite).

**input.ts** needs: pointer event state machine (idle → selecting → dragging → scrolling), keyboard handler map with modifier keys, hidden textarea lifecycle (create on cell focus, destroy on blur, position tracking), focus management for nested grids (which grid owns the textarea), drag-to-scroll threshold and velocity.

**FormaCodex.tsx** needs: state management strategy (what's in React state vs. refs), render loop lifecycle (RAF init → measure → cull → draw → schedule next), ResizeObserver debounce strategy, preset dropdown data flow, mode badge rendering.

**transitions.ts** needs: offscreen canvas capture API, compositor blend modes, timing function for each of the 6 Phase 1 effects (none, slide, dissolve, cube, flip, zoom), cleanup lifecycle (when to release captured bitmaps).

**blocks.ts** needs: text measurement strategy (CanvasRenderingContext2D.measureText vs. offscreen pre-measure), line breaking algorithm, block type registry (h1, h2, body, image, shape — what renders how), content overflow detection for variable-mode row height calculation.

**Required fix:** Expand Items 24–30 to function-level detail matching the Rust module specs. This is the work the user will debug iteratively, so it needs to be right.
