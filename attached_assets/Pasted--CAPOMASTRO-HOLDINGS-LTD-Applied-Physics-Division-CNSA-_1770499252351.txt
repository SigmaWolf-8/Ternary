CNSA 2.0 Algorithm Suite Reference
The complete CNSA 2.0 suite as defined by NSA (December 2024, Ver. 2.1). All algorithms approved for TOP SECRET and below.

Algorithm	Function	Standard	Parameter	Salvi Status
AES-256	Symmetric encryption	FIPS 197	256-bit key	PLANNED
SHA-384	Hash / integrity	FIPS 180-4	384-bit digest	TERNARY EQ
SHA-512	Hash / integrity	FIPS 180-4	512-bit digest	TERNARY EQ
ML-KEM-1024	Key encapsulation	FIPS 203	Level 5 (1024)	PLANNED
ML-DSA-87	Digital signature	FIPS 204	Level 5 (87)	PLANNED
LMS	Firmware signing	SP 800-208	SHA-256/192	TERNARY EQ
XMSS	Firmware signing	SP 800-208	SHA-256/192	TERNARY EQ

TERNARY EQ = Ternary equivalent primitives exist in Rust kernel but have not been validated against NIST test vectors. Full FIPS compliance requires binary-compatible output verification.

P1: Phase 1: Foundation — Symmetric & Hash Algorithms
Deadline: Q2 2026    |    Priority: CRITICAL    |    Tasks: 3
Implement AES-256 symmetric encryption and upgrade SHA hashing to CNSA 2.0 compliant parameters. These are prerequisites for all subsequent cryptographic operations.

Task 1.1: AES-256-GCM Implementation (FIPS 197)
Status: NOT STARTED	Effort: 3-4 weeks	Dependencies: None — foundational

•	Implement AES-256 in Rust kernel (src/kernel/crypto/)
•	GCM mode for authenticated encryption (required by CNSA 2.0 TLS & IPsec profiles)
•	Ternary-native key schedule: map 256-bit key to balanced ternary representation for GF(3) processing
•	Side-channel hardening: constant-time table lookups, no data-dependent branches
•	Integration with existing phase-encryption split/recombine pipeline
•	NIST CAVP test vectors: AES-GCM-256 encrypt/decrypt validation

Acceptance criteria: Pass all NIST AES-GCM-256 known-answer tests. Encrypt/decrypt round-trip with timing-window enforcement.

Task 1.2: SHA-384 / SHA-512 Compliance Verification (FIPS 180-4)
Status: TERNARY EQUIVALENT	Effort: 1-2 weeks	Dependencies: None — existing ternary hash provides head start

•	Current: Ternary sponge hash exists in kernel — verify output equivalence to FIPS 180-4 SHA-384/512
•	Add FIPS 180-4 reference implementation alongside ternary variant
•	Implement binary-compatible SHA-384 output (truncated SHA-512) for interop with external systems
•	Validate against NIST CAVP SHA test vectors (short/long/Monte Carlo)
•	Add SHA-512/384 to HMAC-SHA-384/HMAC-SHA-512 for TLS/IPsec key derivation
•	Document ternary equivalence proof: map ternary sponge state to SHA-2 compression function

Acceptance criteria: Byte-identical output to NIST SHA test vectors. HMAC-SHA-384 interop with OpenSSL.

Task 1.3: SHA-3 Internal Hardware Functions (FIPS 202)
Status: NOT STARTED	Effort: 1 week	Dependencies: 1.1, 1.2

•	SHA3-384 and SHA3-512 for internal hardware functionality only (boot integrity, TPU FPGA checks)
•	Integrate with existing hardware driver framework (src/kernel/drivers/)
•	NOT for general cryptographic use per CNSA 2.0 guidance — scope strictly limited
•	Keccak sponge: map to ternary state permutation for FPGA boot sequence

Acceptance criteria: SHA3-384/512 pass NIST test vectors. Used only in boot and FPGA integrity paths.

 
P2: Phase 2: Stateful Hash-Based Signatures
Deadline: Q3 2026    |    Priority: CRITICAL    |    Tasks: 3
Implement LMS and XMSS for firmware and software signing. NSA mandates immediate transition for this use case. These are the most urgently needed CNSA 2.0 algorithms.

Task 2.1: LMS Implementation (NIST SP 800-208)
Status: TERNARY EQUIVALENT	Effort: 4-5 weeks	Dependencies: 1.2 (SHA-256/192 dependency)

•	Current: Ternary Lamport one-time signatures exist — extend to full Leighton-Micali Signature scheme
•	Implement LMS with SHA-256/192 parameter set (NSA preferred: Section 4.2 of SP 800-208)
•	Merkle tree construction for one-time signature aggregation
•	State management: monotonic counter for signature index tracking (CRITICAL — reuse = key compromise)
•	Persistent state storage integration with PlenumDB for signature counter durability
•	HSS (Hierarchical Signature Scheme) is NOT allowed per CNSA 2.0 — do not implement
•	Binary compatibility gateway: sign firmware images readable by standard LMS verifiers

Acceptance criteria: Sign/verify against NIST SP 800-208 test vectors. State never allows key reuse across restarts.

Task 2.2: XMSS Implementation (NIST SP 800-208)
Status: TERNARY EQUIVALENT	Effort: 4-5 weeks	Dependencies: 1.2, 2.1 (shares tree construction primitives)

•	Extended Merkle Signature Scheme with WOTS+ (Winternitz one-time signatures)
•	Leverage existing Lamport signature primitives as foundation
•	Tree height parameter selection: H=10 (1024 signatures) or H=20 (1M signatures) based on firmware update cadence
•	Forward-secure: expose previous secret keys without compromising future signatures
•	XMSSMT (multi-tree) is NOT allowed per CNSA 2.0 — do not implement
•	Integrate with kernel boot sequence for secure boot chain validation

Acceptance criteria: Sign/verify against SP 800-208 XMSS test vectors. Forward security validated.

Task 2.3: Firmware Signing Pipeline
Status: NOT STARTED	Effort: 2-3 weeks	Dependencies: 2.1, 2.2

•	Build signing tool: salvi-sign CLI for firmware image signing with LMS/XMSS
•	Verification integrated into kernel boot path (src/kernel/arch/*/boot.rs)
•	Key management: hardware-bound key generation via TPU FPGA driver
•	Signature counter persistence: atomic write-ahead log to prevent counter rollback
•	Support dual-signing (LMS + XMSS) for algorithm agility during transition
•	Integrate with existing femtosecond timestamp for signed-at provenance

Acceptance criteria: End-to-end: sign kernel image → boot verifies → reject tampered image. Counter survives crash.

 
P3: Phase 3: Post-Quantum Key Encapsulation
Deadline: Q4 2026    |    Priority: HIGH    |    Tasks: 3
Implement ML-KEM-1024 (formerly CRYSTALS-Kyber) for quantum-resistant key establishment. Required for TLS 1.3, SSH, and IPsec CNSA 2.0 profiles.

Task 3.1: ML-KEM-1024 Core (FIPS 203)
Status: PLANNED	Effort: 6-8 weeks	Dependencies: 1.1 (AES for seed expansion), 1.2 (SHA for key derivation)

•	Module-Lattice-Based Key-Encapsulation Mechanism at security level 5 (1024 parameter set)
•	Key generation: (ek, dk) pair from seed — ternary NTT acceleration for polynomial multiplication
•	Encapsulation: produce (ciphertext, shared_secret) from encapsulation key
•	Decapsulation: recover shared_secret from ciphertext + decapsulation key
•	Ternary advantage: balanced ternary polynomial representation for coefficient arithmetic in Z_q
•	Constant-time implementation: no branching on secret data, masked comparison
•	SHAKE-128/SHAKE-256 internal use (required by FIPS 203, allowed for internal ML-KEM functions)
•	Must be FIPS 203 final standard — earlier Kyber drafts are NOT compliant

Acceptance criteria: Pass all FIPS 203 known-answer tests. Encaps/Decaps round-trip with correct shared secret.

Task 3.2: ML-KEM-768 and ML-KEM-512 (Secondary Parameter Sets)
Status: PLANNED	Effort: 2 weeks	Dependencies: 3.1

•	ML-KEM-1024 is mandatory for CNSA 2.0 — implement 768/512 for commercial interoperability only
•	Share core NTT/polynomial infrastructure with ML-KEM-1024
•	These are NOT CNSA 2.0 compliant but needed for TLS handshakes with non-NSS systems
•	Flag clearly in API as non-CNSA-compliant parameter sets

Acceptance criteria: Pass FIPS 203 test vectors for all three parameter sets. API warns on non-1024 usage.

Task 3.3: Key Encapsulation API & Integration
Status: NOT STARTED	Effort: 2-3 weeks	Dependencies: 3.1

•	Unified KEM API: keygen(), encapsulate(ek), decapsulate(ct, dk) → shared_secret
•	Ephemeral key enforcement: private key destroyed after single use (NIST SP 800-56A compliance)
•	Integration with phase-encryption: use ML-KEM shared secret as seed for split/recombine keys
•	Integration with HPTP: timestamp key establishment events at femtosecond precision
•	Wire format: CNSA 2.0 encoded key/ciphertext sizes (ML-KEM-1024: ek=1568B, ct=1568B, ss=32B)

Acceptance criteria: API round-trip test. Ephemeral keys zeroized. Phase-encryption integration verified.

 
P4: Phase 4: Post-Quantum Digital Signatures
Deadline: Q1 2027    |    Priority: HIGH    |    Tasks: 3
Implement ML-DSA-87 (formerly CRYSTALS-Dilithium) for general-purpose digital signatures. Required for certificates, TLS authentication, and document signing.

Task 4.1: ML-DSA-87 Core (FIPS 204)
Status: PLANNED	Effort: 6-8 weeks	Dependencies: 3.1 (shares NTT/polynomial infrastructure)

•	Module-Lattice-Based Digital Signature Algorithm at security level 5 (parameter set 87)
•	Key generation: (vk, sk) signing key pair
•	Sign: produce signature σ from message M and signing key sk
•	Verify: validate (M, σ, vk) → accept/reject
•	Must use 'pure' ML-DSA (Algorithms 1,2,3 in FIPS 204) — HashML-DSA is NOT allowed in CNSA 2.0
•	Internal SHAKE-256 use (mandated by FIPS 204 for internal operations)
•	Ternary NTT: share polynomial multiplication infrastructure with ML-KEM-1024
•	Constant-time rejection sampling: critical for side-channel resistance
•	Signature size: ~4627 bytes (larger than ECDSA — test bandwidth impact on torsion network)

Acceptance criteria: Pass all FIPS 204 known-answer tests. Signature verification deterministic.

Task 4.2: ML-DSA-65 and ML-DSA-44 (Secondary Parameter Sets)
Status: PLANNED	Effort: 2 weeks	Dependencies: 4.1

•	ML-DSA-87 is mandatory for CNSA 2.0 — implement 65/44 for commercial interoperability
•	Share core infrastructure with ML-DSA-87
•	Flag as non-CNSA-compliant in API
•	Useful for resource-constrained torsion network edge nodes

Acceptance criteria: Pass FIPS 204 test vectors for all three parameter sets.

Task 4.3: X.509 Certificate Support with ML-DSA-87
Status: NOT STARTED	Effort: 3-4 weeks	Dependencies: 4.1

•	CNSA 2.0 certificate profile (draft-jenkins-cnsa2-pkix-profile)
•	Self-signed root CA with ML-DSA-87 for Salvi Framework PKI
•	Certificate chain: Root CA → Intermediate → End-entity (all ML-DSA-87)
•	CRL (Certificate Revocation List) with ML-DSA-87 signatures
•	Integration with torsion network node identity: each node gets ML-DSA-87 certificate
•	Binary encoding: DER/PEM format compatible with standard X.509 parsers

Acceptance criteria: Generate cert chain. Verify with OpenSSL (3.5+ with ML-DSA support). Parse with standard tools.

 
P5: Phase 5: Protocol Integration
Deadline: Q2-Q3 2027    |    Priority: HIGH    |    Tasks: 4
Integrate CNSA 2.0 algorithms into standard security protocols. The NSA publishes CNSA 2.0 profiles for TLS 1.3, SSH, IPsec, and S/MIME through IETF RFCs.

Task 5.1: TLS 1.3 CNSA 2.0 Profile
Status: NOT STARTED	Effort: 4-6 weeks	Dependencies: 3.1, 4.1, 4.3

•	Per draft-becker-cnsa2-tls-profile: ML-KEM-1024 for key exchange, ML-DSA-87 for authentication
•	Cipher suite: TLS_AES_256_GCM_SHA384 (mandatory)
•	Key exchange: mlkem1024 (FIPS 203) — replaces ECDHE
•	Server/client authentication: ML-DSA-87 certificates
•	HKDF with SHA-384 for key derivation (SHA-512 allowed but SHA-384 preferred)
•	Integration with Kong Konnect API gateway: TLS termination with CNSA 2.0
•	Backward compatibility: hybrid mode for transition period (ML-KEM + ECDHE)

Acceptance criteria: TLS 1.3 handshake completes with CNSA 2.0 cipher suite. Interop with OQS-OpenSSL.

Task 5.2: SSH CNSA 2.0 Profile
Status: NOT STARTED	Effort: 3-4 weeks	Dependencies: 3.1, 4.1

•	Per draft-becker-cnsa2-ssh-profile: ML-KEM-1024 key exchange, ML-DSA-87 public key auth
•	Key exchange: mlkem1024-sha384 MUST be first in kex_algorithms list
•	Public key: ssh-mldsa87 MUST be first in public key algorithms list
•	Encryption: AEAD_AES_256_GCM (RFC 5647)
•	No key reuse: ephemeral values used exactly once per key exchange
•	Integration with torsion network node-to-node SSH tunneling

Acceptance criteria: SSH session establishment with CNSA 2.0 algorithms. Interop with OQS-OpenSSH.

Task 5.3: IPsec/IKEv2 CNSA 2.0 Profile
Status: NOT STARTED	Effort: 4-5 weeks	Dependencies: 3.1, 4.1

•	Per draft-guthrie-cnsa2-ipsec-profile: ML-KEM-1024 for IKE key exchange
•	Challenge: ML-KEM-1024 key sizes too large for initial IKE SA (IP fragmentation risk)
•	Solution: RFC 9370 multiple key exchanges — initial with smaller KEM, then ML-KEM-1024
•	ESP with AES-256-GCM for data encryption
•	ML-DSA-87 for IKE authentication
•	Integration with torsion network TTP (Ternary Transport Protocol) security layer

Acceptance criteria: IKEv2 SA establishment with CNSA 2.0. ESP tunnel encrypts/decrypts correctly.

Task 5.4: S/MIME CNSA 2.0 Profile
Status: NOT STARTED	Effort: 2-3 weeks	Dependencies: 3.1, 4.1, 4.3

•	Per draft-becker-cnsa2-smime-profile: ML-KEM-1024 for key transport, ML-DSA-87 for signing
•	CMS (Cryptographic Message Syntax) integration for signed/encrypted messages
•	Relevant for Maestro ERP secure messaging and document exchange
•	Integration with blockchain witnessing: signed messages timestamped via Hedera HCS

Acceptance criteria: Sign and encrypt S/MIME message. Verify with standard S/MIME tools.

Critical Path
The critical path runs through: SHA-384/512 validation (P1) → ML-KEM-1024 (P3) → ML-DSA-87 (P4) → TLS 1.3 profile (P5) → CAVP validation (P7). The firmware signing track (P2) can proceed in parallel as it depends only on SHA and the existing Lamport primitives.

Explicitly Excluded (Per CNSA 2.0 Guidance)
The following algorithms and variants are explicitly prohibited or not approved by NSA for CNSA 2.0. The Salvi Framework will NOT implement these:

•	HSS (Hierarchical Signature Scheme) — multi-tree LMS variant, not allowed
•	XMSSMT — multi-tree XMSS variant, not allowed
•	SLH-DSA (SPHINCS+) — hash-based but NOT part of CNSA 2.0, not approved for any NSS use
•	HashML-DSA — pre-hash mode of ML-DSA, explicitly disallowed (CNSA 2.0 FAQ v2.1, pg 9)
•	SHAKE-256 — not allowed for general use (only permitted internally within ML-KEM/ML-DSA as specified by FIPS 203/204)
•	SHA-3 for general cryptographic use — only permitted for internal hardware functions (boot integrity)
•	Quantum Key Distribution (QKD) — NSA considers it impractical and not recommended
•	PQ/T hybrid solutions — NSA will not require hybrid; standard CNSA 2.0 algorithms are sufficient
