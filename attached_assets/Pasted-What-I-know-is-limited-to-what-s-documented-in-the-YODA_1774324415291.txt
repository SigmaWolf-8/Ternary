Q1: Does YODA have a local Rust backend component running on the user's machine?

No. YODA's entire Rust/Axum backend runs on Replit at yoda.replit.app. Nothing runs locally on the user's machine on YODA's behalf. The only local components are the PlenumNET daemon binaries and llama-server, both of which belong to the PlenumNET side.

Q2: How does YODA currently monitor LLM engine health (8080/8082/8084)?

It doesn't — not effectively. The engine health check in settings.rs has no polling code at all. Engine status is stored in the database and whatever the user last saved. When YODA's Replit backend tries to reach localhost:8080, it's calling its own Replit container's localhost, not the user's machine. Engines therefore always appear offline in the settings UI.

Q3: Where does YODA get cluster status from when asked?

Currently from the database (saved config) and from the WebSocket relay at plenumnet.replit.app. It can query GET /api/salvi/inter-cube/relay/status to see which daemons are connected. It does NOT have live LLM health data — only whether a daemon is connected to the relay.

Q4: Is YODA using the WebSocket relay, and should daemons push LLM status through it?

Yes — YODA is connected to wss://plenumnet.replit.app/ws/relay (cube_relay.rs hardcodes this). It uses the relay for inference routing and discovers peers from connectedPeers in auth_ok. It does NOT currently receive LLM health status through the relay. Pushing LLM status (llama-server up/down, load, etc.) through the relay would be the correct way for YODA to know engine health remotely.

Fair point — let me lay out the complete picture clearly.

What the LLMs do

llama-server runs locally on your machine on ports 8080, 8082, 8084. It's a standard OpenAI-compatible HTTP server that accepts inference requests and returns completions. It only listens on localhost — it has no public internet access and YODA on Replit cannot reach it directly.

What the cube daemons do

The daemons solve exactly that problem. Each daemon (ports 8081, 8083, 8085) sits alongside its paired llama-server and acts as a relay bridge:

The daemon registers with the relay at plenumnet.replit.app and holds a persistent WebSocket connection open
YODA (on Replit) sends an inference request through that relay WebSocket to the daemon's ternary address
The daemon receives it, calls its paired llama-server at LLM_PORT (8080, 8082, or 8084) over localhost — which it CAN reach
The daemon sends the response back through the relay to YODA
So the flow is: YODA → plenumnet.replit.app relay → daemon → llama-server → daemon → relay → YODA

The daemon is the secure tunnel that makes a local LLM reachable from a cloud app without exposing any ports.

What Daemon A specifically does differently

Daemon A runs as CUBE_MODE=crs — it's the local Cube Registration Service. Daemons B and C register with it on startup, so the three daemons form a local ternary mesh. Daemon A also connects to plenumnet.replit.app so the remote relay knows the whole cluster exists.

The browser relay fallback

When no daemon is connected, YODA tells the browser to call localhost:8080 directly. This works because the browser itself is running on your machine. It's a fallback only — no encryption, no relay, no post-quantum routing. The "Daemon required" screen you've been seeing appears when YODA can't route through the proper relay path.

The gaps right now

The daemon binary (v0.2.0) ignores CUBE_API_PORT so Daemon A can't start on 8081 — it crashes trying to take 8080 from llama-server. The fix is the v0.4.0 deployer: irm https://plenumnet.replit.app/api/deploy-yoda | iex — it builds a fresh binary, sets everything up correctly, and starts all three daemons in the right order.
