#### TASK A1: SP 800-90A DRBG (Deterministic Random Bit Generator)
**File:** NEW `crypto/drbg.rs`
**Priority:** P0-CRITICAL — every FIPS module requires an approved DRBG
**Effort:** ~250-350 lines
**FIPS Reference:** SP 800-90A Rev.1

**Why this is critical:** FIPS 140-3 requires all random number generation within the module boundary to use an approved DRBG. Raw entropy sources (femtoclock) feed INTO the DRBG, but all cryptographic operations consume randomness FROM the DRBG only. Without this module, no CAVP certificate, no CMVP submission.

**What to build:**
```
1. HMAC-DRBG (SP 800-90A Section 10.1.2)
   - Preferred for CNSA 2.0: HMAC-DRBG with SHA-384 (matches TLS/IPsec KDF)
   - Internal state: V (value), Key, reseed_counter
   - Security strength: 256 bits (CNSA 2.0 minimum)

2. Core Operations (per SP 800-90A)
   - drbg_instantiate(entropy, nonce, personalization) -> DrbgState
     * entropy: minimum 384 bits from entropy source
     * nonce: minimum 192 bits
     * personalization: optional application context
   - drbg_generate(state, requested_bits, additional_input) -> (output, DrbgState)
     * Must track request count against reseed_interval
     * Max 2^48 requests between reseeds (SP 800-90A Table 2)
     * Max 2^19 bits per request
   - drbg_reseed(state, entropy, additional_input) -> DrbgState
     * Mandatory when reseed_counter exceeds interval
   - drbg_uninstantiate(state)
     * Zeroize all internal state using ct_zeroize()

3. HMAC-DRBG Update Function
   - hmac_drbg_update(provided_data, Key, V) -> (Key, V)
     * K = HMAC(K, V || 0x00 || provided_data)
     * V = HMAC(K, V)
     * If provided_data: K = HMAC(K, V || 0x01 || provided_data), V = HMAC(K, V)

4. Health Tests (mandatory per SP 800-90A Section 11.3)
   - Continuous DRBG output test: compare each output block to previous
     * Fail → enter error state, refuse further output
   - Instantiation test: run once at POST with known seed, verify output

5. Prediction Resistance Mode
   - When enabled: automatic reseed before every generate call
   - Required for CNSA 2.0 highest assurance applications
   - prediction_resistance: bool field in DrbgState

6. Integration Points
   - tl_kem.rs: keygen uses drbg_generate() for seed
   - tl_dsa.rs: keygen + signing nonce from drbg_generate()
   - cipher.rs: IV/nonce generation from drbg_generate()
   - x509.rs: serial number generation from drbg_generate()
   - phase_cnsa.rs: key material from drbg_generate()
   - signature.rs: LMS/XMSS seed generation from drbg_generate()
```

**Tests:**
- SP 800-90A HMAC-DRBG test vectors (NIST publishes these — 14 test cases per configuration)
- Instantiate → generate → compare to known output
- Reseed counter enforcement: hit limit → force reseed
- Continuous output test: duplicate detection
- Zeroization: verify state is cleared after uninstantiate
- Prediction resistance: verify reseed on every generate

**Acceptance:** HMAC-DRBG-SHA384 passes all SP 800-90A test vectors. All crypto modules consume randomness exclusively through drbg_generate().

#### TASK A2: SP 800-90B Entropy Source Module
**File:** NEW `crypto/entropy.rs`
**Priority:** P0-CRITICAL — DRBG requires a qualified entropy source
**Effort:** ~200-250 lines
**FIPS Reference:** SP 800-90B

**Why this is critical:** The DRBG needs entropy input. SP 800-90B defines how to qualify the noise source and run health tests. The `femtoclock.rs` driver provides raw timing data, but FIPS requires a structured entropy conditioning pipeline with mandatory health tests.

**What to build:**
```
1. Noise Source Abstraction
   - NoiseSource trait
     * fn sample() -> u64 (raw noise sample)
     * fn source_description() -> &str
   - FemtoclockNoise: implements NoiseSource using femtoclock.rs
     * Extracts jitter from femtosecond clock LSBs
     * Documents noise model: thermal jitter in clock oscillator
   - TestNoise: deterministic source for testing (NOT for production)

2. SP 800-90B Health Tests (mandatory — module fails without these)
   - Repetition Count Test (Section 4.4.1)
     * Detects stuck noise source
     * Cutoff C = 1 + ceil(-log2(alpha) / H)
     * alpha = 2^-20 (NIST recommended)
     * Track consecutive identical samples; fail if >= C
   - Adaptive Proportion Test (Section 4.4.2)
     * Detects bias drift in noise source
     * Window W = 1024 for binary sources, 512 for non-binary
     * Count occurrences of first sample in window
     * Cutoff per SP 800-90B Table 2
     * Fail if count exceeds cutoff

3. Conditioning Component (vetted — required by CMVP)
   - Use HMAC-SHA-384 as vetted conditioning component
     * Per SP 800-90B Section 3.1.5.1.1
     * Input: raw noise samples (concatenated)
     * Output: conditioned entropy at full strength
     * Narrowest internal width: 384 bits ≥ 256 bits security strength ✓
   - conditioning_function(raw_samples: &[u64], output_bits: usize) -> Vec<u8>

4. Entropy Source Interface (feeds into DRBG)
   - get_entropy(requested_bits: usize) -> Result<Vec<u8>, EntropyError>
     * Collect sufficient raw samples
     * Run health tests on every sample (fail → EntropyError::HealthTestFailed)
     * Condition via HMAC-SHA-384
     * Return conditioned output
   - get_nonce() -> Vec<u8>
     * Per SP 800-90A Section 8.6.7: timestamp or counter-based
     * Use femtoclock timestamp + monotonic counter

5. Error States
   - EntropyError::RepetitionCountFailed
   - EntropyError::AdaptiveProportionFailed
   - EntropyError::SourceUnavailable
   - On any error: module enters error state per finite state model
```

**Tests:**
- Repetition count: feed stuck source → detect failure
- Adaptive proportion: feed biased source → detect failure
- Healthy source: pass both tests with simulated jitter
- Conditioning: verify output entropy matches expected length
- Integration: get_entropy() → feeds drbg_instantiate()

**Acceptance:** Health tests catch stuck/biased sources. Conditioned output feeds DRBG. SP 800-90B documentation describes noise model for lab review.

#### TASK A3: Power-On Self-Tests (POST) Module
**File:** NEW `crypto/self_test.rs`
**Priority:** P0-CRITICAL — FIPS 140-3 Section 7.10.1 mandatory
**Effort:** ~250-300 lines
**FIPS Reference:** ISO/IEC 19790 Section 7.10, SP 800-140E

**Why this is critical:** Every FIPS 140-3 module MUST run known-answer tests on power-up (initialization) before ANY cryptographic service is available. If any POST fails, the module enters an error state and refuses all operations. This is the single most-tested requirement during CMVP lab evaluation.

**What to build:**
```
1. POST Orchestrator
   - pub fn run_power_on_self_tests() -> Result<PostReport, PostFailure>
   - Called ONCE at module initialization before any crypto service
   - Runs KAT for every approved algorithm in the module
   - If ANY test fails → module enters ERROR state
   - Returns PostReport listing each algorithm + pass/fail + execution time

2. Algorithm KATs (one per approved algorithm — minimum 1 known vector each)
   POST-AES-256-GCM:
     * Known plaintext + key + nonce → encrypt → compare to known ciphertext
     * Known ciphertext → decrypt → compare to known plaintext
     * Use first vector from cavp_package.rs AES-GCM set

   POST-SHA-384:
     * Known message → hash → compare to known digest
     * Use NIST "abc" test vector: SHA-384("abc") = cb00753f45a35e...

   POST-SHA-512:
     * Known message → hash → compare to known digest
     * Use NIST "abc" test vector: SHA-512("abc") = ddaf35a193617a...

   POST-SHA3-384:
     * Known message → hash → compare
     * Use NIST "abc" test vector

   POST-SHA3-512:
     * Known message → hash → compare
     * Use NIST "abc" test vector

   POST-HMAC-SHA-384:
     * Known message + key → HMAC → compare
     * Use RFC 4231 test vector 2

   POST-TL-KEM-1024:
     * Known seed → keygen → compare to known pk/sk
     * Known pk + randomness → encapsulate → compare to known ct/ss
     * Known ct + sk → decapsulate → compare to known ss
     * Use first frozen vector from kat_vectors.rs

   POST-TL-DSA-87:
     * Known seed → keygen → compare to known vk/sk
     * Known message + sk → sign → compare to known signature
     * Known message + signature + vk → verify → expect true
     * Use first frozen vector from kat_vectors.rs

   POST-LMS:
     * Known seed → keygen → sign → verify → expect true
     * Verify deterministic output matches known vector

   POST-XMSS:
     * Known seed → keygen → sign → verify → expect true
     * Verify deterministic output matches known vector

   POST-HMAC-DRBG:
     * Known entropy + nonce → instantiate → generate → compare to known output
     * SP 800-90A test case (see Task A1)

3. Integrity Test (SP 800-140E Section 5)
   - Compute HMAC-SHA-384 over module binary/source
   - Compare to stored reference value
   - This verifies the module itself hasn't been tampered with
   - stored_integrity_hash: [u8; 48] (embedded in module or adjacent file)
   - fn verify_module_integrity() -> Result<(), IntegrityFailure>

4. Module State Machine Integration
   - ModuleState::Uninitialized → run_power_on_self_tests() → ModuleState::Operational
   - If POST fails → ModuleState::Error (no crypto services available)
   - All crypto entry points check: if state != Operational → return Err(ModuleNotReady)

5. PostReport struct
   - algorithm_results: Vec<(AlgorithmId, bool, Duration)>
   - integrity_result: bool
   - overall: Pass | Fail
   - timestamp: u64 (femtoclock)
```

**Tests:**
- All KATs pass with correct vectors → PostReport.overall == Pass
- Corrupt one vector → PostReport.overall == Fail, module in Error state
- After failure: call any crypto function → returns ModuleNotReady error
- Integrity test: correct hash → pass; wrong hash → fail
- Timing: measure total POST execution time (benchmark)

**Acceptance:** Module refuses all crypto operations until POST passes. Every approved algorithm has at least one KAT. Integrity verification operational.

#### TASK A4: Conditional Self-Tests
**File:** Extend `crypto/self_test.rs`
**Priority:** P0-CRITICAL — FIPS 140-3 Section 7.10.2 mandatory
**Effort:** ~120-150 lines (addition to A3)
**FIPS Reference:** ISO/IEC 19790 Section 7.10.2

**What to build:**
```
1. Pair-Wise Consistency Test (for asymmetric keygen)
   - Run automatically every time keygen is called
   - TL-KEM: generate keypair → encapsulate with pk → decapsulate with sk → verify shared secrets match
   - TL-DSA: generate keypair → sign test message with sk → verify with vk → expect true
   - LMS/XMSS: generate keypair → sign test message → verify → expect true
   - If test fails → module enters Error state, key pair destroyed

2. Continuous Random Number Generator Test (CRNGT)
   - Already partially in DRBG (A1) continuous output test
   - Wrap in conditional self-test API
   - Compare each DRBG output block to previous
   - Fail → Error state

3. Software/Firmware Load Test
   - Run integrity verification on any module update
   - Re-run integrity HMAC check after loading

4. Conditional Self-Test API
   - pub fn conditional_keygen_test(algorithm: AlgorithmId, keypair: &Keypair) -> Result<(), ConditionalTestFailure>
   - pub fn conditional_rng_test(current_block: &[u8], previous_block: &[u8]) -> Result<(), ConditionalTestFailure>
   - Called internally by tl_kem.rs, tl_dsa.rs, signature.rs, drbg.rs
   - Transparent to caller — integrated into keygen/generate functions

5. Integration Points
   - tl_kem.rs::keygen() → calls conditional_keygen_test() before returning keypair
   - tl_dsa.rs::keygen() → calls conditional_keygen_test()
   - signature.rs::lms_keygen() / xmss_keygen() → calls conditional_keygen_test()
   - drbg.rs::drbg_generate() → calls conditional_rng_test()
```

**Tests:**
- Keygen → conditional test passes → keypair returned
- Force inconsistent keypair → conditional test fails → Error state
- DRBG duplicate output → CRNGT catches → Error state

#### TASK A5: Module State Machine (Finite State Model)
**File:** NEW `crypto/module_state.rs`
**Priority:** P0-CRITICAL — FIPS 140-3 requires formal state transitions
**Effort:** ~150-180 lines

**What to build:**
```
1. ModuleState enum
   - PowerOff          — module not loaded
   - Uninitialized     — loaded, no self-tests run
   - SelfTest          — POST in progress
   - Operational       — all tests passed, crypto services available
   - ApprovedMode      — CNSA 2.0 only algorithms permitted (from agility.rs)
   - NonApprovedMode   — non-CNSA algorithms permitted (hybrid/legacy)
   - Error             — self-test failed or critical error
   - Zeroization       — key destruction in progress
   - Shutdown          — module unloaded, all state cleared

2. Transition Table (deterministic)
   PowerOff       → Uninitialized     [module load]
   Uninitialized  → SelfTest          [run_power_on_self_tests() called]
   SelfTest       → Operational       [all POST pass]
   SelfTest       → Error             [any POST fails]
   Operational    → ApprovedMode      [set_policy(CnsaOnly)]
   Operational    → NonApprovedMode   [set_policy(Hybrid)]
   Operational    → Error             [conditional self-test fails]
   Operational    → Zeroization       [zeroize() called]
   ApprovedMode   → NonApprovedMode   [policy change with auth]
   NonApprovedMode→ ApprovedMode      [policy change with auth]
   *Any*          → Error             [self-test failure / integrity failure]
   Error          → Uninitialized     [module reload only — no recovery without restart]
   Zeroization    → Shutdown          [all keys destroyed]
   Shutdown       → PowerOff          [module unloaded]

3. Transition Enforcement
   - pub fn transition(current: ModuleState, event: ModuleEvent) -> Result<ModuleState, InvalidTransition>
   - All transitions logged with timestamp
   - InvalidTransition: source state, attempted event, reason

4. Approved Mode Indicator (SP 800-140B requirement)
   - pub fn is_approved_mode() -> bool
   - pub fn get_mode_indicator() -> ModeIndicator { Approved, NonApproved, Error }
   - Must be queryable by external services and logged
   - Corresponds to agility.rs CnsaOnly policy = Approved mode

5. Integration
   - Wire into crypto/mod.rs as module-level singleton state
   - All crypto entry points check state before proceeding
   - Replaces ad-hoc checks scattered across modules
```

**Tests:**
- Walk through all valid transitions → succeed
- Attempt invalid transition (Error → Operational) → fails
- After Error state: all crypto calls return ModuleNotReady
- Mode indicator: CnsaOnly → Approved, Hybrid → NonApproved

#### TASK B1: ACVTS JSON Vector Format Migration
**File:** NEW `crypto/acvts.rs`
**Priority:** P0-CRITICAL — NIST requires ACVTS format since 2020, .req/.rsp is legacy
**Effort:** ~300-350 lines
**Reference:** NIST ACVTS Protocol Specification

**Why this is critical:** CMVP will not accept .req/.rsp format submissions. The Automated Cryptographic Validation Testing System (ACVTS) uses JSON. The existing 210 KAT vectors in `cavp_package.rs` need to be exportable in ACVTS JSON format.

**What to build:**
```
1. ACVTS JSON Schema per Algorithm

   AES-GCM (ACVTS spec "acvp-aes-gcm"):
   {
     "algorithm": "ACVP-AES-GCM",
     "revision": "1.0",
     "direction": ["encrypt", "decrypt"],
     "keyLen": [256],
     "ivLen": [96],
     "tagLen": [128],
     "aadLen": [0, 128],
     "payloadLen": [128, 256]
   }

   SHA-2 (ACVTS spec "acvp-sha"):
   {
     "algorithm": "SHA2-384" | "SHA2-512",
     "revision": "1.0",
     "messageLength": [{"min": 0, "max": 65536, "increment": 8}]
   }

   ML-KEM (ACVTS spec "acvp-ml-kem"):
   {
     "algorithm": "ML-KEM",
     "revision": "1.0",
     "parameterSet": ["ML-KEM-512", "ML-KEM-768", "ML-KEM-1024"],
     "function": ["keyGen", "encapDecap"]
   }

   ML-DSA (ACVTS spec "acvp-ml-dsa"):
   {
     "algorithm": "ML-DSA",
     "revision": "1.0",
     "parameterSet": ["ML-DSA-44", "ML-DSA-65", "ML-DSA-87"],
     "function": ["keyGen", "sigGen", "sigVer"],
     "deterministic": [true]
   }

   HMAC (ACVTS spec "acvp-hmac"):
   {
     "algorithm": "HMAC-SHA2-384" | "HMAC-SHA2-512",
     "revision": "1.0",
     "keyLen": [{"min": 8, "max": 524288, "increment": 8}],
     "macLen": [{"min": 32, "max": 384|512, "increment": 8}]
   }

   HMAC-DRBG (ACVTS spec "acvp-drbg"):
   {
     "algorithm": "hmacDRBG",
     "revision": "1.0",
     "predResistanceEnabled": [true, false],
     "capabilities": [{
       "mode": "SHA2-384",
       "derFuncEnabled": false,
```

#### TASK D1: CMVP Build Reproducibility Script
**File:** NEW `scripts/cmvp-build.sh`
**Priority:** P1-HIGH — lab must reproduce exact binary
**Effort:** ~60-80 lines

```bash
#!/bin/bash
# CMVP Reproducible Build Script
# Produces byte-identical binary for integrity verification

set -euo pipefail

RUST_VERSION="1.75.0"  # Pin exact version
TARGET="x86_64-unknown-linux-gnu"
PROFILE="release"

# Verify toolchain
rustc --version | grep "$RUST_VERSION" || { echo "ERROR: Wrong Rust version"; exit 1; }

# Build with deterministic flags
CARGO_BUILD_RUSTFLAGS="-C lto=fat -C codegen-units=1 -C panic=abort -C strip=none" \
  cargo build --target "$TARGET" --profile "$PROFILE" --no-default-features

# Compute integrity hash (matches POST integrity check)
BINARY="target/$TARGET/$PROFILE/libternary.rlib"
INTEGRITY_HASH=$(openssl dgst -sha384 "$BINARY" | awk '{print $2}')
echo "Module binary: $BINARY"
echo "HMAC-SHA-384 integrity hash: $INTEGRITY_HASH"
echo "$INTEGRITY_HASH" > target/integrity-hash.txt

# Generate ACVTS registration files
cargo test --test acvts_export -- --nocapture

echo "CMVP build complete. Submit integrity-hash.txt with vendor evidence."
```
