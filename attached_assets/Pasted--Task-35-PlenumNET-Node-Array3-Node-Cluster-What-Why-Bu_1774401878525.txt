## Rep C and GF(3) — The Dual Representation

**GF(3) {0, 1, 2}** — internal computation. Used in the port formula and offset calculations.

**Rep C {1, 2, 3}** — wire format. Used in every address, every node ID, every multiplexing header, every capability token, every routing message, every handshake.

Conversion: `rep_c = gf3 + 1`, `gf3 = rep_c - 1`.

**Zero is structurally impossible in Rep C.** Its presence in any trit of any address at any trust boundary is mathematical proof of forgery, detectable in constant time with no branching on secrets. This applies universally — slot addresses, classification trits, capability token fields, AND node identities. No exceptions.

| Dimension | GF(3) | Rep C | Meaning |
|---|---|---|---|
| Plane (trit 2) | 0, 1, 2 | 1, 2, 3 | Security domain (Data, Control, Management) |
| Role (trit 1) | 0, 1, 2 | 1, 2, 3 | Functional class (Primary, Secondary, Tertiary) |
| Instance (trit 0) | 0, 1, 2 | 1, 2, 3 | Service variant |
| Node ID | 0, 1, 2 | 1, 2, 3 | Cluster member (Gateway, Replica 2, Replica 3) |

## Port Formula

```
port = BASE_PORT + ((node_id - 1) × SLOTS_PER_NODE)
                 + ((plane - 1) × SLOTS_PER_PLANE)
                 + ((role - 1) × GF3_ORDER)
                 + (instance - 1)
```

All inputs are **Rep C {1, 2, 3}**. The `- 1` converts each to GF(3) offset for arithmetic. The wire carries Rep C. The formula uses SLOTS_PER_PLANE for the plane stride (9 = role × instance slots per plane), NOT SHELL_FACTORS (9 = auth shell factors). Same value, different derivation.

## Hamming Distance Routing

| HD | Count | Meaning |
|---|---|---|
| 0 | 1 | Same slot — loopback |
| 1 | 6 | Adjacent — direct call, same domain |
| 2 | 12 | Crosses boundaries — requires capability token |
| 3 | 8 | Corners — full mutual auth |

The gateway at (2,2,2) Rep C / (1,1,1) GF(3) has HD ≤ 2 from every slot in the cube.

### Two Meanings of Distance

**Hamming distance is the address metric.** It counts how many trit positions differ between two slot addresses. It determines the **auth level** required for a call between two slots: HD 1 = same security domain (direct), HD 2 = crosses a boundary (capability token), HD 3 = maximum separation (full mutual TL-DSA). The address metric is about trust — how semantically different are these two services?

**The gateway multiplexer is the routing topology.** The gateway at (2,2,2) connects to all 27 slots through the star multiplexer (§6.1). Every slot is 1 hop from the gateway. Every slot-to-slot path through the gateway is 2 hops. This is true regardless of Hamming distance — a corner slot at HD 3 from the gateway still reaches it in 1 routing hop through the multiplexer. The topology is about reachability — can this packet get there?

HD ≤ 2 from the gateway means every slot is within 2 routing hops through the multiplexer. The auth level applied to those hops is determined by the Hamming distance between the addresses. A slot at HD 3 from the gateway reaches it in 1 hop but pays full mutual auth for crossing all three domain boundaries. A slot at HD 1 reaches it in 1 hop and pays only same-domain auth. Same path, different cost. The geometry separates the routing question (always fast) from the security question (proportional to semantic distance).

### Routing Guarantees

**Reachability — no dead zones.** The 3³ cube has diameter 3. Every slot is reachable from every other slot in at most 3 hops. There are no unreachable corners, no isolated regions, no routing black holes. This is a property of the Hamming metric on GF(3)³ — proven, not tested.

**Greedy routing is loop-free and optimal.** Hamming distance is a metric: non-negative, symmetric, satisfies the triangle inequality. Greedy routing (at each hop, move to a neighbor that decreases HD by exactly 1) terminates in exactly HD(source, destination) hops. No loops are possible because HD decreases strictly at each step. Verified for all 702 directed pairs in the 3³ cube: zero failures.

**Auth cost scales with semantic distance.** The 27→3 projection places services with similar classifications in nearby slots (low HD) and dissimilar services in distant slots (high HD). The auth requirements scale with HD: loopback (HD 0) needs no auth, same-domain calls (HD 1) are direct, cross-boundary calls (HD 2) require capability tokens, corner-to-corner calls (HD 3) require full mutual TL-DSA auth. This means the security cost is proportional to the semantic distance between the services. Related services call each other cheaply. Unrelated services pay the full auth price. The geometry produces the correct security gradient for free.

**Array3 inter-node routing.** Within a node: max 3 hops (cube diameter). Cross-node: source → Node 1 gateway (max 3 intra-node hops) → inter-node link (1 hop) → remote slot (max 3 intra-node hops). Maximum inter-node path: 7 hops. Same-slot HA replica on a different node: 1 direct hop (the CRS knows the replica's location).

### Coprime Coverage (gcd(27, 28) = 1)

The classification space has 27 dimensions (Z₂₇). The full address space has 28 dimensions (Z₂₈ = 27 classification + 1 shell). gcd(27, 28) = 1 — they are coprime. By the Chinese Remainder Theorem, every (classification_position, shell_position) pair maps to a unique point in the combined space Z₂₇ × Z₂₈. No two services with different classifications AND different shell requirements can collide. The coprime structure guarantees full coverage of the address space with zero wasted positions.

This is not an optimization — it is an algebraic invariant. The dual-circle proof (TM-2026-008) establishes that Z₂₇ (algebraic, classification) and Z₂₈ (geometric, full address) are coprime circles. Their combination covers the full 364° ternary circle without redundancy. Every position in the space is used. None is wasted.

## 27→3 Projection

The projection is source-agnostic per spec §9.3 — takes 27 classification trits from ANY source (internet TDNS, LAN entity scan, manual entry, future methods) and returns 3 cube coordinate trits.

27 classification dimensions partition into 3 groups of 9 (CLASSIFICATION_DIMS / CUBE_DIMS = DIMS_PER_GROUP). Each group determines one cube dimension via `project_to_gf3(k, DIMS_PER_GROUP)` with polarity-adjusted dimensions.

For each cube trit: take 9 classification dimensions, apply polarity (invert if −), count k = polarity-adjusted dimensions with value 3, apply `project_to_gf3(k, 9)` → GF(3) result, lift to Rep C (+1).

### Polarity tables

**Plane group (security domain):** D1, D2(−), D3, D9(−), D10, D17, D19, D25, D26

D19 (PolicyPresence) in Plane: compliance posture is a security domain property.

**Role group (functional class):** D5, D6, D7, D8, D12, D18, D22(−), D23, D24(−)

D8 (Intelligence) in Role: what kind of processing. D18 (DataAppetite) in Role: heavier data interaction → secondary/tertiary role.

**Instance group (temporal/scale):** D4, D11, D13, D14, D15, D16, D20, D21, D27

D20 (CostModel) in Instance with + polarity: subscription implies higher availability. D27 (Confidence) in Instance to balance the 9/9/9 partition — primarily a structural choice (see spec §9.2).

Dimensions marked (−) are polarity-inverted before aggregation: if value is 1→3, if 3→1, if 2→2. Polarity is a structural property of the schema, not a tuning parameter.

## Key Freshness Zones

- **Fresh** (age 0–60): key is in first third. Suitable for all operations.
- **Active** (age 61–121): key is in second third. Required for regulated/sensitive operations. Boundary at 121 = REPUNIT_R5 = 11² resonates with BASE_PORT digit string.

## Zero-Sentinel Pre-Filter

At every trust boundary: if ANY trit in a Rep C value is 0, reject immediately before any cryptographic operation. Rep C values are {1, 2, 3} — zero is structurally impossible and its presence is proof of forgery.

Trust boundaries where the check applies:

- Multiplexing header (3-trit slot destination)
- Caller identity (54-trit TDNS-L address)
- Capability token subject/object fields
- Inter-service routing messages
- Redirect chain entries
- WAN P2P signaling (node addresses)
- **Node IDs in Array3 handshake** — a node claiming ID 0 is forgery

## Array3 Formation Protocol

1. Node boots with `CUBE_NODE_ID=N` (Rep C: {1, 2, 3}, default 1) and `CUBE_ARRAY3_PEERS=ip1:port,ip2:port`
2. Node binds its 27-port range: `BASE_PORT + ((N-1) × 27)` through `BASE_PORT + ((N-1) × 27) + 26`
3. Node 1 (`CUBE_NODE_ID=1`) is always the cluster gateway — its center slot at port `BASE_PORT + GATEWAY_OFFSET` is the single outbound security chokepoint
4. Nodes 2 and 3 route all outbound traffic through Node 1's gateway — their center slots are regular service slots, NOT gateways
5. Node connects to each peer via existing CUBE_PEER_PORT infrastructure
6. First handshake includes: node_id (Rep C), wire protocol version, port range, slot inventory, daemon version, gateway address (Node 1 advertises itself as gateway)
7. Peer validates: no node_id collision, **node_id is valid Rep C (zero-sentinel check)**, wire protocol compatible (V3 accepts V2 during dual-acceptance), port ranges don't overlap
8. On success: peer mesh formed, slot-to-node routing populated, outbound routing through Node 1 gateway confirmed

Single node = `CUBE_NODE_ID=1`, no peers, ports 11111–11137, gateway at 11124. Adding a second node later requires no reconfiguration of Node 1.

## Slot-to-Node Routing

The 3-trit slot address (plane, role, instance) maps to offset 0–26 within EACH node's 27-slot range. The CRS tracks slot→node ownership. Two services with identical classifications on different nodes occupy the "same slot" on different nodes — this IS the HA replica mechanism. The CRS routes to the primary; on failure, traffic fails over to the replica.

## Wire Protocol V3 and Versioning

| Wire Protocol | Features | Platform Version |
|---|---|---|
| V1 | Legacy — no signatures, no auth heartbeats, no ECC | ≤ 2.2.x |
| V2 | Hardened — signed CRS, auth heartbeats, mutual tunnel auth, dual checksum, ECC | 2.3.x |
| V3 | Service Cube — slot addressing, zero-sentinel enforcement, 13-capability registration, key birth epochs in capability tokens, Array3 formation handshake, Rep C node IDs | 2.4.x |

V3 nodes accept V2 peers during dual-acceptance. V2 CRS registrations without slot addresses are assigned slots on first heartbeat.

Version constants: `WIRE_PROTOCOL_VERSION = 0x03`, `DAEMON_VERSION = "2.4.0"`, `TDNS_VERSION = "v2.5"`.

Cube daemon reports version via: health endpoint JSON, startup banner, CRS self-registration metadata.
