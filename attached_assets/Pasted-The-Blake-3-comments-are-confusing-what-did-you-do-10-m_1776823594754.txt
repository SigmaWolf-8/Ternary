Here's what's actually going on with BLAKE3 in this task — in plain terms:

Where BLAKE3 shows up

Snapshot file naming. Each snapshot on disk is named <a>__<b>.bin where:

<a> = first 16 hex chars of BLAKE3(test_id) — a short stable tag for which test produced the file (e.g. the TL-DSA-65 sign test).
<b> = full BLAKE3(input bytes) — a stable tag for what input produced it (seed + message + variant).
So the filename itself is a content-addressed fingerprint. If anyone changes the test inputs, the filename changes and a brand-new snapshot is required — you can't silently overwrite an old one.
What's inside the file is NOT a hash. The file holds the raw crypto output bytes (the actual signature, ciphertext, derived key, etc.) — not a digest of them. The byte-identity check is a literal output_bytes == file_bytes comparison. BLAKE3 is only used for addressing the file, not for the equality check.

Why I used BLAKE3 at all
The G13 gate calls for "BLAKE3-addressed pre-rename signature snapshots." That phrasing means: use BLAKE3 to give every snapshot a deterministic, collision-resistant filename derived from its test id and input. That's the convention I followed.

What it does NOT do

It doesn't hash the crypto output and compare hashes (that would be weaker than byte-identity).
It doesn't sign or authenticate the snapshot file — it's just a naming scheme.
It's not part of the crypto path under test; the crypto under test is TL-DSA / TL-KEM / TLSponge-385 / phase-encryption.
